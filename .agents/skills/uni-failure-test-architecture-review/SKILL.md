# Uni 故障测试架构复盘

## 目标

把故障测试发现的问题从“某一行写错了”提升到可行动的架构结论：完整流程由谁负责、失败后资源由谁收尾、恢复决定由谁作出，以及为什么原有测试没有约束住这些责任。

## 工作边界

- 默认只读，不修改代码、文档、Issue 或提交。
- 只分析已经有测试、日志、提交差异或稳定复现支持的事实；假设必须单独标明。
- “以前没有这个测试”只能解释发现时间，不能作为架构根因。
- 不因为看到多个条件分支就直接主张状态机、事务或新抽象；先证明复杂度确实跨调用方泄露或失败责任断裂。

## 事实来源

先读取根目录和目标目录最近的 `AGENTS.md`，再按需要检查：

- 新增故障测试及其断言；
- 修复前后的提交差异；
- 被测完整流程、后台恢复入口和错误分类；
- 资源创建、发布、关闭、取消和重启恢复路径；
- 对应执行计划、架构说明与可靠性规则。

优先使用真实失败输出和可重复测试。若只能从当前代码反推旧行为，明确说明证据限制。

## 分析方法

1. 列出每个故障点的前置状态、已经发生的不可逆动作，以及测试观察到的失败结果。
2. 沿完整调用路径追踪四项责任：权威状态、旧权限、临时资源、后续恢复。
3. 对每个问题区分：
   - 表面现象；
   - 直接缺陷；
   - 让缺陷容易发生的设计问题；
   - 多个问题共享的架构根因；
   - 原有验证为何没有发现。
4. 检查最近的架构切分是否只迁移了成功路径，而失败、取消、重试或重启路径仍依赖旧假设。
5. 检查一次完整动作是否有唯一负责人。若调用方必须知道内部顺序、清理步骤或重试条件，指出复杂度从哪里泄露出来。
6. 检查处于“已创建但未正式生效”的对象：它必须成功移交给长期负责人，或者由当前负责人完整关闭，不能只依赖普通释放动作。
7. 检查“给调用方看的失败结果”和“后台是否继续恢复”是否被错误地绑定在同一个粗粒度标记上。
8. 评价现有修复：责任是否已回到最接近资源或流程的负责人，还是只在某个调用点补了特殊分支。
9. 给出仍未验证的邻近场景，优先关注取消、超时、进程关闭、重启和在途工作，不把未执行项写成已确认风险。

## 输出要求

先给一句共同根因，再解释各问题如何由它产生。使用简单直白的语言，避免逐行讲代码。

报告至少回答：

- 这些问题是独立偶发错误，还是同一个责任缺口的不同表现；
- 哪个旧假设在新架构中已经失效；
- 为什么成功路径能工作，而失败路径会停住或遗留资源；
- 新增测试具体补上了什么系统约束；
- 当前修复是否收回了责任，还有哪些邻近场景尚未验证。

把“已确认”“合理推断”“未验证”分开。建议保持少而明确，优先提出能让调用方少知道内部步骤、让一个负责人完整处理成功与失败的改进。

## 完成条件

- 每个结论都能追溯到测试、失败输出、差异或流程代码。
- 找到共同根因时，没有把测试缺失、单个错误映射或单个清理调用误写成最终原因。
- 明确评价修复后的责任归属和剩余验证边界。
- 未执行任何修复，也未把未验证场景描述成已经存在的缺陷。
