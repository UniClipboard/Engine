# `facade/` 目录规则

本目录是应用层的对外编排入口，不是业务规则、协议处理或后台实现的存放处。

## 门面职责

- 每个门面动作只表达一个用户或 Engine 可理解的完整意图，接收必要输入，调用负责该结果的内部模块，返回稳定结果、当前状态或状态订阅。
- 门面可以做高层流程选择、统一错误映射、事件转发和运行期接线；调用方不需要知道内部顺序、依赖、重试或恢复方式。
- 新功能开始前必须写清：内部唯一负责人、调用方唯一动作、成功结果、失败结果，以及重启或重试的负责人。

## 禁止放入门面

- 不在门面实现业务判断、状态机推进、逐项循环、分页、去重、重试、退避、超时等待或后台任务循环。
- 不在门面处理协议消息、签名、身份或 Space 校验、加密资料、地址资料、持久化读写或原子提升。
- 不公开 `prepare`、`accept`、`confirm`、`deliver`、`reconcile`、`retry` 等步骤级动作，或让调用方按顺序拼接这些步骤。
- 不把上述细节仅拆到 `facade/` 的另一个私有文件；它们必须归入对应业务目录的内部模块，由该模块完整负责结果。

## 运行期与接口

- 持续运行的工作必须由所属内部模块的运行期统一管理；暂停、恢复和关闭必须覆盖该工作，门面不得遗留独立任务。
- 对外类型只表达意图、稳定结果和可展示状态，不暴露仓库、端口、协议消息、内部错误或执行中间态。
- 若一个门面需要根据内部中间结果决定下一步、维护重试状态或直接操作多个底层依赖，应先创建或扩展一个私有的完整流程模块，再由门面调用它。

## 测试与变更

- 门面测试只证明外部动作到稳定结果的编排；具体规则、失败分类和恢复行为在各自内部模块测试。
- 移动具体逻辑时，先用现有或新增回归测试锁定行为；每次迁移后删除原门面中的重复实现，不保留兼容层或双路径。
- 文件行数不是拆分依据。只有当知识和修改理由能按完整职责集中到一个内部模块时，才进行拆分。
