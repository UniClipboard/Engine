ADR-020 · Visual Explanation

设备如何核对成员历史

上线先核对事实，普通新增自动补齐，未确认的移除交给本机用户决定。接受后恢复一致；拒绝后只隔离发生分歧的设备关系。

这项决策保护的不是一份永远唯一的名单，而是每台个人设备在离线后仍有继续工作的能力，以及用户对破坏性变化的最终决定权。

FIGURE 01

一个负责人把复杂流程藏在内部

产品只需要读取完整状态，并在必要时提交一次接受或拒绝。核对历史、保存进度、恢复重试和停止跨分支分享，都由同一个负责人完成。

怎么看

中间的橙色方框是唯一的完整负责人。上下两侧只是入口和能力，不能各自掌握一段流程后再让产品拼起来。

这解决什么

重启恢复、重复消息、等待用户和分叉隔离都留在内部。产品不需要理解设备之间交换了哪些消息。

FIGURE 02

设备上线时，先比较摘要，再按需补齐

两台设备不会直接互相覆盖名单。它们先确认是否属于同一个空间、各自知道和采用到哪里；只有发现缺口时，才请求有限的一段历史。

为什么先发摘要

绝大多数重连只需确认双方没有差异。只有摘要显示缺口时才补历史，避免每次上线都发送完整名单和全部记录。

两个位置的意义

  • 已知道：已经验证并保存的最远位置。
  • 已采用：真正改变本机成员和分享权限的位置。

关键：一台设备可以已经知道“有人被移除”，但在用户决定之前仍不采用这个变化。这不是延迟或失败，而是刻意保留的决定边界。

FIGURE 03

新增自动前进，移除必须停下来

历史核对不是“远端更新一律应用”。它会区分普通新增、未确认移除、已经接受的移除、明确拒绝以及无法验证的资料。

接受意味着什么

采用收到的那一项移除，而不是再创建一项新的移除。这样双方有机会回到同一段历史。

拒绝不意味着什么

它不会偷偷移除发起者，也不会把整个空间停掉。它只证明这两台设备不再接受同一段历史。

FIGURE 04

分叉隔离一段关系，不冻结整个空间

例子中，A 移除 B，C 上线后拒绝。结果不是“所有设备都停用”，而是 A 与 C 停止彼此分享；B 与 C 所在分支仍可继续工作。

三件事可以同时成立

  • C 在线。
  • C 在自己的分支仍是有效成员。
  • A 与 C 的历史关系已经分叉。

明确接受的代价

被另一分支移除但尚未接受该事实的设备，仍可能继续分享它此前掌握的内容。分叉隔离只能阻止确认分歧之后的交换，无法收回已经披露的内容。

一句话总结：ADR-020 选择“离线可用 + 用户决定”，因此不承诺全空间永远只有一份历史；它承诺的是，差异被发现后不会静默覆盖，也不会把影响扩大到无关设备关系。

为什么需要三层

只测底层规则，无法证明多台设备最终真的恢复分享；只测多设备，失败时又很难知道是历史判断、保存恢复还是通信出了问题。

最重要的判定

端到端测试不能只看“发送方说成功”。它必须在接收方确认内容确实出现，或在应阻断的关系上确认双方都无法传递。
