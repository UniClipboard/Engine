# Space 可用性启动门槛

## 状态

- **状态**：实施完成；本机实体启动已验收，多设备全离线的独立进程场景未在本轮构造
- **日期**：2026-09-17
- **完整负责人**：Application 的成员可用性查询只判断本机权威成员范围是否可读；既有成员维护流程继续负责网络恢复、重试与持久欠账
- **调用方唯一动作**：产品宿主查询一个稳定的 Space 可用性结果，并在结果为可用前保持启动或恢复界面
- **成功结果**：本机持有可验证的当前成员历史时，即使所有其他设备离线也返回可用
- **失败结果**：资料锁定、成员历史待恢复和底层读取失败保持不同结果；不得用旧成员投影或在线状态推断可用
- **重试与重启责任**：成员维护继续拥有恢复；产品宿主只重新读取权威结果，不编排成员同步步骤

## 问题

Desktop 目前在 daemon 可连接且 Space 已解锁后进入主界面。这个门槛没有验证当前成员范围，导致本机成员历史缺失时仍打开设备页，随后以成员不可用错误失败。已知设备联系可以唤醒成员恢复，但它发生在主界面放行之后，用户会看到一个看似可用却无法读取成员的产品状态。

## 设计

1. Application 在成员模块提供只读可用性查询，以当前成员范围为唯一事实来源。
2. 查询成功即表示本机已有可验证的成员历史，不要求任何远端设备在线。
3. 无当前范围或明确需要恢复时返回“成员恢复中”；锁定状态单独返回；底层暂时不可用保留错误。
4. Engine 只投影稳定结果，不读取成员仓储或编排恢复。
5. Desktop daemon 的 lifecycle 状态把 Engine 运行状态、成员可用性与设备名单的实际可读性合成为产品启动状态；权威成员范围可读但名单暂不可读时仍保持恢复中。
6. GUI 在已解锁后重新读取 lifecycle 状态；只有 Ready 才进入主界面。恢复过程中保留启动界面并给出可信设备上线提示。

## 最小端到端切片

- 一个前端测试证明“daemon 已连接、Space 已解锁、成员恢复中”时不能显示主界面，恢复为 Ready 后才放行。
- 一个 Application 测试证明有效本地成员范围在完全离线条件下直接 Ready，缺少当前成员历史时返回 Recovering。
- 一个 daemon 测试证明 lifecycle 不会把 Recovering 投影成 Ready。

## 验收

- 前端定向测试稳定捕获并修复过早放行。
- Application、Engine、daemon 定向测试通过。
- Desktop 全部前端测试、构建、Rust workspace check、格式与架构检查通过。
- 使用本机默认资料重启正式构建，确认恢复完成后正常进入主界面且成员读取成功。
- 多设备均离线但本机成员历史完整的独立进程验收若当前环境无法安全构造，明确记为跳过，不以单元测试替代实体场景。

## 验证结果

- Application 的五项成员可用性测试通过，覆盖本机有效历史、本机身份失效、待恢复、锁定和底层不可用。
- Desktop 的完整前端测试共 1432 项通过；启动门槛、恢复轮询与窗口展示的定向测试通过。
- Desktop 与 Engine 工作区完整编译通过，Rust 格式和新增代码规范检查通过。
- 本机正式构建真实复现启动后约 32 秒名单不可读；修复后 lifecycle 在该时段持续报告恢复中，名单恢复后才放行，随后设备名单请求连续成功。
- 多设备均离线的独立进程验收未构造；离线不阻塞的规则由 Application 定向测试覆盖，但不把它表述为实体设备证明。
