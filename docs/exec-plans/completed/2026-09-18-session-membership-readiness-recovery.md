# 会话恢复后的成员资料立即就绪

## 状态

- **状态**：已完成
- **日期**：2026-09-18
- **完整负责人**：Application 的会话就绪流程
- **调用方唯一动作**：宿主只恢复或解锁 Space 会话，不编排成员维护
- **成功结果**：会话密钥恢复后立即完成一次成员维护，并在成员资料实际可读后才返回成功
- **失败结果**：维护运行期关闭或成员资料仍不可读时，会话恢复保留失败，不伪装成完成
- **重试与重启责任**：成员维护继续拥有串行、网络重试和周期兜底；会话就绪流程只等待本次必要的本地恢复

## 问题

启动成员维护与 Space 会话恢复并发运行。第一次维护可能在会话资料真正就绪前结束，而会话恢复随后读取成员资料失败。失败没有触发立即维护，只能等待三十秒周期兜底，产品约三十二秒后才可用。

## 实现

1. 会话就绪流程在版本准备和回填之后，请求成员维护立即执行一轮并等待结束。
2. 成员维护运行期继续负责排队、串行、暂停和关闭；等待请求没有建立第二套恢复流程。
3. 本轮结束后重新读取成员资料；只有实际可读才完成会话恢复。
4. 删除 facade 在恢复成功后的重复唤醒；三十秒周期任务仅保留为异常兜底。

## 验收

- 自动化测试证明等待请求会在当前轮结束后立即执行，并在目标轮完成前不返回。
- `uc-application` 的 863 个测试通过，其中 1 个既有测试按设计跳过；新增验收同时确认本机身份失效时不会误报可用，而其他设备全部离线不会阻挡有效本机进入。
- Engine 工作区检查和 Rust 编写规范检查通过；仓库结构检查仍被本分支已有的成员历史同步文件改名阻断，和本次改动无关。
