- 日期：2026-09-12；本地完成：2026-09-13。
- 实现提交：`246e28da`，未推送或发布。
- 研究基线：Engine `f6f305d9689e4e79e7ab6d0e4921061f9416e4a6`，版本 `1.1.0-rc.15`，锁定 Iroh `1.0.0-rc.1`。
- 前置设计：[已配对设备自动连接](../../design-docs/automatic-peer-connections.md)及其[已完成实施记录](../completed/2026-09-11-automatic-peer-connections.md)。
- 完整负责人：Application 的 `PeerConnectionCoordinator` 负责单设备连接维护；Infra 的 peer reachability adapter 负责连接证据及协议；`NetworkRecoveryFacade` 只负责被明确请求的整会话恢复。Engine 只装配和执行生命周期替换。

- 成功结果：当前合格设备具有真实通信证据，能自动维持或恢复连接，并实际双向收发内容。
- 失败结果：单次发送失败、对端不可达、资格失效、本机运行失败分别结算；不能相互推导，不能将未知写成成功。
- 恢复责任：单设备的检查、去重、重试和取消仍归同一 Application owner；Iroh 处理传输保活与路径变化；本地 DNS/中继自恢复复用现有能力。
- 完成方式：自动化端到端验收为必要门禁，不依赖物理手机操作。真机、移动操作系统后台策略和特定代理软件的验证单独登记。

下文保留实施合同；实际交付状态以阶段表和执行记录为准。失败、未执行项目和产品采用分别记录，不能将计划中的命令或测试名当作已经通过的证据。

## 2. 问题与证据边界

### 2.1 已确认的现场链路

2026-09-12 的手机与 macOS dev 日志确认了至少一次下列链路：

1. 手机与 Mac 已有 presence 连接，手机此前仍有成功的成员历史交换。
2. 手机中继状态短暂变化，随后启动新的恢复确认拨号。
3. 第一轮约 2004ms 后被中断；第二轮约 2ms 后被中断，两轮实际共用一个截止时间。
4. 手机报告原在线目标不可达，进入整会话恢复，关闭包括既有入站连接在内的资源。
5. Mac 记录远端主动关闭；手机重建完成后，两端又自动连接。

可定位窗口为手机日志 UTC `11:51:29` 至 `11:51:45`；输入为本会话提供的 `11-57-22` 手机诊断包和同日 Mac dev 日志。
原始 ZIP、用户目录、设备身份、地址与正文不进入仓库。必要的证据摘录使用固定节点别名和既有脱敏诊断合同。
这证明一次误恢复链路，不证明用户看到的每次状态变化都由同一原因产生。

手机此前获取异常地址解析结果是另一条调查线索；本规格修复错误的失效判断与恢复影响范围，不宣称修复外部 DNS 或代理行为。

### 2.2 代码中的根因

| 位置 | 已核实事实 | 应修正的责任或推断 |
| --- | --- | --- |
| `crates/uc-core/src/ports/peer_reachability.rs` | `verify_reachable` 文档将强制检查定义为重新拨号，失败即离线；`mark_offline` 允许单次外部拨号失败清除连接 | 检查当前通信能力不能等同于重新建链；外部发送失败只能报告本次操作事实 |
| `crates/uc-infra/src/network/iroh/peer_reachability_adapter.rs` | 原实现拨号失败移除出站连接并写 Offline；验证到期会提前移除旧连接；入站 handler 只处理首次确认后等待关闭 | 已有连接、候选新连接及单次检查结果缺少明确的有效性边界 |
| `crates/uc-infra/src/network/iroh/clipboard_dispatch_adapter.rs` | 新的内容通道拨号失败调用 `mark_offline` | 只修 presence 的拨号失败分支仍会从发送入口误拆连接 |

当前局部草稿通过 `close_reason().is_none()` 保留连接，并扩大等待预算。它修正直接误关闭，但不能证明连接仍能通信，静默断网可能继续显示在线到传输层空闲超时。该草稿也没有修正上述 Port 和发送入口的语义，不能独立合入作为根因修复。

### 2.3 已核实的可复用能力与不足

- 锁定 Iroh 的 `Connection` 提供 `open_bi`、`accept_bi`、`closed`、`close_reason`、路径与统计查询；本次源码核对没有发现可直接等待对端回复的公开 `ping` 方法。路径缓存、RTT、未关闭状态和成功入队均不能单独作为新鲜回应。
- `connect.rs` 已使用 `ConnectOptions::with_additional_alpns`，可复用协议协商；已有分批拨号最坏约 4.5 秒，不重写 QUIC 或其重传。
- `node.rs` 已配置传输保活与 60 秒空闲超时；`net_recovery.rs` 已有受控的 DNS/中继恢复，不新建第二套网络服务。
- `space_membership_auto_pairing_e2e/automatic_connections.rs` 已有真实 Engine、独立资料、配对、只读在线等待和双向正文校验，可以复用。
- `IrohNetworkPartitionGate::replace_blocked` 会主动关闭已有连接，所以现有分区测试不等于静默断网测试。
- [规格 034](034-deterministic-virtual-peer-network-test-suite.md)尚待实施，且明确不模拟 presence/QUIC；本规格不依赖其完成，也不把领域模拟结果当成真实连接验收。

## 3. 目标、不变量与非目标

### 3.1 必须成立的不变量

1. 建立新连接失败，不得否定更新的已认证回应，不得关闭仍被有效证据支持的连接。
2. 仅“没有关闭通知”不能无限延长 Online；新鲜度必须有明确过期和后续检查。
3. 每次检查只影响所检查的连接实例及目标；旧连接的关闭、超时、失败不能覆盖新实例或更新成功。
4. 已认证连接不等于永久授权；资格撤销、空间退出、真正锁定和关闭优先于所有迟到成功。
5. 单个甚至全部远端不可达，都不能单独触发本机整会话重建。
6. 普通发送失败原样返回调用方，不自动重放用户操作；后台检查不能把发送失败改写为成功。
7. 同一目标只有一个完整连接维护负责人；检查、自动重连、手动刷新和机会合并不能形成平行循环。
8. 查询状态不建立连接、不发送确认、不触发恢复。测试的等待阶段同样遵守这一规则。

### 3.2 非目标

- 不改变成员历史、配对资格、内容加密、剪贴板接收或用户操作的幂等规则。
- 不修改用户代理、DNS、路由器，不因失败切换 LAN 兼容模式，不新建发现服务。
- 不实现通用网络模拟器、跨协议万能健康服务或持久化健康数据库。
- 不要求物理设备才能关闭本规格；也不承诺被操作系统冻结的应用能执行后台检查。
- 不把本轮计划编写当作生产代码实施、发布或宿主采用完成。

## 4. 设计与所有权

### 4.1 分开三类事实

| 事实 | 有效依据 | 可以触发 | 不能触发 |
| --- | --- | --- | --- |
| 既有连接活性 | 同一已认证连接上本轮请求对应的有效回应，或同实例更新的可信业务回应 | 保持 Online、更新该连接验证时间 | 授予成员资格、宣称正文已送达 |
| 候选连接结果 | 新连接建立及当前资格确认的结果 | 接纳候选或结算失败、安排目标重试 | 拆掉其他健康连接、重建整个网络 |
| 本机运行状态 | 本地生命周期或底层实例明确的终止事实 | 由生命周期负责人处理，或接受显式恢复请求 | 从远端无回应、中继暂断、地址错误推断本机损坏 |

生产在线状态仍使用现有 `Online / Offline / Unknown`，不新增产品界面状态或第二份名单。
检查进行中的瞬时信息只在内部存在；资格错误保持原错误，不用 Unknown 或连接成功掩盖安全失败。

### 4.2 完整的单目标检查

`verify_reachable` 的目标语义改为“获取当前可达性证据”，而非“强制建立新连接”：

1. 核实当前成员资格并捕获本轮有效期，取得已接纳的入站、出站连接快照；网络等待不持有共用状态锁。
2. 对支持活性确认的现有连接执行有界确认。多个候选可在同一目标预算内并行检查；任一新鲜成功即可满足目标，不按候选数量累加超时。
3. 写回前检查空间/成员有效期、连接实例和成功修订。有效回应更新对应实例，保持 Online；新候选失败不清除它。
4. 所有已接纳连接都明确关闭或在本轮失去活性且没有更新成功时，发布一次 Offline，安排普通目标重连。
5. 不存在可用连接时，使用既有地址解析和分批拨号；完成当前空间准入后才接纳候选并发布 Online。
6. 更换连接按“新连接已确认可用后替换”执行；失败、取消及验证到期均不先拆旧连接。过期但仍待确认的连接不得当作永久 Online 证据。

`ensure_reachable` 可短暂复用新鲜成功；证据过期后委托同一完整检查。后台也必须能驱动该检查，不能只在发送前检查。
权威事实只有接纳连接集合及其证据；状态缓存是投影。候选连接、尚未完成准入的连接与接纳连接分开管理。
每个目标的持有连接和在途确认有界；同向重复连接只在新的确认成功后按一致规则收敛，不能让互相替换形成振荡。

### 4.3 活性确认与协议兼容

采用明确协商的新 presence 协议 `uniclipboard/presence/2`，通过 Iroh 现有双向流完成小型请求/回应。
不在旧协议上盲发新请求，再把旧端不回应解释为断线；当前 `/presence/1` handler 并不会处理后续确认请求。

协议约束：

- 复用原有当前空间准入规则。连接接纳后，双方都能在该连接上发起确认；不能只有接受方处理请求，否则“仅入站连接”仍无法检查。
- 每次确认使用独立双向流，固定消息类型和固定长度挑战/回显；挑战通过现有随机源生成，只在内存保留，本轮与旧回应不可混淆。
- 初次准入沿用 v1 的请求 `0x01` 与结果 `0x01/0x02`，v2 在成功后允许后续确认流；协议布局见下表，P1 以 codec/兼容测试锁定，不能将演进细节泄露给 Core 或宿主。
- 收到挑战不自动授予资格；处理前后检查当前许可。撤销后停止处理，迟到回应不能重新置在线。
- 双方各自最多一个目标检查；接收循环、流处理并发、任务句柄和缓存受连接生命周期管理。恶意请求不能创建无界任务，也不能持锁等待网络。
- 保活周期由现有连接维护负责人安排；不另建每宿主或每协议的独立重试服务。

| v2 消息 | 固定布局 | 校验 |
| --- | --- | --- |
| 活性请求 | `0x10` + 16 字节随机挑战，总长 17 字节 | 只允许在本连接已准入后发送；写完结束流，接收端限长读取并验证结束 |
| 仍具资格的回应 | `0x11` + 原 16 字节挑战，总长 17 字节 | 必须匹配本轮挑战与连接实例，完整收到并验证结束才算成功 |
| 资格已失效的回应 | `0x12` + 原 16 字节挑战，总长 17 字节 | 不刷新活性；按资格拒绝处理，不作为普通网络超时或自动降级依据 |

未知类型、错误长度、错误挑战或缺少流结束不能成功结算；只读一个正确前缀不算合法帧。
确认流接收并发每连接最多 2 个，每目标最多一轮主动确认；超过并发的流有界拒绝，不创建无限后台任务。
连接数上限与候选接纳策略在 P2 与现有双向连接管理一起核实并固定，不能用无限入站连接放大每目标确认成本。

兼容策略：新端优先协商 v2，同时在过渡期接受 v1；只在协议协商确认使用 v1 时进入旧端模式，不以超时或认证失败作为降级理由。
旧端模式继续使用传输层关闭/空闲超时与已有合法通信证据，不要求旧端支持新确认，不用新拨号失败关闭它。
旧端模式不能凭缓存反复刷新新鲜度；静默断网的验收上限按既有 60 秒空闲超时加 10 秒调度余量单独记录。

兼容不是永久双实现：两版本共享身份校验、连接登记、状态结算和关闭流程，只有 wire handler 不同。
首个支持 v2 的发布保留 v1。待 Desktop、iOS、Android、HarmonyOS 当前支持版本都采用 v2，并在发布策略中明确提高最低兼容版本后，移除 v1 handler、协商回退及对应分支；删除任务随首次 v2 发布登记在同一计划中。不得在兼容版本尚受支持时静默移除，也不得无期限保留无删除条件的双 owner。

### 4.4 发送失败入口

审计 `mark_offline` 的全部生产调用，特别是 `clipboard_dispatch_adapter.rs`：

- 内容通道新拨号失败只证明本次发送未建立通道；它报告目标需要重新检查，不直接关闭 presence 或写全局 Offline。
- 某条业务连接的已确认关闭只淘汰对应实例；若没有办法关联到 presence 实例，提交目标复核，不能伪造关联。
- 准入拒绝、内容密钥错误、远端存储失败等不当作网络断开。当前成员资格变更仍走既有撤销路径。
- 当前 `mark_offline` 合同不满足上述语义，实施时移除/替换它及调用方；默认方案是窄的“报告通信失败并请求复核”能力，而不是增加一组可由调用方拼装的状态参数。
- 如果已有内部连接机会流可以表达这一事实，直接复用并删除旧能力；如确需修改 Port，按需要者所有权落地，更新所有真实实现、装饰器、测试替身及文档，不保留旧的破坏性入口。

### 4.5 整会话恢复边界

删除“`LocalRelayRecovered` 后 `PreviouslyOnlinePeerPathExhausted` 触发自动整会话重建”的决策链，以及只为该链服务的重复确认、状态和事件。
中继恢复仍是连接机会；DNS 重置与 `Endpoint::network_change` 保留既有去重和限频，不能一台设备失败就无限重置。
`FreshPeerDialSucceeded` 若仅用于取消上述自动重建，同步删除；仍有其他消费者的事实必须逐一核实，不盲删公共诊断枚举。

本规格不发明新的“本机故障评分”或“连续 N 个对端失败”规则。现有显式 `RecoverNetwork`、真正 suspend/resume 及合法生命周期替换保留。
本地不可恢复终止若已有可靠来源，接入已有生命周期失败处理；若没有，明确记录没有自动整体重建触发器，不能拿外部连通性测试冒充。
普通网络断开期间继续受控重试，网络返回后在原可运行实例上恢复连接。确实终止的本机实例由明确的本地失败/恢复流程处理。

### 4.6 时间、调度与取消

以下为拟实施的统一预算，先写受控时钟测试再落生产常量；不得保留多份互相矛盾的数字。

| 项目 | 目标约束 |
| --- | --- |
| 新协议健康连接后台检查 | 最近有效回应后最迟 10 秒安排一次；显式网络机会或通信失败可提前，纯查询不触发 |
| 一次已有连接确认 | 包含请求和完整回应，总预算 5 秒；同目标多连接并行共用预算，依赖 QUIC 重传，不堆叠无界应用重试 |
| 单目标完整操作 | 外层初始上限 20 秒，涵盖 1 秒资格读取、5 秒已有连接检查、至多 1 秒网络机会提交、现有约 4.5 秒拨号和 5 秒准入，余量用于调度；阶段组合与边界测试必须匹配 |
| 新协议静默离线检测 | 本规格双/三节点拓扑，从丢包规则生效起最多 20 秒；检测阶段完成即结算，不等待后续重拨耗尽预算 |
| 发现/网络机会后的恢复 | 环境可用且成员资格正常起，双/三节点最多 20 秒自动 Online；此后再验证实际传送 |
| 所有机会通知丢失后的恢复 | 既有最大退避 72 秒加一轮 20 秒，总上限 92 秒；不能通过测试发送打断退避 |
| 多目标公平性 | 保留每目标一个任务、全局最多 4 个；8 个合格目标的受控时间测试证明到期检查不被连续重拨饿死，并记录推导上界 |
| 旧协议静默离线检测 | 最多 70 秒，单独报告旧端侧观察边界，不冒充新协议快速检测通过 |
| 正常关闭/撤销 | 不等待健康检查周期，取消并等待受管任务；既有生命周期预算继续有效 |

检查期间保留原状态，超时只结算该轮对应的证据；新成功与撤销优先。失败后的目标重连复用现有退避。
有外层截止时间时，内部阶段使用明确剩余预算；剩余不足不得启动一轮注定立即超时的“确认”，也不得把取消报告成“已完成两次失败验证”。
若删除整会话失败链后无需“两次恢复确认”，直接删除，不为保留局部草稿而继续维护 2 秒加 2 秒的路径。
实测若不满足上界，先查调度和取消原因；改变产品上界必须修改本表与对应断言并说明依据，禁止仅放宽测试。

## 5. 自动化端到端验证设计

### 5.1 验证层次与真实性

| 层次 | 使用真实实现 | 可替换或控制的边界 | 不能声称的结果 |
| --- | --- | --- | --- |
| Application 受控时钟 | 真实协调器、结果结算、取消与恢复决策 | 时钟及网络能力的最小替身 | 不作为真实 QUIC/端到端通过 |
| Infra 协议测试 | 真实 Iroh Endpoint、认证连接、准入/活性协议与关闭 | 候选拨号拒绝、响应延迟、旧版 handler | 不作为完整 Engine/产品通过 |
| Engine 本机 E2E | 独立 Engine、真实加密存储、配对、成员资格、生产连接维护和内容通道 | 本地 rendezvous、窄的连接边界故障注入 | 同进程不证明独立进程退出或内核断网 |
| 独立进程网络 E2E | 两/三个宿主进程、真实 Engine/传输/存储 | 隔离网络中的丢包、断路、中继中断 | 不证明 iOS 后台或特定手机代理 |
| 可选平台补充 | Desktop/模拟器或真机绑定与宿主生命周期 | 原生前后台事件 | 未执行不写通过，也不阻塞本规格核心门禁 |

### 5.2 故障注入不得替换被测结论

复用 `IrohNetworkPartitionGate` 的连接 hook，新增受 dev/test 构建隔离的“只拒绝新连接”模式；规则限本次拓扑及明确协议，不关闭接纳连接。
它控制实际连接边界，不能直接返回伪造的 `ReachabilityState`。自检必须先证明：规则命中新连接，而已建立连接仍可往返。
`replace_blocked` 的现有主动关闭模式保留，名称和测试说明明确它不是静默丢包。

静默断网采用 Linux 网络命名空间、虚拟链路与 nftables 丢包规则，运行真正独立进程。使用成熟系统工具，不手写 UDP 代理或 QUIC 模拟器。
控制连接使用父子进程管道或 Unix socket，不能和被切断的数据网络共用，否则测试无法读取真实状态。
丢弃覆盖双向、IPv4/IPv6、直接路径及任何允许的中继出口；不用正常 `shutdown`、FIN/关闭帧或拒绝包代替静默丢包。
规则生效通过计数器和独立探针核实；仅看程序显示 Offline 不能证明故障注入成立。

默认拓扑无公网依赖，rendezvous 与中继使用本地可控服务。直连场景关闭中继回退；中继场景用锁定 Iroh 依赖对应的成熟测试中继，禁止绕去公共中继“让测试通过”。
Linux 环境可用现有 CI runner或隔离虚拟机，不需要用户物理手机。当前 macOS CI 不具备 Linux 内核能力，P5 必须增加独立 Linux job；本机只能跑到哪一层就报告哪一层。
runner 只改本次新建命名空间中的规则与虚拟接口，不修改宿主默认防火墙、不关闭宿主网络。失败/超时后先停子进程，再删除所属规则、命名空间和资料。

### 5.3 只读恢复等待与完整断言

1. 用公开 Engine 操作真实配对并等待通信资格，记录各进程版本、提交、构建开关及测试节点别名。
2. 先等待准确目标双向 Online，再发唯一合成正文并核对接收端内容完全一致，建立可用基线。
3. 注入指定故障并确认注入生效；恢复等待期间只调用查询，不调用刷新、`RecoverNetwork`、发送正文或直接修改在线缓存。
4. 从规则生效/解除确认时刻计时；按场景断言状态事件、延迟与既有连接是否被替换。
5. 仅在自动恢复已经被只读观察证实后执行双向发送，核对双方精确内容与报告。测试不能由发送隐式帮助恢复。
6. 同时检查整会话重建次数和影响范围。复用现有诊断/生命周期观察，必要的进程内连接实例记录仅限测试；不为验收增加公开业务查询。
7. 记录事件序列而非仅最终快照；短暂错误 Offline 或关闭后又重连不能靠最终 Online 掩盖。
8. 每轮关闭全部节点，确认受管任务结束、子进程退出和网络资源清理。合成正文仅存测试私有资料，公开诊断不输出正文、地址、原始身份或凭据。

### 5.4 必须通过的场景

| ID | 拓扑与操作 | 必须断言 |
| --- | --- | --- |
| E01 | A/B 已连接，只拒绝新 presence 连接，经现有 `NotifyConnectivityOpportunity` 提交一次网络检查机会，再纯读观察超过两个检查周期；分别仅保留入站、仅出站以及双向连接重跑 | 活性确认走既有连接；无错误 Offline、无既有连接被主动替换、整会话重建为 0；双向正文成功；规则自检确实拒绝新连接 |
| E02 | 保持 A/B presence 正常，只拒绝新的内容通道连接，执行一次发送 | 本次发送如实失败；不会调用破坏性的 `mark_offline`，已有 presence 确认继续成功；解除规则后新用户发送成功，不暗中重放前次操作 |
| E03 | A/B 在线后内核双向丢弃全部通信，不通知 Engine | 两端在新协议 20 秒上界内 Offline；不能等 60 秒缓存自然消失才通过；无自动整会话重建 |
| E04 | E03 后解除规则，不发送、不刷新；再以屏蔽全部机会通知的模式重跑 | 有机会模式 20 秒、无机会模式 92 秒内自动双向 Online；随后精确正文双向可达 |
| E05 | A/B/C 均正常，只隔离 C | A/B 不出现 Offline、连接无误关闭、持续内容可达，整会话重建为 0；C 恢复后自动接入，不需要重启 A/B |
| E06 | 固定顺序执行 1 秒短断网、超过检测预算的断网和恢复，共 10 轮 | 短断网在确认预算内恢复时不误拆；长断网按预算 Offline/Online；事件不重复振荡，无任务/连接持续增长 |
| E07 | 旧确认延迟失败，同时另一条已认证连接成功；再交换为旧连接关闭、新连接成功 | 迟到失败/关闭不能覆盖成功或删除新实例；检查与关闭可并发完成，没有共用锁阻塞 |
| E08 | 确认期间移除成员、锁定、退出或关闭，随后放行迟到回应 | 无迟到 Online、无内容权限复活；本目标撤销不取消其他目标确认；关闭不遗留任务 |
| E09 | 新/新、新/旧、旧/新，各自作为主动端；旧端版本固定为 rc.15 对应已发布产物或可复现源码构建 | v2 正常；v1 协商明确，新端不误发新确认；不因旧端不支持而误关闭；旧模式静默断网在 70 秒边界内正确，旧端自身旧缺陷单列，不能改旧代码伪造兼容 |
| E10 | 本地中继短暂断开后恢复；分别运行直连仍通与仅中继可达拓扑 | 前者保持真实通信，后者按普通失联/恢复处理；DNS/网络变化动作有界，不自动整会话重建 |
| E11 | 全部远端退出、本地无法访问公网，但本地 Engine 仍运行；随后启动一个远端 | 不把“所有 peer 不可达”当本机终止；进程稳定、有界重试；远端返回后自动连接 |
| E12 | 单独执行显式 `RecoverNetwork`，以及真实 suspend/resume | 原合法恢复路径继续可用；操作正确结算，新会话重新连接并传送；不将该场景混入无干预自动恢复统计 |

E01/E02/E07/E08 先在真实 Infra/Engine 本机层复现；E03/E04/E05/E06/E10/E11 必须有独立进程网络证据。
E09 的最小旧 handler 仅用于协议负例，不能替代旧版完整 Engine 的互连证据。E10 的本地中继基础设施是本规格交付工作，不能因暂缺而将关键场景降为可选。
每个必选场景固定种子至少连续通过 3 次，失败不得以自动重跑后的绿灯覆盖；E06 每次执行包含完整 10 轮。

## 9. 风险、实施前检查与决策记录

| 风险或需要实证的细节 | 处理方式与完成门槛 |
| --- | --- |
| v2 确认双方接收循环与现有连接关闭管理相互阻塞 | P1 固定流所有权，P2 用双向同时请求、关闭与撤销测试；禁止持状态锁等待网络 |
| 新增检查增加空闲通信与功耗 | 复用健康证据并合并机会，不新增宿主轮询；统计健康稳态每目标请求数、确认字节数和任务数，符合 10 秒周期上限，不借此持续保持系统禁止的后台运行 |
| 活性成立但业务发送失败 | 在线与本次发送结果分开；E02 必须同时观察在线保持和发送失败，不将二者压成一个状态 |

| 中继或 IPv6 绕过断网规则 | 自检规则计数及路径隔离，直连/中继场景分开，任何未受控出口使场景失败 |
| 只有状态字段绿灯，实际上没有恢复 | 只读等待与恢复后精确内容验证分成两个阶段；统计隐式刷新/恢复操作，禁止 helper 促成成功 |
| 临时草稿污染基线或旧版构建 | 同时记录基线提交和工作区差异；旧版使用固定产物或独立构建，不能将当前源码的旧协议模式当作完整旧版本 |

P0/P1 需要核实的是工程事实，不需要用户再提供资料：旧版产物取得与校验、锁定 Iroh 中继测试服务的启动方式、Linux 最小宿主构建依赖、Port 失败报告的已有机会入口、当前健康业务回应能否可靠关联到连接实例。
这些检查必须在对应阶段关闭并记录结论；无法关联的业务回应不用于延长 presence 新鲜度，不以推测继续实现。

## 10. 资料与依据

- 本仓 `Cargo.lock` 及锁定依赖 `iroh/src/endpoint/connection.rs`、`connect.rs` 的实际 API；采用本地锁定源码核对，不按 latest 文档猜测版本能力。
- [既有自动连接设计](../../design-docs/automatic-peer-connections.md)、[原实施矩阵](../completed/2026-09-11-automatic-peer-connections.md)、[可靠性要求](../../RELIABILITY.md)。
- [ip-netns(8)](https://man7.org/linux/man-pages/man8/ip-netns.8.html)：独立网络命名空间和进程归属；本规格据此设计独立进程故障环境，不能用同进程内存隔离代替。
- [nftables 官方手册](https://netfilter.org/projects/nftables/manpage.html)：网络包过滤、规则计数和 IPv4/IPv6 控制；本规格采用系统丢包能力，不手写传输模拟器。
