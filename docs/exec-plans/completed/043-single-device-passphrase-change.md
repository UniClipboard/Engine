# 规格 043：单设备修改加密口令

## 状态

- **状态**：已完成
- **日期**：2026-09-14
- **前置规格**：[026 旧 Profile 隔离与重新配对](../completed/026-legacy-profile-isolation-and-re-pairing.md)
- **完整负责人**：`uc-application` 的单设备口令修改用例
- **调用方唯一动作**：收集用户自定义的新口令及再次输入值，通过一次请求提交修改
- **成功结果**：本机仍能读取原有内容，新口令在重启后可解锁并用于后续配对，旧口令和旧邀请失效
- **失败结果**：Space 未解锁、设备列表不只显示本机、成员状态无法确认、邀请无法撤销或安全资料不可用时返回稳定分类，旧口令继续有效
- **重试与重启责任**：通过输入与资格检查前不修改任何安全资料；开始持久替换后由 Infra 单一负责人前向完成，启动时先恢复未完成替换，再开放 Space 操作

## 1. 背景

旧版本升级后会清理旧设备关系，并要求用户重新配对。当前配对口令同时保护本机资料钥匙并用于新设备认证，
因此忘记旧口令的用户即使本机仍能自动解锁，也无法继续配对。

本次覆盖设备列表只显示当前有效本机的状态，不要求先经过升级清理。已有多设备的口令同步不进入本次范围。

## 2. 用户流程

1. 产品读取设备列表，确认只显示当前设备。
2. 产品收集用户自定义的新口令和再次输入值，并提醒用户妥善保存。
3. 产品通过一个请求把两次输入交给 Engine；输入不一致时直接拒绝。
4. Engine 检查 Space 已解锁且当前成员范围只有本机，撤销当前进程内全部旧邀请，并完成本机解锁资料和配对认证资料的替换。
5. 只有完整替换和回读验证成功才返回成功。`re_pairing_required` 保持为真，直到一台新设备真正完成配对。

产品负责口令输入、再次确认和保存提示，不得由 Engine 生成或替用户决定口令。

## 3. 边界与约束

- 必须同时满足：Space 已解锁、本机成员有效、可用和暂停的其他成员均为空。
- 多设备、成员冲突和成员恢复中均拒绝；是否处于升级重配对状态不参与判断。
- 新口令由用户自定义；两次输入必须一致，两个输入都不得出现在日志、错误文本或调试输出中。
- 口令不写日志、不进入错误文本、不以明文持久化；公开输入和结果的调试输出必须脱敏。
- 保留现有 MasterKey，不遍历、不改写剪贴板历史、文件和搜索内容。
- 替换过程中不得签发新邀请；旧邀请必须先从其实际发行方撤销，再从本机清除。
- 成功后不得清除 `re_pairing_required`，因为它表达“尚未重新建立设备关系”，不是“口令尚未更新”。

## 4. 设计

### Application

新增一个用例，拥有资格检查、口令生成、邀请撤销和替换调用。Facade 用一把与邀请签发共享的互斥锁，避免撤销
邀请后到口令生效前又签发旧口令邀请。Application 只看“替换成功或稳定失败”，不编排文件、数据库和安全存储步骤。

### Infra

新增一个口令替换负责人，保留当前已解锁的 MasterKey，派生新保护资料并准备新的配对认证资料。负责人先把目标
状态写入受保护的恢复记录，再依次发布配对认证、本机 keyslot 和系统安全存储，逐项回读验证后删除恢复记录。
恢复记录只保存完成替换所需的密文或受 Profile 密钥保护的材料，不保存明文口令。

启动时若发现恢复记录，必须完成同一目标替换；不能回滚到来源状态，也不能在本机解锁口令与配对口令不一致时
开放邀请和准入。

### Engine 与绑定

稳定入口增加一个“修改加密口令”操作，接收用户输入的新口令和再次输入值，成功只返回完成状态。
UniFFI 与 HarmonyOS 绑定提供相同动作，秘密字段不得出现在调试输出。

## 5. 验收

- 设备列表只显示有效本机时能修改为用户自定义的新口令。
- 两次输入不一致时拒绝，旧口令、旧邀请和持久资料均保持不变。
- 未解锁、多设备、暂停成员和成员恢复状态均拒绝；普通单设备可以成功修改。
- 修改成功：旧口令无法解锁，新口令可解锁；进程重启后结果不变。
- 新邀请只接受新口令；旧口令认证失败；修改前签发的邀请已失效。
- 替换前后的 MasterKey 及代表性历史内容一致，没有批量重加密。
- 在每个持久发布步骤注入失败并重启，启动恢复到新口令完整可用的唯一结果。
- 公开错误、日志与调试输出不含口令、密钥、邀请、设备名、地址、文件名或路径。
- 执行仓库规定的全量检查；未执行的实体设备项目明确记为“跳过”。
