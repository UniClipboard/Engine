# Process observability and failed-start release specification

Status: Proposed; implementation and acceptance are incomplete.
Decision: [ADR-035](../../design-docs/decisions/035-recoverable-process-and-startup-release-owners.md).
Existing contract: [Engine resource-release contract](../../design-docs/engine-resource-release.md).
Baseline: Engine `0c972cd97503cad73704933e066c728a38e9585f`; network gitlink `413531dd7503c87ce89f21b69196f8c26eed909d`. These identify the reviewed baseline, not a delivered implementation.

# 1. Overview

Mobile needs a positive, scoped release result before it can complete its own runtime-lock handoff. The existing Engine result excludes process observability. The process installation outlives Engine instances, and a flush can retain or reopen its daily file. A detached lifecycle flush can outlive the caller. Terminal process shutdown cannot provide foreground recovery.

A constructor can fail without returning a `MobileEngine`. The startup lifecycle control does not retain a complete cleanup receipt. Partial construction and rollback can outlive a wait or fail. The host must not infer release from a missing object, an error, or a joined worker.

# 2. Goals

- Provide a recoverable process owner that closes admission, drains accepted work, closes each covered file and lease, and resumes without replacing the process singleton.
- Provide a startup-attempt owner before resource production and a host-readable result even when no Engine object is returned.
- Preserve operation errors independently from resource-release classification.
- Retain accepted work after caller timeout, retain failed live closers, and fence results by generation.
- Produce reproducible end-to-end evidence with real temporary resources and independent process probes.
- Deliver bindings and native slices generated from the exact final Engine and network source pair.

# 3. Non-Goals

- Change Mobile source, its dependency pin, JS history policy, or its file acknowledgements in this Engine task.
- Assert that an Engine receipt closes Mobile-owned files, another process's files, or the host runtime lock.
- Select logging coexistence or exclusion policy, or Share interruption policy.
- Disable logging, replace recoverable release with terminal shutdown, or claim the original device crash is fixed.
- Access production App Group data, keys, clipboard contents, or databases; launch a GUI, VM, simulator, or device app.

# 5. Proposed Design

## Components

- **Process owner:** the existing process runtime owns one coordinated state. Input: release or resume request and caller wait deadline. Output: a generation-qualified complete result. It owns admission, drain and close ordering for its full scope. Do not introduce a second process singleton.
- **Startup-attempt owner:** created before capability preparation. Input: one constructor attempt, cancellation or loss of delivery, and wait requests. Output: startup result and independently classified cleanup receipt. It strongly owns the worker and live closers until their obligations are complete or terminally unconfirmed.
- **Existing Engine owner:** remains responsible for one Engine. Its receipt and process receipt are independent. The host combines them with its own resource receipts.

Implementation may split private modules by responsibility. It must not expose internal workflow steps for the host to assemble.

## Source inventory before implementation

The following observations describe the baseline and the existing uncommitted candidate. They are not release evidence.

- `LifecycleGate` retains a timed-out process flush until its worker ends. Network flushing runs within that reserved operation. The worker waits without the caller's deadline for its local and network queue requests, so an accepted queue flush remains owned after the caller stops waiting. The complete process owner must still coordinate every other producer and closer before reporting release.
- Telemetry admission and remote submission have terminal sealing operations. A recoverable owner needs a reversible admission boundary and must account for accepted exporter work before reopening.
- The daily and network queues share `LocalFileWorker`. An `unpark` can time out after enqueueing while the worker later opens the store. A later release must not treat that timeout as proof that the file stayed closed. The current worker reports a late acknowledgement and checks its transition identity before reopening admission; the complete process owner must still serialize all covered operations.
- `EngineLogActivity` serializes its own count and network parking. A private process-release implementation now calls its registration fence. Dropping a registration only decrements the count and does not itself wait for closure.
- `ProcessCensus::stop` joins its worker, but the installed census is held in a `OnceLock`. The current installation has no corresponding restart path.
- Startup handoff retains an Engine during lost delivery, but its cleanup outcome is not exposed through `MobileStartupLifecycle`. A startup error returned by the binding worker is not a complete cleanup receipt.
- The candidate moves lifecycle input consumption before host preparation. Its existing regression test confirms that lifecycle requests stop waiting after host preparation fails. It does not prove that every resource from partial preparation is released.

## Data Model

The following is a contract, not a claim that these concrete Rust types already exist:

```text
ReleaseResult = Pending(generation)
              | Released(generation, operation_error?)
              | Failed(generation, cleanup_error, explicit_retry_supported)
```

`generation` identifies the accepted process or startup attempt. `Pending` retains one accepted operation. `Released` certifies only the documented scope; it may carry an operation error. `Failed` is a completed unconfirmed attempt, not a timer retry request. The owner retains a live failed closer; a terminated worker is terminal for that owner. Error information must not expose paths, content, credentials, device names, or addresses.

Process state must distinguish active, release accepted, released, resume in progress, and failed/unconfirmed. Resume invalidates earlier release authority before any producer or file can reopen. If release is still running, retain and settle that work before reopening. A wait timeout does not cancel either operation. Repeated waits refer to the same accepted release. Concurrent waiters use independent deadlines.

Startup state must distinguish not yet started, constructing, delivered, cleanup pending, released, and failed/unconfirmed. Preserve the original startup error separately from cleanup errors. An unused or rejected lifecycle object must not be confused with a different attempt.

## API / Interface

Add complete operations through `uc-engine` and the relevant mobile binding. Concrete names are implementation choices; the required actions are:

- `release_process(wait_deadline) -> ReleaseResult`: accept or join one process release. A timeout returns `Pending` without cancelling accepted work.
- `resume_process(wait_deadline) -> resume result`: invalidate old release authority before reopening. Report failed reopening without granting a new release receipt.
- `startup_owner.wait_release(wait_deadline) -> ReleaseResult`: observe the same startup cleanup even without a returned Engine. Provide an explicit retry only for a retained, live closer that can actually retry.

The process and startup actions now have provisional Rust and UniFFI declarations in this worktree. Final acceptance remains incomplete, so these declarations are not a shipped contract. Keep existing APIs compatible. Generated declarations and native artifacts must match the exact source pair.

## Workflow

1. Create the startup owner before host capabilities can produce resources. Register every later owner before the associated resource becomes externally active.
2. On successful handoff, transfer the Engine obligation to the returned Engine owner. On failure, loss of delivery, or late completion, retain the startup owner and run its required cleanup.
3. For process release, coordinate all Engine registrations and close producer admission. An active Engine that still requires a shared writer keeps the accepted release Pending until its registration ends. New Engine registrations must not pass the release fence. Do not silently choose cross-process coexistence policy.
4. Drain accepted telemetry, exports, lifecycle flushes, census activity, daily queue and network work. Close their covered files and leases. A late flush cannot reopen them.
5. Return `Released` only after all covered closers positively acknowledge closure. Keep operation errors separate. Return `Failed` for completed unconfirmed closure and retain its owner.
6. Resume only through the owner. Fence the previous generation before reopening resources or admission. A delayed old result has no authority over the resumed generation.
7. The host separately waits for its native, JS, cache, diagnostic and runtime-lock obligations. An absent JS acknowledgement is not release proof.

# 6. Implementation Plan

1. **Evidence and inventory.** Preserve the existing red process flush and pre-input startup scenarios. Record all writer and closer owners. Risk: a controlled closer can hide an untracked real descriptor.
2. **Daily queue slice.** In `local_file.rs`, verify admission, queue order, actual close, failed close, deadline and resume. Keep the existing passing behavior. Risk: an accepted late control message or concurrent resume can reopen a file.
3. **Process owner.** In the process runtime, telemetry, census, network and Engine activity modules, coordinate the complete producer and closer set. Keep one owner and fence generations. Risk: a detached flush or another Engine can escape the fence.
4. **Startup owner.** In Engine startup, runtime construction and UniFFI startup, register ownership before resource creation and retain cleanup across handoff and failure. Risk: rollback drops a failed closer or loses its primary error.
5. **Facade and binding.** Expose only complete actions and results through `uc-engine` and mobile bindings. Generate matching artifacts. Risk: declarations and native binaries can come from different source revisions.
6. **End-to-end acceptance.** Run the scenarios below serially using the repository Cargo entry point. Record commands, exit codes, source and executable hashes, resource probes and skips. Do not start a device application.

# 7. Edge Cases

| Scenario | Expected behavior | Implementation obligation |
| --- | --- | --- |
| No configured writer | Confirm only the documented empty scope; do not infer host-file release. | Represent absent resources explicitly. |
| Two active Engines | No positive process release while a required shared writer remains active. | Serialize Engine registration with release and resume. |
| Old flush finishes after deadline | Caller sees Pending; accepted work stays owned and is drained. | Retain its completion and prevent late reopen. |
| Resume races an old release | Old generation cannot authorize the resumed generation. | Fence authority before reopening. |
| Writer close fails | Failed remains unconfirmed; preserve the actual closer. | Distinguish explicit live retry from terminal failure. |
| Operational error after successful closure | Released carries the operation error. | Classify resource closure separately. |
| Capability preparation fails | No Engine object is required to observe the startup outcome. | Create the startup owner before this stage. |

# 10. Risks and Trade-offs

A process-wide owner adds coordination to shared logging and may delay handoff while an active Engine or exporter remains. It avoids a false positive receipt. Retaining failed closers consumes resources until explicit recovery or process termination; dropping them would remove the ability to verify release. Some third-party actors may lack a positive close acknowledgement. Such an actor keeps the result unconfirmed until its actual contract is established.

The current source-backed audits and controlled host tests do not identify the original device lock. A resource probe only proves the resources it samples. Do not expand a narrow passing probe into an all-descriptor claim.
