### 旧版资料快照锚点

早于 Engine 的 Desktop 发布（0.19.x）没有可构建的测试宿主，改以静态资料快照参与，只进入 D1：

- 清单 `tests/upgrade-matrix/legacy-anchors.json` 人工维护，不由 GitHub 发布生成；快照与来源说明在
  `tests/upgrade-matrix/fixtures/`，由 `scripts/testing/create-legacy-desktop-profile.ps1` 用官方发布 CLI 生成。
- 快照放入设备资料目录的 Engine 私有目录；便携模式的文件钥匙串解码为宿主安全存储，与 Desktop 1.0 便携模式一致。
  使用前按 `SHA256SUMS` 逐个校验。
- 每个快照展开两个单元：`d1-<id>-head`（升级、核对历史/设备名/单设备、重启不变、继续使用），以及
  `d1-<id>-head-commit-interrupted`（首次启动期间外部持有 Space 转换激活租约，使单设备重建在提交边界失败，
  随后必须收敛且可重试）。后者依赖一个内部租约文件名，名称变化时以 `interruption-not-effective` 显式失败。
- D2–D4 不适用：0.19 与 1.0 按设计不能互通，旧版也无法重新打开已升级资料。

### 矩阵维度

设锚点按发布顺序为 V1 < V2 < … < Vn，Vn 为当前源码。“单元”是一个维度下的一对（或一条链）版本。矩阵只覆盖
当前源码（见“已确认的决定”第 9 项）：Vj 固定为 Vn，已发布锚点之间的组合不展开，单元数为 5(n − 1) + 1，另加每个旧版资料快照锚点的 2 个 D1 单元。

| 维度 | 含义 | 展开方式 | 单元数（n = 14） |
| --- | --- | --- | --- |
| D1 单设备资料升级 | Vi 建立资料并写入代表性内容后退出，Vn 打开同一资料目录 | 每个 i<n，外加完整链 V1→V2→…→Vn | 13 + 1 |
| D2 两台设备先后升级 | 两台 Vi 设备已配对并有历史；A 先升到 Vn 并与仍为 Vi 的 B 互通，B 再升到 Vn | 每个 i<n | 13 |
| D3 新旧设备混用 | 一台 Vi、一台 Vn 从零开始配对并互通；邀请方分别为旧版与新版 | 每个 i<n × 两种邀请方向 | 26 |
| D4 降级回退 | Vi 升到 Vn 并写入新内容后，再用 Vi 打开同一资料 | 每个 i<n | 13 |

每个单元内的动作与断言（全部经测试宿主的公开 Engine 操作，不读数据库、不依赖内部类型）：

- **写入（旧版）**：创建 Space、设置设备名，写入文本、文件与图片历史，修改同步偏好；D2/D3 另含配对、双向同步、
  移除后重新加入。
- **升级后核对**：启动成功（含启动升级进度终态），Space 可解锁，设备列表、成员状态与设备更新汇总符合预期，
  历史条目数量与内容摘要一致、文件可读，设置保留；随后继续执行新操作（发送、邀请、移除），证明升级后仍可用。
- **跨版本互通（D2 中段、D3）**：双向发送文本与文件，查询设备组选择，执行一次移除，双方在期限内收敛。
- **降级（D4）**：旧版必须明确报告需要处理（或在其能读懂资料时正常工作），且不改写资料；再次用 Vj 打开时
  内容与降级前一致。

每个单元的期望结果登记为“通过”或“已知不兼容（原因、链接到计划或 ADR）”。“已知不兼容”必须是产品已接受的
行为（例如旧版对端不支持的协议升级明确拒绝），不能用来掩盖缺陷。

### 运行方式

- **PR 冒烟**：只跑“上一个锚点 → 当前源码”（A13 → HEAD）的 D1、D2、D3（两种方向）与 D4，共 5 个单元。
- **夜间、锚点定义变化的 PR 与手动触发**：整个矩阵（n = 14 时 66 个单元），随锚点数线性增长；按维度分片并行，
  旧版宿主按 rev 缓存复用。
- 旧版宿主构建在仓库 `target` 下的可再生目录 `target/upgrade-anchors/<rev>/`，与 rc15 先例一致；
  入口提供清理命令，并在 CI 结束时回收。

### 非目标

- 不覆盖 Desktop 应用外壳、界面或 Desktop 自有存储；只覆盖 Engine 负责的资料与设备间行为。
- 不覆盖移动端（iOS、Android、HarmonyOS）实体设备；绑定层行为由各自宿主契约测试负责。
- 不覆盖 v1.0.0 之前的 Desktop 版本，也不以 Engine tag 为锚点（后续版本可另行扩展锚点来源）。
- 不修改产品代码来迁就测试；测试宿主只使用各锚点已有的公开 Engine 接口与 `dev-tools` 能力。
- 不在本计划中实现版本回退能力本身（计划 043 负责）；D4 只验证现状并固定期望。

## 设计要点

### 一个宿主源码，多个锚点构建

- 所有锚点共用当前的 `tests/hosts/connectivity` 源码与同一控制协议（stdin/stdout JSON）。构建某个锚点时，取该 rev
  的源码快照（`git archive`），覆盖当前宿主目录，应用 `tests/upgrade-matrix/anchors/<锚点>.patch`（仅在该 rev 的公开
  API 与宿主不一致时存在），以 `--no-default-features` 离线构建。补丁只允许改宿主与工作区成员声明，不得改被测 Engine。
- 宿主启动后报告自身锚点标识与支持的指令集合；测试台据此发现能力差异，缺少某项能力时该断言按登记处理，
  不静默跳过。
- 核实结果：13 个旧 rev 的 `uc-engine` 都有 `EngineConfig`、`HostCapabilities`、`HostDirectories`、
  `HostSecureStorage` 与 `dev-tools`，rc15（A07）先例只需 10 行补丁。
- 实施取舍（能力分层）：13 个旧 rev 的公开接口可归为 5 代，差异集中在少数入口。宿主以 7 个按能力划分的 feature
  表达（`test-network-config`、`network-recovery`、`process-observability`、`device-group-choices`、`join-status`、
  `connectivity-opportunity`、`startup-progress`），当前源码的 `current-engine` 启用全部能力；锚点与能力的对应登记在
  `tests/upgrade-matrix/host-features.json`，构建脚本按此传 feature。缺少的工作区成员声明由构建脚本统一补上。
  因此当前没有任何锚点补丁；补丁目录保留给能力分层无法覆盖的差异。

### 外部依赖跳过

A01、A02 的公开接口无法在 Engine 启动前关闭默认 n0 relay 与 pkarr 公共发现（`with_test_relay_fallback` 从 A03
才有，此前网络设置只从资料中的设置文件在启动时读取）。按“风险”一节，宿主在这两个锚点上拒绝启动并报告
`local_network_unavailable`，不访问外部服务；涉及它们的单元登记为 `skip`（收缩后为 10 个），完整链登记排除这两个
版本点。若日后决定以其他方式在首次启动前提供本地网络配置，再重新登记。

### 资料在进程之间传递

- 资料目录由测试台以 `TempDirLease` 持有，跨版本进程复用同一目录；安全存储沿用宿主已有的导出与导入指令，
  由测试台保存在单元目录内。测试资料全部是合成内容，工件不含真实用户资料。
- 新增宿主指令 `observe`：输出规范化的可观察状态（设备与成员状态、设备更新汇总、历史条目数与内容摘要、设置），
  只含测试合成数据的摘要，用于同一单元内升级前后比较。

### 测试台与报告

- 新测试 crate `tests/upgrade-matrix`（依赖 `uc-testkit`），矩阵在编译期由锚点清单展开为具名测试
  （如 `d1::a05_to_head`），nextest 按名称过滤、分片与设定期限。
- 每个单元一个 `Scenario`，阶段为“构建检查、旧版写入、升级、核对、继续操作、清理”；失败分类沿用 testkit。
- 汇总脚本把全部 `result.json` 汇成矩阵表工件（Markdown 与 JSON），标注通过、失败、已知不兼容、跳过。

## 风险

| 风险 | 应对 |
| --- | --- |
| 13 个旧 rev 完整构建耗时长 | 按 rev 缓存；PR 只构建 A13；夜间复用缓存，只在清单变化时重建 |
| 旧 rev 的公开 API 与当前宿主有差异 | 每个锚点一个最小补丁，只改宿主；补丁变大说明需要能力分层，先记录再决定 |
| 旧 rev 依赖的外部服务（rendezvous、relay）不可用或已变化 | 测试一律使用本地直连与本地 relay 宿主，不访问外部服务；无法关闭外部依赖的锚点记为跳过并登记原因 |
| 首轮全矩阵暴露大量不一致 | 先判定并登记，产品问题另行立项，不在测试计划里修产品 |
| 全矩阵夜间耗时过长 | 按维度分片；实测后已收缩为只覆盖当前源码（“已确认的决定”第 9 项） |

### 2026-09-26（t-0054，D3 跨版本拒绝原因）

  真实认证失败都以 `0x52` 关闭，保持 `authentication_rejected`，Engine 单元测试同时固定这两种结果。

  `receive_hello`/`peer_upgrade_required`（错误类型 `peer_incompatible`），并删除只被此处使用的身份检查分类。
