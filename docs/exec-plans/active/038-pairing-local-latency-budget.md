# 规格 038：双设备配对本机耗时压缩到一秒

## 状态

- **状态**：等待用户根据 037 验证结果决定是否实施
- **日期**：2026-09-05
- **前置规格**：[037 OpenTelemetry tracing 与结构化日志](../completed/037-opentelemetry-tracing-and-structured-logs.md)
- **完整负责人**：Application 的 `SpaceAdmissionProtocol` 负责配对推进和持久恢复；Infra 的准入状态仓库与认证传输分别负责持久化成本和纯网络等待证据
- **调用方唯一动作**：调用方仍只提交一次 `join_space`，随后查询双方最终成员状态，不编排确认轮次、维护轮或持久步骤
- **成功结果**：排除纯网络等待后，双设备本机配对耗时 p95 小于 1 秒；双方均看到两名有效成员
- **失败结果**：超时、断网、损坏、并发冲突和旧版本不兼容仍返回现有稳定结果，不以跳过持久提交换取速度
- **重试与重启责任**：每个已对外产生影响的状态先持久化再继续；重启后由原准入恢复流程从最后一个已提交状态继续

# 1. Overview

037 的最终本机双设备测试约耗时 5.3 至 5.6 秒，最新一次为 5.338917 秒。现有证据已足以证明它明显超过 1 秒目标，但当前计算把发送端编码、认证和回包校验的一部分也算进网络时间，同时漏掉初始连接的一部分网络等待，因此不能在接近门槛时作为精确判定。

代码审计识别出准入加密状态的重复整库读取、加解密、写入后再次读取，以及一次状态推进被拆到多个维护唤醒等候选成本；当前证据尚不能证明其占比和排序。仓库确实会在多次提交中重复打开加密单例并在保存后重新读取，但是否先改这条路径，必须由 Slice 0 的可信分项测量决定。

本规格先建立只扣除纯网络等待的可信门禁，再按证据逐层减少重复工作。它不减少必须持久化的安全检查点，不把准入步骤暴露给 Engine，也不让观测接口参与业务编排。

# 2. Goals

- 建立能够区分纯网络等待与两端本机工作的性能门禁，并同时报告端到端总时长、本机时长和观测开销。
- 让一次仓库提交最多打开一次当前加密状态，删除同一事务内无新增安全价值的整库回读。
- 让 Application 优先消费提交返回的最新状态，在同一次维护执行中持续推进，避免无业务需要的重新加载和定时唤醒。
- 若前两片后仍未达标，把整张双层密文单例改为加密索引加逐次准入独立密文行，避免每次改一条记录都重写全部记录。
- 保留配对每个已对外产生影响的持久检查点、密文存储、冲突检测、崩溃恢复和旧成员更新。
- 每个改动片都能独立运行双设备验收并给出前后 p50/p95，未达到收益门槛的改动不合并。

# 3. Non-Goals

- 不减少协议需要的消息或确认轮次；只有测量证明两个相邻本机提交之间没有网络、授权或外部效果时，才允许合并提交。
- 不把准入状态、消息阶段、业务标识或步骤查询新增到 Engine、Facade 或公开绑定。
- 不把网络、加密或持久化失败改成成功，也不放宽密文损坏时的关闭式失败。
- 不引入延迟写入、异步补写或明文缓存；进程内缓存不能成为事实来源。
- 不改变 P2P 默认路线，不增加 LAN 自动降级。
- 不在本规格调整 037 的日志保留、发送后端或产品分析行为。

# 5. Proposed Design

## Components

### 可信耗时分解

- **职责**：只在 Infra 已有传输内部标记同一时钟下、已完成写入到对端数据可读之间能够配对证明的区间；编码、摘要、认证、解码、Iroh 本机握手、执行器调度和无法归类的唤醒延迟都保留为本机耗时。
- **输入**：现有连接与流的异步等待边界，以及已认证的父子调用关系。
- **输出**：固定名称、无业务阶段和无业务标识的网络等待证据。
- **关系**：集成测试接收器读取 dev-tools 证据并计算门禁；Engine 不读取步骤数据，不新增业务接口，也不据此编排流程。

端到端窗口从 `join_space` 提交前开始，到 Sponsor 与 Joiner 都公开显示两名有效成员为止。纯网络时间按窗口内已验证的网络等待区间取并集，不能直接相加；任何无法证明为网络等待的区间一律保留在本机耗时中。当前 client/server 外壳差只作为旧基线，不再作为通过依据。

### 单次打开的仓库提交

- **职责**：每次提交在一个立即事务内读取并打开当前状态一次，校验令牌、应用变化、加密并写入一次。
- **输入**：现有提交令牌和 Core 产生的合法状态变化。
- **输出**：已提交的最新业务视图和下一提交令牌。
- **关系**：SQLite 的事务结果负责确认写入成功；下一次独立读取继续负责发现密文损坏。删除同一事务内整库写后回读，不删除 AEAD 校验、令牌校验或事务提交。

### 加密索引与逐记录存储

- **职责**：若前两片后整库重写仍是主要成本，把仓库元数据保存在加密索引中，每个 admission attempt 使用独立加密行；一次事务同时更新索引和目标行。
- **输入**：现有提交令牌、当前加密索引和目标记录密文。
- **输出**：原子提交后的加密索引与目标记录。
- **关系**：索引、版本、当前加入指针和记录都保持密文；不得增加明文 revision、digest 或业务标识作为快捷列。

### 连续恢复执行

- **职责**：Application 在一次恢复执行中继续使用 `commit` 返回的最新状态；只在发生外部等待、冲突、失败或真正没有可推进工作时退出。
- **输入**：现有 `LoadedPendingAdmission`、提交结果和恢复报告。
- **输出**：同一稳定恢复报告，不增加步骤结果。
- **关系**：维护循环仍只调用一次完整恢复能力；Engine 不知道内部推进次数。

## Data Model

性能证据只存在于测试接收数据和最终报告中：

| 字段 | 含义 | 生命周期 |
| --- | --- | --- |
| `wall_elapsed` | 完整公开配对窗口 | 单次测试 |
| `network_wait_union` | 经验证纯网络等待区间的并集 | 单次测试 |
| `local_elapsed` | `wall_elapsed - network_wait_union` | 单次测试 |
| `repository_open_count` | 窗口内整库打开次数 | 测试构建 |
| `repository_save_count` | 窗口内持久提交次数 | 测试构建 |
| `maintenance_run_count` | 窗口内维护执行次数 | 测试构建 |

这些字段不进入 Core、公开结果、绑定或持久状态。计数只用于测试，不能携带 admission、Space、设备或成员标识。

## API / Interface

- `join_space`、成员查询、错误分类和绑定接口保持不变。
- `SpaceAdmissionProtocol` 的完整恢复入口和报告保持不变。
- 仓库现有 port 的业务语义保持不变；允许在 Infra 私有实现中返回已提交最新视图，不能新增步骤式公开方法。
- 观测只增加固定 Infra 网络等待类型和测试计数，不增加 Engine 可查询的准入步骤。

## Workflow

1. 调用方提交一次 `join_space`。
2. Application 保存开始状态并唤醒完整准入恢复。
3. 恢复 owner 加载待处理状态，在一次执行中推进到必须等待外部输入的位置。
4. 每个对外生效前的检查点在单个事务内完成一次打开、校验、加密和写入。
5. Infra 传输只把真实连接或套接字等待标记为网络时间，本机认证与处理不被扣除。
6. 双方都公开显示两名有效成员后结束计时，并独立确认旧成员更新和重启恢复。

# 6. Implementation Plan

## Slice 0：可信门禁与基线（串行）

**File**：`crates/uc-infra/src/network/iroh/space_admission/` 下的 `client.rs`、`server.rs`、`connection.rs`、`exchange.rs`，以及 `crates/uc-engine/tests/space_membership_auto_pairing_e2e.rs`、观测固定枚举与接收测试。

**Change**：在 Infra 私有 dev-tools 证据中记录 `endpoint.connect` 和 `open_bi/accept_bi` 的总耗时用于诊断，但只有序列化完成后的 write-complete 到已配对 read-ready/read-complete 区间可进入网络扣除。Iroh 本机握手、执行器调度和无法证明来源的 await 墙钟一律留在本机；用可控虚拟传输时钟和固定延迟校准，延迟只允许增加 network。匹配区间在完整窗口内取并集，缺失、重叠错误、关系错误或窗口外数据使本次样本无效。测试等待改为事件驱动或记录轮询上界，不能把当前 100ms/10ms 轮询误差归给业务。每片预热后先运行 5 次，最终运行不少于 20 次，记录 p50/p95、整库打开次数、提交次数和维护次数。

**Risk**：测量本身可能改变调度。只使用已有异步边界和固定低基数字段，并分别测量观测关闭、健康接收和不可达三种状态。

## Slice 1：删除提交内重复整库回读（可与 Slice 2 分 Agent 并行）

**File**：`crates/uc-infra/src/space/admission/repository/codec.rs` 及各状态适配器测试。

**Change**：一次提交只打开当前状态一次；写入成功以事务提交为准，不在同一事务内再次读取、解密和逐值比较。补充下一次读取损坏、写入失败回滚、错误密钥、代际不符和并发令牌冲突测试。

**Exit gate**：所有恢复测试通过；持久密文不变；该片单独使 p95 或整库打开次数出现可复现下降，否则不合并。

**Risk**：原回读可能掩盖错误实现。用真实数据库故障与下一次加载完整性测试替代同事务重复验证。

## Slice 2：同一维护执行连续推进（可与 Slice 1 分 Agent 并行）

**File**：`crates/uc-application/src/space/admission/protocol/recovery/`、`crates/uc-application/src/space/membership/maintenance/`。

**Change**：Candidate 和 Commit 等处理动作返回已提交的最新 `LoadedPendingAdmission`，完整 recovery owner 在无需等待新外部输入时于同一次调用内继续，最多 fast-forward 四轮；删除固定等待尾部和无进展重跑。每个网络交换前的状态仍已持久化，失败立即退出并由 Startup、Resume、Periodic 或状态变化触发重试。

**Exit gate**：相同消息序列产生相同最终状态和恢复报告；维护执行次数下降；037 已修复的无工作停机等待保持不回归。

**Risk**：无进展循环会占满执行器。每轮必须证明状态版本前进，否则立即退出并按原分类报告。

## Slice 3：按准入记录原子存储（串行，依赖 Slices 1-2）

**File**：`crates/uc-infra/src/space/admission/repository/`、数据库 migration、profile upgrade fixture 与各状态适配器。

**Change**：只有 Slices 1-2 后的测量仍指向整库加解密时才实施。把现有整张记录 map 的双层密文改为“加密索引 + 每 attempt 独立密文行”；SQLite 事务同时更新索引和目标行，CAS 继续使用现有 token 与 record version。旧真实 fixture 通过一次性升级进入唯一新格式，不保留双 writer 或长期双 reader。

**Exit gate**：多记录、旧成员规模、重启、代际切换、锁定、并发提交和任一行损坏全部保持原语义；单次变化不再重写无关记录。

**Risk**：格式迁移或索引与记录分离可能产生孤儿行。索引与目标行只在同一事务发布，启动时验证双向完整性，失败关闭。

## Slice 4：仅合并无外部边界的相邻提交（串行，条件执行）

**File**：Slice 0 证明仍为主要成本的具体 Application 动作与对应 Infra 完整提交能力。

**Change**：逐对审计相邻提交。两次提交之间只要存在网络发送、授权决定、宿主可见结果、重试恢复点或旧成员更新，就禁止合并；只有纯本机准备且崩溃后无需独立恢复的变化才能合并为一个 Core transition 和一个事务。

**Exit gate**：在每个保留检查点强制终止并重启，结果与改造前一致；提交次数下降且 1 秒门禁仍需独立通过。

**Risk**：错误合并会破坏 crash consistency。本片默认不执行，必须由前一片测量给出具体候选和收益占比。

## Slice 5：总验收与归档（串行）

**File**：双/三设备验收、设计文档、架构圣经、038 与索引。

**Change**：运行完整性能、重启、安全、兼容和三设备旧成员矩阵；记录每片前后数据；删除只为诊断创建的临时计数，保留长期可信门禁。

**Risk**：单次快结果掩盖抖动。只接受预热后不少于 20 次的 p95，不使用最快值。

# 7. Edge Cases

```text
Scenario: 连接慢或暂时断开。
Expected behavior: 纯网络等待不计入一秒，但总流程仍受现有超时限制；恢复状态保持可重试。
Implementation: 只扣经证明的网络等待区间，保留总时长和超时门禁。
```

```text
Scenario: 进程在任一持久检查点后终止。
Expected behavior: 重启从最后一次成功提交继续，不重用一次性短码，不重复正式成员提交。
Implementation: 对每个检查点执行故障注入和重启测试。
```

```text
Scenario: 两个维护触发同时推进同一准入。
Expected behavior: 只有一个提交成功，另一方得到现有冲突分类并重新加载，不覆盖新状态。
Implementation: 保留提交令牌和 profile 级串行约束，并增加并发测试。
```

```text
Scenario: 加密索引与记录行不一致或任一密文损坏。
Expected behavior: 启动与读取都关闭式失败，不能忽略孤儿或缺失记录继续配对。
Implementation: generation 绑定、事务原子更新、双向完整性校验和真实损坏 fixture。
```

```text
Scenario: 新旧准入消息布局相遇。
Expected behavior: 已认证对端收到明确升级提示，普通网络失败仍保持 Pending 或 Deferred 且不自动降级；当前 Engine 尚未发布，因此不增加 Engine 版本号。
Implementation: 保留 037 已建立的认证后新旧 frame kind 区分、真实旧 Sponsor fixture 和持久升级提示；038 只做回归验证，不改版本号。
```

```text
Scenario: 第三台旧成员在线或稍后恢复在线。
Expected behavior: 旧成员最终收到新成员更新，并能向新成员发送内容。
Implementation: 三设备测试同时覆盖在线和离线后恢复两种情况。
```

# 8. Testing Strategy

## Unit Test

- 仓库一次提交的读取、打开、加密和写入计数符合上限。
- 写入失败回滚，下一次加载能发现损坏、错误密钥和代际不符。
- 加密索引与逐记录行只能同事务更新，孤儿、缺失和损坏组合全部失败关闭。
- 连续恢复只在状态版本前进时循环，无进展、取消和超时立即退出。
- 网络等待证据拒绝本机编码、认证、解码和业务处理区间。

## Integration Test

- 两个真实本机 Iroh endpoint 完成初始认证和全部确认轮次，网络证据完整且关系正确。
- 在每个持久检查点终止 Joiner 或 Sponsor，重建 Engine 后完成或保持原稳定失败。
- 同一 profile 并发触发恢复，最终只有一个合法状态链。
- 本地文件、SQLite 和导出中始终没有明文业务负载或敏感标识。

## Regression Test

- 双设备双方最终均显示两名有效成员并可双向发送。
- 三设备中旧成员收到成员更新，并可向新成员发送；离线旧成员恢复后也收敛。
- 新旧布局双向明确不兼容，P2P 失败不自动切换 LAN。
- 观测关闭、健康接收和不可达各运行不少于 20 次；三组业务结果一致，观测增量仍满足 037 预算。
- workspace、架构、格式和隐私检查全部通过。

# 9. Acceptance Criteria

* [ ] 性能门禁只扣除经证明的纯网络等待，不能把任一端本机编码、认证、处理或调度算作网络。
* [ ] 空闲本机预热后不少于 20 次，双设备本机配对耗时 p95 小于 1 秒，同时报告端到端 p50/p95。
* [ ] Sponsor 与 Joiner 最终都公开显示两名有效成员并可双向发送。
* [ ] 观测关闭、健康接收和不可达三组均不改变业务结果，p95 增量符合 037 预算。
* [ ] 每次仓库提交最多打开一次当前整库状态；删除同事务写后整库回读。
* [ ] 每个必须保留的持久检查点都有终止与重启测试，结果与改造前一致。
* [ ] SQLite、文件、日志、trace 和导出中没有准入明文、设备标识、邀请、地址、路径或密钥。
* [ ] 并发提交保持现有冲突检测，不丢失已提交状态。
* [ ] 第三台旧成员在线与离线恢复两种测试都能收到更新并向新成员发送。
* [ ] Engine、Facade 和绑定没有新增准入步骤、状态对象、业务标识或步骤查询。
* [ ] 所有自动检查通过；未执行实体设备项目明确标为“跳过”。

# 10. Risks and Trade-offs

- 删除写后回读减少了同事务内的重复防御，但不会删除事务结果检查和下一次读取的 AEAD 完整性验证；这是用针对性故障测试替代重复整库工作。
- 逐记录密文减少无关重写，但增加表内实体和升级成本，因此只有前两片后仍有明确收益证据才实施。
- 连续推进减少调度等待，但必须有版本前进条件，防止无进展忙循环。
- 合并提交潜在收益最大，恢复风险也最高；任何跨网络、授权或外部效果的边界都不得合并。
- 只看端到端时间会受网络抖动影响，只看相减值又可能误扣本机工作；两者必须同时保留并使用重复样本。
- 把步骤上报给 Engine 容易测量，但会破坏分层并扩大长期接口；本规格只在能力 owner 内记录固定基础设施等待。
