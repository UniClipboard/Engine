## 2. 已确认事实与待补证据

### 已确认

- [运行期观察任务](../../../crates/uc-engine/src/runtime/mod.rs)按 100 ms 间隔调用完整会话切换检查，使用串行等待及 `MissedTickBehavior::Skip`。间隔不是实际每秒完成十次，也不能按十次并发读取估算流量。
- [会话负责人](../../../crates/uc-engine/src/runtime/session_supervisor.rs)经现有 facade 检查是否需要切换；[检查实现](../../../crates/uc-application/src/space/admission/protocol/joiner/activate_complete/execute.rs)调用激活状态读取，再只判断是否存在结果。
- [激活状态读取](../../../crates/uc-infra/src/space/admission/joiner/activation_state.rs)首先加载整个准入仓库，即使最终没有当前加入也会读取大包。一次检查很慢时，任务可能长期处于持续工作状态。
- 现场只读统计得到 10 条准入记录：9 条 Completed 很小，1 条 SponsorCommitted 占绝大部分。不能将本次问题归为已完成记录数量失控。
- 未完成记录明文编码为 7,157,622 bytes；其独立密文文本为 25,553,814 bytes；仓库整体密文文本为 91,295,926 bytes，约 87.1 MiB。两层数字数组文本表示是约 13 倍膨胀的来源，AEAD 本身不是这个膨胀量的原因。
- 大记录包括成员历史 684,503 bytes、安全状态 3,399,710 bytes、保留回复 3,073,238 bytes。保留这些数据参与恢复或重放，不能未经协议证明删除。
- [成员仓储](../../../crates/uc-application/src/space/membership/ledger/repository.rs)存在恢复并验证历史的路径；现场采样也观察到成员历史重建及校验。
- 旧桌面的三次设备组查询均返回成功，耗时约 4.1–4.4 秒。现场数据副本的仓库首次加载约 3.65 秒，现有复用修改后四次未变化读取合计约 79 ms，10 条记录仍可打开。后者是局部探针结果，不是完整桌面性能验收。

### 待补证据

- 在同一冻结构建、同一输入下，分开测量数据库取数、文本解析、解密、结构恢复、成员历史验证与等待时间；现有总耗时不能直接分摊给磁盘或密码运算。
- 统计检查的实际开始、完成与重活次数，关联状态变化、设备组查询和后台恢复，区分触发次数与执行次数。
- 补充中的 CPU 120%–189%、内存接近 789 MB、启动四分钟后仍持续忙碌属于另一轮现场观测，需按统一口径复测；CPU 100% 按一个逻辑核计。
- 已知 closed-mailbox 噪声与成员更新重试是并发现象，尚未证明各自占用比例。不能直接修改网络超时、重试或通信路径来归因。
- 未完成记录内部的重复材料是否都必要，仍需逐字段测量及恢复契约检查，不能预先承诺将 7 MB 压到 KB 级。

## 3. 责任与边界

| 完整行为 | 完整负责人 | 调用方唯一动作与结果 | 失败、取消和重启责任 |
| --- | --- | --- | --- |
| 推进需要完成的加入及会话切换 | Application 准入流程与现有 Engine 会话生命周期负责人各守原边界 | 消费不透明工作唤醒，调用现有完整切换动作；返回无需工作、完成或明确失败 | Application 保存恢复事实；Engine 负责会话停启与任务收尾；启动和恢复时补查持久状态 |
| 查询与提交加入状态 | Infra 准入仓储 | 调用既有业务读取或提交能力；返回一致的小状态、所需记录或原错误 | 数据、摘要及恢复材料在同一事务边界提交；失败不发布新状态，重启从唯一持久事实恢复 |
| 读取可信成员历史 | Application 成员仓储 | 取得完整、已验证的当前成员视图；不让调用方自己维护多个副本 | Infra 提供密文存储能力；成员仓储拥有验证与失效责任；新资料、密钥或验证上下文不能沿用旧结果 |
| 资料格式升级 | 既有资料升级流程，Infra 实现具体迁移 | 宿主沿用现有初始化/恢复动作；完成、可恢复中断或明确需要处理 | 使用密文、事务或现有升级检查点；失败后旧事实仍完整，重启可继续 |

- Core 保持规则和校验，Engine 不为观测或 benchmark 新增步骤查询、业务标识接口或内部状态对象。
- 新摘要、查找信息和记录默认敏感；不能把原始加入标识或其可关联派生值直接作为明文索引。实施前确定加密定位方式及威胁模型。
- 性能结果只含固定场景、计数、长度、时间和环境类别。实际用户内容、密钥、设备身份、路径、邀请及回复正文不得进入结果或 CI artifact。
- 每次只完成一个有回归证据的切片。完整重试策略不向宿主泄露，不因 P2P 失败切换 LAN。

## 4. 阶段 P0：建立 benchmark 套件与冻结基线

状态：部分完成。已交付可重复运行的准入仓储与成员更新积压基准和合成数据，并冻结本机优化构建下的规模曲线；完整 Engine 空闲资源套件仍待宿主接入和设备验收。

### 4.1 工具和目录

现有 Tokio、SQLite、密码实现及测试构造器继续复用。拟增加仅开发依赖的 Criterion.rs，实施时验证工具链兼容并锁定版本；使用其现有统计与比较能力，不自写微基准统计框架。

- Cargo 支持自定义 benchmark harness，默认 benchmark profile 启用优化；因此必须显式区分 benchmark 与现场开发构建：[Cargo benchmark 文档](https://doc.rust-lang.org/cargo/commands/cargo-bench.html)。
- 异步能力使用与生产一致的 Tokio；纯同步函数保持同步测量，避免混入不必要的异步开销：[Criterion 异步测量](https://bheisler.github.io/criterion.rs/book/user_guide/benchmarking_async.html)。
- 规模曲线和前后对比使用框架现有分组能力：[Criterion 输入与实现比较](https://bheisler.github.io/criterion.rs/book/user_guide/comparing_functions.html)。

拟定目录，均尚未创建：

| 位置 | 职责 |
| --- | --- |
| `crates/uc-infra/benches/` | 真实加密存储、按需读取、写入与格式升级性能 |
| `crates/uc-core/benches/` | 已有历史解码与规则校验算法的规模曲线；仅必要的纯规则场景 |

内部细分计数在所属模块的测试构建中完成，不为取数扩大稳定 API。性能套件不另建一套业务或密码实现。

### 4.2 场景矩阵

| 套件 | 代表场景 | 核心测量与正确性检查 |
| --- | --- | --- |
| `admission_codec` | 小记录、现场量级记录；旧格式与新格式 | 各层字节数、解析与加解密耗时；往返一致、损坏与错误密钥拒绝 |
| `admission_repository` | 无当前加入、待激活、单条恢复、状态提交；首次与连续读取 | 实际读取及解密字节数、解析次数、延迟、分配；返回与恢复事实一致 |
| `membership_history` | 首次验证、相同历史重复查询、追加事件、分叉、撤销、错误签名 | 验证次数、输入规模曲线、耗时；未验证输入不能因复用得到认可 |
| `runtime_idle` | 已稳定、旧成员离线、没有加入、存在不需本机激活的 Sponsor 记录 | 至少十分钟的 CPU 时间、内存、实际检查及大包读取次数；不存在空闲重活循环 |
| `runtime_wakeup` | 提交变化、连续变化、执行中再次变化、通知合并、暂停与恢复 | 不丢工作、不并发重复执行；失败重试有界，关闭后不再工作 |
| `admission_recovery` | 本机两端完整加入、取消、退出、未完成时重启 | 端到端时延与资源；完成结果和持久恢复正确 |
| `storage_upgrade` | 旧资料首次打开、升级中断、磁盘失败、重启继续 | 总升级成本单列；旧资料与未完成加入不丢失，不能重复执行完整迁移 |

输入覆盖记录数 0、1、10、100、1000，以及小、中、约 7 MB 单条材料；历史覆盖现场约 17 个事件与更大规模。按具体问题配对取样，不生成“1000 条乘以每条 7 MB”的全笛卡尔积。默认合成数据集上限拟为 256 MiB，超大压力集显式选择。

协议、历史、恢复场景必须使用可验证的合成数据，通过正确性预检后再计时；随机填充字节只可用于标明为纯编码/吞吐的场景。固定配方与可注入的随机种子；第三方随机源不能固定时，冻结合成 fixture 及校验和，不声称完全确定性。

真实现场资料只作为本机显式启用的只读输入，复制或读取期间不修改原资料；密钥只留内存，原始资料不进仓库、报告或 CI。默认一条命令应能只用合成数据无人值守完成。

### 4.3 公平比较与输出合同

- 基线至少包括 `428c86f5`（局部读取复用前）与 `d8f7df64`（当前局部改善），再与后续候选比较。记录完整 SHA、dirty 状态、工具链、依赖锁文件与构建配置；仅给版本号不算来源证明。
- 同机、同输入、同工具链及相同优化配置进行配对比较。标准优化构建与匹配桌面的开发构建各有独立结果，不把 debug→release 的改善算成修复效果。
- 跨版本复用同一测量配方；旧版本没有套件时，仅移植测量入口与必要测试适配，记录适配差异，不复制新实现到旧基线，也不长期保留两套生产实现。
- 首次读取定义为新的进程/仓储实例且应用缓存为空；这不等于操作系统磁盘缓存为空。操作系统缓存状态单独标注，不通过清理整机缓存制造结果。
- fixture 生成、数据库准备、计时预热与实际测量分开；首次读取、升级和完整启动场景必须包含各自承诺的全部工作，不能预先完成后藏到准备阶段。
- 微基准保存框架统计与置信区间。完整调用另外逐次计时计算 p50/p95；不能把微基准批次均值的分布当成用户请求的尾延迟。
- CPU 用进程累计 CPU 时间除以墙钟窗口，100% 为一个逻辑核。内存分别标明 RSS、平台 footprint 或采样峰值；仅周期采样时命名为 `sampled_peak_rss_bytes`，不得伪称精确峰值。
- 每个资源场景使用独立进程，区分启动峰值和稳定窗口；微基准和资源采样不互相干扰，不在编译、其他重负载或并发 benchmark 期间验收。
- 拟输出版本化 `manifest.json`、`results.json`、原始安全采样与对比报告，位于仓库 `target/performance/`；字段包括来源、profile、fixture 配方版本、场景、样本量、计数、统计、资源口径、通过/失败/跳过。
- 短套件用于每次变更的可运行性及确定性回归；完整时延、十分钟空闲与内存门禁在固定机器串行运行。共享 CI 主机先报告波动，不直接用脆弱的绝对时间判失败。
- 默认复用各 checkout 的现有 `target` 和共享编译缓存；确需隔离时使用独立外置可再生目录，不共享可变构建目录、不用 `/tmp` 构建。运行结束检查进程并回收临时构建和 fixture。

## 5. 阶段 P1：改为按变化触发工作

状态：已完成。加入方持久状态成功进入待切换阶段后发布不透明变化通知；Engine 启动补查一次，之后等待变化，暂时失败按一秒间隔重试，关闭时取消。原 100 ms 固定查询已删除。

1. 先建立持久状态提交成功后的唤醒来源；事务回滚不发布新工作，唤醒不携带业务标识或阶段供 Engine 编排。
2. 订阅后执行启动补查；明确处理订阅建立前后、检查中和完成前后发生变化的竞态。可合并唤醒，但必须再次处理检查期间出现的新变化。
3. 保留 resume、会话重建和进程重启后的持久补查；通知是唤醒线索，持久状态才是恢复依据。
4. 失败分类沿用原契约：暂时失败有界退避，锁定等待可用机会，损坏进入明确恢复结果，不得变成新的短周期忙等；取消和 shutdown 必须停止等待及重试。
5. 先让事件路径完整通过，再移除 100 ms 轮询；不将其永久保留为第二套调度，也不只把间隔调大。

完成标准：确定性时钟与竞态测试证明不会漏工作；无状态变化时不再反复加载大包；完整加入、取消和恢复仍通过。与 P0 基线比较触发次数、实际工作次数及空闲资源。

## 6. 阶段 P2：准入按需存储与紧凑密文

状态：已完成。小状态与各加入记录分别密文保存；当前加入查询只打开元数据和当前记录；旧整体密文首次认证读取后在单一事务内迁移。未变化记录不重新加密，保存后不再整批回读。

- 当前加入/待激活的小状态、单次加入记录和大恢复材料按访问需求组织；普通查询不扫描全部记录，不打开无关材料。
- 小状态与大材料的定位、版本和更改一起提交，不能形成独立更新的第二份业务真相。查询首次打开就应具有同样的小读取范围，不依赖预热缓存遮蔽整包读取。
- 密文直接以紧凑字节表示保存，复用已有 AEAD 与编码依赖，去掉数字文本的重复包装。新格式明确版本和认证上下文，未知或损坏格式明确拒绝。
- 先仅优化本地持久表示，不改变设备之间的消息、签名输入、摘要输入和精确回复重放规则。
- 旧数据接入必须先认证和校验，再原子发布新状态；通过既有升级 owner 实现可恢复升级，不能在频繁查询里反复尝试完整迁移。
- 对约 7 MB 材料逐字段测量。若提出合并或不再保存副本，必须证明重建来源、版本约束、重放字节一致与崩溃恢复；保留必要材料不是失败，未经证明删除材料不算优化。
- 最终按测量评估现有整包读取缓存：新结构若已不需要它，应移除；不让旧整包实现和新结构长期并存。

完成标准：冷的小查询与无关大记录规模脱钩；写入只处理实际变化范围；完成升级、损坏、事务失败和中断重启矩阵。总首次升级耗时单列，不混同升级后的首次查询。

## 7. 阶段 P3：成员历史的唯一验证结果

状态：已完成。Application 成员账本的全部读写在单一会话内复用最近一次已验证的完整视图；首次并发访问合并为一次读取，成员提交后立即替换。准入流程与成员维护共用最新版本，历史内容变化后重新验证，失败结果不进入复用。

- 多个调用方复用同一资料范围内、已经成功验证的结果。设备组完整查询和后台维护不再重复读取、解密和复制未变化的成员账本；写入以已验证的当前版本为起点，并在提交成功后替换共享视图。
- 复用范围同时考虑历史内容、资料/空间、当前密钥及验证/信任上下文。单个版本号、外部声明的摘要或“以前验证过”不能授权新的输入。
- 提交、外部写入、事务回滚、密钥变化、reset、suspend/resume 和重启的失效与释放责任明确；失败结果不伪装为成功，也不产生无界条目或永久持有旧资料。
- 并发请求不能同时重复验证同一份历史；验证期间出现新历史时，新请求不得收到被错误标为当前的旧结果。
- 新事件、分叉与损坏数据保留原有全部必要校验；只有证明现有算法支持时才讨论增量验证，不自行发明绕过签名或历史规则的捷径。

完成标准：稳定历史的重复查询不增加完整验证次数；任何影响可信性的变化都重新进入相应校验；跨资料、错误签名、回滚与并发更改测试均拒绝错误复用。对比冷验证、重复查询及规模曲线。

## 8. 兼容性与失败矩阵

| 场景 | 必须证明 |
| --- | --- |
| 新版本连接旧设备 | 本机存储改造不改变现有通信字节与验证规则；实际新旧版本配对、重试、结算与同步通过 |
| 已完成加入的旧资料升级 | 成员关系与可查询结果保持一致，没有以清理掩盖失败 |
| 未完成加入的旧资料升级 | 每个持久阶段都能继续或按原规则取消；保存回复的重放内容不变 |
| 升级过程中崩溃、磁盘满或写入失败 | 旧状态仍可恢复或新状态完整可继续，不存在半套新旧数据 |
| 密钥失效、权限拒绝、损坏 | 不返回旧缓存伪装成功；保留失败与原始来源 |
| 重复变化、暂停和关闭 | 不漏新工作，不恢复已经取消的任务，不泄露后台任务与无限增长内存 |

已确认范围（2026-09-13）：本机资料升级后不支持回退旧程序，不设计可逆迁移或新增降级门禁，不将降级验证列为本次验收或实施前置条件。该决定不影响旧设备互通要求，也不免除升级中断后的资料完整性与新版本重试恢复责任。

## 9. 阶段 P4：完整验收与收尾

状态：进行中。合成准入规模曲线、Application 全量单元测试、Infra 准入与资料升级测试、Engine 加入后重启传输与已有设备切换场景，以及仓库静态检查已完成。2026-09-13 的本机稳定运行复查又发现成员更新投递每 30 秒处理 21 项积压，每轮选择 8 项时对同一空间密钥材料和撤销阶段重复完整读取；单轮持续约 15～21 秒。当前修复把发送任务、等待原因和下次机会独立密文保存；失败只更新小记录，离线按上限退避，真实上线唤醒对应设备，明确拒绝停止发送并阻止同设备后序。原始安全材料变化时摘要自动失效，下一次按当前事实重建。进一步复查确认每次维护进度提交都会被当成设备分组变化通知桌面端，桌面端再读取完整成员账本；成员账本现由同一会话全部读写共享已验证结果，维护进度仍正常保存但不再发出设备分组刷新通知，真正的成员关系变化仍会通知。桌面端同时只响应相关通知、忽略已读取版本并合并并发刷新。整机复测、实体设备和混合版本验收仍待完成。全量 Engine 网络矩阵在本机出现无可用网络路由，自动连接场景超时；成员状态保持 Active/Usable，直接相关场景单线程复验通过，因此该环境失败不记为本次修复通过或回归。

### 不依赖机器速度的硬要求

- 稳定空闲窗口内，加入检查不持续读取/解密整份材料，成员历史不持续完整验证；其他必要周期工作不能借机重复这些重活。
- 小状态查询读取量不随无关记录的大材料线性增长；更新单条记录不重写所有大记录。
- 新旧版本混合、事务回滚、升级中断、错误签名、权限失效和重启恢复全部符合原契约。
- 资源保留有明确上限和释放时机；关闭后不再有本次任务存活。

### 数值目标草案，讨论及 P0 基线后冻结

| 指标 | 初步目标 | 限定 |
| --- | --- | --- |
| 现场量级的升级后首次小查询 | p95 不超过 100 ms | 固定参考机器；无应用预热；同时记录开发与优化构建 |
| 稳定空闲 CPU | 平均不超过单核的 5% | 十分钟窗口，分别测网络稳定与旧成员离线；不包含用户操作，另报启动峰值 |
| 空闲 CPU 相对原基线 | 至少下降 90% | 同机、同输入、同构建参数；不能只依据第一次采样 |
| 内存稳定性 | 后半窗口相对前半窗口无持续增长，采样中位数增量拟不超过 10 MiB | 启动峰值与稳定占用分开；总量上限在 P0 测出必要工作集后冻结 |
| 紧凑存储体积 | 消除数字数组文本造成的两层放大，报告各层比例 | 约 7 MB 是现有材料规模，不是已承诺的最终体积 |

上述数字不是已批准的产品承诺或已通过结论。P0 后只能依据噪声、必要工作和参考设备证据调整，并记录理由，不能为让结果变绿随意放宽。
