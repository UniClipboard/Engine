# 执行计划 043：升级前备份与软件版本回退

## 状态

- **状态**：实施中；已实现停写资料目录的加密归档切片，尚未接入生产升级及软件版本回退。

# 1. Overview

现有升级会先生成并验证新格式资料，再启用新资料；后续启动清理旧来源。它能处理部分升级中断，却没有提供“重新运行升级前的软件和数据”的产品闭环。

用户需要在升级不满意或出现故障后选择回退。成功必须同时满足两个条件：运行的是升级前的精确软件版本，读取的是与该版本匹配的升级前资料。仅恢复数据库、仅重新安装旧应用、或恢复后再次启动新版本，都不算完成。

本次修订替代原方案中“启动失败自动恢复旧资料”和“恢复后发起一次新版本启动”的约定。升级失败默认保留现场、备份和明确失败结果；软件版本回退由用户明确发起，随后由安装更新程序完成整个过程。

# 2. Goals

- 新版本首次修改用户资料之前，完成、验证并保留升级前备份。
- 备份与精确产品版本、内置 Engine 版本、平台、架构、安装渠道和资料格式绑定，不能把新版本号写成备份来源版本。
- 恢复后旧版本能直接读取自己的数据库、内容文件、设置、身份和解密材料，不需要理解新备份格式。
- 回退前保存当前软件与数据，升级后新增内容保持可找回；不承诺自动合并到旧版本。
- 用户一次确认触发完整回退，安装更新程序负责结果与中断续接；核心负责完整资料恢复。
- 原备份长期保留，不因启动次数、运行时间或正常退出自动删除；删除须由用户明确决定。
- 完成标准包含实际启动精确旧版本并读取代表性资料，不能只检查文件存在。
- 每个平台分别验证安装渠道是否允许保留数据回退；不支持或未验证的平台不得宣称可回退。

# 3. Non-Goals

- 不提供云备份、跨设备迁移、任意历史版本选择或自动合并新旧资料。
- 不因普通启动、网络或剪贴板服务失败自动退回旧版本。
- 不让旧版本读取新数据库，也不让新版本在回退完成后立即重新升级旧资料。
- 不绕过平台签名、安装渠道、权限或数据沙箱限制来安装旧版本。
- 不把旧备份中的成员关系当作当前网络授权证明，也不回退其他设备的状态。
- 不改动用户导出文件的既有格式来伪装它已经具备完整版本回退能力。
- 不在备份失败或空间不足时跳过备份继续升级。

# 5. Proposed Design

## Components

### 完整版本回退负责人

产品现有安装更新程序承担 `ProductVersionRollback` 完整职责，不新建平行更新器。用户唯一动作是确认回到备份对应版本。

它接收备份编号及用户确认，返回完整回退结果；负责安装与数据两个结果的协调、进程隔离、重启续接和防止自动升级循环。该职责必须位于应用主进程之外或可靠的平台安装机制中，不能随待替换的新应用一起退出。

核心只提供完整资料能力，不接收安装路径或执行安装包。产品仅提交版本绑定及不透明编号，不查询核心逐表步骤。

### 核心备份与恢复能力

由 Infra 的完整资料备份模块负责固定资料清单、加密、有界复制、验证、恢复与清理；现有 `ProfileStorageUpgrade` 消费同一备份结果后继续转换。稳定入口通过 `uc-engine` 提供。

手动导出和升级备份共用已验证的数据收集、加密与校验能力。先核对再提取共享代码：现有 secret 清单只列当前 profile KEK，不能直接视为身份、profile 稳定密钥和历史内容密钥的完整清单；现有数据库快照依赖已打开的 pool，不能据此声称在任何迁移写入之前已经备份。

备份负责人必须在版本相关的数据库迁移、目录改名、设置改写、密钥导入之前运行。首次支持该功能时，旧版本可能不认识新备份入口，因此须由保留的新版本恢复组件在维护模式处理原始旧资料；不得先正常启动再补拍快照。

### 两级恢复记录

核心加密记录只保存资料备份与恢复事实。产品加密记录保存安装产物与版本回退进度，并引用核心的不透明编号；不复制核心内部阶段。产品负责两个完成结果的协调，不能把两个文件替换宣称为一个跨系统原子操作。

回退期间必须排除所有可能写入资料的主应用、后台服务、扩展和其他实例。旧程序未必认识新锁，因此仅新增锁文件不足以证明隔离，平台负责人必须证明进程已停止且不会被自动拉起。

## Data Model

```text
UpgradeVersionPair
  source_product_version

  target_product_version
  target_engine_version
  platform / architecture / installation_channel
  source_artifact_digest
  target_artifact_digest

  rollback_id

  preserved_current_backup_id
  source_artifact_digest

         | VerifyingOldVersion | Completed | RecoveryRequired
```

版本来源必须是更新前受信任的安装记录及签名发布资料，不能用当前 Engine 的编译版本推测旧软件版本。来源不明时可保留数据，但不得显示为可一键回退。

备份采用内部随机编号命名，敏感清单、路径映射、身份和安全材料均加密。旧数据中的历史明文字段不能因“原样复制”获得新明文持久化豁免。大文件以有界缓冲处理，备份外层格式由维护组件解开后，还原旧版本原本认识的布局和保护方式。

完整清单必须覆盖或明确标记缺失：

- 数据库及其一致性状态；恢复结果需符合旧版 schema 和编码。
- 图片、附件、历史内容和受管文件。外部文件只保存引用时，应明确不能保证文件本体随回退恢复。
- 原 manifest、目录布局、设置、设备身份与当前资料指针。
- 旧版读取资料实际依赖的安全存储条目、keyslot 和历史内容材料。
- 产品自己拥有的用户设置，由产品负责人纳入同次停写范围。

备份加密密钥不能仅存在于自己加密的备份内；恢复工具和所需系统安全存储访问资格必须在卸载、程序替换后仍可用。不能把普通软件回退宣称为“系统钥匙串全部丢失也可恢复”。

旧版来源备份至少保留一份。下一次不同版本升级不得静默覆盖唯一尚未删除的恢复点；保留策略扩展前，应要求用户处理旧恢复点。回退前当前版本安全副本另存，不循环包含备份目录。

## API / Interface

以下为待实现的完整能力名称与语义，不代表现有公开接口：

```text
prepare_upgrade_backup(version_pair) -> VerifiedBackup | NotRequired
query_upgrade_backup() -> Available | Unavailable
restore_upgrade_backup(backup_id, rollback_id) -> DataRestored | AlreadyRestored | StateChanged
discard_upgrade_backup(backup_id, confirmation) -> Deleted | StateChanged
```

备份和恢复入口通过维护模式调用；普通启动不可把 `DataRestored` 当作启动成功或立即执行 `ensure_v3()`。旧程序不需要调用这些新入口。

产品完整动作：

```text
rollback_to_previous_version(backup_id, confirmation)
  -> Completed | RecoveryRequired | Unavailable | StateChanged
```

`DataRestored` 只证明资料已还原；`Completed` 必须证明精确旧程序启动并读取匹配资料。参数和结果只携带必要版本、稳定原因与不透明编号。内部错误保留原始原因，不对用户暴露路径或密钥。

恢复请求必须绑定当前资料状态及已验证安装产物；重复调用继续同一回退，状态变化时重新查询。删除操作拒绝正在使用的恢复点。

## Workflow

### 升级前准备

1. 更新器确认精确新旧版本、保留或准备可验证的旧版本产物与恢复组件，并检查该安装渠道的回退能力。
2. 停止所有资料写入；核心与产品分别完成自己负责资料的备份，形成同一版本对的完整结果。
3. 完整回读验证备份，确认旧版所需资料和安全材料可获得。失败则保留原版本与原资料，停止升级。
4. 安装新版本并执行既有资料升级。旧备份与程序产物继续保留，不因新版本启动成功而删除。
5. 新版本启动失败时报告原失败并提供符合条件的回退入口，不自动恢复资料。

### 用户确认回退

1. 展示将回到的精确版本、备份时间，以及“升级后新增内容会另存，不自动并入旧版”。
2. 验证旧版本产物、平台安装权限、恢复组件、全部备份和空间；任一前提缺失时不改写当前资料。
3. 停止全部应用和后台写入，并保存、验证当前软件与当前完整资料。
4. 持久记录 `Switching`，禁止任何版本普通启动。核心通过完整恢复动作还原旧资料，安装更新程序切换对应旧程序。
5. 两者均就绪后，记录 `OldPairInstalled`；仅允许已校验旧版本首次启动，新版本不得重新打开旧资料。
6. 实际核对旧版进程版本、历史读取、图片/附件打开和关闭重启；通过后才标记 `Completed`。
7. 更新器保存用户回退决定，不立即自动重装被回退的新版本；再次升级需明确新动作。

### 中断与失败

步骤 4 至 6 发生失败时保留旧备份和当前安全副本，由独立恢复组件继续同一事务。不能启动“新程序配旧数据”或“旧程序配新数据”。

若不能完成旧版安装，使用已保留的当前程序和当前资料恢复原配对；同样需验证后才允许运行。两条路径都无法完成时进入 `RecoveryRequired`，保留所有资料并给出可执行的安装/恢复说明，不伪造成功。

恢复旧成员记录不会回滚远端移除、成员变更和密钥演进。首次旧版启动必须先验证本地读取；能否继续联网需用该精确版本对实际验证，不通过时不能承诺同步可用，也不能以旧关系绕过当前授权。不得假设已发布旧版会识别新加的“暂停同步”标记。

# 6. Implementation Plan

## 当前实施记录（2026-09-12）

- **已实现的基础切片**：`crates/uc-infra/src/security/profile_backup_archive/` 提供 `ProfileBackupArchive`，只负责已停写的一个受管目录。采用已有 tar 与 XChaCha20-Poly1305 依赖，启用 RustCrypto STREAM；以 64 KiB 分块加密处理，包含加密的精确来源记录、文件路径和内容。来源复读与完整归档认证均通过后，才以不覆盖已有文件的方式发布归档。
- **恢复边界**：完整验证先于写出，只能还原到新建的隔离目录；不覆盖现用资料，不安装旧程序，不写回系统安全存储。调用方必须先停止全部写入者，本模块不声称能靠目录扫描证明所有进程已停写。
- **密钥与失败责任**：每份归档的独立保护密钥保存在系统安全存储；读取缺钥时拒绝，不生成替代密钥。失败可留下随机命名的加密 `.partial` 文件及保护密钥；它们不作为成功归档返回，未来完整维护流程负责清理。还原中断留下的隔离目录不是成功恢复点，重试必须另建目录。
- **与导出复用的实际程度**：复用已引入的归档和加密库；未改变 `.ucbundle` 格式及现有导出路径。没有直接复用仅列 KEK 的导出 secret 清单，也没有把单目录归档称为完整用户资料备份。
- **已执行的基础验证**：真实 SQLite 主文件及 WAL 原样备份、旧 schema 读取、附件与设置字节还原、当前新增记录不被覆盖，以及加密探针、缺钥、损坏、版本不匹配和流式分块边界测试。这里的旧数据库为测试创建，**不是已发布旧产品启动证明**。
- **仍未实现**：完整多目录及安全材料清单、来源可信验证、精确新旧版本绑定的升级触发、`uc-engine` 维护入口、当前完整副本保留、资料切换恢复记录、旧软件保留安装、用户入口、更新抑制与恢复出厂清理。生产升级和导出行为均未改变。
- **平台验证**：macOS 本地归档测试已执行；实际产品安装回退、Windows、Linux、iOS、Android、HarmonyOS 均跳过，不从归档测试推导版本回退可用。
- **本切片验证结果**：归档定向测试 14 项通过；Infra lib 全量测试在最后两项补测及密钥回读时机调整前为 859 通过、6 跳过，最终调整再次通过上述 14 项。现有资料升级测试 17 通过、1 跳过，跨进程升级恢复 1 通过、1 子进程入口跳过。`cargo metadata --locked --format-version 1`、`cargo check --workspace --all-targets --locked`、`cargo fmt --all -- --check`、Rust 风格、仓库架构及 `git diff --check` 均通过。workspace check 仅有原有 HarmonyOS 测试未使用导入警告；未运行完整 workspace 测试及实际产品回退。

## 后续实施顺序

1. **版本对与安装接入核对**：产品仓定位更新器、常驻进程、安装渠道和旧产物获取方式。输出平台矩阵、精确版本对及完整回退负责人；具体文件路径经核对补充。
2. **先完成最小闭环**：在一个可验证的桌面安装渠道，用真实旧版生成资料，执行备份、新版升级、确认回退、旧版启动读取。以此证明安装与数据协调，再扩平台。
3. **共享数据能力**：核对 `crates/uc-infra/src/config_migration/` 的快照、加密及清单；补齐旧版布局、全部必需安全资料、流式处理和原始错误。导出行为回归测试必须通过。
4. **升级前接线**：调整 `profile_storage_upgrade/`、`assembly/host.rs` 和 `assembly/wire/mod.rs`，在首次修改来源之前验证备份；避免普通启动产生重复备份。
5. **完整恢复能力**：实现资料停写、当前版本安全副本、耐久恢复、旧格式回读和明确删除。维护工具自身不依赖即将被替换的应用生命周期。
6. **产品完整回退**：安装更新器实现版本绑定、原子替换能力的组合、中断续接、旧版验证和更新抑制；通过 `uc-engine` 调用核心完整动作。
7. **平台接入**：按实际支持的渠道接桌面与移动薄绑定及产品入口。只提供绑定不能算完成旧版安装与启动验收。
8. **交付收口**：复跑升级、导出、恢复、跨进程异常矩阵及仓库门禁，回写架构事实和本计划证据。全部验收完成后才移入 completed。

| 场景 | 预期行为与实现边界 |
| --- | --- |
| 无用户资料 | 数据备份可明确为空；软件版本回退资格仍由更新器判断。 |
| 当前已经是 V3 | 不凭资料格式跳过产品升级备份；同版本普通重启不重复创建。 |
| 空间不足 | 未完成备份不算有效；原软件、原资料保持可用，不跳过备份。 |
| 备份时仍有写入 | 停写未得到证明就不能发布完整快照；单库一致性不等于整份资料一致性。 |
| 双实例或系统重新拉起后台 | 产品启动门禁和核心排他共同拒绝竞争；恢复期间任何普通启动均被阻止。 |
| 备份损坏或保护材料缺失 | 拒绝恢复且保留当前资料，不生成替代密钥掩盖缺失。 |
| 旧安装包缺失、签名或平台不匹配 | 不开始改写数据；显示无法回退原因。 |
| 网络不可用 | 已保存并验证旧安装包时可离线回退；需要下载却失败时不修改当前资料。 |
| 平台要求卸载才可降级 | 未证明卸载后数据、备份和安全材料可保留前，不提供可执行回退。 |
| 程序与数据切换间断电 | 独立恢复记录继续处理，禁止运行不匹配的软件与资料。 |
| 升级后产生新资料 | 先保存当前完整副本；不自动丢弃、合并或覆盖旧备份。 |
| 回退后又被自动升级 | 持久保留用户回退决定，重复启动不会再次触发被回退版本安装。 |
| 多次升级遇到已有恢复点 | 不覆盖唯一恢复点；保留策略未扩展时先要求处理已有备份。 |
| 旧系统已升级且旧来源删除 | 不补造升级前备份，不把当前资料伪装成旧版兼容资料。 |
| 设备关系已经变化 | 本地资料回退与网络资格分开验收；不得恢复远端已撤销的权限。 |
| 符号链接、特殊文件、路径越界 | 固定清单及路径校验拒绝，恢复不得写出受管根目录。 |
| 用户删除备份或恢复出厂 | 明确范围后清除备份及其关联安全副本；进行中的回退禁止删除依赖资料。 |

# 8. Testing Strategy

## Unit Test

- 版本对、安装包摘要、来源记录及资料格式不匹配时拒绝回退。
- 验证完整清单、缺失项、原始文件布局、加密保护、损坏拒绝和大文件有界内存。
- 重复请求继续同一事务；过期编号拒绝；正在使用的备份不能删除。
- 所有恢复错误保留来源；公开摘要不含内容、身份、路径和密钥。

## Integration Test

- **真实版本回退**：用精确旧产品生成文本、图片、附件及设置，升级到新版本，新增一条资料后回退；核实启动的旧版版本、旧资料读取、关闭重启与新增资料安全副本。
- **程序/数据一致**：在数据恢复、程序替换、旧版首次启动各边界强制终止独立进程，恢复后只允许匹配的一对运行。
- **失败补救**：旧包缺失、签名不匹配、安装权限失败、写满、钥匙串不可用时，分别验证未开始覆盖或能恢复原当前版本与资料。
- **运行隔离**：主程序、后台服务、扩展、另一实例和自动启动竞争，均不能在切换中写入资料。
- **跨设备变化**：升级后另一设备移除本机或推进安全状态，再回退；分别记录本地读取与同步资格，不以本地启动成功代替联网验收。
- **平台矩阵**：逐安装渠道执行桌面、iOS、Android、HarmonyOS 实际旧版本安装和读取；不能执行的记为跳过，不从核心测试推导产品可用。

## Regression Test

- 现有 profile storage upgrade、崩溃恢复、导出/导入和启动进度行为。
- 正常重启不重复备份、不全量扫描历史、不自动回退。
- 备份保留、用户明确删除、恢复出厂和失败现场保留。
- 备份及恢复临时文件的明文探针、错误来源、路径与文件边界检查。

# 9. Acceptance Criteria

* [ ] 新版首次改写资料前，完整备份已验证且绑定精确软件版本对。
* [ ] 旧版产物来源、签名/校验、平台和安装渠道均已验证。
* [ ] 用户一次确认能完成软件与数据共同回退。
* [ ] 原发布旧版实际启动，读取历史、图片、附件和设置，关闭重启仍可用。
* [ ] 旧版无需理解新备份格式；新版本不会把已恢复资料再次自动升级。
* [ ] 升级后新增内容和当前程序已另存，并验证失败补救可用。
* [ ] 切换任一阶段被中断都不会启动不匹配的软件与数据。
* [ ] 备份、安装或解密前提不满足时不覆盖当前资料。
* [ ] 备份不因启动成功或正常退出删除；唯一有效恢复点不会被后续升级静默覆盖。
* [ ] 本地读取与设备同步分别验收，不恢复已撤销的网络权限。
* [ ] 每个平台和安装渠道分别记录通过、不支持或跳过。
* [ ] 仓库规定检查及相关行为回归通过；产品安装回退证据独立保留。
* [ ] 文档记录最终实现事实；单独交付核心备份能力不称完整功能完成。

# 10. Risks and Trade-offs

- **安装与数据跨系统提交**：无法用一次 rename 同时完成，需要停写、耐久协调和失败补救。旧版本不能替换这个负责人。
- **旧包可获得性**：仅有版本号或下载链接不够；卸载重装、下架或渠道限制可能使回退不可执行。支持范围按验证的版本对与渠道提供。
- **磁盘与耗时**：旧备份、新旧程序、当前安全副本和升级 staging 都可能共存，不能承诺固定三倍上限。按实际清单估算并以真实写入结果把关。
- **敏感材料**：导出清单并非完整密钥清单；备份必须证明恢复所需材料可取，且不能破坏旧版系统安全存储访问权限。
- **恢复点滞后**：旧软件对应的是升级前资料，升级后新增内容另存不自动合并；产品须让用户知道影响。
- **旧联网状态**：本机恢复不能撤回其他设备的新事实，联网兼容和授权需要单独证明。
- **复用取舍**：共用经过验证的数据能力；保留用户主动导出与产品版本回退的不同负责人。直接调用旧导出入口不足以完成本需求。
- **同盘限制**：本功能防升级故障，不承担整盘损坏或设备丢失恢复。

# 11. Open Questions

用户需要“回退软件版本与对应资料”已经确定，不再把恢复目标作为待选项。实施前仍须用代码和实际环境补齐：

- 各产品安装更新程序的精确路径、现有停写/替换/恢复能力及完整负责人接入位置。
- 第一对实际支持的新旧产品版本、各平台签名安装渠道和旧包保留方式。
- 旧版能否在所需沙箱和安全存储权限下启动并读取资料；不能仅凭新版本恢复工具成功推断。
- 各版本安全材料完整清单，以及旧版启动前可执行的网络隔离与联网验收方式。
- 原用户资料隔离副本和真实平台验收环境；未取得前只记录合成样本证据。
