## 1. Overview

第七片已把真实 blob 下载、提供、有限恢复、取消及独立文件部分失败纳入 Application 完整负责人，
并保留有界非阻塞的旧进度通知。现有反向 `/transfer-progress/1` 仍只发送源条目 ID、字节数及粗粒度状态，
无法区分同一条目的不同接收设备、用户重试和自动重试轮次，也没有业务 ACK 或原任务核对。
Engine 自行维护临时发送侧投影，关闭时会将尚在等待的项标为取消；晚到进度还可能重建已结束项。

本片使发送端如实展示每台接收设备的当前任务及逐项结果。接收端实际保存成功才可通知完成；
通知丢失时显示结果未确认，通过本次运行内有限补发和用户触发的状态核对收敛。
通知失败不能阻塞真实下载、取消或本地结算，发送侧展示不能成为接收业务的第二状态权威。

## 2. Goals

- 新版之间按设备、逻辑结果项、用户尝试及自动轮次隔离；旧任务消息和旧登记不能覆盖新任务。
- 展示等待、传输、处理、正在重试、明确终态及结果未确认；字节接收完成不等于文件交付完成。
- 独立文件显示逐项结果与批次汇总，保留成功项；目录继续按完整目录单元交付和重试。
- 终态在进度接收方 Application 采用后 ACK，支持有界幂等补发，保持真实终态不可回退。
- 正常通知 5Hz 上限、10 秒状态通知、60 秒失联显示及 10 分钟／8 次补发按明确算法验证。
- 后台和挂起不重置期限，恢复后先检查；重启无既有持久依据时显示结果未确认。
- 用户再次发起前由完整负责人核对原任务，区分仍在运行、已有结果、无保留资料、旧版不支持及实际失败。
- 新旧进度收发都进入 Uni 受管连接边界；保持旧版文件互通、当前成员授权及原 blob 字节／ticket 兼容。
- Application 统一拥有进度业务，Engine 只组装与映射；Rust、UniFFI、N-API 同版本提供完整业务视图和动作。

## 3. Non-Goals

- 不新增发送端命令接收端强制下载或取消的远程控制，不替代已有发送、接收、取消和手动重试入口。
- 不承诺跨重启可靠补发、最终必达、断点续传或新共享下载优化；不默认持久化发送侧远端终态。
- 不修改 blob ALPN、ticket、BAO／文件字节、内容加密或 V3 envelope；阶段 0 如证明无法保持，先报告设计阻塞。
- 用户于2026-10-26批准兼容的剪贴板传输头扩展，以补足纯空目录没有blob引用时的源条目关联。新端通过`clipboard-applied/3`协商源身份能力，旧`/2`与`/1`沿用原头字节；同次握手提供受支持版本，不因超时、拒绝或损坏消息重发旧格式。新源身份来自原发送计划，不复用provider、内容摘要或观测字段。
- 不更改第七片下载并发、排队、恢复、输出、清理及提交 CAS 的权威和预算。
- 不承诺系统剪贴板写入成功、用户已打开文件或宿主 UI 已渲染；不新增具体产品布局。
- 不实现 Nearby、不重写 iroh 路径选择、不因 P2P 失败切 LAN；不以本片完成关闭整个 Issue #34。

## 5. Proposed Design

### 5.1 Components：唯一负责人和责任边界

新增 Application `transfer/progress` 作为完整进度业务模块。建议内部拆分 owner、model、projection、
delivery、query、ports、policy、tests；`mod.rs` 仅声明与必要导出，不把模块变成一个大文件。

| 组件 | 输入及输出 | 完整责任 |
| --- | --- | --- |
| 接收／重试原负责人 | 原完整接收动作→实际业务保存、失败或取消事实 | 保持 `ReceiveAction`／`ReceiveBatch`／提交 CAS 权威；产生通知资料，不等待网络 |
| Progress owner | 本地语义交接、认证后的远端消息、生命周期→完整业务视图／交换结果 | 任务登记、发送侧投影、幂等采用、ACK、有限补发、失联显示、原任务核对及资源回收 |
| Application 专属 exchange port | 已准入连接／有界领域请求→业务交换结果或保留来源的失败 | Infra 实现 framing／读写；不替 Application 决定重试、成员业务或是否完成 |
| Core 规则模型 | 已校验状态及输入→纯转换结果与效果义务 | 真实终态不可回退、旧轮次拒绝、逐项／目录汇总；不含网络、时钟读取、序列化或观测字段 |
| Engine／绑定 | 完整能力装配、完整查询与动作→稳定 DTO／错误 | 同版本映射；不解析消息、枚举仓储或编排核对与重传步骤 |

调用方继续只调用已有发送／接收／重试动作；显示通过完整快照查询获得。为观测不得新增阶段查询。
用户在结果未确认时再次发起，核对与后续准入由相应完整动作内部完成，不能要求宿主先查询内部状态再自行决定如何绕过围栏。

成功结果分别是本地实际终态、发送侧采用结果、核对业务结果；三者不可互相替代。
网络通知失败由 progress owner 在本片预算内重试，本地保存与清理失败继续由原接收 owner 修复；
重启只恢复原有接收资料规则，本片通知队列与 ACK 等待不恢复。

### 5.2 Data Model：关联、顺序及生命周期

定义不可拆分的任务身份，字段线上编码归协议模块：

| 字段 | 含义与约束 |
| --- | --- |
| session binding | 当前 Space／本机会话世代与认证对端绑定；旧会话不能授权新消息 |
| source entry | 文件最初发送端条目；与实际 blob provider 分开，不因 ticket 指向第三设备而改变进度目标 |
| receiver device | 从认证连接取得，不信任帧内自报身份 |
| logical item | 原始清单位置＋项类型；同文件名、同内容不得合并；目录为完整目录单元 |
| receive attempt | 接收 owner 已接受的用户尝试；手动重试产生新的 attempt，未选成功项保留原成果关联 |
| producer incarnation／revision | 接收运行实例及 owner 单调修订；用于登记、替换和快照顺序，不用随机 UUID 大小或跨设备时间排序 |
| round／sequence | 同一用户尝试内真实自动下载轮次和本轮通知序号；只有新轮次可按实际进度回落 |
| result revision | 不可变终态版本；ACK 精确绑定身份及该结果，冲突 ACK 不释放待补发项 |

`TransferProgressView` 包含设备、条目、逻辑项、当前 attempt／round、当前阶段、字节、总量、
已知实际终态和联系状态。联系状态与实际业务状态分开：失联只令展示为 `Unconfirmed`，不修改本地 attempt。
阶段为 Waiting／Transferring／Processing／Retrying；实际终态为 Completed／Failed／Cancelled。
失败仅含安全固定类别，不含底层正文、文件名或路径。

新尝试登记必须先取得当前接收 owner 的权威描述，再替换投影；不能根据“后收到的 UUID”判断新旧。
同一 producer 的 owner revision 单调；连接重建不重置它。新 producer 必须通过新的连接挑战完成当前状态确认，
旧连接、旧挑战和旧 producer 的已排队帧同时退休；乱序登记不能重新激活已淘汰的旧 producer。
阶段 0 必须以延迟旧登记、重连、重启及新旧 attempt 竞争证明此规则；失败时停止迁移，不能弱化为只检查普通进度帧。

运行期资料只保存必要身份、数值及固定分类，不保存额外内容副本。活动资料随原动作结束、会话关闭、
条目删除或有界缓存淘汰释放；终态补发保留至匹配 ACK、次数耗尽、保留到期或容量淘汰。
历史旧尝试无需永久保存；缺失只能返回无保留资料，不能返回伪造终态。

### 5.3 API / Interface：完整能力及协议消息

Application progress owner 的公开装配面应保持少量完整操作，具体 Rust 名称可随现有 facade 统一：

- `get_outbound_transfer_progress(entry_id, target_device?)`：读取完整、按设备分组的快照；事件丢失后可重新读取。
- `reconcile_outbound_transfer(entry_id, target_device, expected_attempt?)`：执行一次完整原任务核对；返回 Running、Settled、Superseded、NotRetained、Unsupported 或 Unreachable。
- 原发送／接收／重试入口内部复用上述核对负责人，不让宿主拼接业务步骤。核对只读取事实，不下发远程下载或取消。
- 生命周期复用既有暂停、恢复、离组、删除、关闭入口；内部封口、等待与资源回收由 owner 完成，不增加宿主步骤 API。

读取、授权、存储、传输和协议失败保留完整 source chain；Unreachable 仅限实际网络事实。
AccessDenied 是明确授权拒绝，NotRetained 仅限成功查询后确认缺失；本机锁定、存储错误、解析损坏均不可伪装为缺失或旧版。
Engine／绑定只给稳定分类、可重试标记与安全 DTO，错误来源由完整负责人观测装饰器分类。

新版协议采用 `uniclipboard/transfer-progress/2` 的受管双向交换，旧 `/1` 单向帧逐字节保留。
能力由实际 ALPN 协商确定；只有明确不支持新版时使用旧版，不因超时、损坏或授权失败静默降级。

新版至少包含以下消息语义。阶段 0 已完成[精确线上合同与向量](../../design-docs/transfer-progress-protocol.md)，
当前接收权威与登记已取得真实双端组合证据；完整生产业务接线仍需完成，证据边界见[阶段 0 记录](2026-10-24-transfer-progress-connectivity-feasibility.md)：

| 消息 | 契约 |
| --- | --- |
| Register／CurrentDescriptor | 绑定源条目、原始逻辑项、当前接收尝试、producer 与修订；携带当前挑战，旧登记不得推进新投影 |
| Update／Contact | 携带阶段、round、sequence、真实字节及当前联系证明；重复旧帧不续期，不凭 heartbeat 增加字节 |
| Terminal／TerminalAck | 逐项实际终态及精确结果版本；Application 采用后才 ACK，重复同结果重发 ACK，不重复产生结果变化 |
| Query／QueryResult | 当前授权下核对指定原任务；区分当前、已替换、已结算、未保留，不枚举任意数据库内容 |
| Rejected／Unsupported | 固定安全原因；不回传存储错误正文或目录资料 |

所有变长输入在分配前检查，使用分页或受限批次，不能一次接收无界清单。
起始技术上限为单消息 64KiB、单页最多 64 个结果项、单原始计划最多沿用 V3 的 1024 个引用；
分页须绑定同一 revision，重复／缺页不得算全部项目已确认。只有消息内容与当前会话一致才进入 owner。
正常进度无需每帧业务 ACK；终态、登记与状态核对可在原双向交换响应，FIN／settled 不等于应用采用。

### 5.4 接收事实、逐项结果与展示

接收端通知复用 `ReceiveAction`、`ReceiveBatch`、`ReceiveProgressQuery` 的真实交付规则。
网络字节接收完，尚在校验、解密、输出、提交或必要清理时显示 Processing；保存失败必须报告实际失败，
不能先发 Completed 再改 Failed。文件内容本体按已有例外处理，不能为了本片强改文件加密路径。
进度字节表示已校验的 blob 内容位置，不含传输帧开销。大型表示的原明文长度不能充当压缩加密后的总量；总量由实际校验回调或受保护内容给出，尚未知时保持未知，解密和保存后仍保留同一口径。准确本地缓存只按实际已校验内容计入，不模拟一次网络传输。

独立文件分别报告结果。批次保留等待／运行项计数；有失联未知项时显示“部分结果未确认”，并分列已知成功、失败、取消和未知。
只有所有结果明确后才汇总最终状态：全部成功为完成；含失败为失败或部分失败；无失败但有取消为取消或部分取消，
同时保留精确逐项计数。不能将未知算失败，也不能因最后一项成功宣布整批成功。
批次汇总从同一锁内的完整逐项快照计算。空或已退休范围返回无任务，不视为空批次成功；仍有等待／运行项时不提前归为最终失败或取消。全部结算后，失败优先于取消：全部失败为失败，仅部分项失败为部分失败（包括其他项取消）；无失败时，全部取消为取消，否则有取消为部分取消。联系中断只使未结算项计入未确认，已知终态及其计数保持。
目录的成员字节可累计，但完成取决于目录单元完整发布和原 attempt 结算；成员网络终态不独立宣告目录交付。

手动重试只更新选中逻辑项的新尝试，已成功项保持；未选失败项也保留原结果。
自动重试无法复用数据时按真实本轮百分比回落并显示 Retrying；实际可复用且已校验数据才计入。
此显示计数与第七片有效新增数据高水位分离，不改其总尝试次数、恢复时间、停滞时间或本地状态机的单调规则。

### 5.5 已确认时间、容量及精确补发算法

以下为用户已确认的默认合同，需实际验收，不能据此声称性能已通过：

| 项目 | 默认值／行为 |
| --- | --- |
| 正常中间进度 | 每任务最多 5Hz；终态不因节流延后 |
| 状态通知 | 活跃任务连续 10 秒无其他新通知时补当前状态；不伪造数据进展 |
| 发送侧失联显示 | 连续 60 秒无该任务有效新通知→结果未确认；匹配的新状态／真实终态仍可更新 |
| 终态最长保留 | 从实际终态产生时起 10 分钟，本次应用运行期间 |
| 终态发送次数 | 含首次最多 8 次，单项单尝试计数；相同结果不重复占保留容量 |
| 默认发送时刻 | 相对终态产生时刻：0、2、10、30、60、120、300、540 秒 |
| 单轮通知／ACK | 拨号、额度等待、发送与等待 ACK 合计最多 5 秒，不重叠 |
| 待确认终态容量 | 全局 256／每对端 64，按接收设备＋尝试＋结果项计数 |

补发算法：

1. 固定终态生成时刻 `t0` 与绝对过期时刻 `t0+600s`，保存不可变结果和尚未消费的计划时点。
2. 首轮具备发送资格时进入调度；已过期、次数耗尽、已 ACK、删除或会话退休则不再启动。
3. 同项最多一轮在途。前次仍执行时，第 2 秒等时点不会新开一轮；本次完成后合并所有已到期时点，只产生一次下一轮资格，不追补历史轮次。
4. 每实际启动一次计入 8 次上限，并将启动时刻之前所有已到期时点消费；没有启动的合并时点不额外消耗次数。
5. 网络恢复可提前消费最近的一个未到期时点产生一次资格；重复恢复机会合并，不能创造额外时点。提前发送最早也在前次实际启动后 2 秒且前次已结束，避免网络抖动立即耗尽全部机会；单项从不重叠。
6. 单轮截止为 `min(start+5s, t0+600s)`；成功发送但未获精确 ACK 仍属未确认。超时停止本交换，不关闭其他任务使用的连接。
7. 挂起恢复先检查过期，再将已过时点合并为至多一次资格；其后使用剩余未来时点，不延长保留时间或恢复总次数。

容量释放先清理已确认／过期项；每端满只淘汰该端最早生成的未确认结果，全局满淘汰全局最早项。
淘汰停止该结果补发，不改变真实本地事实、不阻塞新下载；10 分钟是上限，不保证每项保留满额或实际发送 8 次。
大批次超过每端 64 个结果时也适用，不能为保留终态而减少已允许的文件数量。

有效新通知指当前身份内 sequence／revision 前进且语义合法的状态或联系证明；重复、乱序、已退休身份、
仅有 ACK 或本机拨号活动不能刷新对端任务的 60 秒。真实终态不可因新 Contact 重开。
首次等待从原完整发送负责人接受该目标的本轮发送意图时建立；再次发送不能重置原任务的失联与补发预算。
只登记通知候选不代表对端已开始下载，60 秒到期仍只影响显示。

### 5.6 通知调度、受管流及资源策略

本节是实现起始技术策略，不是用户产品配额；阶段 0 冻结并验证，变更须记录证据且不得改变 §5.5 的行为合同。

- 用一个 Application 通知负责人替代旧 64 项邮箱的发送责任；同任务／结果项中间值仅保留最新，终态优先。
- 初始网络交换并发全局 4／每端 1，等待交换全局 64／每端 16；按对端轮转，不同端不共享一个阻塞发送循环。
- 中间待发记录全局 256／每端 64，独立于终态保留容量；满时合并或淘汰最早中间值，实际任务继续，不能丢掉其他任务身份再假称已完整通知。另保留最多256／64个当前任务的节流和已见状态，每任务最多原计划1024项；只回收已退休任务，不能因中间值淘汰重置5Hz资格或已见序号。
- 发送侧活动投影最多全局 256／每端 64 个尝试，每尝试最多 1024 逻辑项，序列化及临时分页缓冲另受消息上限约束。
  淘汰投影只令缺失部分未知，不取消实际下载；不能为每个序号、心跳、已完成页面保留无限历史。
  投影按原意图接受顺序淘汰，重复不续期；变化提示有界128条，丢失时重读完整快照。
  登记采用能力另受4／1本机准入限制，不排队，超额Busy；退休立即释放项状态，但已开始采用保留额度至实际返回。
- 快照／核对共享既有通知交换额度，重复同目标请求合并，不建立第二个无界查询队列；单次完整核对最多 5 秒，超限返回明确未核实结果，不返回任务失败。同一合并查询最多 16 个并发观察者，超额明确 Busy；各观察者保留自己的原期限，取消一个观察者不干扰其余观察者。此观察者上限是运行期有界策略，不是产品任务配额。
- 进度使用独立 manager／profile，每端每方向最多一条协议连接，空闲保留 30 秒、跨请求保留容量 16；活动租约真实结束前不按空闲淘汰。
- 新版使用受管双向流。旧 `/1` 补最小受管单向流租约，保留旧字节及取消只作用本交换的语义；不能长期保留原生连接池旁路。
- 单向和双向流都必须覆盖当前准入、活动许可、取消、读写期限、旧世代封口及关闭结算；不能仅将原生句柄包装为 trait 就记迁移完成。
- 网络响应等待可取消；已开始且不能安全中断的本机读取由原 owner 监督到实际结束，未结束占用继续计入额度，不能 5 秒后释放许可并生成隐形任务。

5Hz 是上限而不是吞吐保证；超载丢弃中间值或终态淘汰的后果通过结果未确认表达，不能影响文件实际结果。
为消息登记和查询新增的适配器须复用当前成员、身份目录和统一撤销登记；认证身份不等于业务访问权。

### 5.7 原任务核对、再次发起与持久化边界

核对仅允许当前 Space 成员对其关联的源条目／接收任务查询。源设备和 blob provider 不同时，
应向实际接收 owner 核对，不能把提供端下载事件当作接收成果。

| 核对结果 | 已有完整动作的行为 |
| --- | --- |
| 原任务仍运行 | 返回当前状态并继续原任务，不启动重复下载 |
| 原任务已有真实结果 | 采用结果；已有成功不自动重下，需要重新传输时由用户已有操作创建新尝试 |
| 已被新尝试替换 | 返回 Superseded 和可安全采用的当前关联，不将旧结果覆盖新任务 |
| 在线但资料未保留 | 原结果继续未知；用户可明确重新发起，提示可能产生重复文件 |
| 旧端不支持查询 | 保留旧版文件互通；说明版本无法核对及重复文件可能性，允许显式重新传输 |
| 对端离线或查询未完成 | 原结果未知，本次不启动重复下载；不把网络失败当作 NotRetained |
| 访问拒绝／读取失败／损坏 | 返回相应安全分类，不能借资料缺失分支绕过授权或存储错误 |

原 `ResendEntry` 增加 `confirm_new_transfer`，缺省的产品意图为核对已有任务；只有明确确认
才可在 Settled／NotRetained／Unsupported 后调用原重投递。Running、Superseded、离线和未完成
不能由该确认绕过。返回的 `reconciled` 按目标保留核对分类、可安全采用的完整当前视图、
是否请求新传输以及可能产生重复文件的提示；`accepted` 等原计数只统计实际投递，不能把继续运行
或读取已有成果计成新接受。Rust、UniFFI 与 N-API 同版本映射这些完整结果。
剪贴板头的 Delivered／Duplicate 不证明文件已保存；文件再次发送的默认目标不能因此跳过核对。
原本可内联的文字和小图继续原投递行为；可能经 blob 交付的大图同样先核对。

跨运行映射遗失时允许 NotRetained，不增加永久历史映射。重新发起仍经过接收端原活动／清理围栏和 expected_attempt CAS；
查询与重发之间的竞争在原接收 owner 最终准入处再次检查，不以查询快照直接授予新任务权限。
状态核对不会重置旧任务补发预算，不要求保存已不可用的原内容；原重试来源不足继续返回 Unavailable。

本片默认不新增 SQLite schema、持久字段或通知 outbox。发送侧缓存和终态补发资料均为运行期。
已存在持久化依据的明确结果可恢复；当前基线没有发送侧远端终态投影，不能将“曾收到 ACK”当作重启仍可恢复的证据。
没有依据的旧任务只显示结果未确认，不恢复持续传输动画，不伪造完成／失败／取消。
重启后的保守视图只使用已有条目及目标投递归属，不把消息 delivery 成功解释为文件交付；
若连旧任务归属也没有依据，则返回无任务资料，不虚构旧 attempt／逻辑项清单。
如果实现需要承诺发送侧已采用终态跨重启保留，须先单独明确完整加密格式、原子提交、升级和恢复责任，不得偷偷扩大本片。

### 5.8 Workflow、生命周期与观测

1. 原发送流程接受目标意图后登记等待视图；接收流程接受 attempt 后向进度 owner 交接原始逻辑计划和当前状态。
2. 新版完成当前任务登记；接收真实字节、排队和本地处理状态按原 owner 事实交接，通知独立调度。
3. 发送侧校验会话、设备、attempt、round、sequence 后采用快照；旧输入 no-op，不重新计时。
4. 原接收 owner 完成所需输出与持久结算后交接逐项终态；进度 owner 有界保留并发送。
5. 进度接收端 Application 原子采用同一终态后回复精确 ACK；事件推送失败不回滚事实，宿主可重新读取完整视图。
6. ACK 丢失时同一结果幂等重发／确认；失联显示和用户再次发起按 §5.5／§5.7 处理。

后台／系统挂起期间期限继续流逝，不要求执行网络任务；恢复首先检查原绝对经过时间。
实现须提供可注入的经过时间来源，证明其包含挂起时间；不能只用普通 wall clock 差值或未经核对的 Instant 宣称满足。
时钟跳变或无法确定挂起经过时间时保守进入结果未确认、停止无法证明仍有效的旧补发预算，不能重建完整期限。
这不改变原接收任务的实际结果或第七片下载计时合同。

离组／撤销／切 Space 后先封新通知和查询、退休关联，再停止本交换并监督真实本地工作结束；旧世代迟到回复不能复活任务。
删除历史条目清理发送侧临时投影；迟到通知不重建条目／卡片。对已删除／退休的终态仅返回固定拒绝或停止处理，
不能 ACK 成“已采用新结果”；对端仍受原补发上限约束。删除不新增远端取消含义，文件资源按原规则清理。
普通网络恢复和会话内部连接重建不重置次数／时间；真正进程重启不恢复通知队列。

观测遵循[业务记录组织标准](../../design-docs/observability.md#业务记录组织标准)：完整接收／手动重试使用原 owner 的实际结果，
用户状态核对可形成独立完整动作；自动 heartbeat、ACK、轮转、清理和补发轮次只作子工作或运行诊断，不能每次生成独立业务根。
ACK 不能延长已经结束的接收动作计时，后台补发不把本地成功改失败；关联由 owner 提供不透明上下文，Engine 不查询内部阶段。
日志只用类型化字段和固定词表，分类区分未核实、明确拒绝、资料未保留与实际失败；不输出原始 ID、源内容、票据、设备名、地址、文件名、路径或错误正文。

## 6. Implementation Plan

具体执行与证据登记见[配套计划](2026-10-24-transfer-progress-connectivity-plan.md)。依赖顺序如下：

| 步骤 | 修改位置 | 完整变更及风险 |
| --- | --- | --- |
| 0 | 既有 connectivity host、protocol vectors、原接收 fixture | 冻结基线；证明登记顺序、旧单向受管接缝、新版 ACK、挂起经过时间；失败保留设计阻塞；实机证据未闭合的实现PR不合入生产 |
| 1 | Core 规则、Application transfer/progress | 纯状态转换＋可控时钟预算＋专属 port；保持 receive 权威，防止出现第二重试循环 |
| 2 | uc-sync-protocol、Infra connectivity、Router | 新 `/2` 与旧 `/1` 双角色受管，固定字节、长度与降级；防止原生旁路和无界分配 |
| 3 | transfer/receive、blob 通知交接、progress owner | 最小真实接收→输出→通知→采用→ACK；随后逐项／目录／新尝试／轮次；不等网络结算本地结果 |
| 4 | Application facade、Engine contract、两套绑定 | 完整发送侧快照／核对与稳定事件；删除 Engine 业务投影及旧邮箱发送责任；防止宿主编排 |
| 5 | 删除／会话／运行生命周期与测试 harness | 补发、挂起、删除、重启、核对竞态、额度及旧新真实网络矩阵；不以 mock 代替传输证明 |
| 6 | 所属设计文档与 CI | 真实观测、全量回归、平台编译、当前候选检查；完成后回写稳定结论再归档 |

每一步先列可观察失败方式，用当前基线证明相关缺陷或新增行为缺失，再完成最小纵向切片；
既有行为基线已满足则记录证据，不为制造红测改变产品语义。

## 7. Edge Cases

| Scenario | Expected behavior | Implementation |
| --- | --- | --- |
| 空文件、纯文本无文件、未知总量 | 空文件经实际结算后完成；无文件不制造任务；未知总量不伪装 100% | 沿用原计划类型和真实大小，不以 total=0 推断完成 |
| 同内容、同名、多设备、多轮次 | 只更新精确关联，互不合并 | 原始逻辑项＋认证设备＋attempt／round／sequence |
| 新尝试后旧 Register／Terminal／ACK 到达 | 不覆盖、不续期、不释放新终态 | 当前描述确认、修订与精确 ACK 匹配 |
| 首帧丢失或广播落后 | 从发送意图计时，超时未知；快照可重读 | 完整 owner 持有投影，广播不是唯一事实源 |
| 字节已满但磁盘失败／慢保存／慢清理 | Processing 或具体失败，不提前 Completed；资源仍真实占用 | 复用原本地结算与失败分类 |
| 自动重试重下且旧高字节通知晚到 | 新轮次显示真实回落，旧轮次忽略，不刷新有效数据预算 | 展示计数与原 ReceiveTiming 分离 |
| ACK 丢失、伪造或结果冲突 | 同终态幂等确认，错误 ACK 无效，真实终态不可回退 | 身份／结果版本校验与纯规则拒绝 |
| 单端不读流／不回 ACK | 最多本轮截止；其他端仍推进，本地下载／取消不阻塞 | 独立额度、公平调度、只停止本交换 |
| 65 个同端终态、超过 256 全局终态 | 按容量淘汰，未知如实呈现，实际下载继续 | 独立保留缓存，不向接收流程施加通知背压 |
| 挂起跨过 60 秒／10 分钟、时钟变化 | 先未知／过期，不补齐历史轮次、不延期 | 可控经过时间＋恢复检查，平台证明分别登记 |
| 查询后原任务立即重试／删除 | 既有准入重新核验，不能重复启动或复活条目 | 原 owner CAS／活动及清理围栏 |
| 对端在线无记录与存储查询失败 | 前者 NotRetained，后者真实错误，不推断同一结果 | 专属结果分类并保留 source |
| 旧端不支持／新版畸形帧 | 明确不支持才兼容旧版；畸形不降级、不授予权限 | 实际 ALPN／协议验证、固定向量 |
| 三设备：消息源与提供端不同 | 进度归实际源条目／接收任务，provider 无权伪造接收结果 | 角色独立关联与当前成员校验 |

## 8. Testing Strategy

### Unit Test

使用可控时间和纯输入序列验证规则，测试可观察结果，不镜像内部实现。

- 输入当前／旧 attempt、round、sequence 及互相冲突的终态；操作乱序与重复采用；断言旧消息无效果、同终态幂等、新轮次真实回落。
- 输入终态 `t0`、计划时点和 5 秒等待；在 2 秒前次未结束、60 秒恢复、600 秒恰好到期等边界调度；断言不重叠、不追赶、次数不超过 8、绝对期限不变。
- 输入重复 Contact、有效新 Contact、失联与恢复；断言旧消息不续期、60 秒未知、实际终态不重开、heartbeat 不修改有效新增数据计时。
- 输入超额缓存与不同对端；断言先清已确认／过期、每端只淘汰自己、全局最早淘汰，下载事实不变。
- 输入部分成功／失败／取消／失联项及目录成员；断言精确汇总、成功继承、未知不当失败、目录不提前交付。

### Integration Test

- 真实双 Engine、SQLite／密钥保护与实际文件：完成输出后才通知 Completed，Application 采用后才 ACK；阻塞输出、存储和清理分别验证无提前完成。
- 故意丢终态／ACK、暂停读取及一端长时间阻塞：验证精确结果重发幂等、另一端前进、下载与取消原完成时间不被反向通知拖住。
- 三端实际源／provider 分离；同源同项两个接收设备、同项新旧尝试与自动轮次交错；断言实际文件读回、逐设备状态和旧登记围栏。
- 状态核对使用真实旧任务；覆盖运行、结算、替换、资料清理、重启、旧版、离线、授权拒绝与数据库错误，并核对实际下载次数不增加。
- 用第二测试 backend 验证租约／取消／业务不依赖原生类型；真实 Iroh 两种流、流停止隔离、连接复用和资源归还另行验证。
- 按正式过滤规则导出真实 OTLP 到 Collector／Jaeger，检查正常、部分失败、单项重试、取消、结果未确认和查询；列表／详情与实际业务结果一致，敏感哨兵扫描通过。

### Regression Test

- 冻结旧 `/1` 字节和本片开工前旧端；新新、两种旧锚点 × 新端两角色 × Direct／强制 Relay，精确读回文件；旧端不要求新 ACK／查询能力。
- 回归第七片全部独立取消、1GiB 流式资源、部分失败、单项重试、目录完整发布、当前授权、旧资料和重启清理，不改阈值／预算。
- 运行 workspace、成员全集、升级 smoke、前六片网络回归与根门禁，当前交付候选线上必需平台编译全部核对。

## 10. Risks and Trade-offs

- 进度新协议比旧定长帧多登记、序号及 ACK，换取可靠归属；保留旧协议仅承担互通，不能伪称旧端满足新隔离。
- 本片是有界尽力通知，超载／退出可丢失结果；完整状态核对及未知显示避免伪造结论。持久可靠送达需另行设计。
- 逐项终态容量小于最大批次，已确认允许淘汰；核对可补齐当前保留的真实事实，但不保证原始资料永久存在。
- 新版双向流复用现有租约较直接，旧版单向接缝仍需生命周期证明；不能以长期绕过 manager 降低迁移难度。
- 自动轮次真实回落与旧高水位冲突，需独立展示语义；直接改旧数据计时器会破坏第七片恢复预算。
- 系统挂起经过时间的平台能力与部分移动绑定尚未证明；无证据的平台必须单列阻塞／跳过，不能用逻辑时钟代替真实平台结论。
- 相比只搬 Engine 翻译器，本片包含协议演进、双角色投影、核对及稳定契约，必须按完整切片交付，不能只完成 trait 替换就结束。
