# 1. Overview

状态：研究与规格完成，待决策项见第 11 节；尚未实现。本文是实现规格与执行计划的唯一正文，不代表现有协议已具备这些能力。

研究基线：2026-09-13，`b8b96105` 加当前工作区。工作区正在修改准入恢复摘要、成员更新投递和性能路径；以下结论包含现场源码，实施前须重新核对，不能覆盖这些修改。

本次解决旧配对因网络中断长期占用加入入口的问题。用户确认的规则是：正式决定前可以直接替换；正式决定后无论能否恢复成功，都允许本机终止，并撤销该次配对造成的成员资格。加入方和邀请方分别保存到期时间，各自处理到期，不要求对方在线或通知。

这里的“到期”针对尚未完成的配对尝试，不是成功成员的永久租约；“清理”包含删除临时材料和撤销已提交成员两种动作。已发布的成员历史不能当作没有发生过，必须以新的撤销事实结束。旧方案中“决定后必须先恢复成功”“到期不能撤销”的约束被本规格取代。

研究发现三个不能隐藏的边界：

- 协议决定持久化、正式数据应用、双方最终确认不是同一时刻。将临时数据放到文件不能使两台设备的最后写入成为一个事务。
- 本机未收到提交消息，不代表邀请方没有提交。不能按本机阶段直接删除全部证据。
- 一端保存成功、最后回复丢失、另一端到期，仍可能发生。两端尚未完成时可以各自到期；已经成功的一端不再运行本次到期任务，之后需要收到可验证的放弃/撤销事实才能知道另一端放弃。不能承诺它在永远收不到任何消息时也自动知道。第 11 节列为实施前必须确认的语义边界。

# 2. Goals

- 新的有效加入意图持久化后，旧尝试不得因对方离线而占用当前加入槽位；旧后台任务不能激活旧空间覆盖新意图。
- 双方在进入正式决定前保存经认证、不可被重试延长的同一到期约定；各自检查本机到期，不依赖取消消息。
- 到期或用户取消后立即停止旧尝试的本机业务使用；已提交的成员通过精确指向该次加入的撤销处理，不能误删后来重新加入的同一设备。
- 每次中断后均能从密文持久记录确定继续、终止或补齐清理；不得先恢复配对成功才允许放弃。
- 临时协调记录与正式成员状态隔离；正式生效后保留正确的成员历史、安全材料和恢复证据。
- 保留用户剪贴板历史和资料解密能力；不以重置整个资料目录代替配对清理。
- 网络失败不阻止本机放弃；磁盘写失败、密钥不可用或状态损坏必须报告真实失败，不假报已经完成。

# 3. Non-Goals

- 不实现跨设备同步原子提交，不保证两端同时显示成功或取消。
- 不保证离线设备立刻收到撤销，不保证删除其已经获得的历史内容或旧密钥。
- 不把所有正常成员改成必须续期的短期成员，不新增中心仲裁服务。
- 不重写成员历史、空间代际切换或传输系统；不自动回退 LAN。
- 不修改产品仓、发布版本或移动界面；本次仅提交文档，后续实现另行执行。
- 不为了配对清理删除整个 userdata、MasterKey、历史密钥或普通资料库。

# 4. Current Architecture Context

以下路径相对仓库根目录。结论以对应源码为依据，不以旧时序图的阶段名代替证据。

Component: 加入与取消入口

Path: `crates/uc-application/src/space/admission/protocol/joiner/start_join/execute.rs`、`joiner/cancel_join/execute.rs`（后者同属 `protocol/`）。

Responsibility: 串行读取当前加入、验证新邀请、保存新意图；取消转换并持久化。

Relationship: 当前先调用旧状态的 `supersede`，再验证新邀请。Core 拒绝替换 Prepared；已提交取消返回 `TooLateCommitted`，Application 返回仍待处理。不是用户要求的本机终止。

Component: 准入状态规则

Path: `crates/uc-core/src/membership/space_admission/state/transition/`。

Responsibility: Joiner、Sponsor、CompletionHelper 的状态转换、消息次序及重放证据。

Relationship: Joiner 的 Active/PendingSettlement 不是双方结算完成；Sponsor 收到 CompleteAck 并保存 Settled 回复后才进入 Completed。Joiner 保存收到的 Settled 后才结束结算。

Component: 正式决定与正式应用

Path: `crates/uc-application/src/space/admission/protocol/sponsor/handle_prepared/execute.rs`、`crates/uc-infra/src/space/admission/sponsor/state.rs`、`sponsor/complete.rs`（后者同属 `space/admission/`）。

Responsibility: 先生成并保存已提交历史、安全材料与准确回复，再应用安全材料、成员投影和账本。

Relationship: `commit_prepared` 保存的是准入仓储内的决定材料，不等于已经写入活动 `membership_ledger_state`。随后 Sponsor activation 才应用正式数据。两者间必须有可恢复的补偿责任。

Component: 密文准入仓储

Path: `crates/uc-infra/src/space/admission/repository/{persisted.rs,codec.rs,recovery_index.rs}`、`joiner/activation_state.rs`（后者同属 `space/admission/`）。

Responsibility: 保存 profile 级协调状态、每次尝试的密文记录、邀请占用关系及恢复摘要。

Relationship: 当前 V3 已拆分小元数据与逐条记录；记录表是 `admission_repository_record`。现场恢复摘要仍在修改中。当前格式没有共同的尝试到期约定；ActivePendingSettlement 可清除 current 指针，因此只扫描 current 会漏掉未完成清理。

Component: 正式空间应用与切换

Path: `crates/uc-infra/src/security/v3_admission_space_transition.rs`、`space_control_generation/mod.rs`、`space_transition_activation/mod.rs`（后两者同属 `security/`）。

Responsibility: 构建目标空间控制数据，验证后提升活动清单，再切换连接池、会话和密钥绑定。

Relationship: 活动清单提升是本机切换边界；提升后不能直接把旧目录重新当作活动空间。源控制数据可能已被回收，普通资料代际仍保留。

Component: 成员撤销

Path: `crates/uc-application/src/space/membership/remove_space_member/use_case.rs`、`crates/uc-infra/src/db/repositories/space_security_store/`。

Responsibility: 校验当前历史和权限，提交 RemoveDevice、待执行安全效果与投递责任，再恢复效果。

Relationship: 现有公开入口按 device_id 查当前有效成员，且拒绝移除自己。不能直接用它完成旧尝试清理；必须复用完整撤销负责人，新增内部精确目标及授权契约，不能只删除关系表。

参考已有模式：SQLite 明确说明 WAL 下多个数据库不是一个整体原子事务；本设计因此使用持久意图、幂等应用和补偿，而不是把多处写入称为“最后一次原子写入”。见 [SQLite WAL](https://www.sqlite.org/wal.html)。MLS 将移除成员与更新后续组密钥结合，并把谁有权移除留给应用策略；本设计沿用这种职责分离，不以引用标准代替本仓的准入授权设计，也不替换现有安全协议。见 [RFC 9420，第 3 节](https://www.rfc-editor.org/rfc/rfc9420.html#section-3)。

# 5. Proposed Design

## Components

完整负责人仍为 `SpaceAdmissionProtocol`；Joiner、Sponsor、Recovery 是其私有分工，不新增一个平行的总调度器。

| 所有者 | 输入 | 输出及责任 |
| --- | --- | --- |
| Core 准入规则 | 当前记录、已验证消息、时间判断、终止原因 | 下一状态及必要效果；禁止终止记录重新激活 |
| Application 准入协议 | 新加入、取消、入站消息、恢复触发 | 完整本机结果；统一创建终止证据和清理责任 |
| Application 成员撤销负责人 | 精确成员实例、合法终止证据、已验证空间历史 | 撤销事实、本机安全应用结果和待投递责任 |
| Infra 准入仓储 | 条件更新、加密记录、到期索引 | 原子更新意图与旧记录；重启后返回待处理项 |
| Infra 空间切换负责人 | 意图代次、终止围栏、目标控制资料 | 激活或停止旧空间，保证旧任务不能覆盖新意图 |
| Engine | 既有完整能力与唤醒信号 | 装配和调度；不根据内部阶段编排清理 |

到期和撤销授权属于业务规则；原子写、密钥封装、计时器属于基础设施。重试退避只影响执行频率，不影响是否到期、是否撤销和是否允许替换；不得用“最近没有流量”等经验条件判断失败。

## Data Model

下列名称是拟议内部模型，不是现有 API。

| 数据 | 必需字段 | 生命周期及约束 |
| --- | --- | --- |
| AttemptDeadline | 协议版本、attempt_id、双方身份绑定、space_id、issued_at、expires_at、期限策略版本、认证证明 | 接受准备材料前双方保存；重试、换连接、Helper 接手均不续期 |
| LocalJoinIntent | profile_generation、递增 intent_generation、当前 attempt_id | profile 级；每次有效新意图原子替换 |
| AttemptRecord | 角色、记录版本、协议进度、终止结果、决定证据、成员实例、到期约定、清理责任 | 业务负载密文；区分“尚未知是否远端提交”和“可证未提交” |
| AttemptTermination | attempt_id、space_id、加入身份、成员实例或提交绑定、原因、终止者、签名证据 | 在释放旧材料前保存；先不知道成员实例时仍可按尝试绑定后续 Add |
| CleanupObligation | 操作标识、精确目标、决定/应用进度、必要封装材料、待投递证明 | 不占当前加入槽位；完成本机处理前不能按原配对到期时间删除 |
| ExpirySummary | 可恢复的下一唤醒摘要及记录定位标记 | 非事实来源；业务时间与关联信息仍加密，索引损坏可由记录重建 |

成员实例必须绑定 `space_id + admission_id + Add 事件身份`（采用现有成员模型的等价稳定标识）。device_id 只作校验，不是删除目标。旧空间的清理必须使用旧空间作用域和授权，不能借用新空间的签名身份。

状态用三个正交维度表达，避免把“用户已经结束”和“后台全部清理”混为一谈：

- 协议进度：准备中、正式决定已保存、正式效果应用中、等待结算、已结算。
- 本机结果：进行中、成功、已取消、已到期、已被新意图替换、成功后被合法撤销。
- 清理责任：无、确认远端决定、提交撤销、应用本机效果、投递待补齐、已完成。

终止原因首次落盘后不可被迟到 Complete/Settled 改回成功。成功记录停止自身尝试到期，但仍接受针对该次成员的合法放弃/撤销事实。重复消息返回已保存结果，不能延长期限。

### 存储选择与最终持久化清单

建议复用 userdata 内现有独立密文准入仓储，按记录保存每一步，不新增每个阶段一个普通文件的第二套事实来源。它满足“中间状态不污染正式成员表”的目的，也允许新意图和旧终止记录在同一事务保存。用户是否要求字面上的独立文件目录，见第 11 节；未经确认不把推荐当成已批准。

| 存储内容 | 准备阶段 | 正式应用阶段 | 成功后或终止后 |
| --- | --- | --- | --- |
| 准入元数据、`admission_repository_record`、恢复摘要 | 密文记录每次转换、准确回复、到期约定 | 保存决定、应用凭据、结算进度 | 成功压缩；终止保留最小防重放证据和未完清理 |
| `membership_ledger_state` | 不发布候选成员 | 保存有效 Add 历史及相关待执行效果 | 撤销追加 Remove，不删除原 Add 冒充从未发生 |
| `encrypted_relationship` | 不发布候选成员、信任及地址 | 从已验证材料应用对应投影 | 撤销精确成员及关联使用权限，不影响新实例 |
| `space_key_epoch_state` 与相关安全投递记录 | 临时材料只在隔离记录中 | 应用目标空间密钥状态及必要更新责任 | 撤销应用后续安全状态，投递可延迟 |
| `space_admission_credentials`、密钥封装/凭据材料 | 为本次准备且密文保存 | 安装正式空间凭据与所需密钥 | 仅清理失效尝试专有材料，保留历史读取所需材料 |
| 活动清单及空间控制代际 | 保持旧活动资料；可准备隔离目标 | 验证目标后提升清单并重新绑定 | 提升前丢弃未使用目标；提升后执行本机脱离，不能盲目回滚 |
| 普通剪贴板资料和历史文件 | 不迁移、不删除 | 保持原资料代际 | 取消和到期不得清空 |

“最后一步写表”具体定义为：双方分别在正式应用阶段写各自正式状态，而非等待一个可被双方同时知道的最终网络消息。双方最后回复用于结算；不宣称跨库、跨清单或跨设备原子。准备目录可包含尚未活动的目标数据库，但不得对外发布其候选成员。

## API / Interface

沿用公开加入/取消入口；在 Application 内部定义完整能力，不向 Engine 暴露阶段查询。

| 拟议能力 | 参数 | 结果及错误 |
| --- | --- | --- |
| replace_join_intent | 新邀请、预期意图代次 | 新意图已保存，或输入/存储/并发错误；不等待旧设备 |
| terminate_attempt | 精确尝试、取消/到期/替换原因、预期版本 | 本机已终止及剩余责任，或真实持久化错误；不返回“必须先配对成功” |
| recover_due_attempts | 有界批次、可信的本机时间观察 | 到期处理与下一次唤醒；包括所有角色和等待结算记录 |
| revoke_admission_member | 精确成员实例、终止证明、空间作用域 | 已撤销、已不存在、本机效果待补齐或保留 source 的失败 |
| detach_abandoned_activation | 意图代次、精确控制代际、终止凭据 | 未提升目标已清除，或提升后已停止旧空间使用；不清空普通资料 |

上述能力由现有完整负责人实现，不要求每项都成为新 trait。公开取消结果需要能表达“本机已结束，远端尚待补齐”；若现有稳定类型无法表达，先形成兼容性变更清单，不把 Pending 当作成功。

## Workflow

### A. 新加入与期限建立

1. 验证新输入的语法和本机必要条件；明显无效输入不得取消旧尝试。短码沿用 Ready→Started 持久化后只查询一次的防重放规则，不能为重试重新兑换同一码。
2. 为有效新意图生成独立 attempt_id。短码尚未解析/身份未认证时只有本机准备期限，尚无双方约定；不得据此撤销他人成员。
3. 在本机短临界区内条件写入新意图、旧尝试终止围栏及其清理责任，再释放锁。若必须先签署旧放弃证明，则签署失败不能宣称旧清理已经保存；可重试，不发起网络等待。
4. 旧任务每次持久化和活动清单提升前核对意图代次；旧回包只用于补齐旧清理，不可推进新加入。
5. 新双方认证后协商并保存共同 DeadlineContract。到期不能大于双方接受的策略上限；邀请兑换有效期与尝试期限是不同字段，不混用。
6. 每次外发确认都在对应转换落盘后；接收重复消息只重放已经保存的答复。

### B. 正式决定与完成

1. 邀请方决定前检查期限、记录版本和终止围栏，保存绑定该尝试的 Add 决定及准确回复。此后旧 Add 不能凭删文件回滚，但仍可通过 Remove 撤销。
2. 正式应用由完整负责人驱动，每个跨存储效果有稳定操作标识与完成凭据。重启后先检查终止/到期，再决定补齐成功路径还是终止路径。
3. 加入方提升活动清单前最后检查意图与期限，检查和提升必须受同一串行化边界约束，不能只在网络调用前检查一次。
4. Joiner 的成功终态为正式应用完成且 Settled 已验证并保存；Sponsor/Helper 的成功终态为正式应用完成且 CompleteAck 已验证、Settled 回复已保存。只有本机成功终态停止该记录到期任务。
5. 本机活动但未结算仍纳入到期扫描。不能根据 current 指针为空或界面已显示设备便回收清理证据。

### C. 到期、取消或替换

1. 本机在启动、恢复前台、接收旧消息、接受新意图以及到期调度时检查。运行时安排最近截止时间；暂停或进程关闭期间不声称定时器运行，恢复后的首次业务动作先处理已到期记录。
2. `now >= expires_at` 且本机尚未成功时，原子保存终止原因、围栏及清理责任。显式取消/替换不必等到期；本机结果不依赖远端回复。
3. 可证明未形成正式决定：清理临时业务材料与占用。保留邀请已消费/拒绝重放证据，不能把一次性邀请变回可重用。
4. 正式决定已知存在：按该 Add 创建撤销；必要时只补齐构造和应用撤销所需的内部材料，不发布成功、不恢复常规同步，也不要求旧设备在线。
5. 远端决定未知：保存已认证放弃证明和尝试围栏，本机仍结束。之后发现匹配 Add 时转成精确撤销；不得因本机停在 Prepared 就把所有证明删掉。
6. 加入方已经提升清单：先隔离该空间的业务使用，再由空间切换负责人完成本机脱离，保留普通资料。源控制代际已被删除时不能假造恢复旧空间成功。新意图可持久化；新空间正式激活须等待本机切换一致性恢复，不等待网络。
7. 旧清理作为独立持久责任重试；完成本机安全效果后不以远端未确认阻止新加入。密钥不可用等真实本机故障须单独报告，不能以无限“配对中”掩盖。

同空间重试与跨空间切换必须分开处理：同空间只停止本次新增成员实例的使用，保留不属于该次尝试的有效身份和关系；跨空间只撤销目标尝试的身份，不能顺便移除来源空间的其他设备。无法验证数据归属时报告状态不一致，不扩大删除范围。

### D. 撤销授权与消息接收

- 加入方只能签署放弃自身这一次尝试的证明，不能凭邀请或 device_id 任意撤销别人。
- Sponsor/Helper 创建正式 Remove 时仍须满足已有成员历史与签名权限。Helper 不能仅凭自报角色获得撤销权限；没有权限时保存并转交合法证明，不伪造账本写入。
- 新证明绑定协议版本、空间、双方认证身份、attempt_id 和对应 Add；授权与签名字节的完整规范须在实施步骤 1 固化，并加入篡改/跨尝试重放反例。
- 对未知 Add 可先保存拒绝继续的尝试记录，不能构造针对“该设备最新成员”的 Remove。匹配 Add 到达时，再由合法负责人在当前已验证历史上追加撤销。
- 本机成员身份已经停止后，普通成员消息通道可能不再放行。终止证明需走受限、独立认证的准入控制消息路径，只能提交该尝试的证明，不能借此获得数据访问。成功记录也必须接受合法证明。
- 并发撤销沿用成员历史冲突处理，不用最后写入覆盖历史。移除事实与本机密钥/权限效果分别持久化；安全效果未完成时禁止继续按旧成员发送业务内容。

### E. 时间、保留与兼容

期限是认证的绝对时间约定，但两端时钟不保证完全一致。进程内用单调时间限制剩余时长，持久化已观察的时间下界，重启不能因简单回拨重新获得完整期限；大幅前跳允许安全地提前结束，不能靠不断延期掩盖。跨关机且系统时钟任意回拨时，没有可信时间源就不能保证真实世界精确截止，必须公开该限制。偏差上限和期限数值见第 11 节。

大准备材料在完成清理后回收；最小终止证据、邀请消费证据和撤销历史不能跟着配对期限一起删除。未建立可验证的重放拒绝下界前，不按任意天数删除最小证据；容量耗尽应在接纳新尝试前明确失败，不能静默丢弃安全证据。

旧记录无共同到期约定时标记 LegacyNoDeadline，不伪造对方已同意的期限。可以实现本机显式放弃，但不能宣称旧设备会自行到期。新版本能力在占用邀请前协商，不支持则明确拒绝新语义；不得悄悄回到旧的长期阻塞流程。迁移只向前，保留旧邀请消费记录；迁移编号实施时重新分配，不能覆盖现场已有的 000002/000003。

# 7. Edge Cases

| Scenario | Expected behavior | Implementation |
| --- | --- | --- |
| 空记录、无当前加入 | 无副作用；仍查其他角色待到期项 | 摘要索引不等同 current 指针 |
| 新邀请格式错误 | 不取消有效旧尝试 | 本机输入校验先于意图替换 |
| Prepared 回包丢失，Sponsor 已提交 | 本机终止但保留撤销责任 | UnknownCommit 与签名放弃证明，不猜测未提交 |
| Sponsor 已成功，Settled 丢失 | Joiner 到期退出；Sponsor 接收合法放弃后撤销 | 明确允许短暂分歧，不无限增加 ACK |
| Complete 与到期同时到达 | 一个条件更新胜出，终止后不能成功 | 记录版本、意图代次、期限在同一决策边界核对 |
| 取消与清单提升并发 | 不得终止后再激活旧空间 | 共享切换串行化边界，提升后走脱离 |
| 同一设备重新加入后收到旧撤销 | 新成员不受影响 | 按 Add 实例和空间匹配 |
| Helper、Sponsor 同时处理 | 不双重扩大撤销范围，不覆盖分叉 | 幂等操作标识与现有历史冲突规则 |
| 磁盘满、密钥锁定、密文损坏 | 报告本机未能安全完成，保留可恢复资料 | 保留 source；不删除原记录或返回假成功 |
| 邀请方切换到其他空间 | 旧清理不能借新空间身份执行 | 旧作用域封装责任；授权不可用明确待处理 |
| App 关闭/手机挂起直到过期 | 再运行时先处理过期，不先继续激活 | 启动和恢复前台检查 |
| 时钟回拨/前跳/极端期限 | 不续期，不溢出；不接受超过策略上限 | 单调剩余时间、持久时间下界、checked 时间计算 |
| 大量无效消息/重复终止 | 不产生无限记录或延长有效期 | 认证后持久化、幂等定位、有界接纳与明确容量错误 |
| 旧记录没有期限、旧端不支持 | 不编造双端保证，不静默降级 | 前向迁移与能力协商 |
| 清理中掉电、重复重启 | 不复活成员、不丢普通资料 | 每个副作用有凭据，删除最后执行 |

# 8. Testing Strategy

## Unit Test

每项按“输入 → 操作 → 预期结果”执行，时间与失败点可注入。

- 全角色每个协议进度、截止前/等于/之后 → 成功消息与到期分别先执行 → 胜者确定，终止不可逆，成功仅停止自身到期。
- A/B 不同 attempt_id、同 device_id、不同 Add → 旧终止或 Remove 重放 → B 不受影响。
- 已绑定期限 → 重连、重启、Helper 接手 → expires_at 不增加。
- 已成功 Sponsor 与 Joiner 签名放弃 → 验证并接收 → 只撤销绑定 Add；错身份、错空间、篡改期限全部拒绝。
- 无本机 Add 的 Prepared → 终止再收到匹配决定 → 从未知提交清理转入精确撤销，不转为成功。
- 旧格式、空仓储、超大时间、溢出代次 → 迁移或条件转换 → 明确结果，无 panic、无默许过期。

## Integration Test

- 两个独立资料目录和时钟 → 完整配对、关闭并重开 → 双方结算成功，正式表与密钥/清单一致，推进时间不自动撤销成功成员。
- 在 Prepare、Prepared、Commit、Complete、CompleteAck、Settled 各消息前后分别断网 → 各自推进到期并重启 → 未完成端自行结束；已提交端产生精确撤销或保留明确责任，不等对方回复。
- Sponsor 保存决定后丢回复 → Joiner 新加入 B → A 的旧决定晚到 → B 不受覆盖，A 得到撤销，不显示 A 成功。
- Sponsor 保存成功后丢 Settled → Joiner 到期、断网 → Joiner 本机可新加入；恢复控制通道后 Sponsor 撤销 A。始终断网时不把 Sponsor 收敛标记为通过。
- 每个正式表写入、清单提升、会话重绑、终止落盘和材料删除处注入崩溃 → 重启 → 成功或终止方向一致，普通历史逐条可读。
- 邀请方离线/目标设备永久离线 → 另一本机有权限执行撤销 → 本机安全效果完成且新加入不等远端投递。
- 三端含 Helper、乱序 Add/Remove、历史分叉 → 合法清理与历史恢复 → 无越权、无错误目标、无盲目覆盖。
- 过期索引丢失或需要重建、大量无关大记录 → 启动恢复与空闲调度 → 恢复范围完整，正常轮询不反复解密全部记录。

## Regression Test

- 历史剪贴板、文件、多个空间历史密钥 → 取消跨空间加入并重启 → 原资料可读，无 FactoryReset 效果。
- 已消费的一次性邀请 → 清理旧尝试后再次兑换 → 仍被拒绝，不释放防重放证据。
- 原公开按设备移除与 SelfTarget 拒绝 → 原入口调用 → 既有用户行为保持；内部自我放弃不扩大公开权限。
- 当前空间仍有远端投递未确认 → 本机效果完成后发起邀请/加入 → 不被网络待确认长期占用，同时保留既有安全门禁。
- 新旧格式混合、升级中断 → 重新打开 → 向前恢复，无明文业务字段，无覆盖现场迁移。
- 最终执行仓库根 AGENTS 要求的 metadata、check、fmt、架构脚本及 diff 检查；实现阶段另跑相关 crate 测试及双端 host 测试。真实 macOS/iOS/Android 未执行项目明确标为跳过。

# 10. Risks and Trade-offs

- 本机优先终止换来暂时不一致；这是用户目标要求的取舍，不是“所有人已经同时撤销”。永久网络分区下不保证远端收敛。
- 正式决定后的撤销是新业务事实。可能需要补齐内部安全材料才能生成撤销，但不能恢复面向用户的成功状态或正常同步作为前提。
- 独立阶段文件并不消除断电、多存储写入和最终确认丢失问题；复用密文仓储减少一套恢复逻辑。若选择文件目录，必须额外设计文件原子替换、目录持久化、版本比较和跨文件恢复，不能只写 JSON。
- 成功后停止期限与完全不依赖任何远端消息的全局自动清理不能同时无条件成立；反例见第 1 节。替代方案是成员持续续期或引入仲裁者，均超出用户当前目标，不暗中采用。
- 时间回拨没有纯本机软件的绝对真实时间保证；过早到期伤害可用性，过晚到期延长占用。策略必须显式，不隐藏在重试经验值里。
- 最小终止证据保留会增加空间；未经安全证明的过早回收更危险。通过受限接纳和压缩控制，后续建立重放拒绝下界后才能回收，不能承诺固定时间全删。
- 跨空间脱离与密钥保留是最大实现风险；必须复用完整切换负责人并做崩溃矩阵，不能使用重置资料接口省略。
- 现有工作区并行性能修改会改变存储/投递入口，实施前对齐，防止把已完成拆分重新合并回大记录。

# 11. Open Questions

下列项是实施前决策门，不阻止当前交付规格，但不能由 Coding Agent 偷填默认值后发布。

1. **成功分歧边界**：是否确认“尚未完成的一端必须自行到期；已成功的一端收到合法放弃后撤销，永久断网时可能保留其本机看法”？这是当前推荐语义。若要求已成功端也必须在完全无消息情况下自行撤销，需重新定义成功或引入持续租约，不能靠再加一次确认解决。
2. **存储载体**：是否接受现有 userdata 独立密文准入仓储逐记录持久化，而不是每步独立文件？推荐前者；正式表隔离要求保持不变。
3. **期限策略**：尝试期限、本机未认证准备期限、允许时钟偏差、极端回拨处理分别取什么值？不沿用测试邀请的示例时长作为产品决定。重试不续期已确定。
4. **授权契约**：现有成员历史能否承载精确 Add 绑定与自我放弃证明；若不能，协议/历史新版本由哪些成员共同支持？推荐由合法在册成员把已验证自我放弃转换成普通 Remove，而非赋予任意外部设备写历史权限。签名规范、Helper 权限和跨空间保留能力需在步骤 1 完成安全评审。
5. **保留与容量**：最小防重放证据暂不按时间删的前提下，允许多少未完成尝试、证据体积和待投递责任？上限应拒绝新接纳而非丢失旧安全责任；需要产品规模输入与现有性能测量。
6. **旧端策略**：推荐新版到期语义要求双方支持，旧端明确提示升级；是否允许用户另行明确选择旧协议？本规格默认不提供静默兼容路径。
