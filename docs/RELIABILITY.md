# 可靠性

## 设计原则

- 正式业务事实与后续网络/安全效果分离；事实提交后不因暂时失败回滚。
- 需要跨重启继续的流程使用加密持久状态、幂等阶段和明确提交点。
- Runtime 只负责触发、合并、暂停、恢复和关闭，完整业务顺序归 Application 负责人。
- 后台任务必须可停止、失败可见；禁止丢弃 `JoinHandle` 的永久循环。
- 重试必须有界、公平且可取消，不能形成无限队列或让排序靠后的 peer 饥饿。
- 成员历史传播以加密 ledger 中逐 peer 的认证确认水位和欠账为准；易失 wake、网络发送成功与关系状态都不能推断完成。
- 持久 retry deadline 遇 wall clock 倒退必须重新到期；已完成入站传输的幂等 ACK 只作固定数量的有界保留。
- 数据损坏、缺钥和不兼容必须失败关闭，不以默认值、空结果或删除数据掩盖。

## 剪贴板启动核对

active register 只是未经确认的启动基线：重建快照与 OS 快照匹配时保留；不匹配、不可重建或 OS 读取/宿主文件导入失败时清除。
成功清除表示不再对当前剪贴板作声明，随后正常捕获负责新激活；核对不写 OS、不广播、不伪造时间戳。
加载或清除持久 register 失败仍阻断剪贴板 worker 启动；身份、密钥及其他启动门禁不因此降级。

宿主文件导入以单次快照为清理边界：任意 representation 失败清除该调用取得所有权的唯一目录，包括零字节与部分文件；
其他调用的成功目录及用户源文件不受影响。成功导入沿既有消费与启动缓存回收生命周期处理。
HostCapabilityError 保留宿主来源，启动失败映射前通过既有模块日志输出安全因果链；标准诊断可读取固定 I/O kind/OS code，
不输出原始错误正文或路径，稳定 EngineError/FFI 仍只返回错误码、分类与可重试标记。

实施与验收状态见[剪贴板启动恢复计划](exec-plans/active/2026-10-07-clipboard-startup-recovery.md)。

## 验证层次

1. Core：状态转换、幂等、乱序、终态和不变量。
2. Application：完整流程、稳定分类、提交边界和恢复责任。
3. Infra：真实 SQLite/文件/协议、损坏与异常路径。
4. Engine：组装、生命周期、双实例与稳定契约。
5. Host/设备：真实平台矩阵；未执行项记为“跳过”。
