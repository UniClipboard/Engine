# 成员历史的职责归属

## 分界

成员资格的唯一事实来源仍是 Core 的 `VersionedMembershipHistory`。Application 使用这些规则完成动作，
Infra 执行实际存储、密码和网络能力。文件拆分不增加另一份成员状态，也不要求调用方手动组合内部步骤。

| 问题 | 负责人 | 理由 |
| --- | --- | --- |
| 一个加入、移除、决定或回执是否合法，作者当时是否有资格 | Core | 与网络、数据库及用户界面无关的规则 |
| 已应用的分支、当前有效成员、待本机决定的移除 | Core | 从已验证历史推导，不能由在线状态或缓存授予资格 |
| 规范签名材料、完整历史证据与后缀证据的身份、连续性和完整性 | Core | 是成员证明本身的固定语义，不能由接收流程重新解释 |
| 什么时候核对某个对端、接收一份证据后怎样完成处理 | Application | 涉及触发、当前事实、旧决定、并发提交和结果 |
| 一次选择如何持久保存、何时重试、何时恢复及回复什么 | Application | 只有完整动作负责人知道成功与失败边界 |
| SQLite 事务、MasterKey AEAD、Iroh 通信、具体验签实现 | Infra | 外部能力的实现，不决定成员业务 |

这里的历史存档是规范成员证据：其字节参与历史摘要和签名恢复包验证，并不是 SQLite 行模型。
同样，证据页约束保护的是完整性、发送者资格和有界验证；Iroh 帧收发、连接、超时与数据库密文封装仍在 Infra。
这些规范字节保留一份定义，不能为了切目录在调用方复制编码规则。

## Core 内部地图

入口是 [`versioned_membership_history/mod.rs`](../../crates/uc-core/src/membership/versioned_membership_history/mod.rs)。
它只保存唯一历史状态、固定常量与精确导出，以下子模块都不公开。外部仍从 `uc_core::membership` 使用原有类型和方法。

| 内部文件 | 责任 |
| --- | --- |
| `credentials.rs` | 成员凭据、凭据身份与历史签名验证能力 |
| `records.rs` | 事件、决定和准入承诺的规范定义 |
| `admission.rs` | 准入证明、完成凭据和激活回执 |
| `history.rs` | 历史构造、身份和成员资格查询 |
| `branches.rs` | 分支、祖先和历史包含关系 |
| `decisions.rs` | 本机移除及接受、拒绝决定的规则 |
| `receiving.rs` | 接纳已验证记录、应用回执和历史合并规则 |
| `validation.rs` | 作者授权、操作验证与成员快照重建 |
| `archive.rs`、`signing.rs` | 规范历史存档和签名材料的唯一编码 |
| `exchange/` | 完整证据页、后缀页和完整性验证，内部再分模型、完整页、后缀页 |
| `outcome.rs` | 稳定领域结果和错误 |

`merge_remote_history` 和后缀验证保留在 Core：它们校验并转换给定资料，没有外部 IO，不安排重试，也不提交数据库。
Application 在候选历史上调用这些规则，验证成功后才通过账本条件提交；格式错误不能把半成品写成正式成员事实。

## Application 完整流程

[`ReconcileMembershipEvidenceUseCase`](../../crates/uc-application/src/space/membership/reconcile_history_evidence/use_case.rs)
完整负责一份已认证来源证据的处理：

1. 读取并验证本机当前事实及来件，确认来源与成员证明一致。
2. 调用 Core 规则判断已应用分支一致或存在可选择分歧。
3. 识别已有本机决定、能够精确对应的旧选择及已完成恢复，不按设备来源猜测旧决定。
4. 将关系、冲突与选择结果条件原子提交；并发变更使本次判断失效时拒绝提交，后续恢复负责重试。
5. 返回实际关系结果与同一快照产生的完整回复，调用方不再补查或拼装另一份回复摘要。

入站 `HandleMembershipHistoryMessageUseCase` 与主动 `SynchronizeMembershipHistoryUseCase` 都调用这个完整入口。
二者分别负责收到消息和主动网络交换的外部流程，不复制证据处理规则。

`MembershipLedger` 保留完整事实的读取、验证、scope 派生及条件原子提交；不再持有
`exchange_conflict_evidence`，也不决定旧选择如何衔接。只有完整 case 知道一次业务动作的处理顺序。

## 候选展示资料

Core 的 `MembershipConflictPolicy::explain` 从已验证历史提取原因类别、共同祖先后的关键新增/移除、
作者、目标及接受/拒绝事实，不生成文案、翻译键或语言设置。多步分歧只摘要关键变化，`details_complete`
为 false，产品不得将其描述成完整时间线。名字来自已验证的准入资料，不保证等于设备最近改名后的名称。

Application 在证据处理的同一条件提交中保存候选名单和原因，与冲突标识、两侧分支绑定。
这些资料是展示快照，不能授予成员资格；发送权限仍由当前成员范围判定。查询组合当前范围与候选资料，
给出预期同步范围、暂停、待确认、重新加入及本机结果。远端候选的同步范围全部先标为待确认，
不能展示为选择后立即同步。成员的 `active` 是该候选内的激活状态，不代表在线或当前可发送。
重新加入名单包含当前组中被该候选排除的设备，以及需要重新取得成员身份的本机；含义是这些设备
若希望加入所选组继续同步，需要重新加入，而不是选择动作会替它们自动发起加入。

Infra 沿用整份账本 AEAD 加密；V3 加入展示资料，显式读取 V1/V2 后升级。旧冲突没有远端资料时，
原因为 Unknown、名单不完整、影响为 None，不把未知编码为空组。后续通过验证的同一证据可补齐资料，
但不会重新打开已经完成的选择。畸形来件不得产生展示事实。

Engine 在既有设备组选择查询上输出名单、原因与影响，产品只转发并组织 i18n 文案：
原因类别选择完整句子，设备名称作为用户内容插值，不翻译、不拼接零散短语。
类别未知或详情不全时使用中性提示；不得猜测离线原因、时间先后或推荐更安全的一组。

## 重构保持不变的合同

- 公开类型和方法不变，不公开私有目录，不新增步骤查询。
- 规范存档、完整证据页和后缀页的确定性字节保持不变。
- 历史规则、签名验证和成员资格仍只有一份实现。
- 已提交选择和恢复继续向前；未知旧材料不被自动解释成用户选择。
- 业务负载仍默认密文，普通日志不增加身份、路径或原始业务标识。

验证入口是 Core 的 `canonical_history_formats_remain_byte_stable` 和完整历史规则测试、Application 证据与选择测试、
真实多 Engine 场景，以及仓库所有权检查。所有权检查同时拒绝流程回到 Core、证据处理回到账本和私有实现目录变成公开入口。
