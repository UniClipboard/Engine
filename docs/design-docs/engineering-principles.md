# 工程与模块设计原则

## 依赖与职责

固定依赖方向是 `uc-engine → uc-infra → uc-application → uc-core`。`uc-engine` 只负责组装、
生命周期和稳定契约；`uc-infra` 可以实现 Core 或 Application 定义的 port，但不能决定业务；
`uc-application` 负责完整流程；`uc-core` 只表达纯业务规则。

跨层功能开工前必须回答：

1. 谁对完整结果负责？
2. 调用方唯一需要执行什么？
3. 成功和失败分别返回什么稳定结果？
4. 重启恢复或重试由谁负责？

回答不清楚时，先设计模块边界，不进入实现。

## 防止复杂度外泄

- 不把判断、流程推进、通信、持久化、失败恢复、后台重试和启动接线同时暴露给调用方。
- 不为每个内部步骤建立一一对应的公共接口。
- 一个行为即使跨多个 crate，也必须能从唯一负责人入口与测试读懂。
- Runtime 只负责触发、并发、暂停、恢复和关闭，不掌握业务步骤。
- Facade 只表达完整意图和稳定结果，不读取仓储或处理协议阶段。
- Composition root 是唯一同时知道 port 与具体 adapter 的位置。

## Port 所有权

Port 归需要能力的层与业务模块所有，不按最终实现位置归类。Core 只有在领域代码直接消费能力时
才定义 port；use-case 专属能力放在相应 Application 业务模块附近。Port 描述业务意图或稳定能力，
不得泄露 SQL、Iroh、HTTP、平台 SDK 或调用方的步骤顺序。

## 构造与测试依赖

- 一个业务对象只保留一个完整构造入口；所有必需能力都必须由调用方明确提供。
- 不得为了减少测试改动而增加仅测试可见的便捷构造、隐式默认值或空实现。这些做法会让测试绕过生产对象图，并掩盖新增能力是否已经正确装配。
- 测试使用明确命名的 fake 或 recorder 提供必需能力；即使当前用例不关心该能力，也要在构造位置显式传入，使依赖变化成为可见的编译影响。
- 可选能力必须源于真实业务语义，并在类型和结果中明确表达；不能把“测试暂时不用”解释为生产依赖可选。

## 持久化格式演进

持久化版本表达已经形成兼容责任的资料格式，不表达开发切片、提交顺序或状态机步骤。代码提交本身
不是版本冻结边界。格式只有在进入受支持发布，或者被允许写入不可丢弃的真实资料后才冻结。

修改持久化格式时必须遵守以下规则：

1. 开工前盘点当前受支持格式，并在第一个落盘切片前写清本次功能最终需要保存的全部事实、恢复责任和旧资料升级路径。
2. 同一未发布功能分支默认只新增一个最终格式版本。后续切片补全同一目标格式，不得因前一切片已经提交而继续增加版本。
3. 开发中的中间布局不能成为长期兼容对象；测试只固定“现有受支持格式 → 最终目标格式”和最终格式自身的读写、损坏及中断恢复。
4. 新增第二个格式版本前，必须证明前一个格式已经越过冻结边界，并在同一份设计决定中写清采用范围、迁移方向、失败处理和删除条件。否则应修改尚未发布的目标格式。
5. 未定稿格式只能写入可丢弃的专用测试资料。需要使用真实资料验证时，必须先完成最终格式设计并备份；一旦允许写入，该格式即按已冻结处理，不能靠覆盖或删除资料回退。
6. 评审必须区分设备间协议版本、数据库结构版本和业务记录格式版本，不能用其中一种版本变化替代另一种兼容判断。

提交前逐项确认：

- 本次是否新增了持久化版本；若是，它是否为该功能分支唯一的新版本？
- 版本增加是由真实兼容边界触发，还是仅由切片、提交或内部状态增加触发？
- 旧资料能否安全向前读取或迁移，失败时是否保留原事实？
- 是否误把开发中间布局加入永久读取分支、迁移代码或兼容测试？

## 删除检查

评审模块时设想删除它：

- 若复杂度会散回多个调用方，说明模块确实隐藏了知识，应保留。
- 若删除后几乎没有变化，说明它只是转发层，应合并或重划职责。

文件数量不是问题；同一行为的知识散落才是问题。
