## 背景

`WorkspaceConvergence` 是成员加入、移除、重新加入、成员历史核对、用户决定、恢复和状态查询的唯一完整负责人。这个边界是正确的：产品端、绑定和 Engine 只能提交一次动作、读取完整结果或接收变化提醒，不能安排中间步骤。

但负责人主文件同时保存了对外入口、加入流程、加入完成后的恢复、成员历史收发与核对、移除决定、旧数据兼容和状态查询。随着成员准入和恢复规则增加，新的完整流程持续直接写入主文件。维护者因此必须在一个过长的文件中还原多项互相独立的工作，既难以判断修改归属，也容易把重试、恢复或业务判断复制到调用方或别的流程中。

问题不是负责人应被拆成多个对外服务，而是负责人内部缺少按完整工作划分的稳定边界。

## 决策

### 保持唯一完整负责人

`WorkspaceConvergence` 继续对成员收敛的完整结果负责。它是唯一可以协调成员状态、保存、网络往来、重试、恢复和变化通知的应用层负责人。

产品端、绑定、`uc-engine` 和其他上层调用方继续只使用既有动作、查询、结果和变化提醒。它们不得获得候选、确认、历史分页、重试、恢复或状态推进的逐步入口，也不得因内部拆分而承担调用顺序。

### 按完整工作划分内部归属

负责人内部按下表划分。相关工作必须先收口为领域子模块，再在领域内按需要拆分文件；不得把每项工作直接拆成一排同级文件。每项工作必须能从同一个领域位置读到其完整流程和对应测试。

| 内部工作 | 负责的完整结果 |
| --- | --- |
| 准入与完成恢复 | 从加入请求到 Active、Pending 或 Rejected；包括候选、提交、确认、取消、重复消息、断线和重启后的继续 |
| 成员历史核对 | 从已认证设备可达或收到历史消息，到一致、补齐、等待用户、分叉或稳定拒绝 |
| 移除与用户决定 | 从发起或收到移除，到接受、拒绝、关系限制、重复处理和重启后的继续 |
| 当前成员范围与状态查询 | 从已接受成员历史派生普通范围和完整状态结果，不把成员资料、地址或在线观察变成第二份授权依据 |
| 旧数据兼容与启动恢复 | 识别旧状态、保存唯一恢复结果并恢复未完成工作；证据不足时保持安全拒绝 |

主文件只保留负责人定义、依赖、稳定入口、少量共同状态操作，以及在不同内部工作之间确有必要的协调。它不得继续承载上述每项工作的长篇具体流程。稳定目录形状由 `docs/exec-plans/completed/024-workspace-convergence-internal-boundaries.md` 定义：加入、成员关系和状态投影各自形成领域子模块；连接维护也在自己的子模块内收口。

内部工作可以共享同一加密状态和受限的 crate 内方法，但不得通过公开逐步接口、复制状态判断、第二个后台负责人或调用方编排来协作。跨工作流程由 `WorkspaceConvergence` 协调；下层模块不自行决定产品结果。

### 整理时保持现有行为与安全边界

内部移动不改变加入、取消、移除、重新加入、成员历史核对、断线和重启恢复的公开结果。已移除设备不得重新取得普通成员资格；保留的历史资料继续只服务于过去事实验证和受限恢复。

所有业务资料仍按既有规则加密保存。整理不得新增明文保存、敏感日志、第二份成员状态或绕过当前成员范围的普通通信路径。失败、重复、乱序和中断必须继续保持现有的安全结束或从已保存位置继续的语义。

### 以完整工作验证，而非以文件行数验证

文件长度是发现问题的信号，不是本决策的验收标准。每次整理必须能指出：该内部工作由谁负责完整结果、调用方唯一需要做什么、成功和失败各返回什么，以及重启或重试由谁继续。

每项整理都必须保留或新增能定位到该工作的测试，至少覆盖成功、重复、中断恢复和稳定失败。不得为了拆文件只创建转发层、泛化工具层或新旧双路径。

## 不做的事

- 不改变成员关系、设备信任、空间加入或移除的产品规则。
- 不把 `WorkspaceConvergence` 拆成多个可由产品端依次调用的公开服务。
- 不将领域规则复制到 `uc-engine`、绑定、产品端或基础设施层。
- 不进行一次无边界的大规模重写，不以兼容转发层保留旧路径。
- 不因整理引入新的第三方依赖、配置开关或 LAN 回退路径。

## 考虑过的方案

### 保持所有流程留在主文件

这保留了唯一负责人的表面形式，却让每项修改都需要穿过无关流程。恢复、重试和状态判断会更容易被复制到其他位置，因此不采用。

### 为每个内部步骤提供公开接口

这会把候选、确认、网络收发和恢复顺序泄露给调用方。调用方一旦必须理解步骤，唯一负责人的价值就消失，因此不采用。

### 按技术名称抽出通用 helper 或 coordinator 目录

这会把同一完整工作再次分散到多个地方，使维护者需要按技术角色拼回业务流程，因此不采用。

### 一次性重写整个成员收敛模块

成员收敛涉及持久状态、重试和恢复。一次性重写难以隔离行为变化，也无法逐项验证，因此不采用。

## 后果

- 成员收敛继续只有一个对外负责人，调用方式和结果保持稳定。
- 内部文件会增加，但每个文件承载的知识更集中；文件数量本身不构成问题。
- 后续成员收敛改动必须先选择已有内部工作，或明确说明新增完整工作的边界和测试；不能默认继续追加到主文件。
- 架构总览必须持续说明唯一负责人和内部工作边界，避免把内部整理误解为多个负责人。

## 实施顺序

1. 先为每项已有完整工作标出当前入口、状态写入点、恢复入口和测试位置。
2. 一次只整理一项完整工作，并在同一变更中移动其测试和内部调用。
3. 每次整理后验证公开结果、重试和重启恢复不变，再开始下一项工作。
4. 删除旧位置和临时转发，不保留长期双路径。
