# ADR-027：成员状态由单一聚合与唯一写入者负责，待办和展示由状态派生

- **状态**：已采纳；待实施
- **日期**：2026-09-23
- **修订**：ADR-015 与 ADR-020 的内部实现结构、ADR-025 规定的 `MembershipLedger` 闭包提交方式、
  ADR-017 中准入正式提交交给成员事实的方式

- **相关文档**：`docs/exec-plans/active/049-single-owner-space-membership-rewrite.md`、

## 背景

2026-09-23 两台桌面 profile 配对成功后，一台移除另一台：移除方一直显示“对方设备已被移除”但设备
不消失，被移除方一直显示“正在更新空间设备状态”。诊断确认两侧各自卡在一条永远无法结束的收尾工作上：

- 移除方的移除通知送达后，只删除了待投递项，对端核对记录仍保留 `PendingRemovalDecision`；收尾窗口
  只处理“待投递项非空”的记录，这条记录因此永不清理，设备列表又把所有核对记录都列出。
- 被移除方接受移除后，把决定排给发起方投递；发起方的身份投影已经去掉该设备，入站连接在身份层即被
  拒绝，这项投递永远无法完成，且因发起方不是“已移除对端”而没有收尾窗口。设备更新汇总据此永远为
  “更新中”；同时本机不再是有效成员时，历史同步检查直接返回 `Corrupt`，把正常结局当作损坏。

这不是单点失误，而是当前结构使这类问题反复出现：

1. **一份大记录，多处任意改写。** `LoadedMembershipLedger` 聚合对端关系、效果日志、分页传输、冲突、
   恢复会话等十余项事实。Application 中 14 个文件读写 `peer_reconciliation`；Infra 的
   `crates/uc-infra/src/space/admission/sponsor/complete.rs` 直接重建整条记录并提交正式 AddDevice，
   `crates/uc-infra/src/security/space_control_generation/material.rs` 另行构造记录。同一规则在两层多处
   分别实现。
2. **对端阶段由字段组合表达。** 关系、待投递列表是否为空、窗口起点、确认位置和同步状态共同决定
   “这台对端处于什么阶段”。非法组合可以写入，没有统一的结束条件。
3. **后台待办与展示各自推导。** 维护按固定步骤链决定做什么，设备信任查询用另一套规则推导“更新中”，
   两者不一致时界面就会永久停留。
4. **身份与授权读取不同来源。** 入站身份解析读取成员投影表，授权读取账本；投影由维护清理步骤异步更新，
   两者之间存在时间差。
5. **持久格式与内存模型耦合。** Infra 直接序列化 Application 的 `LoadedMembershipLedger`，模型每次调整
   都成为格式变化，账本格式已到 V4。

## 决策

### 一条总规则

> **状态唯一 → 待办由状态计算 → 展示由状态与待办计算。**

一个 Space 的全部成员事实只存在于一个 Core 聚合中。后台需要执行的工作是该聚合的纯函数；
`QueryDeviceGroupChoices` 中的设备关系与设备更新阶段也由同一聚合纯函数给出。“界面显示更新中”
与“后台确实有待办”在结构上等价，不再依赖两套规则保持一致。

### Core：`SpaceMembership` 聚合

新增纯规则聚合，持有：

- 已验证签名成员历史（沿用 `VersionedMembershipHistory`，仍是资格唯一正向事实）；
- 本机身份与加入门禁；本机地位（加入中、有效、已移除）由门禁与历史共同得出，不另存；
- 每台对端一个显式状态 `PeerLink`；
- 未完成的成员效果：只保存尚未激活的效果及其类型化材料，激活后删除，不再保留永久效果日志；
- 历史同步轮转游标和统一 revision。

`PeerLink` 区分有效成员与正在离开两类。有效成员携带与本机的历史关系（未确认、一致、需升级、等待本机
决定、分叉、无效）、已确认位置、同步退避和待投递的本机决定；正在离开表示已被本机移除、仅剩一次移除
通知。每个状态只有一个结束条件；聚合在每次转换后规范化，不属于当前有效成员也不在离开中的对端记录
一律删除，非法组合无法持久。

以下资料不进入聚合，但与聚合保存在同一成员记录中，只能经 Owner 写入：历史分页暂存与完成回执（历史
交换协议的工作存储）、分叉记录与分支恢复会话（分叉恢复本次不重写）。组密钥更新欠账继续由独立存储
保存，作为观察输入参与待办与展示。

聚合按 [Core 设计规范](../layers/core.md#5-状态机)建模，只提供一个推进入口和两个只读计算：

- `apply(self, input, now_ms) -> Transition<Self, Outcome, Effect>`：所有改变成员事实的来源——准入正式
  提交、加入方激活、本机移除、收到历史、本机决定、待办执行结果、期限到期——都经此入口。效果按规范声明
  `BeforeCommit` 或 `AfterCommit`；重复、过期等正常情况用 outcome 表达；
- `outstanding_work(&self, now_ms)`：返回全部未完成的持久待办及各自最早执行时间，包括历史同步、
  移除通知与离开到期、决定投递、成员效果推进。执行器只取已到期项，并按最早时间安排下次唤醒。它是
  `AfterCommit` 效果在重启与重试时的唯一登记来源，不另存 outbox。组密钥投递与分支恢复仍由各自存储登记，
  由执行器一并调度；组密钥投递状态作为观察输入叠加到展示；
- `present(&self, security)`：对本机地位与每个 `PeerLink` 做穷尽匹配，得出公开设备关系、同步关系、
  可用范围和设备更新阶段；`security` 为组密钥投递的观察结果。

聚合通过 `snapshot()` / `restore()` 与持久层交换纯数据快照；`restore` 重新校验全部不变量。

### Application：唯一写入者与执行器

- `MembershipOwner` 是成员事实的**唯一写入者**：加载、`apply`、一次条件提交、在同一事务中维护成员读模型、
  发布内存快照、唤醒执行器、发出 `DeviceTrustChanged`。其他用例、查询、准入和 Infra 均不得改写成员记录。
- `MembershipWorker` 循环执行 `due_work`，调用传输与安全能力，把结果作为输入交回 Owner。它不掌握业务
  顺序。维护运行期只负责触发、并发、暂停与关闭。
- `PeerAccess` 从 Owner 发布的快照回答入站对端是有效成员、正在离开（仅允许接收精确通知）还是拒绝；
  公钥到设备的解析使用同一快照中的准入事实，不再读取异步投影表。
- 设备信任查询只调用 `present`，不再保留独立推导规则。
- 账本无法验证只在加载处判定一次，整个 Space 进入需要处理状态；删除固定步骤链与“某步 Corrupt 即中断
  后续步骤”的机制。

### 准入交接

`SpaceAdmissionProtocol` 与 Core `SpaceAdmissionAggregate` 保留。准入在唯一正式提交点调用 Owner，加入方
激活同样以一个 Owner 输入建立聚合。Infra 中构造或改写成员记录的代码全部上移到 Core 构造规则与 Owner。

成员记录与成员读模型位于 `control.sqlite`，由 Owner 在同一事务中提交；准入记录位于 profile 数据库，两者
不能共用一个事务，也不引入跨库事务。因此成员提交是准入转换声明的 `BeforeCommit` 效果：先由 Owner 提交
成员事实，成功后才保存准入终态。Owner 对同一准入事件的重复输入返回 `Duplicate` 且不改变状态；成员已提交
而准入记录未保存时，重启后准入恢复同一尝试并得到相同结果，不产生第二次成员加入。

### Infra 只提供能力

Infra 负责成员记录密文 DTO 的编解码、MLS 与签名原语、Iroh 传输和数据库事务，不再构造成员记录、决定
成员顺序或决定何时结束收尾。当前承担约二十个 port 的 `RuntimeSpaceAccessAdapter` 按能力拆分。

### 协议语义澄清

以下三项已由用户确认采纳：

1. **被移除方接受后不回复决定。** 本机接受以自身为目标的移除后进入已移除终态，不向任何设备排队
   决定投递；发起方此时已不认可本机身份，这条回复在结构上无法送达。ADR-020 第 5 步“向本机当前分支的
   有效设备发送接受决定”在本机已无当前分支时不适用。旧版本对端本来也会拒绝这条消息，互通不受影响。
2. **正在离开的对端以送达或到期结束。** 移除通知送达，或自移除提交起 5 分钟到期后，删除该对端状态，
   设备从移除方列表中消失。这与规格 021 中 `AwaitingRemovalAcknowledgement` 的定义一致：它不是本机
   需要作出的决定，也不阻塞设备更新完成。
3. **本机已移除是终态。** 该状态不产生待办，维护自然空闲；查询返回 `RemovedLocalDevice`，设备更新为完成。
   重新加入沿用现有邀请与 `JoinSpace`，公开动作列表保持现状。

### 分叉恢复

`recover_conflict` 的分支恢复与换组过程本次**不重写**。它作为 Owner 的一项待办与聚合中的分支恢复状态
接入：由 Owner 触发并接收结果，内部阶段、恢复包与 Infra 换组机制保持现状。后续简化另行决策。

### 持久化

- 新增唯一最终格式 `SpaceMembershipRecordV5`，由 Infra 独立 DTO 编码，不直接序列化 Core 或
  Application 类型。同一功能分支不得再新增第二个成员记录格式版本。
- 解锁时从 V1–V4 一次性迁移；迁移失败保留原资料并报告需要处理，不重建、不猜测。
- 映射规则：当前有效成员映射为有效成员并沿用确认位置；已移除且仍有待投递通知的对端映射为正在离开，
  以迁移时刻重新开始 5 分钟窗口；**已移除且没有待投递通知的残留记录直接删除**（已由用户确认）；
  效果日志只迁移尚未激活的效果；本机不在有效成员中时映射为已移除。
- 准入记录格式不变；成员表降级为 Owner 在同一事务中维护的读模型。

### 删除

切换完成时删除且不保留兼容路径：`MembershipLedger` 闭包式提交、四阶段效果执行器与效果日志、
`restricted_delivery.rs`、`anti_entropy.rs` 的收发拆分、作为维护步骤的投影清理、维护固定步骤链、
设备信任查询中的独立推导规则、Infra 中全部成员记录构造与改写代码、`PeerIdentityResolver` 对成员表的
依赖，以及逐项核实后仅剩遗留引用的 Core 成员模块。

## 不做的事

- 不改变 Engine 公开操作、结果类型、事件、错误码和绑定接口。
- 不改变准入消息、成员历史分页、受限投递和组密钥更新的设备间格式。
- 不改变签名历史、OpenMLS、MasterKey AEAD 与日志脱敏规则。
- 不重写准入状态机与分叉恢复内部阶段。
- 不引入新的公开诊断或观测接口；观测仍只装饰既有完整能力。

## 考虑过的方案

### 逐个修补收尾缺陷

可以修掉本次两个症状，但下一种未建模的字段组合仍会以“永远更新中”或“损坏”出现。结构性原因不变，
因此不采用。

### 保留大记录，只收紧写入入口

能减少写入者，但对端阶段仍由字段组合表达，待办与展示仍需两套推导，不能让编译器检查状态覆盖，
因此不采用。

### 简化产品语义（移除不需本机决定）

能进一步缩小状态，但会改变规格 021 的公开行为和 `ChooseDeviceGroup` 结果，超出“对外接口不变”的范围，
因此不采用。

## 后果

- 成员事实只有一个写入者，对端阶段只在一个枚举中表达；新增状态时编译器会指出所有未处理的展示与待办。
- 本次诊断的两个症状在新模型中无法构造；已卡住的现有设备在迁移后自动收敛。
- 需要一次性替换 Application 成员实现并上移 Infra 业务代码，改动面大；中间切片不得独立合入主分支。
- 旧资料迁移成为新的高风险点，必须以固定向量覆盖 V1–V4 到 V5 的映射。

## 验收

1. `crates/uc-engine/tests/public_contract.rs` 与宿主契约测试不修改即通过，绑定无需改动。
2. 全仓库只有 `MembershipOwner` 能提交成员记录；Infra 中不存在成员记录构造或改写。
3. `present` 对全部本机地位与对端状态穷尽匹配，无通配分支。
4. 性质测试：任意状态下，阻塞设备更新的未完成待办（含尚未到期的重试）非空，当且仅当成员部分的设备
   更新阶段为更新中或可重试失败；需要处理状态除外。移除通知不阻塞设备更新，不计入。
5. 多节点确定性场景覆盖配对、移除、被移除后延迟接受或拒绝、离线、重启与分叉，断言最终收敛：移除方
   不残留设备，被移除方进入已移除终态，任何一方不永久停留在更新中，资格从不在缺少签名事件时扩大。
6. 本次诊断场景作为固定回归：被移除方在移除方撤销身份之后才作出决定，双方仍在期限内收敛。
7. V1–V4 旧记录迁移到 V5 的固定向量全部通过，迁移失败不改写原资料。
