# ADR-019：工作空间收敛等待状态按设备精确公开

- **状态**：等待名单已实施；ADR-020 的上线核对、待用户决定和分叉关系待重新同步
- **日期**：2026-08-11
- **修订**：ADR-016 的对外收敛状态展示边界
- **被修订**：ADR-020 不再把等待名单解释为全局一致；名单只描述本机已知传播，待用户移除决定
  和分叉设备分别公开，不能由普通在线状态推断
- **相关文档**：`docs/design-docs/decisions/016-workspace-wide-convergence.md`、
  `docs/design-docs/decisions/020-membership-reconciliation-and-user-decisions.md`、
  `docs/design-docs/features/019-device-specific-convergence-waiting-status.md`、
  `docs/architecture/architecture-bible.md`

## 背景

ADR-016 已规定 `WorkspaceConvergence` 是工作空间收敛的唯一负责人，并且产品端不得根据在线状态推断
收敛是否完成。当前对外摘要只给出阶段和等待数量。产品端因此只能知道“有设备等待”，不能知道具体
是哪台设备。

把所有离线设备都标为等待会产生错误提示：离线设备未必阻塞当前资料更新；反之，当前阻塞的设备必须
由工作空间收敛状态确认，而不是由产品端的临时在线记录、设备列表或缓存猜测。顶部统一提示也不能帮助
用户找到需要重新上线的设备。

## 决策

### 由工作空间收敛负责人给出等待设备名单

`WorkspaceConvergence` 继续是唯一判断者。它在形成当前收敛摘要时，从已经保存的成员变化、当前有效
成员、当前确认结果、待交接记录和暂时不可达记录中推导等待设备名单；不新增第二份等待队列、缓存或
持久化字段。

名单只在 `workspace_completion` 为 `WaitingForOfflineMember` 时公开，并且每个设备必须同时满足：

- 是当前有效成员，而非已移除或历史成员；
- 尚未确认当前工作空间目标；
- 当前确实不可达，并且该不可达状态是当前剩余收敛条件；
- 不是本机当前成员实例。

名单按设备标识稳定排序，并去除重复项。`workspace_completion.waiting_member_count` 直接等于名单
长度；在任何其他工作空间完成阶段，名单必须为空且数量必须为零。下一项成员变化同时处于
`membership_transition=AwaitingCommit` 时，不能遮住这份提交后等待名单。

同一设备移除后重新加入会产生新的成员实例。推导只使用当前有效实例，因此旧实例的不可达、待交接或
确认记录不得出现在新实例的等待名单中。

### 查询与通知共用一份完整摘要

`QueryWorkspaceConvergence` 和 `WorkspaceConvergenceChanged` 必须使用同一份 Engine 摘要，在
`workspace_completion` 内包含 `waiting_member_device_ids` 及与其一致的等待数量。绑定、宿主和
产品侧投影只完整透传该摘要，不重新
计算名单，不按在线状态补充或删除设备。

产品端以设备条目的稳定设备标识匹配该名单，只在命中的设备条目上显示等待状态及说明。产品端不保留
自己的等待队列，也不在页面顶部显示笼统的“等待资料更新”状态。

### 公开边界与隐私

公开的仅是当前等待设备的稳定设备标识；它已属于当前成员设备列表可见的标识范围。摘要不得增加设备
名称、成员实例、地址、签名、密钥、资料内容或底层失败原文。用于推导名单的工作空间状态仍按既有规则
加密保存，且本决策不引入新的数据库字段或迁移。

## 不做的事

- 不让桌面、移动端或 Web 服务根据在线状态、设备列表或历史缓存推断等待对象。
- 不把“离线”直接等同于“阻塞当前资料更新”。
- 不新增产品端重试、轮询或待办队列；重试和恢复仍由工作空间收敛负责人管理。
- 不保留旧的仅数量结果作为客户端的兼容分支；所有支持该摘要的绑定和投影都必须同步携带名单。
- 不把设备版本、能力或升级需求伪装成等待状态；这些需要独立、权威的设备能力事实。

## 考虑过的方案

### 保持只返回等待数量

这不能让产品端定位目标设备，顶部提示仍然无法指导用户完成操作，因此不采用。

### 产品端标记所有离线设备

设备离线不等于它阻塞当前收敛。该方案会造成错误提示，并把领域判断分散到各产品端，因此不采用。

### 产品端保存自己的等待名单

产品端无法可靠处理成员移除、重新加入、确认、重启恢复和事件乱序。它会形成与收敛状态并行的第二份
事实，最终产生漂移，因此不采用。

### 在收敛摘要生成时推导名单

现有收敛状态已经保存判断所需的全部事实，且由唯一负责人维护。派生名单不增加持久化事实，查询和通知
天然可以复用同一结果，因此采用。

## 后果

用户可以直接在需要重新上线的设备条目上看到等待状态，非阻塞的离线设备不会被误标。成员移除、重新
加入、完成确认和阶段变化都会随下一份统一摘要自然更新，产品端无需补偿性逻辑。

代价是所有公开此摘要的绑定和宿主都必须增加同一字段并更新测试，产品仓的 HTTP 投影、实时事件和生成
客户端类型也必须随 Engine 新版本同步更新。旧版本产品不能以猜测方式补齐该信息；发布时必须明确升级
边界。

## 验收标准

1. 三台设备中仅 B 未完成且不可达时，摘要只列出 B，数量为 1；
2. B 与 C 都未完成且不可达时，摘要稳定列出 B、C，数量为 2；
3. B 重新可达并完成确认后立即从名单消失；全部完成后名单和数量均为零；
4. 仅有其他离线设备、但它们不阻塞当前收敛时，名单不包含它们；
5. 成员移除后，该成员不会继续出现在名单中；
6. 同一设备移除后重新加入，旧成员实例不会污染新实例的名单；
7. 非等待完成阶段始终返回空名单和零数量；
8. 下一项变化处于 `AwaitingCommit` 时，前一项提交后等待名单仍完整保留；
9. 查询结果与实时通知携带完全一致的名单和数量，绑定与产品侧投影不自行推导。
