# ADR-025：Application Space 成员关系一次性重写

- **状态**：已实施（application 范围）
- **日期**：2026-08-25
- **取代**：ADR-021 的渐进整理方式与规格 024 的实施顺序
- **保留**：ADR-020、ADR-022、ADR-023、ADR-024 已固定的业务和安全决定
- **相关文档**：`docs/exec-plans/completed/027-application-space-membership-one-shot-rewrite.md`、
  `docs/architecture/architecture-bible.md`

## 背景

ADR-021 选择保留 `WorkspaceConvergence` 总负责人，再按准入、成员关系、状态投影和连接维护逐项搬迁。
后续实践证明，这种方式让旧总对象、迁出的标准用例和散落在 facade、assembly、runtime 中的流程长期并存。
每次迁移都必须维护临时可见性、共享锁、转发入口和旧测试，当前中间结构已经不能清楚表达最终业务归属。

问题不在于文件多少，而在于成员真相、关系、网络收发、恢复和产品结果仍需要通过多个入口拼回完整流程。
继续渐进迁移只会把中间结构固化为新的长期结构。

## 决策

停止围绕旧总对象的渐进迁移。先以实际产品入口、签名成员历史、加密持久状态、网络协议、失败恢复和
Space 生命周期为证据，固定完整规格，再在一个不可拆分的切换中替换旧成员关系及所有散落实现。

实施必须满足：

1. V2 签名成员历史继续是当前成员资格的唯一正向事实。
2. 每个用户动作、查询、网络接收和后台维护各有一个完整用例入口。
3. `SpaceFacade` 是 application 唯一公开 Space 业务入口；内部用例、总对象和 runtime 不再公开。
4. 成员历史、加入记录、关系、传输、待处理效果和产品修订只通过一个 application 原子提交 port 更新。
5. 删除 application 内旧总对象、旧综合状态、旧 gossip 编排、旧 runtime、旧诊断入口和所有兼容转发。
6. Core、Infra、Engine、绑定、数据库和网络实现不在本次修改；已经固定的加入、移除、拒绝分叉、重启恢复和旧资料重建规则不变。
7. 中间开发步骤不得独立合入或发布；主分支只接受完整目标结构。

目标对象、接口、流程、删除清单和验收矩阵由规格 027 固定。

## 后果

- 变更只覆盖 application 的 Space、facade、内部消费者和测试；其他层另行接入。
- 不再为迁移方便保留别名、双写、回退或 feature 开关，未完成调用点会直接表现为编译或测试失败。
- 现有中间改动只能用于证明行为和依赖，不能直接合并为目标结构。
- 目标 application 接口可以暂时与 Core、Infra、Engine 或绑定不兼容；外层不兼容不能成为保留旧 application 结构的理由。
- 旧 profile 不迁移成员授权，继续按既有决定重建单设备 Space 并重新配对。
- 目标结构减少调用方需要理解的入口，并把持久化、重试、恢复和关闭集中在完整用例内部。

## 考虑过的方案

### 继续按 ADR-021 渐进搬迁

这可以缩小单次差异，但已经造成旧总对象、临时转发和新用例长期并存，无法稳定判断谁负责完整结果，因此不采用。

### 保留旧总对象，只把文件继续拆小

文件会变短，但组装、调用顺序、共享状态和恢复知识仍由总对象及调用方共同掌握，删除检查不成立，因此不采用。

### 新旧实现双写后切流

成员历史、决定和准入包含不可回滚的安全事实。双写会产生两个提交点和无法证明的一致性窗口，因此不采用。

### 删除旧业务规则并从当前代码重新设计

当前代码和既有规格已经包含多设备、离线、重放、跨 Space 和恢复行为。忽略这些事实会引入产品和安全回归，
因此只替换内部归属与提交结构，不重新发明业务规则。
