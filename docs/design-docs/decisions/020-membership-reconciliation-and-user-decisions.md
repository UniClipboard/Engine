## 1. Overview

### 问题

UniClipboard 的个人设备会休眠、关机、断网或永久丢失。设备重新上线时，简单发送“我在线了”不能
说明双方是否仍认知同一个 Space。A 可能在 C 离线期间移除 B；C 上线时仍认为 A、B、C 都是成员。
如果 A 直接覆盖 C 的名单，用户失去决定权；如果 C 的旧状态覆盖 A，又会撤销 A 的本机安全决定。

前两版 ADR-020 分别选择了“多数设备决定唯一历史”和“允许分支，但发现后停止整个旧 Space”。用户
最终选择更符合个人设备的规则：上线先交换各自认知的成员历史；普通增加和已接受历史可以自动补齐；
接收设备从未亲自接受的移除必须等待本机用户决定。接受后双方可以在原 Space 恢复一致；拒绝后双方
保持不同分支并停止彼此分享，但各自分支仍可继续使用。

### 核心决定

成员关系围绕签名事件历史，而不是一张可被网络消息直接覆盖的当前成员表。设备上线时通过统一核对
流程回答：对方是谁、对方认知的历史位置是什么、哪些事件导致当前状态。网络只传播可验证事实，
不替用户接受破坏性变化。

拒绝一项移除只表示“我不接受这段成员历史”，不会自动移除该操作的发起者。`DIVERGED` 与
`REMOVED` 是不同事实；`OFFLINE` 又是独立的可达性观察，三者不能放进一个互斥状态字段。

### 明确接受的风险

已经在另一分支被移除、但尚未收到或接受该事实的设备，仍可在自己的分支邀请设备并分享该分支
已经掌握的内容。以后拒绝、移除或切换 Space 都不能收回已经披露的内容。

签名只能证明操作由哪个当时有效的成员发出，不能证明所有离线设备都认可该操作。该保密性代价是
本决策为了离线可用和用户最终决定权而明确接受的结果。

## 2. Goals

- 每次已认证设备连接建立后，自动启动一次完整的成员历史核对，不依赖产品端轮询或编排。
- 上线问候只携带有界摘要；发现差异后按需请求签名事件，不默认发送完整成员名单或全部历史。
- 相同历史、对方缺少历史、本机缺少普通增加、本机等待移除决定、历史分叉和无效资料得到不同结果。
- 新增设备事件在历史连续且验证通过时自动应用；未由本机接受的移除事件绝不自动生效。
- 用户接受移除时应用收到的同一事件，不重复创建第二条移除；双方可在原 Space 恢复一致。
- 用户拒绝移除时保存签名决定，并把相关设备关系标记为分叉；不自动移除发起者或其他设备。
- 分叉设备之间停止普通内容和成员历史传播；每个分支内部继续加入、移除和内容同步。
- 可达性、当前分支成员资格和双方历史关系分别保存、查询和展示。
- `WorkspaceConvergence` 完整负责核对、补齐、用户决定、分叉隔离、重启恢复和统一结果。
- 删除 OpenRaft、多数确认、最后到达覆盖、自动接受移除和冲突后全 Space 停止。
- 版本低于 `1.1` 的设备与本次 `1.1` 设备共存时，保留已有 Space、成员资料和可发现性，但暂停双方
  普通内容同步，并由 `1.1` 设备提示对端需要升级后才能继续同步。

## 3. Non-Goals

- 不保证所有设备拥有唯一成员历史，也不保证离线设备立即知道其他分支。
- 不让发送方单方面要求接收方接受移除，也不让网络消息直接改写接收方成员表。
- 不要求用户确认普通新增事件；只有本机尚未接受的移除属于破坏性决定。
- 不把拒绝移除解释为自动移除操作发起者。
- 不把分叉解释为整个 Space 不可用；只隔离已经确认分叉的设备关系。
- 不自动合并分叉，不按时间、版本号、成员数量、在线数量或消息到达顺序选择赢家。
- 不用成员核对消息传输剪贴板内容、文件、完整密钥目录或无界成员历史。
- 不引入服务器、固定主设备、恢复管理员、投票或多数确认。
- 不在本 ADR 中定义产品页面的最终视觉设计，只定义必须表达的事实和动作。

## 4. Current Architecture Context

```text
Component: WorkspaceConvergence
Path: crates/uc-application/src/space/convergence/
Responsibility: 成员加入、移除、重新加入、交接、恢复、查询和通知的唯一流程负责人。
Relationship: 调用 uc-core 规则和 uc-infra 能力，由 uc-engine 组装；产品端不得编排核对步骤。
```

```text
Component: Space membership domain
Path: crates/uc-core/src/membership/
Responsibility: 成员实例、成员事件、历史关系、用户决定、摘要和签名验证规则。
Relationship: 不创建网络连接，不安排后台任务，不依赖具体持久化或传输实现。
```

```text
Component: Infrastructure adapters
Path: crates/uc-infra/src/
Responsibility: 加密持久化、已认证 P2P 传输、OpenMLS 安全状态和地址解析。
Relationship: 提供能力，不决定自动应用、等待用户、分叉或移除。
```

```text
Component: Stable Engine entry
Path: crates/uc-engine/src/
Responsibility: 组装完整流程并通过唯一稳定入口提供操作、查询和通知。
Relationship: 不保存第二份成员状态，不逐消息编排核对协议。
```

当前 Engine 已把“已验证并保存的历史”与“本机已经接受并应用的历史”稳定分开。最后到达的状态
不能覆盖本机，未确认移除也不能被当作普通缺失更新自动应用。

## 5. Implemented Design

### Components

#### `WorkspaceConvergence`

- **职责**：收到设备可达事件后启动一次核对，完成问候、历史比较、有界补齐、普通事件应用、移除
  决定等待、用户决定、确认回复、分叉隔离、加密保存、重启恢复和统一通知。
- **输入**：设备可达/失联观察、成员命令、已认证核对消息、用户接受或拒绝决定、查询。
- **输出**：一致、正在补齐、等待用户、已接受、已拒绝并分叉、资料无效和完整当前快照。
- **边界**：产品端只提交用户决定并读取完整结果；不能逐步发送问候、请求事件或标记分叉。

#### `MembershipHistory`

- **职责**：验证不可变事件、构建单父历史、判断祖先关系、计算成员结果和稳定摘要。
- **输入**：本机事件、收到的事件或有界证明。
- **输出**：相同、严格祖先、严格后继、缺失证明、不可比较分支或无效。
- **边界**：不读取在线状态，不请求用户，不决定是否自动应用破坏性事件。

#### `MembershipReconciliation`

- **职责**：把历史关系和本机决定记录转换为核对结果：自动应用普通新增、暂停未确认移除、继续已
  接受移除、隔离已拒绝或不可比较的历史。
- **输入**：本机已知头、本机已应用头、本机决定集合、远端摘要和验证后的事件。
- **输出**：一致、请求历史、应用普通事件、等待移除决定、分叉或无效。
- **边界**：是 `WorkspaceConvergence` 内部的深模块；网络层和产品端看不到逐事件判断。

#### 分支安全状态适配器

- **职责**：为加入或已接受移除生成、验证和应用对应 OpenMLS 状态，并保证不同分支后续秘密隔离。
- **输入**：父事件、安全状态、成员事件和加入方准入材料。
- **输出**：结果安全状态、摘要和加入交付材料。
- **边界**：不决定用户是否接受移除，不合并分叉安全状态。

### Data Model

#### `MembershipEvent`

每项成员变化都是不可修改的加密业务负载，至少包含：

- `lineage_id`：随机 Space 沿革；不同 Space 永不复用。
- `event_id`：对除 `event_id` 和 `signature` 外的规范编码正文计算的稳定摘要。
- `parent_event_id`：唯一父事件；创世事件没有父事件。
- `parent_depth`：父历史深度加一，只用于有界检查，不能决定赢家。
- `operation_id`：不可重放随机标识。
- `author_member_instance_id`：发起成员实例。
- `operation`：`AddDevice`、`RemoveDevice` 或以新成员实例重新加入。
- `resulting_members_digest`：应用事件后的完整成员集合摘要。
- `security_state_digest`：该分支结果安全状态摘要。
- `admission_bundle_digest`：加入时绑定同一加入方和结果的交付材料摘要；非加入为空。
- `signature`：发起成员对 `event_id` 和完整正文签名。当前 V1 验证仍通过已应用头和当前 OpenMLS 成员树
  解析作者；“从精确父历史取得当时有效身份和永久公钥”是规格 023 的待实施替换规则。

事件只允许一个父事件。多个事件引用同一父事件时形成历史分支；没有多父事件和自动合并事件。

#### `MembershipDecision`

本机对一项移除事件的不可修改决定，至少包含：

- `decision_id`：不可重放随机标识。
- `lineage_id`、`removal_event_id`：精确绑定被决定的移除。
- `decided_by_member_instance_id`：作出决定的本机成员实例。
- `decision`：`Accept` 或 `Reject`。
- `observed_applied_head`：决定时本机已经应用的历史位置。
- `resulting_members_digest`：接受时的结果摘要；拒绝时保持本机分支摘要。
- `signature`：由作出决定的成员实例签名。

接受决定不会生成第二条 `RemoveDevice`。拒绝决定也不会生成 `RemoveDevice(author)`；它只证明双方
对指定事件的处理不同。

移除发起者创建并应用 `RemoveDevice` 事件本身，就已经表达发起者对该移除的接受，不再为自己生成
一份 `MembershipDecision`。决定记录只由后来收到该事件、且本机尚未接受它的其他成员产生。

#### 双历史位置

每台设备必须分别保存：

- `known_head`：本机已经验证并保存的最远事件；其中可以包含尚未接受的移除及其后继。
- `applied_head`：本机已经实际应用到成员集合和安全状态的最远连续事件。

如果 `known_head` 之后包含一个尚未决定的移除，`applied_head` 停在该移除之前。其后事件可以加密
保存，但不能越过待决定移除应用，也不能授予内容权限。

#### 三个独立状态维度

不得用一个互斥枚举同时表达以下事实：

1. **可达性**：`Online`、`Offline`；只表示当前连接观察。
2. **本分支成员资格**：`Active`、`Removed`；只由本机已经应用的成员历史决定。
3. **双方历史关系**：`Unknown`、`Consistent`、`LocalAhead`、`RemoteAhead`、
   `PendingRemovalDecision`、`Diverged`、`Invalid`。

同一设备可以同时是 `Offline + Active + Consistent`，也可以是 `Online + Active + Diverged`。
`Diverged` 表示双方历史不再互认；`Invalid` 表示签名、摘要、身份或结构无法验证；两者不能混用。

#### `ReconciliationAttempt`

保存一次有界核对的对端成员实例、双方摘要、请求范围、已收事件、待决定移除、最终结果和重启进度。
同一对端重复上线复用或替换已终止尝试，不能并发运行多个会改写同一对端关系的核对流程。

### API / Interface

对外继续保持一个完整负责人和少量稳定动作：

- `reconcile_on_peer_reachable(peer)`：内部入口，由运行期在已认证设备变为可达时调用；产品端不可见。
- `decide_membership_removal(decision)`：产品端只提交待决定标识和接受/拒绝，不传成员表、事件或摘要。
- `query_workspace_convergence()`：一次返回当前分支、核对状态、待用户决定、分叉关系、传播进度和
  已知等待设备。

稳定结果至少区分：

- `Consistent`：双方 `applied_head` 和成员摘要一致。
- `HistoryRequested`：需要有界补齐，尚未改变成员状态。
- `UpdatesApplied`：只自动应用了验证通过且不越过待决定移除的普通事件。
- `RemovalDecisionRequired`：保存了有效移除事实，等待本机用户决定。
- `RemovalAccepted`：本机应用收到的同一移除，已向对端确认。
- `RemovalRejected`：本机状态保持，双方历史关系进入 `Diverged`。
- `Diverged`：不可比较历史或有效拒绝已经证明双方分叉。
- `InvalidHistory`：资料无法验证，拒绝且不改变成员状态。

错误和日志不得包含设备名、设备标识原文、成员实例原文、完整事件、决定签名、安全材料、文件名、
路径、密钥或剪贴板内容。

### Protocol Messages

协议消息是 `WorkspaceConvergence` 私有实现，不能逐项暴露给产品端：

#### `SpaceHello`

已认证连接建立后发送，包含协议版本、`lineage_id`、本机成员实例引用、`known_head`、`applied_head`、
已应用成员摘要、决定摘要和能力摘要。不重复发送连接层已经认证的身份公钥，不默认携带完整成员表、
加入时间或全部事件。

#### `MembershipSummary`

返回本机对应摘要、双方头关系的已知判断以及可提供的历史范围，不包含未请求的完整成员名单。

#### `MembershipEventsRequest` / `MembershipEventsResponse`

按父事件范围请求和返回固定条数、固定字节上限的加密签名事件。响应必须连续，不能跳过父事件；
超限通过后续请求继续。

#### `MembershipDecisionMessage`

传递对指定移除的签名 `Accept` 或 `Reject`。接受方验证决定者身份、事件绑定和摘要；决定只影响双方
关系和完成观察，不能替决定者创建成员事件。

#### `MembershipAck`

返回一致、已应用、等待决定、已接受、已拒绝、分叉或无效，以及必要的脱敏引用。它不能命令对端
删除设备。

### Workflow

#### 设备上线核对

1. 运行期确认对端连接身份后通知 `WorkspaceConvergence`。
2. 负责人加密保存或复用该对端唯一核对尝试，发送 `SpaceHello`。
3. 双方先比较沿革、`known_head`、`applied_head` 和摘要。
4. 完全一致时返回 `Consistent`，不请求完整成员表或事件。
5. 资料不足时按父范围交换有界事件，逐项验证后保存到 `known_head`。
6. 普通新增和已由本机接受的移除按父顺序应用；遇到第一项未确认移除时停止推进 `applied_head`。
7. 不可比较历史、已验证拒绝或同一事件存在相反决定时，标记双方 `Diverged`。
8. 核对结果进入统一快照和通知；产品端不拼接协议消息。

#### 接收未确认移除

1. 验证移除的沿革、父历史、目标成员、签名和结果安全状态。当前 V1 对旧作者资格的解析仍依赖已应用头
   和当前 OpenMLS 成员树；规格 023 实施后才改为从精确父历史验证发起者当时资格和永久凭据。
2. 保存事件和对应安全材料，但不修改本机已应用成员集合和普通内容权限。
3. 将双方历史关系设为 `PendingRemovalDecision`，发布一次明确用户决定。
4. 同一事件重复到达只引用同一待决定项；重启后继续，不重复提示为新操作。
5. 待决定期间，不向移除分支越过该事件传播普通内容，也不应用其后继事件。

发起设备本机创建移除时不进入这条流程：事件保存和本机限制在同一提交中完成，事件本身即为发起者
的明确决定。

#### 用户接受移除

1. 产品端提交待决定标识和 `Accept`。
2. 负责人确认待决定仍绑定本机当前 `applied_head`，没有先发生其他本机成员变化。
3. 原子保存签名接受决定、应用收到的同一移除、安全状态和新的 `applied_head`。
4. 如果本机正是被移除目标，先持久化停止成员权限，再停止该 Space 的普通共享。
5. 向本机当前分支的有效设备发送接受决定和当前摘要；相同决定进入 `Consistent`，相反决定进入
   `Diverged`。不能依赖“谁先把该设备标成等待”的消息顺序选择接收方。
6. 继续按顺序处理此前已经保存的后继事件，下一项未确认移除仍需单独决定。

#### 用户拒绝移除

1. 产品端提交待决定标识和 `Reject`。
2. 负责人原子保存签名拒绝决定，本机成员集合、`applied_head` 和安全状态保持不变。
3. 双方历史关系进入 `Diverged`，停止这两个分支之间的普通内容和后续成员历史传播。
4. 向本机当前分支的有效设备发送拒绝决定；相同拒绝进入同一旧分支并恢复 `Consistent`，相反决定
   才进入 `Diverged`。不能依赖“谁先把该设备标成等待”的消息顺序选择接收方。
5. 不生成移除发起者的事件，不把发起者设为 `Removed`，也不修改其他成员。
6. 双方各自在自己的分支内继续使用 Space；任何后续移除都必须由用户另行明确发起。

#### 发现不可比较历史

双方事件共享祖先但互不为祖先时，无需把普通差异伪装成待确认移除。负责人保存分支证明，将双方
关系直接设为 `Diverged`，停止跨分支分享。两个分支继续各自运行，不自动合并或选择赢家。

#### 新增设备传播

连续的 `AddDevice` 事件验证通过后可以自动应用。待实施的规格 023 进一步要求发起方和加入方都保存并
确认同一事件和安全状态后才返回加入成功；这不表示所有离线旧成员已经应用。旧成员上线后可自动补齐
新增，除非补齐路径先经过一项尚未决定的移除或已分叉历史。

### 内容与成员传播门禁

- `Consistent`、`LocalAhead`、`RemoteAhead` 可以进行受历史关系约束的核对和正常传播。
- `PendingRemovalDecision` 只能交换完成决定所需的受限历史，不能越过待决定事件分享普通内容。
- `Diverged` 只允许身份证明、拒绝确认和用户明确启动的新 Space 准入，不交换普通内容或旧 Space
  成员历史。
- `Invalid` 关闭该核对入口并返回稳定错误，不能降级为 `Diverged` 或普通离线。
- `Offline` 只暂停网络动作，不改变上述任何成员或历史关系。
- `UpgradeRequired` 是已认证的对端版本低于 `1.1`，不是离线、连接失败、身份不符、资料损坏、成员移除或历史分叉；
  它保留 Space 和成员关系，但阻止双方普通内容同步，直到对端升级到本次 `1.1` 并被重新确认。

### 版本升级与流程选择

本次 ADR 只有两类设备：版本低于 `1.1` 的旧设备，以及本次 `1.1` 设备。当前成员历史核对、内容门禁
和自动恢复流程只服务于 `1.1` 设备之间；旧设备不参与该流程，也不存在为旧设备继续同步内容的备用流程。
升级不能要求用户清空 Space、重新配对或丢弃已有资料。

每台 `1.1` 设备必须加密保存已认证的对端版本结果。这里的版本不是发布渠道、构建号或配置里的
应用版本字符串；本 ADR 只判断对端是否已经具备本次 `1.1` 流程。连接建立后，
`WorkspaceConvergence` 只做一次有界识别，并为该对端选择唯一结果：

- 对端版本低于 `1.1` 时，确认双方保留同一 Space 和成员关系，保存 `UpgradeRequired`，并关闭该设备对的
  普通内容发送与接收。`1.1` 设备的完整状态必须列出该对端为“需要升级后才能继续同步”；旧设备不能理解
  该提示，不要求它显示新状态。
- 对端也是 `1.1` 时，清除 `UpgradeRequired`，进入当前成员历史核对流程；确认通过后恢复普通内容同步。
- 版本结果尚未知、离线、连接失败、身份不符或资料损坏时，保留各自的原有结果并在下一次可达时有界重试；
  不得写入 `UpgradeRequired`，也不得把这些问题显示为需要升级。

版本识别使用两份正面证据，不能从一次失败反推版本：

1. 已认证对端完成本次 `1.1` 的轻量确认，才判为 `1.1`，随后才启动成员历史核对。
2. 只有已认证对端成功接受“旧入口仍在监听”的空连接，才判为低于 `1.1`。这个探测只完成连接后立即关闭，
   不发送任何请求，不改变成员、安全状态或资料。本次 `1.1` 不再监听旧内容入口；因此已确认的 `1.1`
   对端不可能提供这份旧证据。

新入口不支持、超时、连接中断、地址过期、身份不符、旧入口不支持或旧入口本身失败，都只是“尚未确认”，
必须在下次已认证可达时重试。它们不能生成升级提示，也不能暂停一个此前已经确认可同步的 `1.1` 设备对。

识别顺序固定为：先请求本次 `1.1` 确认；成功后普通流程只运行当前成员历史核对。只有这一步没有得到确认时，
才尝试一次旧入口空连接；空连接成功写入 `UpgradeRequired`，其他结果保持未知。每对设备由
`WorkspaceConvergence` 串行执行这两个动作。

独立的旧空间安全提升入口必须继续由 `1.1` 监听。它只用于让原有低于 `1.1` 的 Space 在设备逐台升级时
原地建立共同保护状态，不接收或发送普通内容，也不把旧成员表转换成当前成员历史。双方升级后，每台设备
提交自己签名的当前身份资料；旧成员表只用于首次确定保留成员和唯一发起端，由该端建立唯一历史起点。
历史起点建立后，普通列表、连接和内容只使用当前成员历史；持久升级记录中的保留成员仍可完成已经开始的
同一次共同保护和历史接纳，但不因此获得普通成员资格。只有共同保护状态和已应用历史都覆盖全部保留成员后，
旧空间安全提升才结束并永久停止该有界升级入口，不保留第二套普通成员事实来源。

版本识别、探测节流、重启恢复、内容门禁和升级提示都由 `WorkspaceConvergence` 统一负责，产品端只读取
完整状态。`UpgradeRequired` 必须跨重启保留，直到同一对端以 `1.1` 重新完成确认。旧资料继续保留，直到
单独结束低于 `1.1` 的兼容支持并完成验收。

### 删除旧方案

实施时必须删除以下内容，不保留并行路径：

- OpenRaft、投票、多数、选主、learner、联合成员配置和唯一正式后继；
- 最后到达成员表覆盖本机状态；
- 只比较成员集合而不验证事件历史；
- 连续历史中的移除在接收设备上自动生效；
- 用户拒绝移除后自动创建 `RemoveDevice(author)`；
- 把 `Online`、`Active`、`Diverged`、`Invalid` 和 `Removed` 塞进一个互斥状态；
- 发现分叉后停止整个 Space 或强制创建新 Space；
- 自动合并分叉或选择赢家。

版本低于 `1.1` 的设备不能验证本 ADR 的事件、决定和门禁时，必须标记为 `UpgradeRequired`，不能把它当作
成员历史失败、分叉、移除或普通离线，也不能继续同步内容。已有 Space 不得从本机成员表补造历史；保留
本机资料，等待对端升级到 `1.1` 后再进入当前流程。

- **Change**：增加 `MembershipEvent`、`MembershipDecision`、双历史位置、三维设备状态和纯历史比较；
  删除多数提交与单一综合状态类型。
- **Risk**：规范编码或父历史判断不一致会误报分叉，必须先以固定向量锁定。

### Step 2：实现核对深模块

- **File**：`crates/uc-application/src/space/convergence/`

  自动新增、移除暂停、决定和分叉门禁。
- **Risk**：把逐消息步骤暴露给 Engine 或产品端会重新分散流程知识。

### Step 3：接入已认证 P2P 消息

- **File**：`crates/uc-infra/src/`
- **Change**：实现有界问候、摘要、事件请求/响应、决定和确认；复用已认证连接身份，不重复发送公钥。

- **Change**：加密保存事件、决定、双历史位置、三维关系、核对尝试和门禁状态；每次回复前先落盘。

- **Change**：普通新增可顺序应用；移除安全状态保存待定，接受后应用；拒绝后不跨分支合并。
- **Risk**：必须证明同一父状态产生的不同分支不会复用后续秘密。

### Step 6：收口稳定入口和绑定

- **File**：`crates/uc-engine/`、`bindings/`
- **Change**：只暴露完整核对快照和一次用户决定；各平台完整映射待决定、分叉、无效和三维状态。

### Step 7：完成升级共存和拓扑验收

- **File**：全仓成员同步、旧状态、文档、测试和依赖
- **Change**：删除多数、覆盖、自动移除和全 Space 冻结；实现低于 `1.1` 与本次 `1.1` 的版本识别、
  `UpgradeRequired` 内容门禁和 `1.1` 对端确认后的自动恢复；覆盖混合版本重启、上线、乱序、同时决定和多分支。
- **Risk**：版本识别与当前 `1.1` 流程并发拨号会造成连接争用；错误地把网络故障或身份问题显示为“需要升级”，
  或在对端尚未确认 `1.1` 时恢复内容同步，会误导用户或破坏版本边界。

## 7. Edge Cases

### Scenario：成员集合相同但历史不同

- **Expected behavior**：不能只按成员摘要判定一致；补齐事件后判断祖先或分叉。
- **Implementation**：`SpaceHello` 同时携带头事件和摘要，摘要相同但头不同仍进入历史比较。

### Scenario：A 移除 B，C 离线后上线

- **Expected behavior**：C 保存移除但保持 A、B、C，等待用户；接受后变为 A、C，拒绝后仍保持原分支。
- **Implementation**：`known_head` 可前进，`applied_head` 停在移除前。

### Scenario：C 选择保留 B

- **Expected behavior**：A 与 C 标记为 `Diverged`，不再互相分享；C 不自动移除 A。
- **Implementation**：保存 `Reject` 决定并执行关系门禁，不创建成员事件。

### Scenario：C 已拒绝，之后又想移除 A

- **Expected behavior**：必须执行一项新的明确移除操作，与此前拒绝决定分开审计。
- **Implementation**：拒绝结果不提供隐式移除效果。

### Scenario：待决定移除后还有多个新增事件

- **Expected behavior**：可以保存事件，但不能越过移除应用；接受后顺序继续，拒绝后保持分叉。
- **Implementation**：`known_head` 与 `applied_head` 分离，应用器禁止跳过父事件。

### Scenario：同一移除被重复发送或重启后再次收到

- **Expected behavior**：只存在一个待决定项和一个最终决定，不重复提示或重复应用。
- **Implementation**：按 `removal_event_id` 和本机成员实例唯一去重。

### Scenario：两边同时对同一移除作出相反决定

- **Expected behavior**：决定各自有效，双方进入 `Diverged`；不按时间选择一个覆盖另一个。
- **Implementation**：决定是签名事实，不是可变布尔值。

### Scenario：设备已经观察到自己被移除并接受

- **Expected behavior**：该分支上本机成员资格变为 `Removed`，停止普通共享；可达性仍独立保留。
- **Implementation**：先原子保存决定和成员限制，再关闭运行期入口。

### Scenario：分叉设备仍然在线

- **Expected behavior**：显示 `Online + Active + Diverged`，不能交换普通内容。
- **Implementation**：所有内容发送、接收和成员历史入口检查历史关系门禁。

### Scenario：收到未知父事件或超大历史

- **Expected behavior**：在固定限制内请求补齐；超限、永久缺失或结构损坏返回稳定错误，不覆盖本机。
- **Implementation**：限制批次、深度、字节、并发和保存头数量。

### Scenario：低于 1.1 的客户端上线

- **Expected behavior**：A 升级到本次 `1.1`、B 低于 `1.1` 时，两台设备仍能发现彼此并保留原有 Space、
  成员关系和资料，但 A/B 的普通内容双向暂停。A 将 B 显示为“需要升级后才能继续同步”，不把该状态显示为
  离线、分叉、移除或损坏；B 升级到 `1.1` 并重新确认后，A 自动清除提示并恢复双向内容同步。
- **Implementation**：先以已认证的本次 `1.1` 确认判断是否进入当前流程；只有旧入口空连接成功才把对端写为
  `UpgradeRequired`。本次 `1.1` 不监听旧内容入口，探测本身不发送旧请求；独立的旧空间安全提升入口继续运行，
  但不传输普通内容或产生第二份成员事实。统一门禁同时拒绝入站和出站内容。未知、网络失败和身份失败使用
  各自原有结果，不能写入 `UpgradeRequired`；同一对端不同时启动版本识别与当前 `1.1` 流程。

### Scenario：双方都完成 1.1 升级

- **Expected behavior**：B 升级到 `1.1` 并完成共同保护与成员历史接纳后，A/B 的普通流程只运行当前成员历史
  核对并自动恢复双方普通内容同步；已有资料仍可用于恢复和审计。若进程在历史起点或共同保护完成后中断，
  重启后继续同一次提升，不重新选择发起端。
- **Implementation**：负责人保存 A/B 均已确认 `1.1` 的结果，清除两端的 `UpgradeRequired` 内容门禁；
  旧空间安全提升先建立共同保护状态，稳定发起端建立唯一历史起点，每台设备提交自己签名的当前身份资料；
  当前历史起点不单独表示提升完成，只有共同保护状态和已应用历史都覆盖保留成员后才清除持久升级状态；
  完成后不再从旧成员表补造历史，也不影响其他仍处于混合版本状态的设备对。

## 8. Testing Strategy

### Unit Test

- 相同头和摘要得到 `Consistent`；相同摘要但不同头继续比较历史。
- 严格祖先链中的新增自动应用，第一项未确认移除产生 `RemovalDecisionRequired`。
- 接受应用原移除且不生成新事件；拒绝不改变成员集合且不生成移除发起者事件。
- 发起者创建移除时不为自己生成重复决定；只有其他接收成员产生接受或拒绝记录。
- `known_head` 可以领先 `applied_head`，应用器不能跳过待决定移除。
- 不可比较事件和有效拒绝得到 `Diverged`；无效签名得到 `InvalidHistory`。
- 可达性、成员资格和历史关系可以组成所有合法组合，互不覆盖。
- 规范编码、事件摘要和决定签名使用跨平台固定向量。

### Integration Test

- 连接建立自动发送有界问候，一致时不请求完整成员表或事件。
- A 离线移除 B，C 上线后等待决定；重启 C 仍是同一待决定项。
- C 接受后双方摘要一致并恢复普通分享；拒绝后双方在线但普通内容双向拒绝。
- 拒绝后 C 分支仍能与 B 同步并邀请新设备，A 分支也能与其一致成员继续使用。
- 待决定期间收到后继新增只保存不应用；接受后按序应用，拒绝后不跨分支传播。
- 加密存储、WAL、SHM、缓存、索引和日志扫描不出现成员资料、事件、决定、安全材料或内容明文。

### Regression Test

- A、B、C 同源；A 移除 B；C 上线时不能被 A 直接覆盖，也不能反向覆盖 A。
- C 接受后 A/C 一致；C 拒绝后双方均保留各自成员集合，且 C 不自动移除 A。
- A、B、C 同源；A 离线后 B/C 移除 A 并加入 D；旧 A 邀请已经在另一历史的 D 时，D 在任何
  Space Switch 副作用前识别历史关系，不能被旧 A 覆盖。
- 两个分支最终成员集合相同但事件历史不同，仍按事件关系判断，不能仅按成员摘要宣布一致。
- A 为 `1.1`、B 低于 `1.1` 时，保留原有关系与资料，双方内容同步暂停，A 显示“需要升级后才能继续同步”；
  B 升级到 `1.1` 并确认后，双向内容同步恢复。
- 三台设备混合低于 `1.1` 与 `1.1` 并反复上线、下线和重启时，低于 `1.1` 的设备对始终暂停内容；每个 `1.1`
  设备对每次只出现当前流程的一次有界核对，不发生并发拨号或无限重试。
- 全部保留设备完成共同保护和成员历史接纳后，设备之间只运行当前成员历史核对流程，既有 Space 数据保持可读。
- 分叉、待决定和普通离线均不会触发 P2P 到 LAN 自动回退。

## 9. Acceptance Criteria

截至 2026-08-13，核心规则、应用流程、加密保存、重启恢复、三至四设备分支场景和关闭边界已由当前
仓库测试验证。正式 `v0.19.0` 标签及其固定提交已用于重新构建旧版后台和命令行程序；两个旧端已完成
真实配对和双向内容接收基线。单边升级首次运行暴露出网络身份接线错误，当前修复保持旧端配对时的原
身份。随后以同一组正式 `v0.19.0` 双机资料完成全流程：A 单独升级后保存 B 的升级提示，A 重启后提示保留，

## 10. Risks and Trade-offs

### 保密性

未收到或拒绝移除的设备继续自己的分支，因此仍能分享该分支掌握的历史内容。分叉门禁只能阻止已
识别设备之间的后续交换，不能撤回此前内容，也不能让尚未知情的第三台设备立即停止。

### 用户负担

每个接收设备都可能分别确认同一移除。设备多、长期离线或连续移除时，用户会看到多次决定。产品
必须按事件去重、解释发起者和影响，但不能用自动接受来消除提示。

### “一致”的范围

`Consistent` 只表示当前两台设备的已应用头和摘要一致，不证明全 Space 所有离线设备一致。任何界面、
日志和结果都不能把点对点一致描述为全局一致。

### 状态复杂度

双历史位置、签名决定和三个独立状态维度比单一成员表复杂，但它们隐藏在
`WorkspaceConvergence` 内部。调用方只理解完整快照和一次用户决定，不能承担协议步骤。

### 替代方案

- **OpenRaft 多数确认**：阻止分支，但成员变化依赖多数设备在线；不采用。
- **连续移除自动追赶**：简单，但离线设备没有最终决定权；不采用。
- **拒绝后停止整个 Space**：安全边界清楚，但牺牲各分支继续使用；已被本决策取代。
- **拒绝时自动移除发起者**：把两个用户动作混成一个不可见副作用；不采用。
- **只比较成员集合**：无法发现相同集合背后的不同历史；不采用。
- **发送完整成员表和历史**：泄露更多资料且无界；改为摘要和按需补齐。

## 11. Implementation Conclusions and Product Follow-up

实施已经固定以下答案：

1. 收到但尚未接受的移除及其后继保存在已知历史中，已应用历史停在移除之前；接受后按同一条连续历史应用。
2. 拒绝后保留已验证的远端记录用于审计和去重，但不把它们应用到本机分支，也不跨分支继续传播。
3. 已签名保存的接受或拒绝不可撤销；产品若需要“反悔”，必须定义新的明确成员操作和单独决策。
4. 历史按固定页面补齐，每页最多 64 条，并受消息字节上限约束；同一对端的版本识别和当前核对串行执行。
5. 同一已认证设备成功完成本次 `1.1` 的轻量确认后解除 `UpgradeRequired`。旧空间安全提升先建立共同
   保护状态，稳定发起端建立唯一历史起点，每台设备提交自己签名的当前身份资料；当前历史起点建立后，
   普通流程只按双方已保存的历史头请求和验证缺失事件。持久升级记录只允许保留成员完成同一次保护和接纳，
   不授予普通资格；共同保护状态和已应用历史都覆盖保留成员后才结束提升，不从旧成员表补造历史。
6. 历史作者验证材料的长期保存，以及新 AddDevice 从候选到普通权限的完成边界，由待实施的规格 023
   细化；本 ADR 的离线分支、移除决定和分叉规则保持不变。

产品如何呈现移除发起方、目标设备和影响仍属于界面设计，不改变本 ADR 已实施的事实、动作和安全边界。

这些问题不改变已经采纳的核心规则：上线先核对历史；普通新增可自动应用；未确认移除由各设备用户
决定；接受可以恢复同一历史；拒绝只建立分叉关系；分叉后各分支继续、彼此停止分享。
