# 文档记录系统

## 目标

文档保存难以从代码恢复的意图、边界、取舍、状态与证据。`AGENTS.md` 只作为短地图，不承载百科正文。

## 文档类型

### Product Spec

位置：`docs/product-specs/`。

回答“为谁解决什么问题、为什么、范围和验收是什么”。推荐包含状态、背景、目标、需求、非目标、约束与验收标准，
不写详细算法、内部接口或实施步骤。

### Design Doc

位置：`docs/design-docs/`。

描述长期有效的架构、组件职责、数据/控制流、状态机、不变量、失败行为、兼容与性能边界。它说明设计意图，
不逐行翻译源码，也不记录每日实施进度。

### ADR

位置：`docs/design-docs/decisions/`。

当存在多个合理方案、取舍重要且难以逆转时记录决策。ADR 使用稳定顺序编号；被取代后保留原文件、更新状态并链接替代决策，
不删除、不重新编号，也不改写历史理由。

### Exec Plan

位置：`docs/exec-plans/active/` 或 `completed/`。

记录可执行工作、依赖、分阶段步骤、验收矩阵与实际状态。Active plan 完成或明确被取代后，先把稳定结论同步到设计文档/ADR，
再移入 `completed/`。Completed 计划用于追溯，不是当前事实。

### Generated / Reference

`generated/` 保存可再生资料，必须标注来源、生成时间和权威边界。`references/` 保存词表、来源映射等查询资料，
不通过参考资料暗中引入新设计决定。

## 选择规则

```text
做什么、为谁、为什么？      → Product Spec
长期应该怎样工作？          → Design Doc
为什么选择这个方案？        → ADR
如何分步交付、现在到哪里？  → Exec Plan
能从代码或工具重建？        → Generated
供跨文档查询的稳定资料？    → Reference
```

一次变更可以更新多种文档，但同一事实只能有一个正文来源，其他文件只链接。

## 状态与一致性

- 代码和文档冲突时，不默认任一方正确；先判断实现错误、文档过期还是意图已改变。
- 行为、接口、不变量或重要取舍变化时同步更新对应事实来源。
- 普通重构不复制文档；若当前架构事实未变，只更新架构圣经的维护记录。
- 不创建只为满足流程、没有长期信息价值的文档。
- 历史原因没有证据时明确标为未知或推断。

## 写作与链接

- 文档与图中说明使用中文；代码标识符保持英文。
- 仓库路径使用相对路径，Markdown 链接优先于裸路径。
- 说明意图、约束、理由和失败边界；避免把函数 A 调用函数 B 的表面流程抄成正文。
- 使用具体例子帮助理解，但不把示例变成第二份契约。
- 文档过长且混入不同变更理由时，按知识所有权拆分并建立索引。

## Agent 工作顺序

1. 从根 `AGENTS.md` 和最近的局部 `AGENTS.md` 确认范围。
2. 阅读相关 Product Spec、Design Doc 和被引用 ADR。
3. 若有 active plan，确认状态、负责人和验收条件。
4. 修改实现与唯一事实来源。
5. 更新架构圣经正文或维护记录。
6. 检查相对链接、孤儿文档、旧路径和交付门禁。
