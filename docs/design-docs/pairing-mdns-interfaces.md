# 多网卡主机的配对 mDNS 接口选择

## 背景与根因

当 Windows 与 macOS 同时保留各自的上网链路，并通过另一块网卡直连时，
直连链路可能不是系统默认组播出口。配对邀请中的地址列表包含直连 IP，
不代表承载邀请发现的 mDNS 数据包会从该接口发送。

`Discoverer::with_addrs` 只设置公告中的地址；发送与组播组加入由
`with_multicast_interfaces_v4` 控制。仅设置前者会使邀请发布或查询落在默认接口，
因此双方即使处于同一子网，交换邀请发起角色也可能都失败。

## 责任与行为

这是 `uc-infra-p2p` 配对适配器的接口选择缺陷。`MdnsInterfaceSnapshot` 是发布端与解析端
共同的本机地址筛选入口，消除分别枚举或只配置一侧造成的差异。

- 每次开始发布或解析时重新捕获本机接口，去重并排除回环、未指定和组播地址。
- 发布端使用快照内的地址生成公告，同时显式配置全部合格 IPv4 接口。
- 解析端使用同一筛选规则显式配置 IPv4 查询接口。
- IPv6 仍沿用 `IpClass::Auto` 的既有行为；本修复不声明覆盖 IPv6 多接口。
- 枚举失败时记录固定失败分类与 IO 错误类别，沿用库的默认接口行为。
  不输出原始错误正文、IP 或接口名称。

调用方仍只执行原有发布或解析动作。发布返回的 guard、解析成功/超时/失败结果、
取消和关闭语义不变；重试仍由原配对流程负责。本实现不新增持久状态或后台接口监听。
活动期间网卡发生变化时，应结束并重新创建邀请或重新解析以捕获新快照。

## 范围与兼容性

不修改邀请格式、认证协议、加密、数据库结构、云发现策略或配对后传输协议。
保留正式版已有的错误 source chain；不回退到旧版本的字符串错误。
本修复替换发布端旧的独立地址枚举方法，没有并行维护第二条配对流程。

全部合格 IPv4 接口包括系统暴露的虚拟接口。接口选择不保证防火墙、组播策略或
链路本身允许收发；也不等同于对任意 VPN、网卡热插拔或休眠恢复的完整验证。
