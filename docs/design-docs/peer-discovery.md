# 设备发现与候选目录

## 边界与身份

发现回答“当前有哪些地址线索”，连接和授权回答“能否建立及使用连接”。Application 的 discovery 模块拥有观察合并、来源失效、按需查询和候选目录；Infra 将已有服务适配为 provider，并将目录输出转换到 iroh 地址查找契约。设备级网络节点拥有发现任务，Space 会话不拥有它。

目录的 `DiscoveryPeerId` 包含后端标识与不透明传输身份，不是逻辑 `DeviceId`。允许保留尚未绑定的陌生设备观察，但不自动拨号、建立配对或授予成员资格。本切片没有增加 Engine 的附近设备列表。逻辑设备与传输公钥的映射仍来自现有成员身份负责人；连接后密码身份验证、当前成员授权和 session generation 围栏继续生效。切换 Space 不缓存旧 DeviceId 绑定，也不清空仍有效的网络线索。

## 来源与有效期

- mDNS 复用节点已有 `_irohv1._udp.local` 服务与线格式。持续订阅包括主动 resolve 的设备，晚订阅获得当前快照，地址变化替换该来源的旧观察。
- 长期发现与配对发现共用同一接口策略（`network::mdns_interfaces`）：在全部非回环、非未指定、非组播的本机 IPv4 地址所在接口上收发，而不只是默认路由接口；没有组播能力的接口（如 WireGuard）只在建立该接口套接字时被跳过。接口集合在启动时读取，并在本机发布地址变化时重新读取；没有引入额外的网络变化监视器。长期发现把每次读取的结果作为期望集合交给 `swarm-discovery`，由它统一维护期望集合与已安装接口：只有套接字、接收者和主通配套接字上的组播成员关系都建立后才算已安装，未安装的期望接口按 1 秒起、最长 60 秒的有界退避重试，持续失败的接口最多每 60 秒尝试一次；移除接口时先停止并等待其接收者退出，再释放套接字并退出组播组。组播成员关系按操作系统接口而不是地址生效，同一网卡上的另一地址退出会带走仍保留地址所需的成员关系，因此退出后为其余保留地址重新加入，重新加入失败的地址算作未安装并按同一退避重试。配对发现不提交期望集合，保持单次尝试和默认 IPv6 接口。
- 长期发现另外在上述具有合格 IPv4 地址的同一组接口上收发 IPv6 mDNS，不扩大接口范围。适配器资格按接口名关联（Windows 两个地址族的索引可能不同），不记录接口名；实际期望集合按 IPv6 接口索引维护，每个接口只保留一个发送套接字和一个主通配套接字上的组播成员关系。同一网卡有多个 IPv6 地址时优先绑定 link-local，否则取最小合格地址；绑定 link-local 时以接口索引作为 scope。绑定地址变化时先停止并等待旧接收者、释放旧套接字并退出组播组，再安装新地址；其他索引的成员关系不受影响。安装完整性和有界退避与 IPv4 相同。没有可用主 IPv6 套接字时跳过 IPv6 接口；从未使用新接口的调用方保持默认接口行为。
- IPv6 link-local（fe80::/10）只能作为带 scope 的本机绑定地址，不写入 mDNS 的 AAAA 通告：AAAA 无法携带 scope id，对端无法确定拨号接口。其他 IPv4、ULA 和全局 IPv6 地址照常通告，再由拨号策略过滤。
- 本机 mDNS 是可降级来源：两种地址族都无法建立组播套接字时记录一次固定警告，节点在没有 mDNS 的情况下照常启动，诊断来源标记为不可用；显式地址、已保存的直连线索、用户配置的地址和启用时的云端发现不受影响。长期 mDNS 不因启动失败而关闭到重启：`discovery/lifetime_mdns.rs` 在后台按 1 秒起、每次翻倍、最长 60 秒的有界退避重新建立（与接口安装重试同一节奏），不阻塞 endpoint 启动；建立后补发最近一次本机发布的地址，启动前已创建的目录订阅从此开始收到观察，诊断来源改记为可用并记录一次恢复。节点关闭时取消尚未成功的重试。
- 该服务是通用 iroh 服务；陌生观察只能说明发现了一个传输端点，不能据此确认它运行 UniClipboard。未来附近设备列表须另行验证产品能力，不能把未经识别的候选展示为已确认设备。
- CloudDiscoveryProvider 适配已有 DNS/PKARR 地址解析；PKARR 发布仍由同一个 endpoint 持有。查询只在连接需要地址时发生，不新增周期轮询。邀请码 rendezvous 不属于本目录。
- ConfiguredAddressProvider（`discovery/configured.rs`）提供用户为已配对设备配置的地址，适合没有组播、也不使用 relay 的网络（例如 WireGuard 隧道，隧道地址通常固定）。配置保存在设置 `network.peer_addresses`，键为设备的 `DeviceId` 字符串（不是设备名），值为单播 IPv4 或 IPv6 字面量（字段 `ip`，IPv6 可带方括号，保存时去掉）加端口；不接受主机名，因为解析主机名要走系统 DNS，LAN-only 下这类查询可能离开本地网络。这是明文配置，不含凭据或用户内容，不进入日志、错误文本或 `Debug` 输出。它是按需来源，没有订阅：只有连接需要某个传输身份的地址时，才经成员身份目录把该身份映射为设备（没有当前 Space 或不是已知设备时没有候选），读取当时的设置条目，所以修改即时生效、无需重启；手工改坏、不是 IP 字面量的条目被忽略，不尝试解析。观察期限同为 60 秒副本。它与 mDNS 一样两种模式都装配，结果经过目录 lookup，因此 LAN-only 下配置的公网地址不会被拨号。宿主通过 `UpdateSettings` 的 `network.peer_addresses` 按设备修改：值为地址时设置或替换，为 `null` 时删除，未列出的设备不变；IP、端口或设备标识不合法（包括主机名）时整个更新被拒绝，原因不回显该值。设备解除配对后不自动删除条目：该设备不在成员身份目录中时条目不会被读取，宿主在解除配对时可用 `null` 删除。两端地址都可能变化的隧道需要更新配置，或依赖 mDNS 与地址变化后的传播。
- 一份观察包含一个后端不透明 locator，locator 可编码该来源的多条地址。来源不同的观察独立保存，不能以 mDNS 更新覆盖 Cloud，不能以 Lost 删除整个 peer。
- 原服务没有向适配层暴露可直接采用的 TTL；目录副本采用 60 秒上限。mDNS 的原观察时间保留在 `Item.last_updated`，读取缓存只交付剩余有效期，不重新续期；时间不明或过期的 mDNS 观察不进入目录。Cloud 沿用原 DNS resolver 的缓存语义，并为返回结果设置 60 秒目录副本期限。mDNS 的 Expired 提前删除来源。查询和每 5 秒维护都清理过期项，停止的订阅清除该来源；广播不再刷新或订阅掉包时，副本也不会永久有效。
- 容量按来源独立限制为 1024 份观察；新观察达到容量时淘汰该来源最早观察，不淘汰其他来源。身份最多 512 字节、locator 最多 16 KiB。所有候选只存内存，默认 Debug 隐藏身份与地址材料。

## 连接与失败责任

iroh 的生产 address lookup 消费 DiscoveryManager 输出。缓存候选先交付，provider 查询并行轮询，云端失败或缓慢不能阻塞有效本地候选。按需查询异常保留 source chain，不删除此前仍在有效期内的来源事实；没有查到新地址不能解释为设备已离线。

目录候选不改变 iroh 内部路径选择、QUIC、Relay、地址过滤或 LAN-only 设置。LAN-only 根本不装配云端解析与发布，目录交给 iroh 的候选也按下文的本地网络范围收敛。现有传输协议和业务重试负责人保持唯一，不增加应用层的 LAN/Internet/Relay transport。

查询取消通过丢弃流完成，不创建分离查询任务。正常节点关闭先关闭目录，禁止迟到结果重新填充，再取消并等待发现任务；未完整构建的节点由任务 guard 取消。进程重启重新发现，不新增持久化格式或恢复资料。

## 已保存的配对设备地址与固定端口

配对设备的地址记录（密文保存）只是拨号线索，不是可达性证明。记录同时保留 relay 与至多 8 个直连 IP 线索：本机公告保留当前全部 relay 与前 8 个直连地址；成员历史验证成功后的刷新只把本次连接正在使用的路径作为新证据，使用中的 relay 替换旧 relay，使用中的直连排在最前，并保留尚未被否定的旧直连线索（同一 IP 已在另一端口上被证实可用时旧端口才被否定）；没有使用中路径或结果不变时不改写记录。初次准入仍保存对端当时的完整地址。

本机地址变化后，当前可达的配对设备随即学到新地址（#952 的第一步），复用既有的 presence 交换而不新增线上消息：endpoint 的本机地址变化已作为 `ConnectionHint::NetworkChanged` 交给连接协调器，协调器合并后对每个配对设备执行一次强制在线确认（已保留的连接上发挑战，否则新建 presence 连接，拨号同样经过下文的 LAN-only 边界）。应答方在对端身份已认证且当前获准时（入站 presence 准入成功，或应答获准的挑战）对该对端执行同一个已验证地址刷新（`RefreshVerifiedPeerAddressPort`），记录这次连接正在使用的路径，即对端的新地址；刷新在后台进行，不延迟应答，没有已保存记录、没有使用中路径或结果不变时不写入。成员历史与 presence 两条路径共用同一个刷新负责人（`IrohVerifiedPeerAddressRefresh`），它按对端串行执行并合并请求：每个对端最多一次运行、一次待运行，运行期间到达的请求只标记待运行并立即返回，较早的刷新因此不会覆盖较新的地址，未完成工作也不随联系次数增长。应答频率受发起方在线确认的 10 秒快速路径约束，不新增周期轮询，也不转发第三方设备地址（#949 验证之前不做）。两端地址都变化且彼此都无法到达时，这一机制无法覆盖，需要 mDNS 或用户配置的地址。

拨号把记录交给 iroh；没有选定路径时 iroh 同时启动地址发现，并把初始包发往全部已知候选，任一可用路径胜出，所以陈旧线索不会阻塞新发现的地址，也从不作为唯一放行条件。LAN-only 只拨本地网络范围内的直连地址：IPv4 私网（10/8、172.16/12、192.168/16）、环回、link-local 169.254/16、CGNAT 100.64/10（Tailscale 等 overlay 隧道），以及 IPv6 环回、ULA fc00::/7 与 link-local fe80::/10；此外还允许落在本机接口当前子网内的地址（例如没有 ULA 的 IPv6 局域网中对端的全局地址），Clash fake-ip 198.18/15 除外。relay 线索与公网直连线索（例如 relay 开启时保存的反射地址或公网网卡地址）不拨，LAN-only 因此不会向 relay 或公网地址发起连接（用户自行配置的隧道地址除外，其流量由该隧道承载）。这条规则只在 `crates/uc-infra-p2p/src/network/iroh/addr_filter.rs` 定义一次，并在拨号地址进入 iroh 的两个入口统一应用：一是出站拨号入口（已保存记录、邀请路由与 blob 地址提示，见 `connect.rs` 的 `restrict_dial_addr_if_lan_only`），二是目录 lookup 交给 iroh 的地址发现结果。relay 开启时两处都原样交出全部线索。

`network.bind_port`（默认 `None`，即每次启动随机端口）把 IPv4 与 IPv6 的 UDP 监听固定到同一端口：IPv4 必须绑定成功，端口被占用时网络节点启动失败；IPv6 尽力绑定，本机没有 IPv6 或端口不可用时跳过。固定端口让保存的直连线索在对端重启后仍然有效，适合没有组播、也不使用 relay 的 WireGuard 等隧道，以及只放行一个端口的防火墙。优先级只在 Engine 组装层定义一次：有效的 `UC_IROH_BIND_PORT` 覆盖设置，环境变量未设置或无效时使用设置，`0` 与未设置同为随机端口。修改后需重启网络生效。

## 验证边界

纯目录与测试provider证明多来源／期限／取消契约，真实mDNS adapter测试证明订阅和地址变更，目录lookup的真实QUIC测试证明连接桥与双向多流。

独立进程的云故障产品验收由[发现网络脚本](../../scripts/testing/run-discovery-connectivity.sh)执行：Cloud保持开启，两端完全退出并更换双栈端口；防火墙持续阻断旧端口且namespace没有公网路由。先阻断mDNS，要求实际Cloud失败终态、无成功路径和内容；再只放行mDNS，要求实际本地候选、Direct连接及合成剪贴板宿主准确读回。该对照排除持久旧地址和已有连接作为成功路径，不要求删除既有身份映射，也不新增测试专用Engine查询。

该场景复用既有合成剪贴板宿主，证明完整Engine到宿主写入口及准确读回；本地独立进程证明不代表原生桌面剪贴板、物理设备、多网段或全部平台网络栈验收。当前执行状态见[后续计划](../exec-plans/completed/2026-10-30-issue-34-followups.md)，原切片实施历史见[第一个切片计划](../exec-plans/completed/2026-10-11-peer-discovery-slice.md)。
