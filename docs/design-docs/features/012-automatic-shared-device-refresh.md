# 主动刷新共享设备技术说明

## 状态

已实现。本说明将 [ADR-012](../decisions/012-automatic-shared-device-refresh.md) 的决策转换为稳定行为约定。

## 概览

新设备完成配对后，可能尚未认识同一 Space 中已被其他设备认识的设备。用户发起一次“刷新共享设备”后，核心向当前 Space 内可信的已配对设备查询这些缺失资料，并自行完成确认、保存和后续收敛。

这是一项设备关系刷新动作，不是剪贴板同步。调用成功只表示刷新已被接受，不表示所有设备都已经连接完成。

## 目标

- 用户只需发起一次刷新，不需要选择设备或编排内部步骤。
- 尽早告知发现、确认、连接和等待中的真实进展。
- 任何候选设备都必须经本机重新确认，确认成功后才成为已连接设备。
- 离线设备继续交由已有成员关系收敛机制处理，不要求用户重复操作。
- 对产品端公开的资料和错误保持最小且稳定。

## 非目标

- 不同步剪贴板、历史内容、文件或最新内容。
- 不重新发起配对，不要求邀请码、口令或逐台确认。
- 不提供设备选择、取消正在进行刷新或另一套后台队列。
- 不因 P2P 不可达自动切换到 LAN 兼容通道。
- 不维护独立于成员关系收敛的设备名单、可信关系或重试记录。

## 责任边界

| 范围 | 负责事项 |
| --- | --- |
| 核心公开入口 | 接受刷新、返回请求编号、提供当前请求状态并发送状态变化。 |
| 成员关系收敛 | 查询可信来源、分页接收资料、去重、确认候选、提升可信关系、保存离线候选和后续重试。 |
| 网络与绑定 | 传递经过认证的消息、操作结果和状态通知；不判断候选是否可信，也不编排流程。 |
| 产品端 | 发起一次刷新、显示状态；收到事件流滞后通知后重新查询当前状态。 |

成员关系收敛是完整流程的唯一负责人。产品端不得依次调用“查询设备”“确认设备”“保存关系”或“重试连接”等内部步骤来拼接流程。

## 发起与状态恢复

### 发起刷新

核心为每一次被接受的刷新分配请求编号。相同 Space 已有进行中的刷新时，后续请求返回原请求编号，不再启动第二轮查询。

一个请求只关联当前核心运行期的用户可见进度，不持久化为第二份设备名单。核心重启后，已经保存的候选和重试仍由既有成员关系收敛恢复；旧请求编号不再用于恢复界面。用户可重新发起刷新以取得新的进度。

### 会话恢复后自动查找

设备重启并自动解锁后，核心在会话恢复成功时自动发起一轮与手动刷新相同的已有设备查找，产品端无需任何界面操作。该自动触发由成员关系收敛运行期在解锁恢复完成时调度：

- 会话仍锁定时不会调度查找；解锁成功、身份和成员关系可读取后才开始。
- 一次恢复只启动一轮。重复解锁通知、就绪通知或并发调用被合并：进行中的一轮直接复用，刚完成的一轮在短冷却期内不再重启；锁定会重置自动调度，因此锁屏后再次解锁总是重新开始一轮。
- 已知来源设备暂时离线时，本轮如实结束并等待来源设备重新在线；来源上线事件会以同一语义继续完成发现，不要求用户手动触发，也不进入无限重试。
- 自动查找复用与手动刷新完全相同的查询、确认、保存和状态通知流程，不新增第二套发现逻辑，也不需要产品端保存查找队列或负责重试。

### 状态通知

状态通知至少包含：请求编号、阶段、稳定状态、设备数量，以及在有单台设备变化时所需的展示资料。发现候选时，资料按稳定顺序去重后给出。

产品端可展示的单台资料仅限：

- 稳定设备标识
- 设备名称
- 当前状态

事件流不能保证消费者永不滞后。产品端收到“需要刷新”通知后，必须查询该请求的当前完整状态，不能依据已错过的过程事件推断结果。

### 状态含义

| 范围 | 状态 | 含义 |
| --- | --- | --- |
| 请求 | 已开始 | 刷新已被接受，正在向可信来源查询。 |
| 设备 | 已发现 | 已从可信来源取得候选资料，尚未完成本机确认。 |
| 设备 | 确认中 | 正在直接确认候选的身份、Space 和准入状态。 |
| 设备 | 已连接 | 确认成功，已通过既有原子提升流程进入本机设备列表。 |
| 设备 | 已存在 | 设备本来已是当前 Space 的成员，不重复建立关系。 |
| 设备 | 等待上线 | 候选暂时不可达，已交由既有收敛机制后续处理。 |
| 设备 | 等待更新 | 候选需要等待已有安全或成员资料更新后才能继续确认。 |
| 设备 | 版本不兼容 | 候选无法使用当前成员资料协议。 |
| 设备 | 已拒绝 | 身份、Space、准入或资料校验未通过。 |
| 请求 | 本轮完成 | 本轮查询和即时确认已结束；结果包含各状态数量及仍在等待的数量。 |

“本轮完成”不表示所有候选均已连接。存在“等待上线”或“等待更新”时，核心继续使用原有机制推进，并以同一请求编号继续发送后续状态变化，直到核心重启或该候选进入终态。

## 资料查询与确认

刷新只向当前 Space 内已配对且仍可信的设备查询。来源返回的是候选资料，不能直接视为已建立关系。

查询与回复复用现有成员资料交接所使用的候选资料和认证边界。单条成员消息最多容纳 64 个设备或事件，因此来源必须按稳定游标分页回复；接收方按设备身份去重并稳定排序。Space 中设备数量超过单批上限时，不能静默遗漏后续设备。

收到候选后，核心必须直接与该候选重新确认：

1. 候选仍属于当前 Space，且来源和候选均处于准入状态。
2. 身份资料、签名和安全历史能够通过既有校验。
3. 设备版本和资料大小符合当前协议限制。

只有全部确认成功，核心才复用既有原子提升流程保存成员、可信关系和可连接资料。任何确认失败都不得把候选显示为“已连接”，也不得留下部分正式关系。

## 失败与后续处理

- 某个来源设备不可用、超时或拒绝查询时，其他来源继续处理；公开状态只反映稳定失败类别，不暴露底层原因。
- 候选离线时显示“等待上线”，不能误报为已连接。既有持久化候选和重试机制在其上线后继续确认。
- 已移除、不同 Space、身份不匹配、资料被篡改或版本不兼容的候选必须被拒绝，不能写入设备列表、可信关系或地址资料。
- 重复发起刷新不得产生重复查询、重复候选、重复成员或重复可信关系。

## 隐私与持久化

公开状态、错误和日志不得包含地址、身份指纹、签名、安全资料、底层网络错误原文或剪贴板内容。日志只记录请求编号、请求内的脱敏设备序号、阶段、数量、耗时和稳定失败类别。

本动作不新增明文持久化字段、临时明文文件或第二份设备名单。候选、成员、可信关系、地址和重试继续使用既有的加密持久化与原子提升流程。

## 验收场景

1. A 已与 C 建立关系，B 与 A 配对后刷新：B 先收到 C 的“已发现”，确认成功后收到“已连接”，且设备列表包含 C。
2. C 离线时：B 显示“等待上线”，不把 C 视为已连接；C 上线后由既有机制完成确认，不要求再次刷新。
3. 同一 Space 连续或并发发起刷新：所有调用返回同一进行中请求编号，且每个来源只被查询一次。
4. 已移除、不同 Space、被篡改或版本不兼容的候选：均不能进入设备列表，公开状态只给出稳定类别。
5. 公开结果、状态通知、日志与持久化：均不包含地址、身份指纹、安全资料或剪贴板内容。
6. 状态通知消费者滞后：产品端重新查询请求状态后，能取得与核心当前事实一致的完整结果。
7. 设备重启并自动解锁：无需任何界面操作即自动发现同一 Space 的其他设备，设备列表最终包含全部已确认成员；来源设备离线后再上线也能完成发现。
8. 一次恢复中的重复解锁、就绪和在线事件：不产生多轮并发查找。
