# Rust 编写规范

## 目标

Rust 修改应形成一个可独立验证的完整结果，同时让模块边界和名称来源容易阅读。本规范只保存 Rust 编写与交付规则；领域分层、错误、安全和观测规则仍分别由对应设计文档维护。

## 开工规划

修改前先根据任务规模写清以下内容。小改动可以只放在当前任务的完成标准中；跨层、新功能或恢复责任变化必须进入 active plan。

1. 谁拥有完整行为，调用方只做什么。
2. 成功、失败、取消和关闭分别得到什么结果。
3. 重试、重启恢复和持久状态由谁负责。
4. 哪个最小端到端切片可以先证明方向正确。
5. 用哪些实际检查证明完成，哪些平台或设备无法执行。

实现前检查已有依赖、相邻模块和成熟做法。只有现有能力确实不能满足需求时才增加依赖或抽象。

## 名称与路径

- 默认在模块入口通过 `use` 集中引入所需名称，正文使用最短且含义明确的名称。
- 函数签名、实现正文和普通类型实现中不得重复书写 `crate::` 完整路径。
- 同一来源的一组名称合并引入；不同职责的来源保持分组清楚。
- 只有出现真实同名冲突时才使用别名，别名表达职责，不使用无意义缩写。
- 不使用 glob 引入掩盖依赖来源；由成熟 prelude 或测试 DSL 明确提供的固定集合除外。

下列情况允许保留完整路径：

- 测试需要验证 crate 根公开入口；
- Rust 文档链接需要指向完整名称；
- 宏或语言限制无法通过普通引入表达；
- 同名冲突经别名仍会降低可读性。

生产代码中的局部例外必须在前一行写明具体理由：

```rust
// rust-style: allow-qualified-path -- 宏要求从 crate 根解析该名称
crate::generated_macro_entry!();
```

不得用“更清楚”“方便”或重复规则本身作为理由。

## 实现

- 先完成最小端到端切片，再增加已经证明必要的范围。
- 完整行为只有一个负责人；辅助模块提供能力，不把流程决定泄露给调用方。
- 生产代码不使用 `unwrap()`、`expect()`、`println!()` 或 `eprintln!()`。
- 下层失败保留原始来源，转换由拥有目标错误类型的层负责。
- 测试覆盖可观察行为、失败边界或真实回归，不机械复述实现。
- 修改过程中发现范围外问题时保留证据并单独处理，不顺手扩大当前变更。

## 交付

先运行直接受影响的测试，再执行根 `AGENTS.md` 中的交付检查。任何失败都要区分为本次回归、已有基线或环境阻塞；本次回归必须修复后重跑。

`scripts/architecture/check-rust-style.mjs` 检查相对基线新增的 Rust 行，也检查尚未纳入版本管理的新 Rust 文件。它不会要求一次性清理全部历史代码。CI 通过 `RUST_STYLE_BASE_SHA` 指定比较起点，本地默认比较当前 `HEAD` 与工作区。

自动检查只负责可以稳定判断的规则。模块责任、实现完整性和验证充分性仍需按本规范及相关设计文档审查。
