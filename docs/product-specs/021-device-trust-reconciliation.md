# 1. Overview

`v1.1.0-rc.1` 已经能够保存和核对签名成员历史，在其他设备提出移除时等待本机用户决定，并在
本机接受后采用同一变化、在本机拒绝后隔离分歧设备。它也能够公开待决定编号、移除目标、已分歧
设备、需升级设备和本机已被移除等基础事实。

但这些字段仍接近内部收敛状态，不能独立回答产品需要展示的完整问题：谁提出变化、两个选择分别
影响哪些设备关系、每台设备当前为何能或不能同步、用户现在能执行什么动作，以及一次决定究竟是
首次完成、重复完成还是已经过期。产品若直接使用现有字段，就必须自行拼接在线列表、成员列表和
多个内部集合，并推断结果，形成第二套成员关系规则。

本规格要求由现有 `WorkspaceConvergence` 继续负责完整结果。调用方只需读取一次当前设备信任状态、
对当前待决定项提交一个结果导向选择，并在收到变化提醒后重新读取完整状态。网络核对、事件验证、
排序、持久化、重启恢复、内容门禁和后台重试都不暴露给调用方。

# 2. Goals

- 一次查询足以在启动、重启、通知丢失或页面晚打开后恢复当前 Space 的完整产品事实。
- 由 Engine 从已验证成员历史解析移除的原始发起设备，不让产品根据消息转发者猜测。
- 对当前唯一可决定项同时返回移除目标、本机是否为目标和两个选择的设备关系影响。
- 按设备分别返回可达性、成员资格、设备组关系和版本兼容性，并提供一个可直接展示的同步关系结果。
- 用户决定只作用于查询中返回的当前变化；首次提交、相同重复提交和状态已变化具有稳定结果。
- 决定、关系和恢复进度均先加密保存再对外完成，应用退出、离线和 Engine 重启不丢失。
- 提醒只表示完整事实可能变化，产品不需要合并增量事件。
- 为恢复方向提供可评审的安全与数据边界，不在产品确认前锁定公开动作。
- 多设备验收以每个后续接收设备实际保存、应用和内容门禁结果为准。

# 3. Non-Goals

- 本轮不修改桌面端交互或兼容桌面端试接字段。
- 不引入账号、管理员、固定主设备、服务器仲裁、多数投票或自动选赢家。
- 不允许产品传入成员表、来源设备、影响范围、历史摘要或协议步骤。
- 不把在线、离线、超时、到达顺序、设备数量或版本号用作分支正确性的判断依据。
- 不自动合并不同设备组的成员历史或剪贴板历史，不补发分歧期间内容。
- 不改变 `v1.1.0-rc.1` 已发布产物或同名标签。
- 不承诺在产品确认前提供恢复共同设备组动作。

不足；**尚不可行**表示当前没有完整可执行能力；**依赖产品决定**表示技术可行但产品结果未确认。

| --- | --- | --- |

| 查询经过确认的原始发起设备 | 已有 | 从移除发生前的签名成员历史解析并由稳定结果返回，转发设备不参与判断。 |

| 查询应用变化后的关系影响 | 已有 | 完整结果返回本机可用、暂停和需重新加入的设备范围。 |

| 表达资料无法验证的相关设备 | 已有 | 局部无效关系和全局完整性失败都会暂停同步并返回稳定限制。 |
| 查询允许动作和不可执行原因 | 已有 | 当前变化、逐设备和全局结果均返回动作或稳定限制。 |
| 接受或保留当前设备组 | 已有 | 当前决定入口只接收待决定编号和选择，由完整负责人验证、签名、保存和传播。 |

| 重复提交返回稳定完成结果 | 已有 | 相同重复返回已完成，相反重复返回状态已变化，并跨重启保持。 |

| 完整替换式变化提醒 | 已有 | 当前变化事件携带完整快照，事件积压时要求重新读取。 |
| 所有产品事实变化均触发提醒 | 已有 | 成员权威状态保存后发出只带版本号的失效提醒，产品重新读取完整结果。 |

# 6. Proposed Design

## 6.1 Ownership and Interface

`WorkspaceConvergence` 继续拥有从已验证事实到产品结果的完整流程。调用方唯一需要执行：

- `query_device_trust()`：读取完整当前结果；
- `decide_device_trust_change(change_id, choice)`：决定当前变化；
- 订阅 `DeviceTrustChanged`，收到后重新读取完整结果。

恢复方向获批后，仍由同一负责人增加恢复预览和执行能力，不得新建并行负责人。若删除该模块，
来源解析、待决定排序、影响计算、关系组合、决定幂等、加密保存、重启续接和提醒判断都会重新散落
到产品端与多个层，说明它应继续承担完整职责。

## 6.2 Complete Query Result

建议在应用层定义产品视图，再由 `uc-engine` 转换为稳定类型：

```text
DeviceTrustSnapshot
  revision: u64
  local_device_id: DeviceId
  local_membership: DeviceMembership
  current_change: Option<DeviceTrustChange>
  devices: Vec<DeviceTrustRelationship>
  recovery: RecoveryAvailability
  allowed_actions: Vec<AllowedAction>
  updated_at_ms: i64
```

`revision` 只在产品可观察事实成功保存后递增，用于刷新去重和测试，不作为决定正确性依据。
`local_membership` 区分 `Active`、`Removed` 和 `Unavailable`。

当前变化同一时刻最多一个：

```text
DeviceTrustChange
  change_id: String
  kind: RemoveDevices
  proposed_by_device_id: DeviceId
  target_device_ids: Vec<DeviceId>
  includes_local_device: bool
  apply_impact: DeviceTrustImpact
  keep_current_impact: DeviceTrustImpact
  allowed_choices: Vec<DeviceTrustChoice>
  blocked_reason: Option<ActionUnavailableReason>
```

来源必须来自已验证事件的发起成员，并按事件发生前的成员历史解析。转发消息、当前连接或最先到达
的设备都不能替代它。无法解析时不返回部分待决定项，完整结果进入无法验证状态。

目标按稳定设备标识排序、去重，来自事件精确指向的成员实例，不能用当前名单差集推导。本机是否为
目标由负责人计算。

```text
DeviceTrustImpact
  relationships_remaining_usable: Vec<DevicePair>
  relationships_paused: Vec<PausedDevicePair>
  local_device_outcome: DeviceMembership
  requires_rejoin_device_ids: Vec<DeviceId>
```

影响范围只描述当前已验证事实可确定的关系，不预测离线设备未来会选择什么。“应用变化”按收到的
同一移除计算本机分支；“保留当前设备组”保持本机成员集合并暂停与已采用该变化的已确认关系。
不能确定的远端决定返回未知，不能声称仍可同步或必然暂停。

逐设备结果：

```text
DeviceTrustRelationship
  device_id: DeviceId
  display_name: String
  is_local: bool
  reachability: Reachability
  membership: DeviceMembership
  group_relationship: GroupRelationship
  compatibility: DeviceCompatibility
  sync_relationship: SyncRelationship
  available_actions: Vec<AllowedAction>
  blocked_reason: Option<ActionUnavailableReason>
```

设备名称来自 Engine 认可并加密保存的成员资料，不能从临时连接或转发消息取得。四个独立事实为：

- `reachability`：`Online`、`Offline`、`Unknown`；
- `membership`：`Active`、`Removed`、`Unknown`；
- `group_relationship`：`Consistent`、`PendingLocalDecision`、`Diverged`、`Unverifiable`、`Unknown`；
- `compatibility`：`Compatible`、`UpgradeRequired`、`Unknown`。

`sync_relationship` 是负责人基于上述事实和内容门禁给出的直接产品结果，至少包含：

- `Usable`
- `WaitingForLocalDecision`
- `PausedGroupDiverged`
- `PausedUpgradeRequired`
- `PausedUnverifiable`
- `RemovedLocalDevice`
- `RemovedPeerDevice`
- `Unknown`

选择直接结果的优先级为：本机已移除、对方已移除、资料无法验证、等待本机决定、设备组分歧、
版本过旧、正常可用、未知。在线或离线永不覆盖其他事实。

`AllowedAction` 至少包含应用当前变化、保留当前设备组、确认本机退出、重新加入、更新本机，以及
恢复能力正式实施后才出现的开始恢复预览。

`ActionUnavailableReason` 至少包含：无当前变化、变化已不是当前项、需要本机退出二次确认、本机已
移除、当前版本没有恢复、恢复方向未确认、对端需升级、资料无法验证、Engine 未解锁和 Engine 不可用。
禁止返回底层存储、签名、摘要、网络或协议错误原文。

## 6.3 User Decision

```text
decide_device_trust_change(change_id, choice) -> DeviceTrustDecisionResult

DeviceTrustChoice
  ApplyChange
  KeepCurrentDeviceGroup

DeviceTrustDecisionResult
  Applied { change_id, snapshot }
  KeptCurrentDeviceGroup { change_id, snapshot }
  AlreadyCompleted { change_id, completed_choice, snapshot }
  StateChanged { current_change_id: Option<String>, snapshot }
  LocalDeviceConfirmationRequired { change_id, snapshot }
```

行为规则：

1. 只有完整查询当前返回的编号可以首次决定。
2. 若应用变化会移除本机，首次应用不执行，只返回二次确认要求；确认后用同一编号和明确确认标记提交。
3. 首次完成先原子保存签名决定、成员结果、关系、门禁和最近完成记录，再返回结果与新快照。
4. 同一编号、同一选择重复提交返回 `AlreadyCompleted`，不生成新决定。
5. 同一编号、不同选择重复提交返回 `StateChanged`，不得改写已完成决定。
6. 编号不是当前项或当前历史位置已变化时返回 `StateChanged` 和最新快照。
7. 网络离线不阻止本机决定落盘；后续传播由负责人重试，决定完成不代表所有离线设备已采用。
8. 当前项完成后按成员历史因果顺序公开下一项，产品不得排序、合并或跳过。

为支持重启后的幂等结果，状态中保存有界的最近完成决定。至少保留当前成员历史仍可能引用的决定；
不能按短时间窗口清理。该记录与工作空间状态一起加密保存。

## 6.4 State Change Notification

稳定事件建议为 `DeviceTrustChanged { revision }`。它不携带需要产品合并的增量事实；产品收到后调用
完整查询。消费者落后时继续使用现有刷新要求。

待决定项出现、消失或切换，决定完成，设备组关系、版本兼容、成员资格、无法验证归属、允许动作
或限制原因发生变化时，成功保存后必须提醒。恢复实施后，恢复阶段变化也必须提醒。普通在线抖动
不能误报为成员关系变化。

## 6.5 Persistence and Privacy

- 成员事件、决定、最近完成记录、设备名、逐设备关系、无法验证归属、恢复计划和进度均按敏感业务
  数据处理，使用当前 Space MasterKey AEAD 保存。
- 可从权威状态确定性派生且无需跨重启保持的产品投影不重复落库。
- 数据库只允许不透明查找令牌、密文负载和不含业务内容的必要时间字段明文存在。
- 日志不得记录设备名、完整设备标识、成员实例、变化编号、关系图、签名、摘要、安全材料或内容。
- 分析只记录不含身份的稳定结果类别和耗时区间。

## 6.6 Recovery Feasibility and Boundary

### 技术可行性

从用户选择的可信设备建立新的共同设备组，再让其他可信设备重新加入，符合现有安全和离线约束，
前提是创建全新的 Space 沿革、MasterKey、安全组状态和成员实例，而不是合并旧分支或恢复旧资格。
现有 Space 切换已有分阶段迁移本地历史、重启续接和安装新准入资料的基础；现有重新加入也证明旧
移除不会命中新成员实例。这只是可行性结论，不代表当前版本已有恢复动作，也不替产品作决定。

### 设备处置

若产品确认该方向，预览必须逐台返回以下一种结果：

- `RecoveryAnchor`：用户当前操作且选择为恢复起点的可信设备；
- `RejoinRequired`：仍受信任但不在新组中的设备，需通过新邀请加入；
- `StopUsingOldGroup`：不再信任、已丢失、已出售或明确不保留的设备；
- `UnavailableForVerification`：资料不足，必须由用户处理或保持隔离。

在线、设备较多、更新时间较晚或版本较高都不能让设备自动成为恢复起点。

### 本地历史和分歧内容

- 恢复不能收回此前已披露给旧分支的内容。
- 不同分支的新内容不自动合并、不自动补发，也不作为新组成员资格依据。
- 恢复起点的可读历史若迁入新 Space，必须逐条解密并用新 MasterKey 重新加密；不可读记录必须在
  执行前给出数量和明确选择，不能静默丢弃。
- 其他设备的本地历史留在各自设备；加入新组不会上传或合并这些历史。
- 本机被移除后是否只读旧历史，取决于产品对旧 MasterKey 生命周期和访问许可的决定。

### 恢复能力形状

产品确认后应补充以下能力，当前不得发布：

```text
preview_device_group_recovery(anchor_device_id) -> RecoveryPreview
start_device_group_recovery(preview_id, confirmation) -> RecoveryResult
query_device_group_recovery() -> RecoveryStatus
```

预览绑定当前版本，列出设备处置、历史可迁移和不可读数量、分歧内容不合并说明及允许动作。状态变化
会使预览失效。恢复使用加密保存阶段：准备、本地历史处理、新组安装、旧关系退出、等待重新加入和
完成。重启从最后保存阶段继续，相同预览编号重复执行不创建第二个新组。

完成只表示恢复起点的新组已建立，且已完成加入的设备保存并应用相同新成员事实。未上线或未重新
加入的设备保持需重新加入，不能被计入完成。

### 恢复开放问题

1. 是否统一采用新设备组方案。
2. 是否允许旧分支无限期各自使用，以及提示是否持续存在。
3. 本机被移除后是否允许只读旧历史及旧密钥保留期限。
4. 恢复前逐台预览是否为强制步骤。
5. 哪些状态由产品宿主发送一次系统通知。

# 7. Implementation Plan

产品批准后，先完成不包含恢复策略的最小端到端产品结果，再单独实施经确认的恢复能力。

## Step 1: 领域产品事实

**位置**：`crates/uc-core/src/membership/`

补齐从当前已应用历史、待决定事件和对端关系确定性计算来源设备、精确目标、成员资格和关系影响的
领域结果。不能用当前成员表解析历史发起者，必须使用事件发生前的历史。

## Step 2: 完整产品视图和决定结果

**位置**：`crates/uc-application/src/space/convergence/`、`crates/uc-application/src/facade/`

由现有负责人聚合可信设备资料、可达性、成员资格、历史关系、兼容性、内容门禁和允许动作，并加入
最近完成决定的加密状态与稳定结果。查询必须是同一逻辑时点的自洽结果。

## Step 3: 稳定 Engine 契约

**位置**：`crates/uc-engine/src/contract/`、`crates/uc-engine/src/operations/device/member.rs`

增加完整查询、稳定决定结果和替换式提醒；只转换应用层产品视图，不重新计算规则。

## Step 4: 三个平台绑定

**位置**：`bindings/uc-engine-uniffi/`、`bindings/uc-ohos-napi/` 及移动验收宿主

iOS、Android、HarmonyOS 同版本完整透传查询、决定和提醒。任一平台省略字段都会迫使产品重新推断。

## Step 5: 多设备与重启验收

**位置**：`crates/uc-engine/tests/space_membership_auto_pairing_e2e.rs` 及绑定宿主测试

按第 9 节验证独立数据目录、真实保存、重启、双向内容门禁和稳定结果。操作返回或发送计数不能证明
接收设备已保存并应用。

## Step 6: 经批准的恢复能力

产品确认后另行细化，优先复用现有负责人和 Space 切换流程。先补规格和失败测试，再实现预览、执行、
重启续接和完成结果。恢复作为独立交付，不与完整查询字段扩展混成一次不可验证的大改动。

# 8. Edge Cases

| 场景 | 预期行为 |
| --- | --- |
| 没有 Space 或 Engine 未解锁 | 返回稳定不可用状态，不伪造空设备组。 |
| 同一移除重复到达 | 保持同一变化编号，不新增任务。 |
| 待决定期间收到后继增加 | 保存但不越过移除应用，仍只公开当前移除。 |
| 多项未确认移除 | 按因果历史只公开第一项，完成后再推进。 |
| 同一变化连续双击相同选择 | 第二次返回已完成。 |
| 同一变化先应用后提交保留 | 返回状态已变化，不改写决定。 |
| 查询后本机成员历史先变化 | 旧提交返回状态已变化和最新快照。 |
| 本机属于移除目标 | 首次应用只返回二次确认要求。 |
| 发起成员无法从事件前历史解析 | 进入资料无法验证，不返回猜测来源。 |
| 对端在线但设备组分歧 | 在线仍为在线，同步关系为分歧暂停。 |
| 对端离线但关系正常 | 离线只改变可达性，关系仍为可用。 |
| 连接超时或身份不明 | 不标记需要升级，不标记分歧。 |
| 已确认旧版本设备升级 | 清除升级暂停，重新核对后恢复关系。 |
| 保存失败 | 不发布新快照，不返回决定完成。 |
| 事件消费者积压 | 发出刷新要求，完整查询恢复事实。 |
| 状态密文损坏 | 返回无法验证或存储不可用，不删除或重建状态。 |
| 被移除设备重新加入 | 使用新成员实例，旧资格不复活。 |
| 恢复预览后事实变化 | 预览失效，必须重新预览。 |
| 恢复执行中断 | 从加密保存阶段续接，不创建第二个新组。 |

# 9. Multi-device Acceptance Matrix

所有场景使用独立 Engine 数据目录。涉及可同步时，发送唯一内容并在接收端读取持久记录；涉及暂停
时，在截止时间内确认接收端没有保存该内容。只观察发送成功、在线、配对、事件计数或单台快照不算通过。

| 编号 | 场景 | 设备步骤与接收端必须证明的结果 | 当前覆盖 |
| --- | --- | --- | --- |
| DTR-01 | 离线后应用变化 | A、B、C 一致；C 离线；A 移除 B；C 上线并应用。C 保存来源 A、目标 B 和决定；A/C 一致且双向实际到达；B 不再收到 A/C 新内容。 | 通过：新入口三设备场景验证来源、目标和决定收敛；离线恢复、双向实际到达和被移除设备阻断由既有真实场景组合证明。 |
| DTR-02 | 离线后保留当前组 | C 选择保留，仍认可旧组的 B 也保留。C/B 保存与 A 分歧；A 与 C/B 双向无新内容；B/C 双向实际到达；在线事实独立。 | 通过：真实三设备场景验证同分支双向到达、跨分支双向阻断；产品测试证明在线事实独立。 |
| DTR-03 | 并发不同决定 | B、C、D 对 A 的同一移除并发决定，至少一台应用、一台保留。每台保存自己的决定；同分支可同步，跨分支无接收。 | 通过：真实四设备场景验证各分支保存、分支内到达和跨分支阻断。 |
| DTR-04 | 待决定与决定后重启 | 第一次重启恢复相同编号、来源和影响；决定后第二次重启恢复完成结果与关系；重复提交返回已完成。 | 通过：真实三设备待决定重启保留同一编号；完成记录重建后相同重复返回已完成。 |
| DTR-05 | 版本过旧 | 当前版 A 与旧版 B 运行，B 后续原地升级。只在已认证旧版本证据后暂停；普通超时不触发；升级后双方保存兼容并双向收到内容。 | 跳过：当前环境未提供正式旧版程序和固定端口；版本暂停、普通超时不误判和升级清除规则由应用测试通过。 |
| DTR-06 | 本机被移除 | A 移除 C，C 明确应用并二次确认。C 保存本机已移除、停止分享并返回重新加入；新邀请加入后取得新资格并恢复内容。 | 通过：二次确认与本机移除结果测试通过；真实多设备重新加入取得新资格并恢复接收。 |
| DTR-07 | 资料无法验证 | 对连续性、签名、身份或摘要受控破坏。接收端不改成员集合、不收越权内容，返回相关设备无法验证和真实限制；重启保持。 | 通过：局部无效关系和全局完整性失败均返回无法验证、暂停同步和无可执行变化；加密状态重启测试通过。 |
| DTR-08 | 多项变化顺序 | C 离线期间产生两项需确认移除。每次只看到因果顺序中的一项；第一项保存后才出现第二项；旧编号不能作用于第二项。 | 通过：领域因果顺序与旧编号失效测试通过；真实三设备连续两项移除从第一项结果继续。 |
| DTR-09 | 决定重复与竞态 | 同一编号并发提交相同选择，再提交相反选择。只保存一个决定；相同选择均为完成；相反选择为状态已变化；重启后相同。 | 通过：并发同选择只产生一次首次完成；相同、相反与负责人重建后的结果均有直接测试。 |
| DTR-10 | 提醒丢失 | 状态变化时停止消费事件，随后重新订阅。一次完整查询恢复全部事实，不需要本地决定队列或增量回放。 | 通过：提醒仅使完整结果失效，积压发出刷新要求；完整查询和三端透传测试覆盖恢复所需全部字段。 |
| DTR-11 | 普通离线 | 一致设备短暂离线再上线。只改变在线事实，不出现决定、分歧、需升级或无法验证；上线后双向内容恢复。 | 通过：产品测试证明离线不改变一致、兼容和可用关系；既有真实离线恢复场景验证接收端内容到达。 |
| DTR-12 | 恢复共同设备组 | 方案获批后执行预览、中断、重启和重新加入。设备处置与预览一致；新组实际互传；未加入设备无新内容；分歧内容未自动合并。 | 依赖产品决定，当前不可执行 |

# 10. Testing Strategy

## Unit Tests

- 覆盖历史发起者后来被移除、同设备重新加入、消息由第三台设备转发，验证来源始终来自事件前历史。
- 对接受和保留计算关系影响，验证目标、本机结果和暂停关系稳定排序且不预测未知决定。
- 覆盖四个独立事实到直接同步结果的全部优先级组合。
- 覆盖当前决定、相同重复、相反重复、过期编号、本机退出二次确认和多项顺序推进。
- 覆盖无法解析来源、损坏状态和未知兼容性，保证不返回部分或猜测事实。

## Integration Tests

- 保存设备名、决定、关系和最近完成记录，重开数据库后完全恢复；扫描数据库、WAL、SHM 确认敏感
  标记没有明文出现。
- 验证保存成功后才提醒；保存失败不递增版本、不发布完成。
- 验证完整结果与内容发送、接收门禁使用同一关系事实。
- 验证 Engine、UniFFI、HarmonyOS 字段和枚举一致，未知值不会错误降级。

## Regression and Multi-device Tests

- 保留现有接受、拒绝、并发、重启、历史移除、重新加入和版本升级测试。
- 执行 DTR-01 至 DTR-11；恢复获批并实现后再执行 DTR-12。
- 测试前等待所有后续会使用的设备达到预期成员事实，不能用可发现或已连接代替准备完成。
- 每个测试记录各设备最终完整查询、接收端持久内容、未接收截止时间和重启结果。

# 12. Risks and Trade-offs

## Interface size

完整结果字段多于当前汇总，但它减少了每个产品重复理解的规则。外部只保留一个查询、一个决定和
一个提醒；逐设备状态是查询结果，不拆成多个步骤。

## Snapshot consistency

在线事实和加密成员状态来自不同来源。应用层必须先取得带版本的成员快照再附加可达性观察；可达性
变化可以导致刷新，但绝不能回写或改变成员关系判断。

## Idempotency retention

稳定重复结果要求保留最近完成决定。按固定天数清理可能让离线产品重试失去语义，因此应按成员历史
仍可引用的范围保留。成员变化频率低，少量加密状态增长可以接受。

## Recovery scope

复用现有 Space 切换能力能降低数据迁移风险，但恢复仍需要新预览和设备处置语义。直接把加入操作
暴露为恢复会让产品负责旧关系退出、历史处理和中断续接，因此不可采用。

## Compatibility

这是新增稳定契约，不改变旧字段含义。正式 Engine 和三个移动平台在同一交付中只公开完整设备信任
查询、决定和失效提醒；旧查询、旧决定和旧提醒不再进入产品构建。多设备测试仍可在明确开启诊断
能力时读取旧内部快照，但该能力不属于发布契约，也不能被产品使用。

三个移动平台透传同一份带版本的完整 JSON 结果，不在绑定中重复维护嵌套字段映射或重新计算关系。
验收宿主必须验证完整字段、未知字段可忽略以及提醒后重新读取；结果结构的演进仍受本规格约束。

# 13. Open Questions

## 产品必须确认

1. 是否采用选择可信设备建立全新共同设备组，再重新邀请，作为唯一恢复方向。
2. 是否允许多个分歧设备组无限期各自使用，以及是否持续建议恢复。
3. 新变化、本机被移除和首次确认需升级的系统通知范围是否按 PRD 草案执行。
4. 本机被移除后是否允许只读旧历史，以及旧 MasterKey 的保留和解锁边界。
5. 恢复前逐台设备处置预览是否为强制确认步骤。

## 实施前工程确认

1. 三个平台对新增嵌套结果和未知枚举的兼容策略，实施前需用验收宿主确认。
2. 最近完成决定的历史可达清理规则需用领域测试固定，不能退化为时间窗口。
