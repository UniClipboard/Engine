# 工作空间全局收敛

## 状态

已采纳，实施中（阶段 1-5 和旧实现清除已完成；阶段 6 多设备端到端验收待完成）。

本文定义 ADR-016 的稳定行为、唯一负责人、对外状态、交接规则和验收门槛。它描述目标
架构，不表示当前分散的成员资料投递、共享设备刷新和成员移除状态已经形成完整工作空间
收敛。

## 目标

- 任一当前有效设备只要重新可达，就能从本机已保存状态连续恢复到当前工作空间，而不依赖
  最初发起加入、移除或安全更新的设备仍在线。
- 成员加入、移除、重新加入、设备发现、资料交接、确认、重启恢复和完成判定由应用层一个
  负责人完成；产品端不拼接内部步骤。
- 只有全部当前有效设备已经保存同一连续安全状态，并建立彼此可用的可信关系后，才能向
  产品端报告完成。
- 所有持久化业务载荷保持加密；恢复交接不让陌生设备读取成员名单、地址、安全资料或业务
  内容。
- 正常加入、重新加入和恢复由实际事件立即推进；离线和连接中断只延后推进，不改变安全
  结果，也不触发 LAN 自动回退。

## 范围与取代关系

本文覆盖一个既有 Space 内的成员加入、成员移除、重新加入和由此产生的关系恢复。ADR-015
的离线意图合法性、移除优先合并和新成员实例规则仍然有效；本文明确取代 ADR-015 原先的
完整流程负责人、独立公开状态和完成判定。ADR-012 的已验证候选、直接证明和已共享设备发现
仍是可复用的内部能力。

下列原有职责在实施本文时合并到同一个流程，不再各自决定完成、持久化重试或对外状态：

- 成员关系收敛中的候选发现、资料补齐和可信关系提升；
- 配对成功后的成员资料交接；
- 成员移除后的安全资料投递、确认和恢复；
- 手动或解锁后共享设备刷新。

`RefreshSharedDevices`、`QuerySharedDeviceRefresh`、`SharedDeviceRefreshChanged`、
`QueryMembershipConvergence`、`QueryMemberRemoval` 和 `MemberRemovalChanged` 的独立对外
契约在实施完成时删除，不建立转换层、旧状态映射、旧队列或兼容入口。产品若保留“刷新”
按钮，只能查询当前工作空间状态；它不能直接驱动设备发现、网络发送或重试。

本文不定义：

- 固定协调设备、中心服务器、多数在线门槛或基于时间的排序；
- 对并发 OpenMLS 分叉直接合并；成员意图仍先按 ADR-015 得到统一目标，再向前形成安全状态；
- 让陌生设备通过恢复通道枚举设备、读取内容或取得当前工作空间资料；
- 从旧的分散队列、旧状态或旧持久化记录转换出新流程。发布前必须清除旧实现；发现未完成的
  旧记录时，核心只能给出稳定的不兼容结果或 `RecoveryRequired`，不得回退处理它；
- P2P 失败后的 LAN 自动切换。

## 术语

| 术语 | 含义 |
| --- | --- |
| 工作空间变化 | 一次成员加入、移除或重新加入被接受后形成的、可验证且连续的事实。 |
| 连续变化链 | 从接收方已保存的安全世代起，逐步到达当前目标的有序工作空间变化集合。 |
| 当前有效成员 | 经已验证变化和 ADR-015 移除优先规则计算后，仍属于当前目标的成员实例。 |
| 成员实例 | 一次准入形成的成员身份。同一物理设备重新加入时产生新实例。 |
| 交接设备 | 向落后设备转交连续变化链的设备；它可以不是原发起者，也不因此拥有成员决策权。 |
| 工作空间摘要 | 由空间沿革、当前有效成员和连续变化链得到的稳定摘要；重复、转交路径和到达顺序不改变它。 |
| 确认 | 接收方在本机完成验证、保存、应用和关系建立后，对对应摘要保存的可验证事实。 |

## 唯一负责人和调用方式

应用层的 `WorkspaceConvergence` 是工作空间收敛的唯一负责人。删除它会使资料保存、交接、
重试、完成判断和事件恢复重新散落到配对、移除、网络与产品调用方，因此这些职责必须由它
保持集中。

| 范围 | 负责事项 | 不负责事项 |
| --- | --- | --- |
| `WorkspaceConvergence` | 接受成员变化、构造和保存连续变化、合并合法移除意图、安排交接、验证接收、确认、重启恢复、当前状态和通知。 | 不把网络传输步骤暴露给产品端。 |
| `uc-core` | 成员实例、变化链、摘要、状态转换、验证结果和持久化/传输能力约定。 | 不创建网络连接或安排运行期。 |
| `uc-infra` | 加密持久化、P2P 受限通道、身份/地址证明和 OpenMLS 安全变化的具体适配。 | 不决定成员目标、完成或重试策略。 |
| `uc-engine` | 一次组装负责人、路由稳定入口和转发完整状态。 | 不分步编排加入、交接或移除。 |
| iOS、Android、HarmonyOS 绑定 | 公开同一操作、状态、错误和变化事件。 | 不维护本地队列、成员副本、重试或完成推断。 |
| 产品端 | 提交一次成员操作、查询状态、订阅变化和展示结果。 | 不选择交接设备、不发送资料、不筛选成员、不根据在线状态猜测完成。 |

调用方只有下列外部行为：

| 入口 | 输入 | 成功结果 | 稳定失败 |
| --- | --- | --- | --- |
| `JoinSpace` | 有效邀请或准入资料 | 本机准入、与发起方的最小关系、可接收会话和就绪记录已保存；返回本机当前工作空间状态。它只表示本机已准备接收，不表示发起方已保存工作空间变化或整体已收敛。 | 当前空间不允许准入、邀请无效、会话不可用或需要恢复。 |
| `RemoveMember` | 一个当前目标设备编号 | 移除意图、本机限制和新的工作空间变化已保存；返回当前完整状态。 | 本机或目标不在当前成员视图、当前空间不允许操作或需要恢复。 |
| `QueryWorkspaceConvergence` | 无 | 当前 Space 已保存的完整工作空间状态。 | 当前 Space 不可读或会话未就绪。 |
| `WorkspaceConvergenceChanged` | 订阅事件 | 与查询完全相同的完整状态。 | 不适用；消费者滞后后按通用规则重新查询。 |

重新加入仍使用 `JoinSpace`，但必须产生新成员实例。当前移除意图尚未收敛或状态为
`RecoveryRequired` 时不得开始新的准入；不能以换邀请、换发起设备或改走旧配对路径绕过该
判断。仍有效成员在 `Converging` 时可以继续提交合法移除；负责人合并意图并形成新的统一
目标，不要求用户等待上一轮网络传播。

加入方只能在本机关系、可接收会话和待确认就绪记录成功保存后返回 `JoinSpace`。它随即向
发起方发送“本机已准备接收”的就绪确认，但在收到发起方的“准入变化已保存”确认前，不能
接收或发送普通内容、不能对其他成员宣布关系可用，也不能把自身算入完成确认。发起方收到
就绪确认后，才在同一保存提交点写入加入变化和待交接记录，再回送该确认。发起方在此之前
终止时，加入方保留本机准备状态，重启后的发起方从已保存的准入会话重新取得或等待就绪确认；
不得生成第二个成员实例、误报完成或让未保存的变化参与内容收发。

## 对外状态

`QueryWorkspaceConvergence` 和 `WorkspaceConvergenceChanged` 共享同一种完整快照。快照至少
包含：

- `phase`：下表定义的稳定阶段；
- `revision`：只随成功持久化状态变化递增的不透明版本；
- `change_count`：已验证工作空间变化数量；
- `removal_intent_count`：已验证、尚用于计算当前目标的移除意图数量；它不等同于工作空间变化
  数量；
- `effective_member_count`：当前有效成员实例数量；
- `confirmed_member_count`：已确认当前摘要且关系可用的有效成员数量；
- `waiting_member_device_ids`：仅在 `WaitingForOfflineMember` 阶段出现的、当前确实阻塞收敛的
  非本机设备稳定标识列表；按标识稳定排序，其他阶段为空；
- `waiting_member_count`：`waiting_member_device_ids` 的长度；其他阶段为零；
- `convergence_digest`：当前工作空间摘要；尚未形成时为空；
- `removed`：本机当前成员实例是否已经观察到自己被移出；
- `updated_at_ms`：最近一次成功保存状态的时间；
- `failure_category`：可选的稳定类别，不含底层错误原文。

快照不得包含设备名称、成员实例、地址、在线名单、签名、密钥、安全变化正文、邀请资料、网络错误
原文或剪贴板内容。`waiting_member_device_ids` 是唯一例外：它只在等待阶段给出当前阻塞收敛的稳定
设备标识，设备卡片用其精确匹配条目；产品端不能再从在线状态、设备列表或缓存自行推断等待对象、
设备关系或完成结论。完整规则见[按设备精确公开收敛等待状态](019-device-specific-convergence-waiting-status.md)。

| 阶段 | 含义 | 必须满足的条件 |
| --- | --- | --- |
| `LocallyApplied` | 本机已保存一项成员变化及其本地安全效果，或加入方已保存最小关系、可接收会话和就绪记录，尚未证明其他有效成员已应用。 | 移除目标已停止从本机取得新内容；加入方尚未收到发起方“准入变化已保存”确认时，只能处理准入和恢复资料，不能参与普通内容收发或完成确认。 |
| `Converging` | 当前目标的连续变化正在交接、验证、应用或确认。 | 仍有可立即推进的工作，或尚未能归因为仅等待离线成员。 |
| `WaitingForOfflineMember` | 当前唯一未完成条件是一个或多个已知有效成员暂时不可达。 | 已保存待交接资料；其余可达成员已处理当前摘要。 |
| `Complete` | 整个当前工作空间已收敛。 | 每个当前有效成员已保存并应用同一摘要和连续安全状态，且所有需要的可信关系和可达资料已落盘。 |
| `RecoveryRequired` | 当前事实无法安全自动继续。 | 连续性、空间、身份或摘要无法验证；发现不可自动解决的分叉；或没有有效成员。 |

`Complete` 只针对当前已知的变化链和有效成员集合。新的合法变化、此前缺失但后来补齐的连续
变化，或新成员关系恢复失败，都会立即使旧完成结论失效，状态重新进入 `Converging` 或
`WaitingForOfflineMember`。发送成功、网络写入、配对返回、单台设备本地应用或等待一段时间
均不足以进入 `Complete`。

`RecoveryRequired` 停止自动推进。后续只能由用户明确选择可信设备创建独立的新 Space 或执行
已定义的人工恢复；这不是撤销、编辑或重新解释旧变化。

## 变化链和持久化

每个工作空间变化至少绑定以下事实：

- 空间沿革、前一安全世代和前一工作空间摘要；
- 变化标识、变化类型、目标安全世代和变化后的工作空间摘要；
- 可按序验证的安全变化；
- 新成员的已签名身份、成员实例、可达资料和直接证明所需资料，或移除/替换成员实例所需的
  可验证事实；
- 创建该变化所需的成员授权、签名和因果证明；
- 当前有效成员对该摘要的确认，以及尚未确认的有界交接进度。

成员实例、身份资料、地址、签名、因果证明、安全变化、确认和交接进度都属于敏感业务载荷，
必须在 SQLite、WAL、SHM、缓存和任何索引中经 MasterKey AEAD 加密。仅可为去重、范围限制和
查询保存经批准的随机标识、版本、计数、状态和时间；不得借此保存第二份明文设备名单。

持久化必须满足下列不变条件：

1. 变化、其本机安全效果和需要的交接事实在同一提交点保存。移除变化保存成功后，本机不能
   重新信任或向目标发送新内容；加入方先保存本机最小关系、可接收会话和就绪记录，发起方
   收到就绪确认后才保存加入变化和待交接事实。加入方收到“准入变化已保存”确认前，只能安全
   接收准入/恢复资料，不能参加普通内容收发。
2. 接收方只有在连续安全变化、身份资料、可信关系、地址和确认都成功保存后，才能回复确认。
   任一失败不得留下“已确认”或“已连接”的部分正式关系。
3. 变化和确认按 Space 严格隔离。空间切换、锁定或旧后台任务不得把来源空间资料写入当前
   Space，也不得改变当前 Space 的状态。
4. 重复变化、重复交接和重复确认必须幂等；重放不能推进世代、生成新成员实例或重新打开已被
   拒绝的资料。
5. 变化链可以压缩为独立可验证的检查点，但不能删除仍可能供落后有效成员恢复的中间连续性。
   普通清理不得把可验证的合法恢复变成无法判断。

## 受限恢复交接

工作空间恢复使用独立、版本化的受限 P2P 通道。它不复用“双方已经建立可信关系”才允许
处理的普通成员资料通道，因此落后设备可以从尚未认识的交接设备取得恢复所需资料；传输
来源不因而获得信任。具体通道标识由基础设施在实施阶段与协议版本一同固定。

该通道的业务载荷必须在 Iroh 的经身份认证加密连接之上，再使用应用层 AEAD 密封。请求方
声明自己已持有且能证明的历史 `Transport` 密钥编号；交接方只在它也保存同一经验证的连续
前驱资料时，使用该历史密钥以专用 HKDF 域派生本次交接密钥，并用仓库既有的
XChaCha20-Poly1305 能力密封消息。绝不使用“当前空间密钥”作为替代，也不因没有共同历史
密钥改发明文、转入 LAN 或猜测另一把密钥；仍在进行的受认证准入由配对协议继续处理，其他
情况只得到不泄露状态的拒绝或 `RecoveryRequired`。

每次派生都必须使用新的请求编号和双方随机数。AEAD 的附加认证数据必须包含经域分隔摘要的
协议版本、空间沿革、所选历史密钥编号和前驱世代、发送/接收成员实例与传输公钥、变化范围、
目标摘要、请求编号及单调回复编号。实现修订：密封信封的定长明文头携带绑定重建所需的版本、
空间指纹、历史密钥编号、请求/回复编号、变化范围、目标摘要与双成员实例，因为接收方在解密
前必须重建完整绑定（未知交接方场景下接收方无法从本地状态推导发送者实例）。该头部处于 Iroh
连接的身份认证加密之内，只暴露 32 字节随机实例标识与编号/摘要哈希，不携带设备资料、地址、
签名、安全变化或内容。请求编号、回复编号和已接受范围作为敏感交接进度加密持久化；重复编号、
错误方向、错误绑定或已消费编号一律拒绝。

交接方解开 `RecoveryRequest` 后，必须先验证连接身份、请求证明和请求方在所声明前驱状态的
成员实例，再按本机当前已验证变化链计算该实例是否仍是当前有效成员。历史证明只证明可以请求
受限验证，不能授权读取当前资料。实例不在当前有效集合时，交接方不得发送 `RecoveryOffer`、
成员资料、地址、安全变化、摘要、在线状态或暗示性的失败详情；该旧实例只可使用 ADR-015 的
移除通知和迟交历史意图入口。

该通道只允许有界的 `RecoveryRequest`、`RecoveryOffer`、`RecoveryAck` 和
`RecoveryReject`：

- `RecoveryRequest` 只携带空间沿革、请求方已保存的前驱摘要/安全世代、共同历史密钥编号、
  新请求编号和可由历史成员资料验证的请求证明；不能借请求枚举成员或探测当前状态；
- `RecoveryOffer` 只包含目标设备可从自身已保存状态连续应用的一段变化、必要的身份/证明资料
  和目标摘要。它必须声明连续起止范围、是否还有下一批和同一目标摘要；单条最多 64 个变化或
  安全事件，字节总量不得超过通道的既有消息上限；
- `RecoveryAck` 只确认已持久化的连续范围、已应用摘要、目标摘要和对应回复编号，不返回成员
  名单、在线状态、密钥或内容；
- `RecoveryReject` 只返回不泄露成员或状态的稳定类别，例如空间不符、范围越界、连续性缺失、
  身份不符、未获授权、摘要冲突或版本不兼容；
- 每个来源、目标和 Space 的并发数、缓存量与重试频率都必须有固定上限。超限、重复或格式
  错误的消息在入站边界拒绝，不创建长期任务。

接收一份 `RecoveryOffer` 时，负责人必须严格按以下顺序执行：

1. 检查外层范围、大小、协议版本、目标、空间沿革、请求/回复编号和 AEAD 绑定；解密失败、
   重放或错误绑定立即拒绝；
2. 检查变化数量、声明范围和本机已保存前驱是否精确相接；
3. 从本机当前已保存的安全状态验证变化链连续性，按顺序验证并应用每一个安全变化；
4. 只用更新后的已知成员资料验证交接设备的身份、签名、直接证明和新成员准入资料；
5. 在一个加密提交点保存成员、可信关系、地址、变化链、已消费编号、确认和当前快照；
6. 持久化成功后发送 `RecoveryAck`，并立即唤醒本机后续交接。

任何一步失败都不改变当前安全状态，不建立关系，也不产生确认。接收方不得跳过缺失变化，
不得用“最新结果”覆盖旧状态，不能以交接设备编号、网络路径、到达时间或重试次数决定哪个
结果可信。交接设备也不能通过本通道读取接收方的成员列表、业务内容或当前安全资料。

一台已跟上当前摘要的设备必须保存它能够证明的连续变化和确认。原始发起设备离线、重启或
永久不可达后，任何符合条件的在线设备都能继续向落后设备交接。待交接记录必须保存接收方、
已确认前驱范围、当前目标摘要和是否仍有下一批；收到中间范围的 `RecoveryAck` 后立即安排下一
连续批，交接设备可以改变。只有 `RecoveryAck` 确认已到达记录中的当前目标摘要时，才能清除
该接收方的完整待交接记录并把它计入完成；中间确认、旧目标确认或发送成功都不能清除记录。

## 运行时闭环

### 1. 加入

配对只完成准入，不能单独代表工作空间完成。加入方必须先保存发起方关系、恢复本机会话并
启动收敛运行期和待确认就绪记录，再在同一会话发送“本地关系已保存且可接收”的就绪确认。
此时 `JoinSpace` 只能返回本机已准备，不代表工作空间变化已保存。发起方收到确认后才由
`WorkspaceConvergence` 在同一保存提交点写入加入形成的工作空间变化和待交接事实，并回送
“准入变化已保存”确认。

发起方在保存前终止时，加入方保持本机准备状态，既不发送也不接收普通内容；发起方重启后从
准入会话取得或等待同一成员实例的就绪确认，再只保存一次变化。负责人保存变化后，由当前已
跟上状态的设备向所有尚未确认的有效成员交接连续资料。新加入设备先验证并应用连续变化，随后
确认其他当前成员；只有所有当前有效成员的关系与摘要满足完成条件，状态才变为 `Complete`。

### 2. 移除与连续移除

`RemoveMember` 继续按 ADR-015 创建、验证和合并不可变移除意图。负责人根据合法意图集合
计算当前有效成员集合，并从已经生效的状态向前形成下一份连续工作空间变化。不得拼接并发
OpenMLS 提交、按先后到达覆盖另一分支，或让网络层选择成员目标。

用户在 `Converging` 或 `WaitingForOfflineMember` 时提交的新合法移除意图会扩大意图集合、
使旧摘要和旧确认失效，并形成新的目标。被移除成员不参加新的完成确认，也不能通过普通成员
通道或恢复交接取得当前空间资料；它的历史迟交能力仍按 ADR-015 的受限入口处理。

### 3. 重新加入

被移除设备重新加入只能经新的 `JoinSpace` 准入，产生新的成员实例。旧实例的移除、确认和
交接记录只用于历史验证与去重，不能再次移除新实例、阻塞新实例完成或作为新实例的确认。

尚未完成的移除意图、旧邀请或 `RecoveryRequired` 不能被重新加入绕过。负责人在创建或兑换
邀请、处理准入和切换目标 Space 前给出唯一允许/拒绝决定；调用方不得从设备列表或旧事件
自行判断。

### 4. 事件和重启

新的变化、收到交接、收到确认、设备上线、会话恢复、加入方就绪确认和当前摘要发生变化都
必须立即唤醒负责人。正常加入、重新加入、连续交接和已知设备恢复不能依赖固定间隔扫描或
定时重试才能推进。

离线、连接中断和超时是异常恢复路径：负责人保存待交接事实，状态在只剩离线成员时进入
`WaitingForOfflineMember`，并在对应设备上线时立即继续。会话锁定时不处理交接；解锁恢复后
从同一份加密状态继续。进程终止、暂停或重启不得丢失已保存变化、确认或待交接资料，也不得
恢复已废弃的内存状态。

同一 Space 的状态转换和持久化决策必须串行化；网络发送和等待确认在提交点外进行。收到更
新的合法变化时，旧发送计划和旧确认不能覆盖新快照。产品端从不保存重试队列，也不以固定
睡眠、发送计数或网络写入结果宣布完成。

## 失败、安全与隐私

| 情形 | 必须行为 |
| --- | --- |
| 对方离线、连接中断或超时 | 保留已保存交接，等待对应上线事件；不撤销变化、不自动改走 LAN。 |
| 变化链断档 | 不越级应用；只通过带历史证明的 `RecoveryRequest` 向可达当前成员请求缺失连续段。无法取得时保持收敛或等待，无法验证时进入 `RecoveryRequired`。 |
| 没有共同可验证的历史 `Transport` 密钥 | 不发送恢复资料；仍在进行的受认证准入继续由配对协议处理，其余情况给出不泄露状态的拒绝或进入 `RecoveryRequired`，不使用当前密钥、明文或 LAN。 |
| 已被移除的旧成员实例请求恢复 | 交接方在发送任何 `RecoveryOffer` 前按当前有效成员集合拒绝；不返回当前成员、地址、安全变化、摘要、在线状态或区别性错误。旧实例只使用移除通知和迟交历史意图入口。 |
| 跨空间、伪造、身份不匹配、摘要冲突或版本不兼容 | 拒绝该交接，当前状态不变；只发布稳定失败类别。 |
| 中间批次确认、交接设备切换或收到更高目标摘要 | 保留确认范围和目标；从精确下一前驱继续。只有确认当前目标摘要才清除待交接记录，旧目标确认不得结束新目标。 |
| 收到新合法变化 | 使旧完成结论失效，从已生效状态向前形成新摘要；不恢复旧密钥或旧成员实例。 |
| 有效成员集合为空或没有可验证基准 | 进入 `RecoveryRequired`；不自动挑选幸存者、生成替代状态或重新信任旧成员。 |
| 事件消费者滞后 | 发送通用刷新要求；消费者调用 `QueryWorkspaceConvergence` 读取一份完整当前事实。 |
| 日志和观测 | 只记录脱敏流程标识、阶段、计数、耗时和稳定失败类别；不得记录设备名、设备编号、地址、签名、密钥、安全资料、文件名、路径或内容。 |

## 实施顺序

每个阶段的完成条件未满足前不得进入下一阶段，也不得提前公开新对外状态。

| 阶段 | 负责方 | 必须完成的工作 | 阶段完成条件 |
| --- | --- | --- | --- |
| 1. 前置验证 | 安全实现与独立验证 | 证明连续安全变化可由非发起设备转交，落后成员能独立验证、按序应用并导出与当前成员相同的安全状态。 | 覆盖三设备中发起设备离线后的转交；断档和分叉不能被直接应用。 |
| 2. 核心模型和密文保存 | `uc-core`、持久化实现 | 定义工作空间变化、摘要、确认、状态转换和独立可验证检查点；以加密事务保存本机效果与交接事实。 | 故障注入覆盖提交点两侧；重复、重放、空间切换和重启不改变已保存事实。 |
| 3. 统一负责人 | `uc-application` | 以 `WorkspaceConvergence` 接管加入、移除、重新加入、发现、交接、确认、状态和生命周期恢复。 | 调用方只经成员操作、查询和订阅得到完整结果；没有独立后台决定完成。 |
| 4. 受限交接与运行期 | P2P 适配和应用层 | 实现受限恢复通道、大小/并发限制、连续验证、确认、上线唤醒和断线恢复。 | 未认识的交接设备只能转交可验证连续资料；接收成功后关系和确认原子落盘。 |
| 5. 稳定接口和绑定 | `uc-engine` 与三端绑定 | 公开统一快照、稳定失败和变化事件；删除旧查询、旧事件、旧刷新入口和映射。 | iOS、Android、HarmonyOS 只暴露新契约；仓库不存在旧状态转换、旧队列或产品端重试编排。 |
| 6. 端到端验收与发布 | 测试宿主、发布流程 | 按下列矩阵执行独立进程、真实离线、重启和跨端验证。 | 每项有可复查的接收端证据；未执行设备项明确写为“跳过”。 |

## 验收总则

- 每台设备使用独立进程、独立身份和独立持久化目录。
- “离线”必须同时断开设备间直连、中继和变化转发，不能只暂停后台任务。
- “重启”必须销毁原进程，再从原磁盘状态启动新进程。
- 所有完成结论以接收端实际保存的成员关系、当前摘要和双向内容接收为准；发送端返回、发送
  次数、网络写入和固定等待时间不是证据。
- 交接的上线顺序至少随机重复，验证重复、乱序和不同转交设备不会改变最终摘要。
- 设备矩阵中未执行的 Android、iOS 或 HarmonyOS 项必须标记“跳过”，不得标记“通过”。

## 验收场景矩阵

| 编号 | 场景 | 预期结果 | 必须观察到的证据 |
| --- | --- | --- | --- |
| W01 | A/B 已可用，A 离线；B 准入 C 后离线；C 与重新上线的 A 相遇。 | A 先验证并应用 B 签发的连续变化，再与 C 恢复关系。 | A、C 保存同一摘要并完成双向内容接收；不要求 B 重新上线。 |
| W02 | 四台设备中两个早期发起设备相继离线，剩余在线设备继续准入最新设备；最早设备随后恢复。 | 在线交接设备让最早设备与最新设备恢复。 | 所有恢复设备的关系和摘要一致；最早设备与最新设备双向内容接收。 |
| W03 | 五台设备连续移除两台，分别由不同保留设备重新准入。 | 五台新旧实例按当前目标重新形成完整工作空间。 | 每个当前实例均看到其他当前实例；跨多对设备双向内容接收。 |
| W04 | `Converging` 时再提交合法移除。 | 旧摘要失效，合法意图合并为唯一新目标。 | 不出现并行安全状态；所有保留成员最终确认同一新摘要。 |
| W05 | 重新加入后重放旧移除、旧确认或旧交接。 | 新成员实例不受旧实例事实影响。 | 新实例可接收当前内容；重放不改变成员集合、摘要或世代。 |
| W06 | 交接含断档、伪造、跨空间、身份不符、摘要冲突、错误 AEAD 绑定、重放或过大批次。 | 全部拒绝且当前状态不变。 | 没有成员、可信关系、地址、确认或安全状态的部分写入。 |
| W07 | 在保存变化、应用接收、发送确认和通知前后分别终止进程。 | 重启从最后一个已保存事实继续。 | 变化标识、摘要和本机限制不倒退；不依赖曾经发送的事件。 |
| W08 | 产品端错过多个状态事件或事件流滞后。 | 一次查询恢复完整事实。 | 查询快照与核心当前快照一致；产品端无需拼接旧事件。 |
| W09 | 全部加入、移除、交接、确认和恢复路径。 | 敏感资料始终加密且日志已脱敏。 | SQLite/WAL/SHM/缓存/索引和日志扫描均无设备资料、签名、密钥、地址、文件名、路径或内容原文。 |
| W10 | 同一场景在 iOS、Android 和 HarmonyOS 绑定查询与订阅。 | 三端公开的状态、错误和事件一致。 | 平台契约测试和已执行的设备结果可复查；未执行项标记“跳过”。 |
| W11 | P2P 恢复失败或所有待确认成员暂时离线。 | 保留 `WaitingForOfflineMember` 或进入稳定失败，不走 LAN。 | 未观察到 LAN 自动请求；上线事件后由负责人继续。 |
| W12 | 删除检查。 | 旧的分散投递、独立刷新和成员移除状态不存在。 | 全仓库搜索、接口检查和产品调用检查均只剩统一工作空间契约。 |
| W13 | 加入方发送就绪确认后，发起方在保存加入变化前终止；随后双方分别重启并重连。 | 加入方只保持本机准备状态；发起方只保存一次加入变化后才允许普通内容收发。 | 没有第二成员实例、重复变化或提前内容收发；最终保存一个摘要并完成双向内容接收。 |
| W14 | 已被移除的旧成员实例带正确历史证明和共同历史密钥请求恢复。 | 不得到 `RecoveryOffer` 或任何当前资料。 | 只观察到不泄露状态的拒绝；当前成员、地址、安全变化、摘要和在线状态均未离开交接方。 |
| W15 | 捕获、篡改、跨空间重放或以错误成员实例/传输身份重放恢复密封消息。 | 密封消息不能被解开、验证或应用。 | AEAD、请求编号和绑定检查均拒绝；没有持久化副作用或关系创建。 |
| W16 | 某设备缺失超过单批上限的连续变化；中途重启并由另一台已跟上设备继续交接。 | 每批精确连续，最终到达当前目标摘要。 | 中间确认不清除待交接记录；最终确认后才进入完成判定，并验证恢复设备双向内容接收。 |
| W17 | 三台设备中仅一个当前有效未确认成员离线，随后重新可达、移除和以新实例重新加入。 | 只在等待阶段精确公开该设备；重新可达、移除或切换为新实例后旧标识立即消失。 | 查询与事件给出同一稳定名单和相同数量；不标记非阻塞离线设备、本机或旧实例。 |

## 当前证据边界

工作空间负责人、加密变化链、受限恢复通道和统一公开状态已经落地。恢复交接全链路已接通：
已跟上成员主动向未确认成员交接、落后成员按轮转向已知成员请求、确认由本机签名产生并经普通
成员通道广播、交接方以 Ack 把接收方计入完成；受限通道收发两侧接入应用层 AEAD（信封明文头
携带绑定重建字段，见"受限恢复交接"的实现修订）；未知交接方被允许建立连接，由密封、空间
指纹与变化链验证把关；接收方应用交接变化时在同一提交点保存成员资料、可信关系与地址；
加入产生的 OpenMLS 组更新经变化链携带并在恢复时应用；sponsor 重启后从已保存准入记录重新
等待同一加入方就绪；运行期关闭不被网络交换阻塞；被移除设备以新实例重新加入时丢弃旧实例
本地链与移除事实。

已执行端到端验收：W01（B 离线后 C 向重新上线的 A 转交，双向内容收发）、W02（四台设备两个
发起方离线的中继恢复）、B 重启后与新增成员收敛、三设备移除收敛、连续移除、离线剪贴板投递
与稳定加入路由均通过。加入前置同步已实现：发起加入的 sponsor 在保存准入变化前先向已知成员
拉齐本地链头（尽力而为、有界），避免在旧链头追加形成分叉；组更新应用对"已到达或超过该
代次"的更新幂等跳过，后加入者应用历史变化链时不会因旧更新乱序而失败。未通过/未执行：
W03（五台设备从不同保留 sponsor 连续重新加入）的传播在多设备旧 Offer 拒绝循环下慢于 60 秒
测试窗口，传播最终可完成但窗口内不稳定；W04-W16 其余场景与 Android/iOS/HarmonyOS 设备
矩阵未执行。在 W03 稳定通过与设备矩阵执行前，不能报告工作空间全局收敛完成。
