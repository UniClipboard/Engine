# 配对作为工作空间准入通道

## 状态

- **状态**：配对通道私有化已实施；单一事务负责人、成员历史证明和准入激活待按规格 023 实施
- **日期**：2026-08-10
- **修订**：2026-08-15，删除已被 ADR-020 取代的 OpenRaft、多数、learner、`LogId` 和最终成员配置方案
- **实现依据**：[规格 023：可持续验证的成员历史与准入激活](023-durable-membership-proof-and-admission-activation.md)

本文只定义一个稳定边界：配对是 `WorkspaceConvergence` 内部使用的受限通信通道，不是成员加入的
第二个流程负责人。历史验证材料、候选准备、正式提交、激活门禁、恢复、迁移和验收全部由规格 023
定义，本文不再保存另一份流程。

## 概述

成员加入是工作空间变化，不是独立完成的配对结果。邀请、口令和双方身份验证只能证明本次通信可以
继续，不能单独产生成员资格、普通内容权限或“加入成功”。

`WorkspaceConvergence` 从一次加入请求负责到明确结果。配对只验证和传递负责人指定的准入资料；它
不保存正式成员变化，不决定候选，不宣布成功，也不负责断网或重启后的完整恢复。

ADR-020 继续定义当前分支、离线设备、移除决定和分叉。规格 023 继续定义旧作者如何长期验证，以及
候选何时成为可参与普通运行的正式成员。规格 022 继续定义普通运行范围。

## 目标

- 产品端正常流程只创建邀请或调用一次 `JoinSpace`；后续只通过现有 `QueryDeviceTrust` 查询、
  `CancelJoinSpace(join_id)` 请求取消，或把快照候选交给现有 `RemoveMember(device_id)`，不接触内部握手
  和确认顺序。
- `WorkspaceConvergence` 是邀请许可、成员准入、持久恢复和最终结果的唯一负责人。规格 023 实施后，它的
  应用运行期随 profile 常驻，即使没有活动 Space 也完整构造；活动 Space 只是零或一个完整上下文，
  `uc-engine` 不接管准入步骤或状态。
- 配对通道只传完成本次身份验证和准入所需的有界资料，不传普通内容或无关成员资料。
- 配对连接消失不丢失已经持久化的准入尝试，也不要求产品重新拼接步骤。
- P2P 失败保持等待，不自动切换 LAN 兼容线。

## 非目标

- 不在本文定义成员事件格式、历史验证算法、激活证明、迁移检查点或消息状态机；统一见规格 023。
- 不在本文定义远端移除的接受、拒绝和分叉；统一见 ADR-020。
- 不在本文定义当前成员如何进入设备列表、在线、内容和恢复范围；统一见规格 022。
- 不把配对实现扩展成工作空间状态机，也不让工作空间负责人拥有底层拨号、报文编解码和密码握手细节。
- 不引入投票、多数、固定主设备或服务器排序。

## 唯一负责人与职责边界

| 范围 | 负责事项 | 不负责事项 |
| --- | --- | --- |
| `WorkspaceConvergence` | 邀请许可、当前分支预检、唯一准入尝试、候选、正式成员事实、激活、拒绝、恢复、状态和通知 | 底层拨号、报文编解码和密码握手实现 |
| 配对通道 | 验证邀请码、口令、双方身份和能力；建立受限会话；传递负责人指定的版本化准入消息 | 决定成员资格、写成员历史、开放普通权限、创建重试或宣布成功 |
| 准入续接通道 | 重新认证并恢复同一持久尝试；重放负责人已保存的下一消息 | 创建新候选、读取普通成员目录、内容或不受限历史 |
| `uc-core` | 准入和成员历史业务规则、稳定状态和值对象 | 网络、SQLite 或 OpenMLS 具体实现 |
| `uc-infra` | 已认证 P2P、密码握手、加密存储和安全状态能力 | 决定何时提交、何时 Active 或如何映射产品结果 |
| `uc-engine` 与绑定 | 公开一次加入和完整状态查询，统一映射少量结果 | 暴露候选、分页、暂存、确认或恢复步骤 |
| 产品端 | 创建邀请、提交一次加入、查询状态和展示结果 | 根据配对、在线或网络发送状态推断成员资格 |

删除检查：如果删除 `WorkspaceConvergence`，候选、提交、激活、门禁和恢复会重新散落到配对、空间切换
和产品端，说明这些知识必须由负责人隐藏。配对不能通过增加同名步骤接口成为平行负责人。

## 对外入口与结果

稳定产品入口固定为：

```text
IssueInvitation -> IssuedInvitation
JoinSpace -> Active | Pending | Rejected
CancelJoinSpace(join_id) -> Active | Pending | Rejected
RemoveMember(device_id) -> 现有成员移除结果
QueryDeviceTrust -> 含 current_join 和 pending_inbound_member 的完整快照
DeviceTrustChanged { revision } -> 重新查询提醒
```

`DeviceTrustSnapshot.revision` 在同一 profile 内跨 Space 单调递增。相同或更小 revision 不覆盖已查询
结果；消费者收到更新 revision 或 `RefreshRequired` 时重新查询，不能让晚到提醒覆盖更新结果。
`QueryWorkspaceConvergence` 及其变化事件继续只用于 dev-tools 诊断，不是产品准入接口。

`Active`、`Pending` 和 `Rejected` 的精确定义与兼容迁移见规格 023。握手完成、对端可达、本机准备完成、
发起方已保存、消息已发送或同步调用超时都不能单独解释为 Active。

`Pending` 由 Engine 跨重启继续，不公开内部阶段。Sponsor 复用现有 RemoveMember 处理快照里的候选：
正式提交前不产生 AddDevice，正式提交后保留完整 Add/Remove。存储损坏或恢复失败仍是 Engine 错误，
不能伪装成普通拒绝。

## 配对通道规则

配对允许交换：

- 一次性邀请码、口令挑战和证明；
- 双方当前会话身份、能力和新鲜随机数；
- 加入方本次准入凭据、KeyPackage 和受保护恢复材料；
- 规格 023 定义的版本化 Candidate、Prepared、Commit、Applied、Complete 业务消息，以及
  CancelRequested、Rejected、普通 DeliveryAck、RejectedAck 和 CompleteAck 控制消息；
- 完成本次历史验证所需的有界连续页、凭据和精确摘要。

配对不得交换：

- 普通剪贴板内容、文件、完整成员地址目录或在线状态；
- 与本次候选无关的密钥、身份资料或恢复记录；
- 未经负责人验证和版本检查的持久业务负载；
- 能绕过成员历史或激活门禁的“配对成功”声明。

配对适配器只验证线路身份、消息版本、类型、大小和会话绑定，再把消息交给负责人。它不解释历史、
安全摘要或产品结果。未知版本、错误会话、跨 Space、超大、重复或乱序消息按规格 023 交由负责人幂等
处理或稳定拒绝。

## 邀请、会话与恢复

- 邀请绑定创建时的当前分支位置，一次只能由一个加入方消费；过期、取消、已消费或基础历史变化后失效。
- 邀请和内存会话不是成员资格，也不是恢复依据。外部渠道留下的邀请码不能恢复旧权限。
- 初次验证形成持久准入尝试后，连接中断通过独立准入续接通道恢复同一尝试；不能复活旧会话或创建第二
  成员实例。
- 同一 profile 同时只占用一个准入槽，不区分本机加入或为另一设备发起；非终态、共享写前恢复、Space
  切换或改变活动世代的清理结束后释放；业务终态后隔离的消息重发与压缩继续恢复但不占槽。远端入站竞争失败时返回 AdmissionUnavailable 并保持 Pending，
  本机第二次 JoinSpace 返回冲突；两者都不形成 Rejected，不能让 Cross-Space 切换遗弃原 Space 的尝试。
- 负责人在每次网络回复前先加密保存阶段和待发消息。重启从持久状态继续，不要求产品重新提交内部步骤。
- 正式提交前可以稳定拒绝并放弃暂存状态；正式提交后只向前交付同一事件和确认，具体边界见规格 023。
- CancelJoinSpace 只请求正式提交前拒绝；提交先保存时取消已经太晚，同一尝试继续到 Active，不自动追加
  成员移除。用户仍要退出时从另一台当前成员设备另行使用现有明确移除流程。

## 安全与隐私

- 配对、续接和准入网络消息必须分别版本化、认证并设固定大小上限；未知版本不降级到旧协议。
- 准入尝试、身份绑定、候选、历史页、凭据、签名、安全资料、确认和 outbox 都按敏感业务负载处理，
  经 MasterKey AEAD 加密保存。Fresh J0 尚无目标 Space MasterKey 时，先使用系统安全存储保护的 profile
  admission MasterKey，并由它包裹单次尝试数据 key；目标状态取得 Space MasterKey 后按目标 Space 和世代
  显式加密暂存，终态先重封装到 profile key 才清临时 key。
- 日志只记录脱敏尝试标识、稳定阶段、重试次数和失败类别；不得记录邀请码、口令、设备名、设备标识
  原文、地址、公钥、签名、密钥、安全材料、文件名、路径或内容。
- 候选在规格 023 的激活门禁解除前，不能使用 Presence、邀请、成员公告、普通历史、内容、文件、活动
  状态或补送通道。
- P2P 暂时失败只保持 Pending，不自动进入 LAN。

## 实施与证据边界

ADR-017 已实施的部分仅是：配对不再作为对外独立成功流程，成员变化和后续核对由工作空间负责人承接。
单一事务负责人、无 Space 常驻恢复和完整准入状态机尚未实施，不能把局部私有化称为完整职责收口。

截至本次修订，配对已经是应用内部通道，但仍通过逐步 `WorkspaceAdmissionOwnerPort` 在赎回、发起方
编排和空间切换之间推进状态；规格 023 的完整职责收口尚未实施。当前代码仍存在以下缺口：

- V1 AddDevice 没有永久保存历史验签公钥，旧事件验证仍依赖当前 OpenMLS 成员树；
- 发起方先正式保存新增，加入方之后才完成完整历史核对和安全安装；
- Engine 和全部绑定尚未统一提供 Active、Pending、Rejected 结果。

因此，现有配对或成员测试通过不能证明规格 023 已交付。只有规格 023 的验收清单、故障矩阵、迁移
夹具和跨平台结果全部满足后，才能把成员历史证明与准入激活标记为已实施。
