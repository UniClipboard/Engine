# 配对作为工作空间准入通道

## 状态

已采纳，实施中（阶段 1-5 已完成；阶段 6 的多设备端到端验收待完成）。

本文定义 ADR-017 的稳定行为：成员加入是工作空间变化，由 `WorkspaceConvergence` 完整
负责；配对是工作空间准入实现内部使用的私有通信通道，不再作为独立的应用层流程负责人。
本文描述目标架构；当前配对流程仍保存部分加入状态、直接驱动旧成员收敛补送并自行宣布
成功，这些路径在实施本文时删除，不保留兼容入口或并行实现。

## 概述

本文只定义准入这一段：谁推进加入、通过什么内部通道完成、什么被持久化、失败后由谁
恢复。工作空间收敛本身（连续变化链、交接、确认、阶段、完成判定、受限恢复通道）仍由
[工作空间全局收敛](016-workspace-wide-convergence.md)定义，本文只引用不重复。

一次加入从产品端视角只有两步：创建邀请、加入工作空间。中间的一切（握手、验证、就绪
确认、成员变化保存、后续交接与恢复）由 Engine 内部完成。加入成功不是配对握手的结果，
而是工作空间已经保存该成员变化的事实；配对握手结束既不产生成功事件，也不单独构成
成员资格。

## 目标

- 成员加入、重新加入与因此产生的关系恢复由工作空间收敛负责人完整负责，产品端只提交
  一次加入操作、查询状态和订阅变化。
- 配对只完成邀请验证、身份验证、受限会话和准入安全材料传递，不保存成员加入、不决定
  推进、不宣布成功、不定义重启后的恢复。
- 不存在“配对成功但成员尚未正式加入”的可观察中间状态；加入成功必须有已保存的工作
  空间成员变化。
- 配对会话和邀请都不是持久事实；进程中断后只依据已保存的成员变化与准入记录恢复，
  未保存加入变化的未完成会话不产生成员资格。
- 工作空间负责人不因此掌握底层拨号、报文编解码或密码握手细节；通信替换、测试和协议
  演进局限在内部适配位置。
- 不因 P2P 失败自动切换到 LAN。

## 范围与取代关系

本文取代配对作为独立应用层流程负责人的角色，以及“配对成功”作为对外结果的表达。本文
不改变 ADR-016 已定义的工作空间收敛语义；本文只定义准入这一段由谁推进、通过什么内部
通道完成。

下列原有职责在实施本文时删除或收回，不建立转换层、旧状态映射或兼容入口：

- 配对流程直接保存成员实例、信任记录、设备地址和本机已设置状态；
- 配对流程直接唤醒旧成员收敛、保存种子或启动已有成员资料补送；
- 配对流程持有的可选工作空间负责人依赖及“不可用即失败”的绕过路径；
- 配对流程自行宣布成功的结果与订阅（`subscribe_pairing_completion`、
  `PairingCompleted` 事件、配对成功分析事件，以及仅开发环境保留的结果流）；
- 空间切换流程作为平行入口自行编排配对握手。

本文不定义：

- 底层拨号、报文编解码和密码握手的实现细节；
- 工作空间收敛的交接、确认和完成判定本身（由规格 016 定义）；
- 受限恢复交接通道（`workspace-recovery/1`，由规格 016 定义）；
- 移除意图的合法性、合并与旧实例限制（由规格 015 定义）；
- LAN 兼容线的行为；P2P 失败不自动切换。

## 术语

| 术语 | 含义 |
| --- | --- |
| 加入成功 | 工作空间层面的结果：新设备与发起设备都已保存加入所需的本地事实，且工作空间已经保存该成员变化。它不表示所有既有成员已经恢复可用；后者仍由规格 016 的完整工作空间状态表达。 |
| 本机已准备 | 加入方已保存本机准备事实（与发起方的最小关系、可接收会话和待确认就绪记录），只能安全接收准入与恢复资料，尚不能参与普通内容收发或完成确认。 |
| 本机准备事实 | 加入方在本机加密保存的一组事实：发起方成员实例与其传输公钥、可接收会话、待确认就绪记录。它是“已保存的加入所需本地事实”在加入方侧的最小集合。 |
| 发起方准入记录 | 发起方在进入就绪等待前加密保存的进行中准入记录：会话标识、加入方标识、当前准入代数、待取得就绪确认的标记。发起方重启后据此重新取得或等待同一成员实例的就绪确认。 |
| 就绪确认 | 加入方在保存本机准备事实后向发起方回复的“本机已准备接收”确认，由配对通道承载并交还工作空间负责人。 |
| 准入变化已保存确认 | 发起方在同一保存提交点写入加入变化和待交接事实后向加入方回复的确认。加入方收到它之前不参加普通内容收发。 |
| 配对会话 | 一次加入尝试期间建立的受限通信会话；只存在于内存，不是持久事实。 |
| 邀请 | 创建邀请动作产生的准入凭证；只存在于内存，不是本地持久事实。 |
| 准入代数 | 创建邀请时绑定、由已验证移除意图数量推进的编号；代数推进后旧邀请失效，不能在收敛完成后恢复旧权限。 |
| 准入安全材料 | 完成验证和准入所需的安全载荷：MLS KeyPackage、KDF 参数、挑战、证明材料、MLS welcome、加密密钥目录、安全世代和已签名就绪事实。 |
| 工作空间决定 | 工作空间负责人对加入的接受、拒绝或会话关闭要求；配对通道只执行该决定，不自行生成。 |
| 适配位置 | 工作空间负责人与配对通道之间的私有内部接缝：工作空间经它请求验证加入者、发送工作空间决定，不接触通信实现。 |

| --- | --- | --- |

| 配对通道（内部实现） | 验证邀请、秘密和双方身份；建立受限会话并传递准入安全材料；把已验证的加入者事实和就绪回复交还工作空间负责人；按工作空间要求关闭或拒绝会话。 | 不单独保存成员加入、不创建成员交接、不宣布成功、不启动旧成员补送、不定义重启恢复、不持有可选的工作空间负责人。 |
| `uc-core` | 邀请聚合、会话消息和准入事实的领域类型、验证规则与持久化/传输能力约定。 | 不创建网络连接或安排运行期。 |
| `uc-infra` | 受限会话适配、wire 编解码、拨号、码铸与云目录适配。 | 不决定加入目标、完成或重试策略。 |
| `uc-engine` 与三端绑定 | 只公开创建工作空间邀请与加入工作空间两个动作，以及工作空间状态查询与订阅。 | 不暴露握手阶段、就绪确认、成员资料种子、交接唤醒或补送步骤。 |
| 产品端 | 提交一次创建邀请或加入操作、查询状态、订阅变化并展示结果。 | 不排列内部步骤、不根据“会话结束”或“握手完成”推断加入成功。 |

## 对外入口与“加入成功”的分层表达

对外只有两类动作，与[规格 016](016-workspace-wide-convergence.md)的入口表一致：

| 入口 | 输入 | 成功结果 | 稳定失败 |
| --- | --- | --- | --- |
| `IssueInvitation` | 无 | 返回一次邀请及其过期时间和可用性。 | 当前空间不允许创建邀请、移除尚未收敛或需要恢复、网络通道未就绪。 |
| `JoinSpace` | 邀请码、口令、可选设备名 | 返回本机当前工作空间状态；它只表示本机已准备，不表示发起方已保存成员变化或整体已收敛。 | 当前空间不允许准入、邀请无效、口令不符、会话不可用、发起方拒绝或需要恢复。 |
| `QueryWorkspaceConvergence` | 无 | 当前 Space 已保存的完整工作空间状态。 | 当前 Space 不可读或会话未就绪。 |
| `WorkspaceConvergenceChanged` | 订阅事件 | 与查询完全相同的完整状态。 | 不适用；消费者滞后后按通用规则重新查询。 |

`JoinSpace` 的稳定失败类别及其含义：

| 失败类别 | 含义 |
| --- | --- |
| 邀请无效 | 邀请不存在、已消费、已过期、已被取消或准入代数已推进；不区分具体原因。 |
| 口令不符 | 口令验证失败；不泄露任何可枚举信息。 |
| 空间不允许准入 | 当前空间已有有效成员身份、移除尚未收敛或处于 `RecoveryRequired`；由工作空间准入决定给出。 |
| 发起方拒绝 | 发起方明确拒绝本次加入，或会话被要求关闭。 |
| 会话不可用 | 发起方不可达、传输失败或握手超时；不泄露对端状态。 |
| 需要恢复 | 本机或当前空间需要先完成人工恢复，不开始新准入。 |

“加入成功”不作为一个同步返回值，而是按两个层面表达，两者都不存在歧义：

- **本机已准备**：`JoinSpace` 同步返回，语义与规格 016 相同——加入方的本机准备事实已
  保存，且已发送就绪确认。
- **成员变化已保存**：发起方保存加入变化后，由 `QueryWorkspaceConvergence` 与
  `WorkspaceConvergenceChanged` 表达；变化计入 `change_count`，加入方在收到“准入变化
  已保存”确认前不参与普通内容收发、不对其他成员宣布关系可用、不计入完成确认。

配对通道的会话终态（拒绝、超时、关闭）只是通信内部结果，不构成对外结果。实施本文时
删除 `subscribe_pairing_completion`、`PairingCompleted` 事件及配对成功分析事件；配对
握手结束既不产生成功事件，也不改变工作空间状态。产品端因此无法观察到“配对成功但未
加入”的结果：唯一的结果出口是工作空间状态。

重新加入仍使用 `JoinSpace`，但必须产生新成员实例；空间切换复用同一准入门，由负责人在
接收侧按 ADR-015 的规则对目标空间做允许/拒绝决定，不形成第二条握手编排路径。

## 固定加入顺序与保存边界

工作空间按以下顺序推进加入，任一步骤的负责人都是 `WorkspaceConvergence`；配对通道只
在第二步和第三步内提供通信：

1. **准入判断**：判断当前空间是否允许创建或接受该邀请。移除尚未收敛、状态为
   `RecoveryRequired` 或本机已是有效成员时拒绝，不进入握手。创建邀请时绑定当前准入
   代数，赎回时核对代数未推进。
2. **双方验证**：通过内部配对通道验证邀请、秘密和双方身份；验证失败只导致会话拒绝，
   不产生成员资格，也不改变工作空间状态。
3. **保存加入方本地事实并获得就绪回复**：加入方保存本机准备事实，随后发送就绪确认；
   发起方在等待期间保存发起方准入记录。发起方只把已保存且可验证的就绪事实交回工作
   空间负责人。
4. **原子保存连续成员变化**：发起方在收到就绪确认后，在同一保存提交点写入加入形成的
   工作空间变化、待交接事实和回送确认所需资料。
5. **通知双方并继续交接和确认**：仅在保存成功后，工作空间才发布状态事件并继续向
   尚未确认的有效成员交接连续资料；后续推进、重试和完成判定按规格 016 进行。

### 每步保存的事实

| 步骤 | 保存方 | 保存内容 | 保存时机 |
| --- | --- | --- | --- |
| 2-3 | 加入方 | 本机准备事实：发起方成员实例与其传输公钥、可接收会话、待确认就绪记录 | 握手验证通过后、发送就绪确认前，单次加密提交 |
| 3 | 发起方 | 发起方准入记录：会话标识、加入方标识、准入代数、待就绪确认标记 | 开始等待就绪前，单次加密提交 |
| 4 | 发起方 | 加入形成的工作空间变化、新成员待交接事实、回送确认资料 | 收到就绪确认后，同一提交点 |

### 三类重启结果

| 中断时点 | 重启后行为 | 依据 |
| --- | --- | --- |
| 任何事实保存前 | 无成员资格、无普通内容权限、无成功通知；本次加入完全消失，可发起全新准入。 | 未保存的会话与邀请不产生成员资格。 |
| 加入方准备事实已保存、变化未保存 | 加入方保持本机准备，不参与普通内容收发；发起方从发起方准入记录重新取得或等待同一成员实例的就绪确认，只保存一次变化。 | 发起方准入记录跨重启保留。 |
| 成员变化已保存 | 工作空间从已保存状态继续交接和确认；不要求调用方重新执行内部步骤。 | 规格 016 的重启恢复。 |

任一步在成员变化保存前失败，都不得留下新成员、普通内容权限或任何“配对成功”的对外
结果。保存后发生的离线、退出或交接失败是工作空间的 `Converging`、
`WaitingForOfflineMember` 或 `RecoveryRequired`，由它在重启和重新可达后继续；调用方不
重新拼接配对和补送步骤。

## 加入闭环与既有成员衔接

### 1. 创建邀请

`IssueInvitation` 由工作空间准入决定许可：代数可推进、状态允许时生成邀请并绑定当前
准入代数；否则返回稳定失败。邀请不落盘，进程中断后由外部渠道保留的记录只能用于发起
全新准入。

### 2. 加入与验证

`JoinSpace` 拨号并发起握手。配对通道在受限会话内依次完成：邀请匹配与消费、口令与
身份验证、KDF 参数与挑战交换、证明验证、MLS welcome 与加密密钥目录传递。任一环节
失败都以稳定拒绝类别关闭会话，不保存任何成员事实。邀请单次有效：并发赎回时只有一个
加入方成功，其余得到稳定拒绝。

### 3. 就绪事实与变化保存

加入方在验证通过后保存本机准备事实并回发就绪确认。发起方收到后，由工作空间负责人
在同一提交点保存加入变化与待交接事实，并回送“准入变化已保存”确认。加入方收到确认
前处于本机准备状态：只能接收准入与恢复资料，不能参与普通内容收发或完成确认。

### 4. 与既有成员的衔接

配对只建立加入方与发起方之间的最小关系。加入方与其余既有成员的可信关系、连续变化链
和其他可达资料，由工作空间按规格 016 的交接与受限恢复规则建立：发起方保存变化后，由
当前已跟上状态的设备向尚未确认的有效成员交接连续资料；加入方通过受限恢复通道取得
从自身已保存状态连续的缺失资料并确认。发起方离线、重启或永久不可达不影响这一过程，
任何已跟上状态的设备都能继续交接。该衔接不属于配对流程，配对不创建、不唤醒、不驱动
它。

### 5. 完成判定

只有全部当前有效成员已保存同一摘要且关系可用，工作空间才进入 `Complete`；加入方在
此之前不得被产品端展示为“整个工作空间已完成”。`LocallyApplied`、`Converging` 与
`WaitingForOfflineMember` 期间的新合法变化会立即使旧完成结论失效（规格 016）。

### 唤醒点

加入相关的以下事件必须立即唤醒工作空间负责人，不依赖固定间隔轮询：收到就绪确认、
收到“准入变化已保存”确认、成员变化保存完成、加入方上线、发起方上线、会话恢复、收到
交接或确认。离线、连接中断和超时保留为异常恢复路径；会话锁定时不处理交接，解锁后从
同一份加密状态继续。

## 通信适配位置

配对通道不是第二个公开入口，而是工作空间准入实现内部的私有适配位置。工作空间经该
位置只做三件事：

- **请求验证加入者**：传入邀请、加入方标识与已验证证明材料，取得允许/拒绝决定；
- **提交加入方就绪事实**：把已保存且可验证的就绪事实交还工作空间，由它保存变化并
  回送“准入变化已保存”确认；
- **发送工作空间决定**：接受加入、拒绝加入或要求关闭/拒绝会话。

工作空间不因使用该位置而掌握底层拨号、报文编解码或密码握手细节；通信实现替换、独立
测试和协议演进都发生在该位置之后，不影响加入顺序和完成判定。该位置必须提供两个独立
测试面：工作空间侧用通道替身验证加入顺序与保存边界；配对侧用工作空间替身验证通信与
验证行为，两侧都不依赖真实网络或真实负责人。

### 消息职责

配对会话内的消息只承载准入安全材料与验证结果，消息的收发与验证由配对通道完成，消息
含义的解释、保存与推进由工作空间完成：

| 消息 | 只承载 | 不得承载 |
| --- | --- | --- |
| 加入方请求 | 邀请码、加入方设备与身份指纹、随机数、传输地址、安全能力、MLS KeyPackage | 成员名单、空间内容、密钥明文 |
| 发起方准入要约 | 空间标识、KDF 参数载荷、挑战随机数、会话标识 | 当前成员资料、摘要、密钥 |
| 加入方证明回复 | 加密证明字节 | 密钥、内容 |
| 发起方确认 | 发起方设备与身份、传输地址、MLS welcome、加密密钥目录、安全世代 | 既有成员资料、内容 |
| 加入方就绪回复 | 已签名就绪事实（成员实例、设备与身份、传输公钥与地址、签名） | 成员名单、在线状态、内容 |
| 拒绝 | 稳定类别（邀请不匹配、准入不可用、口令不符、发起方拒绝、超时、内部） | 成员名单、摘要、安全状态、区别性错误详情 |

就绪回复是“已验证加入者事实和就绪回复交还工作空间负责人”的载体；一条会话中重复或
乱序的消息、已消费邀请的再次使用、已关闭会话的迟到消息一律拒绝，不产生任何持久化
副作用。

### 会话生命周期

配对会话只存在于内存，绑定到邀请、双方身份和一次加入尝试。进程中断后会话消失，不落
盘、不恢复、不得续用。会话既不是成员资格的证据，也不是完成判定的依据；对端可达或
握手结束都不等同于成员加入或工作空间完成。会话有固定的超时与并发上限；超时以稳定
拒绝类别关闭会话，不影响已保存事实。

### 邀请生命周期

邀请只存在于内存持有人中，一次只能被一个加入方赎回，过期、被消费、被取消或准入代数
推进后失效。本地进程中断后邀请消失；外部渠道（如云目录）保留的记录只能用于发起一次
全新的准入，不能使未完成的加入延续。工作空间恢复只依据已保存的成员变化与准入记录：
没有保存加入变化的未完成会话与邀请不产生成员资格，也不得被误报为成功。

## 持久化与恢复边界

### 必须加密保存的事实

| 事实 | 保存方 | 说明 |
| --- | --- | --- |
| 本机准备事实 | 加入方 | 发起方成员实例与其传输公钥、可接收会话、待确认就绪记录；与发送就绪确认的决策在同一提交点。 |
| 发起方准入记录 | 发起方 | 会话标识、加入方标识、准入代数、待就绪确认标记；跨重启保留，用于重新取得或等待同一成员实例的就绪确认。 |
| 工作空间变化与待交接事实 | 发起方 | 按规格 016 的变化链持久化规则，与确认资料同一提交点。 |
| 就绪确认与准入变化确认的进度 | 双方 | 已消费编号与进度按规格 016 的交接进度规则加密保存；重复编号一律拒绝。 |

上述事实属于敏感业务载荷，在 SQLite、WAL、SHM、缓存和任何索引中经 MasterKey AEAD
加密；仅可保存经批准的随机标识、版本、代数、计数、状态和时间，不得借此保存第二份
明文设备名单。邀请码、口令与身份证明材料不得明文落库、入缓存或入日志。

### 不保存的事实

- 配对会话本体、会话消息原文与握手中间状态；
- 邀请本体（内存持有人是唯一来源）；
- 未完成加入的临时状态（未保存加入变化的任何中间事实）；
- 握手过程的分析统计可保留脱敏计数，但不得绑定设备资料或内容。

## 失败与恢复

| 情形 | 必须行为 | 负责人 |
| --- | --- | --- |
| 邀请无效、过期、已消费、已取消或代数推进 | 拒绝会话；工作空间状态不变；返回统一“邀请无效”类别，不区分原因。 | 配对通道执行，工作空间决定 |
| 口令不符 | 拒绝会话；不泄露可枚举信息。 | 配对通道 |
| 身份验证失败或证明无效 | 拒绝会话；不保存成员状态；不进入握手后续步骤。 | 配对通道 |
| 发起方明确拒绝 | 关闭会话；邀请失效；无任何成员事实保存。 | 工作空间决定 |
| 握手超时或对端不可达 | 以稳定拒绝类别关闭会话；不重试握手、不自动切换 LAN。 | 配对通道 |
| 成员变化保存前进程中断或失败 | 不留下新成员、普通内容权限或成功结果；重启后无该加入的任何事实，可发起全新准入。 | 工作空间 |
| 发起方等待就绪期间中断 | 加入方保持本机准备；发起方重启后从发起方准入记录重新取得或等待同一成员实例的就绪确认，只保存一次变化，不生成第二成员实例。 | 工作空间 |
| 成员变化保存后进程中断 | 工作空间从已保存状态继续：重启后按待交接事实推进，不要求调用方重新执行内部步骤。 | 工作空间 |
| 保存后加入方离线 | 以 `WaitingForOfflineMember` 等待，上线后立即继续交接和确认。 | 工作空间 |
| 工作空间不可用或准入决定不可得 | 拒绝入站请求或返回稳定失败；不得以“负责人不存在”的方式绕过准入继续握手。 | 装配层保证负责人恒存在 |
| 会话在握手中被对端或网络关闭 | 仅关闭该会话；不影响已保存事实，也不宣布任何结果。 | 配对通道 |
| 重复、乱序或重放消息 | 一律拒绝；不产生持久化副作用、不推进任何状态。 | 配对通道 |
| P2P 传输失败 | 保留已保存事实并等待；不自动切换到 LAN。 | 工作空间 |

## 删除并行责任

实施本文时必须删除下列路径，删除检查按规格 016 的 W12 方式执行：

- 配对流程中直接保存或推进工作空间成员变化的代码路径，包括成员实例、信任记录、设备
  地址和本机已设置状态的配对侧写入；
- 旧成员收敛流程被配对直接唤醒、保存种子或补送资料的路径及其无操作替身；
- 配对持有的可选工作空间负责人依赖及“不可用即失败”分支；
- 配对成功结果、订阅与相关分析事件，以及依赖它们的开发结果流；
- 空间切换对配对握手的平行编排，统一改经工作空间准入决定；
- 以“握手完成”为成功语义的测试断言，改为以“成员变化已保存且可由工作空间继续推进”
  为断言。

删除后全仓库不得存在第二套加入路径、兼容回退或产品端补偿逻辑；配对代码整体成为工作
空间准入的内部通信实现，不形成第二个公开入口。

## 安全与隐私

- 配对通道消息在 Iroh 经身份认证加密的连接之上传输；会话消息与准入安全材料不得明文
  落库、入缓存或入日志。
- 邀请、口令、身份证明、MLS welcome、密钥目录、就绪事实与准入进度属于敏感载荷；任何
  持久化字段默认经 MasterKey AEAD 加密，遵循仓库不可破坏规则。
- 日志和观测只记录脱敏流程标识、阶段、计数、代数、耗时和稳定失败类别；不得记录邀请
  码、口令、设备名、设备编号、地址、签名、密钥、安全资料、文件名、路径或内容。
- 拒绝消息只返回稳定类别，不泄露成员名单、摘要、安全状态或区别性错误详情；邀请无效
  与口令不符等类别不区分具体原因，防止枚举探测。
- 会话、邀请与消息均绑定空间沿革与本次会话标识；跨空间重放、错误会话绑定的消息一律
  拒绝。
- 邀请赎回单次有效，配合会话超时与并发上限，防止无限重试与并发占用。

## 实施顺序

每个阶段的完成条件未满足前不得进入下一阶段，也不得提前公开新对外行为。

| 阶段 | 负责方 | 必须完成的工作 | 阶段完成条件 |
| --- | --- | --- | --- |
| 1. 保存边界收回 | `uc-application`、持久化实现 | 把成员实例、信任、设备地址与设置状态的保存从配对流程移入工作空间变化保存提交点；加入方与发起方按本文保存边界落库。 | 故障注入覆盖各提交点两侧；配对代码不再单独写入成员相关状态。 |
| 2. 负责人接管编排 | `uc-application` | `WorkspaceConvergence` 经适配位置编排五步加入顺序；接线就绪事实保存、发起方准入记录、变化保存与确认回送；删除配对侧流程编排。 | 加入顺序与三类重启结果全部由负责人表达；配对只剩通信与验证。 |
| 3. 删除可选负责人与补送 | `uc-application` | 删除配对持有的可选负责人依赖与无操作替身；删除旧成员收敛补送驱动。 | 全仓库无 `None` 负责人分支；无配对驱动的补送路径。 |
| 4. 删除成功宣布 | `uc-application`、`uc-engine`、绑定 | 删除 `subscribe_pairing_completion`、`PairingCompleted` 与分析事件；成功表达只剩工作空间状态。 | 对外无配对成功结果；加入结果全部经工作空间快照可查。 |
| 5. 平行入口收回 | `uc-application` | 空间切换统一经工作空间准入决定；删除第二条握手编排路径。 | 切换与重新加入共用同一准入门与加入语义。 |
| 6. 测试改造与端到端验收 | 测试宿主、发布流程 | 测试断言从“握手完成”改为“成员变化已保存并可继续推进”；新增通道替身与负责人替身测试面；按验收矩阵执行。 | 每项有可复查的接收端证据；未执行设备项明确写为“跳过”。 |

## 验收标准

1. 外部调用者只能创建邀请或加入工作空间，不能直接推进加入的中间步骤；
2. 任一成功加入均可查询到已保存的工作空间成员变化；不存在“配对成功但未加入”的成功
   结果；
3. 成员变化保存前终止进程后，重启不会出现新成员、普通内容权限或成功通知；
4. 成员变化保存后终止进程后，重启由工作空间继续收敛，不要求调用方重新执行内部步骤；
5. 加入方、发起方和既有离线成员恢复后，最终完成仍以规格 016 的接收方实际可用为准；
6. 全仓库不再存在配对直接保存成员变化、直接驱动旧成员补送或绕过工作空间负责人的路径。

## 验收总则

- 每台设备使用独立进程、独立身份和独立持久化目录。
- “离线”必须同时断开设备间直连、中继和变化转发，不能只暂停后台任务。
- “重启”必须销毁原进程，再从原磁盘状态启动新进程。
- “加入成功”的证据是已保存的成员变化与后续收敛推进，不是会话结束、发送成功或等待
  时间；所有完成结论以接收端实际保存的成员关系、当前摘要和双向内容接收为准。
- 同一加入场景至少执行发起方先离线、加入方先离线与双方交错重启三种顺序，验证重复
  事件、乱序与不同转交设备不改变最终摘要。
- 适配位置测试必须在无真实网络、无真实配对通道的情况下独立验证加入顺序与保存边界；
  配对通道测试必须在无真实工作空间负责人的情况下独立验证通信与验证行为。
- 设备矩阵中未执行的 Android、iOS 或 HarmonyOS 项必须标记“跳过”，不得标记“通过”。
