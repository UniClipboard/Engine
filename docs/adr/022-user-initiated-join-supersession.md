# ADR-022：用户明确加入创建新尝试并安全取代旧尝试

- **状态**：已采纳，已实施
- **日期**：2026-08-18
- **修订**：ADR-017 和规格 023 中“重复调用 `JoinSpace` 恢复当前未结束尝试、另一邀请返回冲突”的规则
- **相关文档**：`CONTEXT.md`、

> **后续修订**：ADR-024 已取代本文关于 `ResetSpace` 只在准入静止时执行轻量清理的规则。
> 用户明确加入的取代规则不变；`ResetSpace` 现为清除全部旧设备关系的设备管理重置。

## 背景

当前 `JoinSpace` 在发送网络请求前查找本机未结束加入。只要找到记录，就把本次输入当作同一加入的恢复，
继续使用原加入编号、成员凭据和安全材料。输入与旧记录完全相同时，这能保证断网和重启不会生成第二个
成员事实；但当用户退出加入页面、取得新的邀请码并再次明确提交时，这个行为把新的用户意图误判成后台重试。

现场问题中，第一次加入已经发出请求，随后连接失败并留下 `Initiated` 记录。用户第二次使用另一邀请码
提交时，Engine 在本机恢复旧记录，再因为新旧输入不一致而返回内部错误。第二次请求没有到达邀请方。
相同邀请码也存在产品语义问题：用户的第二次明确提交应当是新的加入，而不是继续界面中已经放弃的旧操作。

调用方不能通过依次执行取消、普通重置和加入来解决。取消要等待邀请方裁决；普通重置在加入未静止时拒绝；
彻底重置会销毁设备身份和本机资料。把这些步骤交给产品端还会破坏 ADR-017 确定的唯一流程负责人边界。

## 研究结论

成熟系统通常把“同一操作的重试标识”和“新的业务操作”分开：

- [Stripe 幂等请求](https://docs.stripe.com/api/idempotent_requests)要求同一次请求重试复用同一唯一键和相同
  参数；同一键配不同参数会明确失败。新的业务操作使用新的键。
- [Amazon EC2 幂等请求](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html)同样要求同一
  客户端令牌只配同一组参数，并指出调用方未取得最终结果时，异步操作可能已经完成。此时应恢复同一操作，
  不能假定旧操作不存在并直接创建冲突结果。

对 UniClipboard 的适用结论是：每次用户明确提交必须取得新的加入身份；同一次加入内部的断线、超时、消息
重放和重启恢复必须继续使用原身份。一旦本机已经发出足以让邀请方正式提交的证明，即使本机尚未看到提交
结果，也不能再安全取代旧加入。

## 决策

### 每次用户明确提交都是新的加入

每次通过稳定 Engine 入口提交 `JoinSpace` 都表示一次新的用户操作。无论邀请码、设备名、口令或保留选择
是否与上次相同，只要本次操作通过输入和来源历史预检，就必须创建新的 `attempt_id`、`join_id`、
`local_join_ordinal`、成员实例、KeyPackage、续接密钥和其他恢复材料。

宿主不得通过再次调用 `JoinSpace` 恢复一次已经开始的加入。第一次调用结果丢失、应用重启或网络恢复时，
宿主只查询或订阅 `DeviceTrustSnapshot.current_join`。`WorkspaceConvergence` 在内部继续原尝试、重发原消息
并恢复原状态。Engine 的短期请求编号不能代替持久加入身份。

同一时刻到达的多个 `JoinSpace` 由 profile 负责人串行裁决。后保存的新用户操作可以按本 ADR 取代仍处于
安全阶段的前一个本机加入；不能由调用顺序、网络快慢或产品端缓存决定谁是当前加入。

### `WorkspaceConvergence` 完整负责取代与新建

`WorkspaceConvergence` 继续是唯一完整负责人。调用方仍只执行一次 `JoinSpace`，成功取得新的
`Active`、`Pending` 或 `Rejected`，或收到一个明确的不可取代冲突。调用方不执行取消、重置、清理、
生成编号、判断阶段或重放消息。

取代不是 `CancelJoinSpace`、`ResetSpace` 或 `FactoryResetSpace` 的别名：

- `CancelJoinSpace` 仍表示用户希望停止当前加入，并等待邀请方在正式提交前拒绝；
- `ResetSpace` 仍只在全部准入工作静止后清设置、未消费邀请和公开投影；
- `FactoryResetSpace` 仍是销毁本机 profile 的唯一强制边界；
- 本 ADR 的取代只结束一项尚未到达不可安全取代点的本机加入，并在同一持久操作中创建下一项加入。

### 安全取代点固定在本机持久保存 `Prepared` 之前

邀请方只有收到加入方的 `Prepared` 后才能正式提交成员事实。因此，旧本机加入只有在以下条件全部满足时
才可被新的用户操作取代：

1. 旧记录属于本机加入方，且尚未进入终态；
2. 阶段为 `Initiated` 或 `Candidate`，本机从未持久保存 `Prepared`；
3. 没有正在恢复的写前记录、Space transition 或会把阶段推进到 `Prepared` 及其后继的持久工作；
4. 记录结构、版本和安全材料可完整验证，不处于 `RecoveryRequired`。

一旦 `Prepared` 已持久保存，就必须假定它可能已经送达邀请方并触发正式提交。即使本机尚未收到 `Commit`，
也不得清除、拒绝、回滚或取代该尝试；原尝试继续向前恢复到 `Active` 或由协议允许的稳定 `Rejected`。
本次新的 `JoinSpace` 不创建任何新编号、材料、邀请消费或目标 Space 副作用，而是返回专用、稳定、可公开
判断的 Conflict 结果 `PreviousJoinCannotBeSuperseded`。实施时必须为它分配独立 Engine 错误码，不能继续
映射为通用 `JOIN_SPACE_FAILED_CODE = 1238`。

已有非终态入站准入、共享写前恢复、Space transition、彻底重置或其他不能由本机加入取代的 profile 工作时，
仍返回既有的准入忙碌结果并保持原工作不变。新的本机加入不得借“用户重新提交”清除入站候选或当前 Space
的成员变化。

### 旧终态与新尝试必须一次持久提交

可安全取代时，负责人必须通过一个数据库事务或同等的加密写前恢复记录完成以下不可分割的变化：

1. 再次核对旧尝试版本和安全阶段；
2. 把旧本机尝试保存为内部终态 `SupersededByNewJoin`；该终态只表示本机不再接受旧尝试推进，不伪造邀请方
   已经拒绝，也不写入成员历史；
3. 单向停止旧 JoinRequest、Candidate 和其他可被取代的待发消息，保留向旧邀请方发送取消或终止通知所需的
   隔离清理工作；
4. 保存旧尝试能够识别重复、迟到和乱序消息的最小防重放事实；
5. 创建全新加入及其全新编号、序号、成员凭据、安全材料、初始请求、当前投影和 DeviceTrust revision；
6. 提交成功后才允许发送新请求。

任一步失败都保持完整旧状态或恢复同一写前记录，不能出现“旧加入已结束但新加入不存在”、两个当前加入、
新旧材料混用或投影先于事实变化。新操作在预检、材料准备或持久提交前失败时，原加入保持不变。

`SupersededByNewJoin` 不是新的公开 `JoinSpaceStatusSummary` 分支。当前快照在同一提交后只显示新加入；旧终态
留在加密历史中供防重放、迟到消息和后台清理使用。终态压缩不得删除识别旧 attempt、join、邀请绑定和
被取代结果所需的事实。

### 迟到消息不能重新打开旧加入

所有旧消息继续按旧 `attempt_id` 路由。收到被取代尝试的 Candidate、取消回复、重复请求或其他提交前消息时，
负责人只重放已保存的被取代结果或发送幂等终止通知，不改变当前加入、当前 Space、成员历史或新尝试的
待发消息。

按照协议，未保存 `Prepared` 的加入方不可能授权邀请方正式提交。若被取代尝试收到有效 `Commit` 或更晚
消息，说明持久阶段、协议身份或消息证明存在矛盾；负责人必须失败关闭并进入稳定恢复错误，不能接受该消息、
回退新尝试或静默产生第二成员事实。

旧尝试的隔离取消通知和清理可以在新尝试开始后继续，但只能读写旧 attempt 的记录。它们不占用本机加入
投影，也不能覆盖新尝试；是否仍占用共享准入槽由其能否改变活动 Space 或成员事实决定，不能简单以 outbox
是否为空判断。

### 邀请仍然一次性消费

相同邀请码的第二次用户提交会创建新的本机尝试，但不改变邀请方的一次性消费规则。如果第一次请求尚未被
邀请方受理，新尝试可以正常使用该输入；如果邀请码已经绑定旧 `attempt_id` 或另一身份，邀请方必须稳定
拒绝新尝试为邀请已使用或身份冲突。不得把已消费邀请改绑到新尝试，也不得把旧尝试的邀请绑定、候选或
安全材料复制给新尝试。

“创建新的加入”只保证本机不复用旧尝试，不保证一次性邀请码可以被成功消费两次。

### 当前 Space 与本机资料保持不变

取代旧加入只处理该尝试的加密临时资料、待发消息和恢复事实。设备身份、profile 主密钥、当前活动 Space、
本机历史、设置、关系、搜索和受管文件均不得清除。Cross-Space 加入在新尝试完成 J3 前继续使用原 Space；
旧尝试尚未开始的迁移副作用不得被补做，新尝试使用自己的独立目标暂存世代。

## 不做的事

- 不允许用户操作取代已经持久保存 `Prepared` 或更晚阶段的加入。
- 不改变邀请的一次性消费和防重放规则。
- 不把取代步骤公开给产品、绑定或 `uc-engine` 编排。
- 不新增长期并存的第二个本机加入；同一 profile 仍只有一个当前本机加入投影。
- 不用超时推断旧加入可以取代，也不因 P2P 失败自动切换 LAN。
- 不把旧加入的本机被取代终态伪装成邀请方拒绝、成员移除或历史回滚。
- 本 ADR 不实施代码，只确定后续规格和实现必须遵守的行为。

## 考虑过的方案

### 每次 `JoinSpace` 无条件清除旧加入

实现表面简单，但旧 `Prepared` 可能已经让邀请方正式提交。无条件清除会丢失恢复能力，并让两端对成员事实
产生永久分歧，因此不采用。

### 继续按输入是否相同决定恢复或报错

这正是当前问题的来源。邀请码只是用户输入，不是同一次用户操作的稳定身份；相同输入也可能是新的明确提交，
不同输入更不能绑定旧尝试，因此不采用。

### 产品端先取消或重置，再调用加入

取消需要远端裁决，普通重置拒绝未完成加入，彻底重置会销毁过多资料。该方案还要求产品理解内部顺序和
失败恢复，破坏唯一负责人，因此不采用。

### 新旧加入并行运行

并行会让两个邀请、两套安全材料和两个目标 Space 竞争同一 profile 与当前 Space，显著扩大冲突和恢复范围。
本产品没有同时加入多个 Space 的需求，因此不采用。

### 用户再次提交后始终等待旧加入先完成

这在不可安全取代点之后是必要规则，但对仍处于 `Initiated` 或 `Candidate` 的旧加入没有必要，会继续让一次
失败请求永久阻塞用户。因此只在 `Prepared` 及以后采用。

## 后果

- 用户退出并再次提交时得到真正的新加入，不再因旧输入不一致返回内部错误。
- 后台重试和用户新操作有了不同身份；恢复幂等性不再依赖邀请码内容猜测。
- `WorkspaceConvergence` 的外部接口保持小：调用方仍只提交一次加入并查询统一状态，复杂度留在负责人内部。
- 准入仓储需要新的内部被取代终态、原子“结束旧尝试并创建新尝试”能力，以及隔离的旧消息清理。
- Engine 需要一个专用的不可取代冲突错误；三套绑定和产品必须稳定映射，但不需要新增步骤式操作。
- 规格 023 中“Pending 重复调用恢复同一尝试”和“另一邀请总是冲突”的旧规则必须整体修订。
- 相同邀请码的新尝试仍可能因邀请码已消费而被拒绝，这是一次性邀请安全规则的预期结果。

## 验收标准

1. 第一次加入停在 `Initiated` 或 `Candidate` 时，再次提交不同邀请码会原子保存旧被取代终态并创建全新加入。
2. 相同邀请码再次明确提交也创建全新本机加入；邀请方已消费时返回稳定邀请拒绝，不复用旧 attempt。
3. 新旧加入的 attempt、join、序号、成员实例、KeyPackage、续接密钥和目标暂存世代全部不同。
4. 在结束旧加入与创建新加入的每个持久写入点注入失败并重启，只能恢复完整旧状态或完整新状态。
5. 应用重启、网络断开、自动退避、消息重复和响应丢失继续同一 attempt，不创建新加入。
6. `Prepared` 及以后再次提交返回专用不可取代冲突，原加入继续向前恢复，新加入没有任何持久或网络副作用。
7. 旧 Candidate、取消回复、重复请求和恢复扫描不能重新打开旧尝试或覆盖新 `current_join`。
8. 被取代尝试收到 Commit 或后继消息时失败关闭并保留证据，不接受第二成员事实。
9. Fresh、Same-Space 和 Cross-Space 均保持原活动 Space、历史、设备身份和本机资料，直到新加入按既有边界完成。
10. 本机入站准入或其他 profile 级不可取代工作继续返回稳定忙碌，不被新用户操作清除。
11. 本流程不再返回通用错误 1238；不可取代与邀请已使用分别返回稳定、可判断的公开结果。
12. Android 真机连续执行“失败一次，再明确加入一次”时，第二次请求到达邀请方并可继续完成；未执行的实体
    设备项目只能记录为跳过。
