# ADR-016：工作空间采用可转交的连续变更实现全局收敛

- **状态**：已采纳，实施中
- **日期**：2026-08-10
- **修订**：ADR-015 的完整流程负责人、对外状态和完成边界；保留其移除意图合法性、合并和新成员实例规则
- **被修订**：ADR-020 把收敛改为设备上线后的点对点成员核对；新增可自动补齐，未确认移除等待
  用户，拒绝后相关设备分叉隔离但各自分支继续运行

## 背景

本文中关于 OpenRaft、多数提交、唯一后继、最终成员配置、提交引用和“全空间最终只有一条成员
历史”的条款已被 ADR-020 取代，不能作为实施依据。`WorkspaceConvergence` 的唯一负责人、完整
查询和重启恢复职责继续保留。

当前配对、成员资料交换和安全状态更新由多条独立流程推进。它们可以完成一次直接配对，
但不能保证整个工作空间最终恢复可用。

典型场景是：A 与 B 已配对；A 离线；B 让 C 加入；B 离线；C 再见到重新上线的 A。此时
C 持有 B 签发、A 连续恢复所需的资料，但 A 尚未认识 C，旧流程在资料到达前就拒绝 C，导致
A 与 C 永远无法建立关系。四台、五台设备以及移除后从不同设备重新加入时会放大同一问题。

这不是 OpenMLS 的能力限制。验证已证明：落后的成员可按连续顺序应用变更；新成员可转交
原发起成员签发的变更，离线旧成员能独立验证并恢复到相同状态。OpenMLS 不能把两条并发
分叉直接拼接；这仍按 ADR-015 的规则先得到一个统一目标，再向前恢复。

## 决策

### 一个负责人管理整个工作空间

应用层新增唯一的“工作空间收敛负责人”。它完整负责成员加入、移除、重新加入、资料保存、
转交、确认、重启恢复和对外状态；产品端只提交成员操作、查询状态和订阅变化。

配对流程只完成准入。成员移除流程只产生不可撤销的成员变化。两者都把变化交给工作空间
收敛负责人，不能各自再决定何时向其他设备分发、何时显示完成或如何重试。

ADR-017 进一步规定配对是工作空间准入的内部通信通道，而非另一个流程负责人；外部只有
创建邀请和加入工作空间两个动作。

本 ADR 修订 ADR-015 中“成员移除模块完整负责”和单独公开成员移除状态的边界。ADR-015
继续定义移除意图的合法性、移除优先合并、旧实例限制和新实例规则；这些规则由
`WorkspaceConvergence` 的成员移除部分执行。成员加入、移除、重新加入、资料交接、确认和
工作空间完成只由这一负责人对外给出一份结果。

### 工作空间变更必须连续、可保存、可转交

每次成员变化形成一份工作空间变更，至少包含：

- 空间沿革和前后安全世代；
- 可验证的连续安全变更；
- 新成员的已签名身份、可达地址和连接所需资料；
- 已提交排序记录、最终成员配置和提交引用；
- 变更摘要及每台设备的确认记录。

所有敏感资料加密保存。任一已跟上当前状态的设备都保存它所能证明的连续变更链，因此原始
发起设备离线、重启或永久不可达时，不会成为恢复其他设备的前提。

接收设备只接受能从自己当前状态连续推进的资料。它不得跳过中间变化，不得用“最新结果”
覆盖旧状态，也不得根据到达时间、网络路径或发送者编号选择结果。

### 先验证内容，再建立新关系

为工作空间恢复建立独立受限通道，不复用“双方已经认识”才可使用的普通成员资料通道。

交接请求必须以双方共同可验证的历史成员资料建立一次性、受应用层加密保护的交接上下文，
不能假定落后设备持有当前空间密钥。该上下文绑定空间沿革、双方成员实例和传输身份、起止
世代、变化摘要及本次随机请求；任何重复、跨空间或篡改的交接均不得被解开或应用。交接设备
在发送任何当前资料前，必须按自己当前已验证状态确认请求方成员实例仍然有效。历史证明只足以
请求受限验证，不能使已被移除的旧实例读取当前资料；旧实例仅保留 ADR-015 的移除通知和迟交
历史意图入口。

接收方处理一份恢复交接时按以下顺序执行：

1. 限制消息大小和变化数量，确认空间一致；
2. 验证并按顺序应用连续安全变更；
3. 用更新后的已知成员资料验证转交设备的身份和证明；
4. 原子保存成员、可信关系、地址和确认；
5. 返回确认。

陌生设备不能仅凭连接取得成员资料、设备名单或业务内容。无效、断档、跨空间、重复冲突或
身份不匹配的资料全部拒绝。有效变更可以由任何网络对端转交，因为其合法性由本机已有状态
和变更本身验证，而不是由传输来源保证。

### 完成只表示整个工作空间完成

对外状态至少区分：

- `Idle`：当前没有待提交或待激活的成员变化；
- `LocallyApplied`：本机已保存移除意图和收发限制，正式成员集合尚未改变；
- `AwaitingCommit`：候选排序记录、联合配置或最终成员配置尚未全部提交；
- `AwaitingActivation`：加入变化已经提交，但加入方尚未完成安全材料激活；
- `Committed`：最终成员配置、提交引用和新的正式成员状态已提交并应用，加入变化也已激活；
- `Converging`：已提交变化正在交接、应用或确认；
- `WaitingForOfflineMember`：正式提交后的未完成只因已知有效设备暂时离线；
- `Complete`：所有当前有效设备已确认相同状态，并已保存彼此可用的关系；
- `RecoveryRequired`：变化无法验证、出现不可自动解决的分叉或没有有效成员。

前五项属于 `membership_transition`；`Converging`、`WaitingForOfflineMember`、`Complete` 和对应的
`RecoveryRequired` 属于 `workspace_completion`。两条进度同时公开，不按优先级折叠。

单台设备本地限制、成员变化提交和整个工作空间完成是三个不同结果。用户可在提交后收敛期间继续
创建移除意图；负责人先保存本机限制，再从最新已提交链头形成下一候选，不能改写已经排序的后继，
也不能要求产品端编排等待与接管。统一快照分别公开 `membership_transition` 和
`workspace_completion`；新的提交前工作不能遮住此前已提交变化的交接阶段或等待设备名单。

### 事件驱动，不以时间顺序兜底

成员变化、设备上线、会话恢复、收到变更和收到确认都会立即唤醒负责人。离线、连接中断和
超时保留为异常恢复情形；正常加入、重新加入和成员关系恢复不能依赖应用层固定间隔的扫描或
重试。OpenRaft 内部为选举、心跳和复制使用自己的计时器，这些计时器完全封装在排序适配中，
不成为产品流程、公开阶段或降低确认门槛的依据。

## 不做的事

- 不设置固定协调设备、中心服务器或全体在线门槛；正式成员变化按 ADR-020 同时满足旧、新配置
  各自的多数。
- 不允许未验证的陌生设备读取工作空间资料。
- 不让产品端保存待办、决定重试或猜测完成状态。
- 不保留旧的“先认识发送者才接收恢复资料”路径作为兼容分支。
- 不因 P2P 恢复失败自动切换到 LAN。

## 后果

工作空间恢复不再依赖某一台发起设备持续在线。三台、四台和五台设备的复杂拓扑都遵循同一
机制：持有连续资料的在线设备帮助落后设备恢复，接收方自己验证后再建立关系。

代价是必须持久保存确认和可转交资料，并把旧的配对后补资料、单独安全更新投递和成员关系
发现流程合并为一个负责人。实施完成后删除旧流程，不保留并行实现。

## 验收标准

至少覆盖以下真实用户路径：

1. A、B、C 已提交同一状态，A 离线后 B、C 提交移除 A，再由包含 D 的联合配置和最终配置提交
   加入 D；B 随后离线，C 或 D 向重新上线的
   A 转交已经提交的连续变化；A 先验证并应用变化，再与 D 建立关系和恢复双向同步；
2. 四台设备中两个早期发起设备离线，在线设备满足当时旧、新配置各自多数后，仍能让最早设备与
   最新设备恢复双向同步；
3. 五台设备中用户连续移除两台设备，两个变化各自提交当时的联合配置和最终配置；分别从不同保留设备重新
   加入后，五台当前实例恢复整体同步；
4. 重新加入使用新成员实例，旧移除事实不会再次移除新实例；
5. 断档、伪造、跨空间、身份不匹配、篡改或重放的恢复交接被拒绝；
6. 已被移除的旧成员实例即使持有有效历史证明，也得不到当前成员、地址、安全变化或其他交接
   资料；
7. 超过单次交接上限的连续变化能分批恢复，只有接收方确认当前目标摘要后才算完成；
8. 全部验收以接收端实际收到内容为准，不以发送次数、时间等待或单台设备状态为准。
