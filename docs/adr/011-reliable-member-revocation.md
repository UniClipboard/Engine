# ADR-011: 可靠成员撤销采用群组代次与分层内容密钥

状态：已接受 (2026-07-29)；离线与并发移除语义已由 ADR-015 及
`docs/specs/015-offline-first-member-removal.md` 取代。

## 背景

当前成员移除只删除本机成员、地址和信任记录。被移除设备仍持有 Space 主密钥，
因此既能读取历史内容，也能继续使用同一把密钥完成准入证明。单纯停止同步不能构成
安全撤销。

本决策处理的是前向撤销，不是远程擦除。系统无法收回已经被设备下载、解密或复制
的历史内容，也不对已落在对方磁盘上的文件作删除承诺。

## 威胁模型

假设被撤销设备及其操作者不再可信，并保留撤销前获得的全部本地数据、历史内容密钥
和网络报文。攻击者可以重放旧消息、伪造旧客户端行为、长期离线后重连，也可以尝试
利用旧主密钥重新加入。

不处理设备操作系统已经失陷后窃取其他活跃设备内存、系统安全存储或用户口令的情形；
也不处理保留成员主动把新内容转交给被撤销成员的情形。

## 决策

### 前向撤销的定义

撤销生效后，被撤销成员：

- 不能进入新的成员状态；
- 不能取得新代次秘密或新内容密钥；
- 不能通过旧主密钥重新完成准入；
- 不能解密、接收或提交撤销后的业务内容；
- 可以继续读取撤销前已经获得的历史内容。

### 群组成员状态

群组成员状态使用经过阶段 0 跨平台与行为验证的 OpenMLS，不自行设计群组密码协议。
每个 Space 对应一个群组，每台设备使用独立凭据。成员增加与移除都产生新的群组代次，
新代次秘密只属于新成员集合。

OpenMLS 只存在于内部实现，不进入 `uc-core` 或 `uc-engine` 的稳定接口。如果阶段 0 的
三成员移除、秘密导出、离线补提交、分叉恢复或任一交付目标构建失败，后续协议实现
暂停，并用新的 ADR 记录阻塞；不得以临时自研协议替代。

### 准入权与内容解密权分离

群组代次负责成员资格和准入。内容使用独立、可轮换的内容密钥；正文、传输和搜索再
按用途隔离。持有历史内容密钥不代表仍是活跃成员，也不能生成当前代次准入凭据。

当前 Space 主密钥作为 `legacy-v1` 历史内容密钥保留。撤销不重加密历史正文或 blob，
只生成新的当前内容密钥，并为保留成员重新包装小体积历史密钥目录。新密文携带内容
密钥标识和群组代次，旧格式只读，不双写。

### 代次提交点

撤销至少经历准备、暂存、本机激活、分发和完成五个持久状态。群组提交、新内容密钥、
密钥目录、撤销记录和待发送消息必须先原子暂存。

本机合并新群组代次并把新内容密钥设为当前密钥，是不可逆的激活提交点：

- 激活前失败可以安全取消或回滚暂存；
- 激活后不得恢复旧代次写入，只能重试分发并向前完成；
- 被撤销成员不得出现在新提交或新密钥目录的收件集合中；
- 激活后收到的旧代次业务消息一律拒绝。

### 持久化边界

撤销仓储只把恢复、筛选和数据库约束所需的结构信息明文保存：随机撤销编号、前后代次、
流程状态、安全模式和时间戳。前后代次用于保证单调前进，流程状态用于恢复未完成任务，
安全模式用于决定是否允许可靠撤销，时间戳用于稳定排序和恢复判断。

真实 Space 标识不得明文保存，查询和唯一约束使用 MasterKey 按独立用途派生的不可逆查找值；
当前内容密钥编号只存在于加密负载中，不再设置重复的明文字段。成员身份、收件人、群组提交、
群组状态和密钥目录同样只存在于加密负载。新增任何明文字段都必须在变更说明中逐项解释查询
或约束需要，并获得明确批准。

### 离线成员

撤销不要求所有保留成员同时在线。本机可以先激活，并把结果显示为“本机已生效，等待
若干保留设备”。离线保留成员重连后必须先按顺序合并缺失的群组提交，再恢复业务同步；
完成补交前视为过期成员，不能收发新代次内容。

消息允许重复和乱序，但处理必须幂等。ADR-015 进一步规定先合并经过验证的离线移除意图，
再把有效成员集合向前落实为统一安全状态；只有因果历史不可验证、恢复资料冲突或有效成员
集合为空时进入“需要恢复”。网络保持失败关闭，不使用旧密钥继续同步。

### 单一移除流程与进度

本节关于单一未完成流程、不同目标冲突和重复发起的规定已由 ADR-015 取代。应用层完整负责
结果、状态快照、重启恢复和 `Applied` 不等于完成的规定继续有效。

一个 Space 同时只允许一项未完成的成员移除。应用层成员移除流程是完整结果的唯一
负责人，负责本机生效、等待设备、确认、重试、重启恢复和最终完成。产品端不得保存
内部步骤或自行安排重试。

- 同一目标被重复移除时返回原流程的当前进度，不创建第二项任务。
- 另一目标被移除时返回稳定冲突；已有流程需要安全恢复时返回独立的稳定错误。
- 重启后通过“查询当前移除”直接恢复界面，不要求产品保存旧流程编号。
- 每次状态变化都发送完整快照，包含流程编号、结果、已移除设备、等待设备、等待数量
  和更新时间；等待数量只由等待设备列表计算。
- `Applied` 固定表示本机已经进入新安全状态，但仍在等待保留设备，不等于完成。

### 永久丢失设备恢复

普通离线、超时、网络失败、重启和自动重试都不能把设备判定为永久丢失。只有用户
明确确认当前等待设备已经永久丢失后，产品端才能提交一次恢复请求。

恢复继续使用原流程编号，并从已经生效的当前安全状态向前产生新代次。每轮新状态、
密钥目录、待发送更新和恢复进度必须原子保存；不得恢复旧代次，也不得把原流程简单
标记完成。被确认永久丢失的设备从后续成员集合和收件集合中排除，其他保留设备按代次
顺序补齐全部缺失更新，后一轮不能越过前一轮。

恢复请求只能选择当前仍在等待的设备。本机、已确认设备、已移除设备、无关设备、重复
设备和空列表都必须拒绝。安全状态损坏或分叉产生的“需要恢复”与永久丢失是两种问题，
不能使用永久丢失入口绕过失败关闭。

### 旧客户端与迁移

现有 Space 依次经过 `Legacy`、`Migrating`、`Ready`。只有所有保留成员满足安全换钥
能力后，Space 才进入 `Ready` 并提供可靠撤销。

迁移期间同一个成员移除入口可以返回明确的 `LocalOnly`：本机停止与目标同步并保存
加密撤销事实，但界面和接口不得宣称目标已被安全撤销。旧客户端可以读取已有内容，
不能参与新代次写入。不得因 P2P 或新代次协商失败自动退回 LAN 或旧共享密钥。

迁移窗口结束后删除 `LocalOnly` 分支，不长期保留两套成员移除实现。

### 恢复原则

- 每个阶段都先持久化事实，再产生可重试的外部动作。
- 重复开始同一撤销返回同一个进行中流程，不创建第二次换代。
- 重启时从持久撤销记录、群组状态和发送队列判断继续方向，不依赖内存状态。
- 无法证明可以安全回滚时，选择向前恢复或失败关闭。
- 日志只记录流程标识、代次、状态和计数，不记录密钥、正文、文件名或路径。
- 多轮撤销记录只在加密负载中保存；旧单轮记录读取为一轮，新写入只使用多轮格式。

## 后果

可靠撤销的成本与成员数和历史内容密钥数量相关，不与历史条目数或 blob 总大小相关。
保留成员继续读取历史，但需要保存仍被历史密文引用的旧内容密钥。旧客户端在迁移完成后
会失去新内容写入能力，这是安全边界，不作为兼容故障处理。

## 阶段 0 验证结果

OpenMLS 0.8.1 的独立验证于 2026-07-29 通过：

- 三成员撤销后，保留成员导出一致的新代次秘密；被撤销成员进入失效状态，无法导出
  新秘密，也无法处理新代次消息。
- 保留成员离线跨越两个代次时，直接处理后一个提交会被拒绝；按顺序补齐后恢复一致。
- 两个成员并发提交造成真实分叉后，可以通过重新加入恢复到同一群组和同一秘密。
- 群组状态经完整快照、销毁原提供器和冷载入后，代次及导出秘密保持一致。该测试只在
  内存中验证完整性；产品持久化必须由 MasterKey AEAD 加密后写入。
- 验证项目可为桌面、iOS、Android 和 HarmonyOS 的 Rust 目标编译。模拟器与真机运行
  均跳过，不计为通过。
- 开启分叉恢复和存储测试后的优化验收程序为 1,535,632 字节。该数字包含测试框架，
  只作为阶段 0 体积基线，不代表最终应用增量。

`crypto-debug` 和 `content-debug` 均未启用。验证代码固定依赖版本，并纳入工作区锁文件。
