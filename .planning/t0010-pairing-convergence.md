# t-0010 配对失败与进程退出后的双端收敛

## 完成标准

- 正式提交前，加入方失败、退出或失联都能由持久状态恢复或在共同期限后收尾。
- 邀请方不依赖对端通知，也能终结可证明尚未正式提交的候选；只清理该尝试未启用的准备资料。
- 正式提交后，即使回复丢失或越过期限也不回滚成员，并重放同一成功结果。
- 无法证明是否提交的旧记录进入 `NeedsAttention`，不自动清理。
- 未安全收尾的旧尝试阻止新尝试；候选状态不影响既有正式设备查询和使用。
- 独立进程矩阵、完整门禁、严格审查和本地原子提交完成。
- 真机与保留模拟器只在明确授权后原地验收；未执行时不得报告整体完成。

## Phase 14：加入收尾与成员移除不再锁住空间

### 现场事实

- 2026-09-22 21:29:38（本地时间），邀请方已经完成最终确认并提交正式成员；设备关系资料在 21:34:16 完成。
- 加入后剩余失败来自对端仍有一条旧版加入记录：该记录缺少当前版本的尝试期限，恢复时反复返回“需要升级”，没有进入明确终态，因而对端不运行普通维护并持续拒绝正式设备确认。
- 2026-09-22 23:20:51（本地时间），Desktop 发起移除。Engine 约半秒后返回失败；同一时刻本机成员历史变化已经唤醒维护，随后受限历史投递和安全资料更新失败。重启后的公开资料仍显示两个正式设备，整体状态继续延期。

### 可能失败方式（实现前固定）

1. 已终止加入只剩一条无法投递的放弃通知，却仍被算作“配对进行中”；对端要求升级时又没有保存可推进结果，导致普通维护永久没有运行资格。
2. 正式移除已经提交，但移除接口为了回显整份设备状态再次读取候选或安全资料；该读取失败后把已提交动作报告成失败，调用方无法区分“没有移除”和“已移除、后续待收尾”。
3. 被移除设备的受限通知或安全关系撤销长期无法送达；如果持久投递窗口没有开始、到期后没有删除精确核对记录，整体设备状态会永久停在更新中。
4. 移除后的旧加入记录、候选或历史确认仍参与新加入资格，造成同一设备无法重新加入，或重启后重新出现锁定。
5. 公开整体状态遗漏上述任一待处理事实会误报完成；反之，已经有界结束的通知若仍参与完成条件会永远不完成。

### 红绿验收

- [ ] 旧版、无共同期限的终止加入记录在不联网的情况下结束无法投递通知，保留终止围栏，普通维护恢复资格。
- [ ] 正式移除提交后，即使对端离线或公开状态的其他部分暂时不可读，也能返回“移除已提交、空间设备状态待收尾”的稳定结果，重复调用幂等。
- [ ] 被移除设备离线时，受限投递在固定窗口后只结束本次移除的投递记录；正式历史、身份和其他设备资料不被删除。
- [ ] 独立进程完成加入、等待整体状态完成、移除、同设备重新加入并重启，公开状态不会重新锁死。

## 安全边界

- 不清空、重置或静默改写身份、正式成员历史和已启用安全资料。
- 不依赖离线状态自动删除；主动通知只加快收尾，不是唯一机制。
- 不新增第二份配对模式开关；所有状态从同一份加密准入记录推导。
- 状态与安全资料变化必须在同一持久动作中完成，崩溃后可重复执行。
