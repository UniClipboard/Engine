# 成员移除等待与永久离线恢复方案

## 目标

让 Engine 独立负责成员移除的等待、重试、进度查询和永久离线恢复；产品端只发起移除、展示状态，并在用户明确确认设备永久丢失后提交一次恢复请求。

## 完成标准

- 第一次移除在本机生效后，明确返回仍在等待的设备，而不是提前宣称完成。
- 前一次移除未完成时，再移除其他设备会返回稳定、可识别的“已有移除正在进行”错误。
- 应用重启后，无需保存旧标识也能查询当前未完成的移除。
- Engine 能告诉产品端具体在等待哪些设备，并在进度变化时主动通知。
- 同一目标的重复移除返回原有进度，不创建第二个流程。
- 用户明确确认某个等待中的设备永久丢失后，Engine 能在不恢复旧安全状态的前提下继续向前完成。
- 永久离线恢复不会被普通超时、网络失败或产品端重试自动触发。
- iOS、Android、HarmonyOS 绑定返回完全一致的结果、错误和事件。
- A、B、C、D 场景、重启恢复、消息乱序和敏感信息检查全部通过。

## 唯一负责人

`uc-application` 的成员移除流程是唯一负责人。它负责：

- 判断是否允许开始新的移除；
- 创建和推进安全状态；
- 记录等待设备及确认结果；
- 自动重试和重启恢复；
- 执行用户明确授权的永久离线恢复；
- 产生统一的结果、错误和状态变化。

`uc-core` 只保存业务规则和状态约束，`uc-infra` 只负责加密保存、群组变更和消息投递，`uc-engine` 只提供稳定入口和组装。绑定只转换数据。产品端不得编排内部步骤。

## 产品端只需要三个入口

### 1. 移除设备

输入目标设备，返回当前移除快照。

可能结果：

- `applied`：本机已生效，仍在等待其他设备；产品文案必须显示为等待中；
- `complete`：所有保留设备已经确认；
- `recovery_required`：出现无法自动处理的状态损坏或分叉；
- 明确错误 `member_removal_in_progress`：另一项移除仍未完成。

保留现有 `local_only`、`applied`、`complete` 和 `recovery_required` 取值，避免为这次修复制造无关的破坏性变更。`applied` 的稳定含义固定为“仅本机生效，尚未完成”。

同一目标被再次移除时不报“找不到设备”，而是返回原有快照。

### 2. 查询当前移除

无需传入旧标识，返回当前未完成的移除快照；没有进行中的移除时返回空。

现有按标识查询可保留用于兼容和诊断，但产品主流程不依赖它。

### 3. 继续处理永久丢失设备

输入当前移除标识和用户明确确认永久丢失的设备列表。Engine 校验这些设备确实属于当前仍在等待的保留设备，然后继续向前推进。

该入口不是“强制完成”，也不能跳过仍被保留的设备。它表达的是：这些设备也不再保留，必须从新的安全状态中排除。

## 统一状态快照

产品端看到的快照至少包含：

- 当前移除标识；
- 已移除设备列表；
- 当前状态；
- 正在等待确认的设备列表；
- 最近一次状态变化时间；

保留现有等待数量字段以兼容已有使用方，但数量必须由等待设备列表计算，不能形成第二份事实。

稳定结果建议扩展为以下字段：

```text
MemberRevocationSummary
  revocation_id
  outcome
  removed_device_ids
  pending_recipient_device_ids
  pending_recipients
  updated_at_ms
```

`pending_recipients` 只作为兼容字段，始终等于 `pending_recipient_device_ids` 的长度。设备显示名和在线状态继续由现有设备列表提供，避免在移除结果中复制另一份易过期信息。

## 阻止第二次移除的错误

新增独立、稳定的错误类型 `member_removal_in_progress`：

- 归类为操作冲突，不再伪装成内部故障；
- 标记为稍后可重试；
- 不暴露数据库或群组协议错误文本；
- 桌面、移动和 HarmonyOS 能使用同一个错误编号；
- 产品收到错误后可直接显示“上一次设备移除仍在等待其他设备”，并读取当前移除快照展示详情。

现有笼统的群组移除失败只保留给真实的内部故障。

如果当前流程已经进入 `recovery_required`，再移除设备应返回另一个稳定错误 `member_removal_recovery_required`，避免产品误导用户继续等待网络恢复。

当前错误结构只适合携带编号、类别和是否可重试，不在这次改动中把业务详情塞入所有 Engine 错误。具体移除标识和等待设备由“查询当前移除”返回，保持错误契约小而稳定。

## 永久离线恢复规则

以 A、B、C、D 为例：

1. A 移除 B，本机进入新状态，C 和 D 是保留设备。
2. D 已确认，C 长期离线，状态显示等待 C。
3. A 再移除 D 时，Engine 返回 `member_removal_in_progress`，不会创建并行流程。
4. 用户确认 C 已永久丢失后，产品调用一次“继续处理永久丢失设备”。
5. Engine 在当前安全状态上继续向前，把 C 也排除；D 收到按顺序排列的所有缺失更新。
6. D 确认后，原移除流程完成，此后 A 可以继续移除其他设备。

关键约束：

- 永久离线恢复继续使用同一个移除标识，产品不管理多个相互依赖的任务。
- 已确认设备和仍保留但尚未确认的设备，都必须按顺序收到自己缺失的更新。
- 被标记永久丢失的设备不能取得恢复后的新安全状态。
- 如果没有其他保留设备，恢复可在本机完成。
- 普通离线、等待超时、应用重启和网络失败都不能自动把设备判定为永久丢失。
- 安全状态损坏或分叉导致的 `recovery_required` 与“设备永久离线”是两种不同问题，不共用一个恢复按钮。

## 入口执行顺序

新的移除请求必须先查询当前空间是否已有未完成流程，再检查目标是否仍在成员列表中：

1. 当前流程已包含同一目标：返回已有快照，实现重复请求幂等。
2. 当前流程正在等待，目标不同：返回 `member_removal_in_progress`。
3. 当前流程需要安全恢复：返回 `member_removal_recovery_required`。
4. 没有当前流程：再执行本机设备、目标存在性和空间保护状态检查，然后开始新移除。

这样可以避免第一次移除已经删除目标记录后，重复请求错误地变成“设备不存在”。

## 同一任务中的多轮安全更新

现有加密记录只保存一轮新状态和一组待发送消息，无法直接表达“B 已移除后，又因 C 永久丢失而继续向前”的第二轮更新。实施时把加密负载扩展为按顺序保存的多轮记录：

```text
MemberRevocation
  revocation_id
  originally_removed_device_id
  permanently_lost_device_ids
  generations[]

Generation
  previous_epoch
  next_epoch
  protected_group_state
  protected_key_catalog
  recipient_updates[]
```

规则如下：

- 第一次移除创建第一轮；每次用户确认新的永久丢失设备时追加一轮。
- 每轮只从当前已生效状态继续向前，不能替换或回滚旧轮次。
- 每台仍保留设备按轮次顺序接收缺失更新；后一轮不能越过前一轮。
- 一个设备只要仍缺少任意必需更新，就出现在等待设备列表中。
- 新一轮追加、当前安全状态切换和发送队列写入必须在同一次持久化提交中完成。
- 旧版单轮加密记录读取时视为只有一个元素的列表；新写入只使用多轮格式，不长期双写。

## 状态变化通知

新增成员移除状态变化通知，至少在以下时机发出：

- 第一次本机生效；
- 任一等待设备确认；
- 永久离线恢复开始并产生新状态；
- 全部完成；
- 进入需要安全恢复的状态。

通知携带完整当前快照。产品端只需替换旧状态，不负责推导差异或安排重试。

## 持久化与隐私

- 当前移除、等待设备、确认结果和恢复步骤继续放在加密负载中。
- 不新增明文设备标识、设备名、文件名或路径。
- 数据库只保留恢复和唯一约束所需的随机标识、代次、状态和时间。
- 永久离线恢复作为原流程中的追加步骤保存，不删除或覆盖已经生效的安全事实。
- 日志只记录移除标识、状态、代次和数量。

## 必测场景

1. A 移除 B，C 在线并确认：直接完成。
2. A 移除 B，C 离线：返回等待 C，B 是否在线不影响结果。
3. 等待 C 时移除 D：返回明确的进行中错误。
4. 等待 C 时再次移除 B：返回原有进度。
5. C 重连：先补安全状态，再恢复业务同步，随后完成。
6. 应用在等待期间重启：当前移除仍可直接查询，自动重试继续。
7. 用户确认 C 永久丢失：C 被继续排除，其他设备按顺序确认后完成。
8. 用户试图把本机、已确认设备或无关设备标记为永久丢失：明确拒绝且状态不变。
9. 永久离线恢复中再次重启：恢复继续，不能重复生成新状态。
10. 消息重复、乱序和确认重复：结果保持一致。
11. 安全状态损坏：进入需要安全恢复，不允许使用永久离线流程掩盖。
12. 数据库与日志扫描：不出现设备标识、设备名或其他敏感业务内容明文。

## 不采用的方案

- 不允许产品端自行安排重试、拼接多次移除或推导安全状态。
- 不把等待超时自动视为设备永久丢失。
- 不提供不改变成员状态的“强制完成”。
- 不用错误字符串表达“已有移除正在进行”。
- 不把新的恢复流程做成第二套成员移除实现。
