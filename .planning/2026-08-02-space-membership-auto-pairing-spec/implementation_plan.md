# Space Membership Gossip 实施计划

## 总体原则

第一版只交付“通讯录传播、当前成员确认、三设备离线收敛”。复杂 CRDT、Kademlia、libp2p、成员历史合并和并发安全变更均不进入第一版。

旧关系数据加密作为并行工作线推进，但它是正式交付前的硬门槛。

## Phase 0：关键前提验证

### 目标

用最小实验验证第一版依赖的三个技术前提，避免完成大量代码后才发现核心路径不成立。

### 验证内容

- 三个独立节点中，A 仅从 B 获得 C 的持久地址，验证 A 能直接连接 C。
- 使用当前 OpenMLS 成员私钥签名握手内容，并由另一成员从当前成员树验证。
- B 接纳 C 后，把 A 缺少的安全更新交给 C；B 停止后，C 能把更新转交给 A 并由 A 成功应用。

### 测试驱动方式

- 本地自动化增加三 Engine 测试驱动器，直接使用 `Engine::start`、公开操作和生命周期入口；每个实例使用独立目录、密钥存储和宿主剪贴板。
- 为避免依赖外部服务，测试构建可以使用现有开发验收能力选择本地邀请地址；该能力不得进入发布产物。
- 现有应用 facade 级网络测试保留为聚焦验证，但不得替代 Engine 最外层完整流程。
- 真机验收通过 `tests/hosts/` 下的 iOS、Android 和 HarmonyOS 最小宿主驱动，不新增正式 CLI。

### 反例

- 地址中的 direct 项已经过期。
- 仅保留 NodeId 和 relay。
- 签名设备编号与成员树身份不一致。
- P2P 公钥与签名内容不一致。
- 更新缺少中间版本或顺序错误。
- 被移除成员使用旧状态签名。

### 退出条件

- 三项验证都有可重复的自动化结果。
- sponsor 离线后的更新转交成立。
- 若任一前提不成立，先修改规格，不进入 Phase 1。

### 删除项

- 删除验证用固定密钥、固定地址和静态放行。
- 删除被证伪的方案分支。

## Parallel A：敏感关系数据加密迁移

### 目标

把现有成员、信任和地址记录迁移为密文，并为 Gossip 新数据提供同一加密存储规则。

### 修改范围

- 增加新格式的加密关系存储。
- 解锁后逐条迁移旧记录。
- 每条新记录写入后立即解密校验，再删除对应旧记录。
- 保存迁移进度，支持中断后继续。
- 增加数据库版本保护，阻止旧版本误读新数据库。

### 验证

- 新建、升级、中断、恢复和重复迁移。
- 锁定状态不能读取或迁移敏感关系。
- 使用代表性设备名、指纹和地址运行明文探针扫描。

### 退出条件

- 不再写入明文关系数据。
- 不保留新旧双写。
- 必须在 Phase 5 真实设备验收前完成。

### 删除项

- 删除旧明文写入路径和临时迁移兼容层。
- 删除降级所需的明文副本。

## Phase 1：空间通讯录与候选状态

### 目标

建立“知道如何联系，但尚未信任”的空间通讯录，并让待办跨重启恢复。

### 负责模块

`uc-application::SpaceMembershipGossip` 负责完整状态；`uc-infra` 提供加密存储。

### 修改范围

- 增加 sponsor 候选种子、设备自签名公告、公告序号和通讯录摘要。
- 增加候选状态、失败分类、下一次尝试时间和信息来源。
- 增加按当前空间隔离的加密候选仓储。
- 增加重复合并、地址新旧判断、身份冲突和过期清理。
- 增加正式关系的原子或可恢复提升入口。

### 验证

- 重复种子、旧地址、新地址、公告序号倒退和身份冲突。
- 切换空间后，旧空间候选不能触发连接。
- 候选不能通过普通 presence、剪贴板和文件准入。
- 写入任一步失败或进程退出后，重启不会得到半套正式关系。
- 数据库明文扫描。

### 退出条件

- 通讯录和正式成员有明确边界。
- 所有可重试状态都能持久恢复。
- 外部调用方不需要逐步推进候选状态。

### 删除项

- 删除把 sponsor 通讯录直接写入正式成员表的入口。
- 删除产品端或 Engine 逐步编排候选状态的接口。

## Phase 2：双设备安全确认

### 目标

两台已经处于同一当前 OpenMLS 成员树、但本地尚未互相登记的设备，在已知地址时自动建立正式关系。

### 修改范围

- 增加独立 Gossip P2P 通道和有界消息。
- 增加挑战、双方 OpenMLS 独立成员签名和确认消息。
- 签名绑定空间、安全版本、双方设备编号、双方 P2P 公钥、随机挑战和设备公告。
- 从当前成员树查找声明设备的签名公钥并验证。
- 验证成功后原子写入成员、信任、最新地址和候选完成状态。

### 验证

- 两节点从互不入册到双向正式登记，再完成一次文本同步。
- 错空间、错误签名、设备编号冒用、P2P 公钥不一致、重放和超限消息全部拒绝。
- A 已应用移除更新后，旧成员签名不能通过当前成员树验证。
- 双方同时拨号只产生一组正式关系。

### 退出条件

- Issue #953 的最小正反例完成。
- 证明前连接无法触达普通业务通道。
- 不使用空间共享密钥冒充设备独立身份。

### 删除项

- 删除测试用固定证明和静态成员放行。
- 删除使用共享空间秘密证明具体设备身份的路径。

## Phase 3：配对 v5 与通讯录传播

### 目标

C 通过 B 加入后获得 A 的候选信息，B 也为 A 保存 C 的候选公告。

### 修改范围

- pairing wire 升级到 v5，增加有界通讯录种子。
- sponsor 收集正式成员地址和本次生成的连续安全更新。
- joiner 把老设备保存为候选，不写正式成员。
- sponsor 为在线和离线老设备生成持久的新设备公告待办。
- 增加 `Digest`、`RequestMissing`、`EventBatch` 和 `Ack`。
- 新设备与已知成员直接连接时，用设备自己的签名公告替换第三方提示。

### 验证

- A、B 在线，C 经 B 加入后，A 与 C 无需额外操作完成互认。
- A 离线时，C 本地保存 A 的候选、地址和安全更新。
- 空通讯录、重复条目、超限消息、损坏地址、身份冲突和 v4/v5 组合。
- 配对成功但通讯录待办写入失败时，不允许静默丢失。

### 退出条件

- Issue #954 按 v5 和候选语义完成。
- 三台在线设备加入后自动形成完整直连关系。

### 删除项

- 删除在 v4 上追加字段的兼容假设。
- 删除 sponsor 与 joiner 重复实现的通讯录保存规则。

## Phase 4：离线收敛、重启与生命周期

### 目标

A 离线时 C 经 B 加入；之后 B 离线，A 与 C 仍能自动补齐并直接同步。

### 修改范围

- C 持久保存并转交 A 缺少的连续 OpenMLS 更新。
- A 应用更新后再验证 C 的独立成员签名。
- 增加首次立即尝试、带随机偏移的退避、低频摘要核对和单候选互斥。
- 启动、解锁、暂停、恢复和关闭接入 Engine 生命周期。
- 已知正式成员上线只作为提前唤醒信号。
- 缺少中间安全更新时保持等待，不跳过版本。

### 验证

- A 离线、C 经 B 加入、B 关闭、A 上线、A 与 C 自动互认并直接同步。
- A 或 C 在候选写入后、安全更新后、签名后和正式提升中途分别退出并恢复。
- 长期离线不持续空转；事件丢失仍由低频核对补偿。
- 重复公告、重复安全更新和响应丢失保持幂等。
- 暂停和关闭后没有遗留网络任务。

### 退出条件

- Issue #955 的核心场景通过，收敛时 B 不在线。
- 测试使用有截止时间的状态等待，不使用固定 sleep 作为成功依据。

### 删除项

- 删除散落在 Engine 中的成员 Gossip 重试循环；Engine 只持有运行句柄。
- 删除依赖 sponsor 在线才能完成的路径。

## Phase 5：状态、收口与真实设备验收

### 目标

让产品看到真实收敛状态，并用交付构建完成三设备验收。

### 修改范围

- 增加 `Complete`、`Converging`、`WaitingForUpgrade` 和 `Blocked` 状态。
- 增加不含设备身份的待办数量和失败原因计数。
- 审核日志和调试输出的脱敏。
- 清理过渡入口和重复状态来源。

### 自动化验证

- 状态与真实候选一致，重启后不会错误显示完成。
- v4 sponsor 明确要求升级且不部分写入。
- 已有 v4 老设备使空间保持等待升级，升级后自动补齐。
- 日志不包含设备名、指纹、完整地址、证明和密钥。
- 完整仓库检查、密文探针和关闭测试通过。

### 真实设备流程

1. A 与 B 已在同一空间。
2. A 离线。
3. C 通过 B 加入。
4. B 离线。
5. A 上线。
6. 等待 A 与 C 自动互认。
7. A 与 C 双向发送文本并核对内容。
8. 重启 A、C 后再次直接同步。

### 退出条件

- Parallel A 已完成。
- 至少三台真实设备使用同一交付构建完成核心流程。
- 每个平台分别记录“通过”“失败”或“跳过”；未执行绝不记为通过。
- 产品调用方只执行加入和读取状态。

### 删除项

- 删除测试固定地址、固定签名和内存捷径。
- 删除不再需要的旧协议入口和迁移开关。

## 后续路线图

第一版完成后单独规划：

- Issue #952 的复杂多分支收敛。
- 并发 OpenMLS 成员变更的排序、冲突检测和恢复。
- 通用 Membership CRDT 或更大规模摘要结构。
- Kademlia、DHT 或其他无 sponsor 地址发现。
- libp2p、WebRTC 或其他传输实现的必要性评估。
- 多活动空间。

这些项目不得提前扩张第一版的外部接口。
