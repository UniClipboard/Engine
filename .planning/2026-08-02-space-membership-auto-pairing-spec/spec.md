# Space Membership Gossip 规格

## 1. 目标

设备通过空间中的任意现有设备加入后，自动获得空间通讯录，并在后台与其他设备建立直接关系。

第一版必须完成一个核心场景：

1. A 与 B 已在同一空间。
2. A 离线。
3. C 通过 B 加入。
4. B 离线。
5. A 上线。
6. A 与 C 自动认识并直接同步，不要求用户再次配对。

## 2. 采用的方案

采用 `Space Membership Gossip`。

它的基本规则是：

- 每台设备保存一份本地空间通讯录。
- 已经建立连接的设备互相交换通讯录摘要。
- 双方只发送对方缺少或已经过期的信息。
- 第三方提供的信息只能帮助找到设备，不能直接产生信任。
- 两台设备直接确认对方仍属于当前空间后，才正式建立关系。

## 3. 两类事实

本方案严格区分两类事实。

### 3.1 OpenMLS：当前成员资格

OpenMLS 是“谁现在仍属于空间”的唯一依据，负责：

- 成员加入。
- 成员移除。
- 安全版本推进。
- 每台设备独立的成员签名身份。

通讯录、旧成员表、旧地址或长期共享秘密都不能替代当前 OpenMLS 成员状态。

### 3.2 Gossip：空间通讯录

Gossip 负责传播：

- 设备编号。
- 设备名称提示。
- P2P 地址。
- 地址版本。
- 对方可能缺少的连续安全更新。
- 通讯录条目的来源和新旧程度。

Gossip 信息先进入候选区。只有直接确认成功后，候选才提升为正式成员、信任和地址关系。

## 4. 当前代码缺口

当前配对是严格的一对一闭环：sponsor 和 joiner 只为彼此保存成员、信任和地址记录。

无法自动扩展到全空间的原因是：

- 当前加入确认没有空间通讯录。
- 本地成员登记不会向其他设备传播。
- 在线探测只处理本机已经保存地址的正式成员。
- 普通连接要求对端已经是正式成员并通过当前空间保护检查。
- sponsor 已生成给老设备的安全更新，但没有把可转交更新交给 joiner。

## 5. 第一版范围

### 5.1 包含

- 加入时把已有设备通讯录交给新设备。
- sponsor 把新设备信息传播给在线老设备。
- 新设备主动联系当时离线的老设备。
- 设备之间交换有界通讯录摘要和差异。
- 使用 OpenMLS 独立成员签名完成双向身份确认。
- 转交并按顺序应用对方缺少的安全更新。
- 候选和待办的加密保存、重启恢复、退避重试和关闭。
- 当前收敛状态查询。

### 5.2 暂不包含

- 通用 Membership CRDT。
- Kademlia、DHT、libp2p 或 WebRTC。
- Git 式成员历史合并。
- 同时发生多个成员加入或移除时的自动分叉合并。
- 多个活动空间同时运行。
- P2P 失败后自动切换到 LAN 兼容线。

这些内容进入后续路线图，不作为第一版完成条件。

## 6. 唯一负责模块

`uc-application` 新增 `SpaceMembershipGossip`，它负责完整结果。

它内部拥有：

- 通讯录种子接收。
- 候选合并。
- 摘要与差异交换。
- 安全更新转交。
- 双向成员确认。
- 正式关系提升。
- 定时重试、启动恢复、暂停和关闭。
- 状态汇总和错误分类。

其他层职责：

- `uc-core`：保存通讯录条目、候选状态和纯判断规则。
- `uc-infra`：实现加密存储、OpenMLS 签名、P2P 通道和地址处理。
- `uc-engine`：安装一次、持有运行句柄、关闭时停止。
- 产品端：继续只调用“加入空间”，可选读取收敛状态。

产品端不得逐步调用“请求通讯录、应用更新、验证签名、写入成员、安排重试”。

## 7. 通讯录数据

### 7.1 设备公告

每台设备可以直接声明自己的设备公告：

- 设备编号。
- 设备名称。
- 当前可转交 P2P 地址。
- 单调递增的公告序号。
- 当前 OpenMLS 安全版本。
- 过期时间。
- 设备自己的 OpenMLS 成员签名。

公告序号用于比较新旧，不依赖设备系统时间。

第三方可以转发设备公告，但不能修改。接收方只有在当前 OpenMLS 成员树中找到该设备并验证签名后，才能把公告视为已验证自述。

### 7.2 sponsor 种子

新设备刚加入时，老设备可能还没有生成新版自签名公告。sponsor 可以提供候选种子：

- 已知设备编号、名称提示和身份指纹提示。
- 已知 P2P 地址及观察时间。
- 信息来源。
- 该设备可能缺少的连续安全更新。

sponsor 种子只用于寻找目标。目标设备直接响应后，以目标自己的签名公告替换第三方提示。

### 7.3 通讯录摘要

第一版空间规模较小，不引入 Merkle Tree 或通用 CRDT。摘要直接包含有界版本表：

- 本地 OpenMLS 安全版本。
- 当前安全更新头摘要。
- 每个设备的最新公告序号和内容摘要。

发现差异后，请求缺少的公告或安全更新。所有消息都有条目数、字节数和频率上限。

## 8. 加入与传播流程

### 8.1 C 通过 B 加入

1. C 与 B 完成现有一对一配对。
2. B 在 OpenMLS 中接纳 C，并生成从版本 N 到 N+1 的更新。
3. B 把 OpenMLS Welcome 安装材料交给 C。
4. B 同时把 A、B 的通讯录种子和 A 需要的 N 到 N+1 更新交给 C。
5. C 把 A 保存为候选，不写正式成员和信任。
6. B 为 A 保存 C 的候选公告；A 在线时立即发送，离线时保留待办。

### 8.2 A 当时离线

1. C 持久保存 A 的地址和安全更新。
2. C 立即尝试一次，失败后退避。
3. B 可以离线，不影响 C 的待办。
4. A 与 C 第一次同时可达时，C 主动连接 A。
5. C 把 A 缺少的连续 OpenMLS 更新转交给 A。
6. A 验证并应用更新，在当前成员树中看到 C。
7. A 与 C 完成双向签名确认。
8. 双方正式保存成员、信任和最新地址。
9. 现有 presence 和剪贴板同步路径接管后续连接。

## 9. Gossip 协议

使用独立 P2P 通道：

```text
uniclipboard/membership-gossip/1
```

第一版消息类型：

- `Digest`：本地安全版本和通讯录版本摘要。
- `RequestMissing`：请求缺失公告或连续安全更新。
- `EventBatch`：发送有界公告和安全更新。
- `AttestationChallenge`：发出随机挑战。
- `AttestationProof`：返回设备独立签名。
- `Ack`：确认已经持久应用。

未知设备可以进入该通道，但证明完成前只能访问上述消息，不能触达普通 presence、剪贴板、文件或历史能力。

## 10. 双向成员确认

不能使用空间成员共享的同一秘密证明具体设备身份，因为任意当前成员都可能伪造另一个设备的声明。

双方使用各自在 OpenMLS 成员树中的独立 Ed25519 签名密钥。

签名内容至少绑定：

- 协议名称和版本。
- 当前空间和 OpenMLS 安全版本。
- 发起方与接收方设备编号。
- 双方当前 P2P 公钥。
- 双方随机挑战。
- 双方设备公告摘要。
- 本次转交的安全更新摘要。

接收方从当前 OpenMLS 成员树查找声明设备对应的签名公钥并验证。验证成功意味着：

- 对方持有该 OpenMLS 成员的私钥。
- 该成员仍存在于本地当前成员树。
- 证明只适用于本次 P2P 连接。

## 11. 安全版本落后与移除

安全更新只能从本地版本的下一版开始连续应用。缺少中间版本时保持等待，不能跳过验证。

已更新到最新移除结果的设备，不会在当前成员树中找到被移除设备的签名公钥，因此必须拒绝其公告和互认请求。

客观限制：长期离线设备在收到移除更新前无法凭空知道空间已经变化。第一版保证它从任意当前成员取得连续更新后立即按最新成员状态判断，不承诺完全隔离期间的实时撤销。

## 12. 候选与正式关系

候选表示“知道如何联系，但尚未直接确认”。候选不能通过普通业务准入。

候选状态：

- `Pending`：等待首次尝试。
- `WaitingForPeer`：对端离线或地址不可用。
- `WaitingForUpdate`：缺少连续安全更新。
- `Verifying`：正在完成双向确认。
- `Ready`：已经正式互认。
- `Blocked`：版本不兼容或身份冲突。
- `Rejected`：证明无效或不属于当前成员树。

成功提升时，成员、信任、地址和候选完成状态必须原子提交或具备完整恢复记录，不能留下半套关系。

## 13. 存储与迁移

- 新候选、设备公告、地址、安全更新和重试状态必须加密保存。
- 现有成员、信任和地址中的敏感字段需要迁移为密文。
- 旧数据迁移作为并行工作线推进，不阻塞早期网络与协议验证。
- 正式交付前必须完成迁移，不能保留明文双写。
- 升级后不支持旧版本读取新的加密数据库。

## 14. 传播时机

第一版采用事件驱动加低频核对：

- 配对完成后立即传播。
- Engine 启动、解锁或恢复时核对。
- 已知正式成员上线时核对。
- 本机地址或设备公告变化时传播。
- 后台低频定时核对，并加入随机偏移。
- 失败后按退避时间重试，长期离线设备不持续空转。

现有 presence 只作为已知正式成员上线的唤醒信号，不能作为未知成员发现来源。

## 15. 版本兼容

- 当前 pairing wire v4 不追加字段后继续使用原版本号。
- 携带通讯录种子的 pairing 使用 v5。
- v5 joiner 遇到 v4 sponsor 时明确提示升级，不做部分写入。
- 空间中已有 v4 设备时，新加入可以完成，但空间状态保持“等待设备升级”。
- Gossip 协议使用独立版本，未知版本显式拒绝。
- P2P 失败不能自动退回 LAN 兼容线。

## 16. 第一版验收

### 核心场景

- A 离线，C 经 B 加入；B 离线后 A 上线，A 与 C 自动互认并直接完成一次文本同步。
- A 或 C 在互认前重启，恢复后仍能完成。
- 互认完成后重启 A、C，双方仍能直接同步。

### 安全

- 候选在证明前不能使用普通同步和文件能力。
- 错空间、错误签名、连接公钥不一致和重放均被拒绝。
- A 应用移除更新后，被移除设备无法重新互认。
- 本地锁定时不解密候选、不发起 Gossip。
- 数据库和缓存中找不到代表性设备名、指纹和地址明文探针。

### 恢复与兼容

- 候选、公告和重试进度跨重启恢复。
- 重复公告、重复更新和重复确认保持幂等。
- v4/v5 行为明确，不出现半套加入或虚假的“全部完成”。
- 暂停和关闭后没有遗留后台任务。

## 17. 后续路线图

第一版完成后再评估：

- 多分支通讯录反熵。
- 同时发生多个 OpenMLS 成员变更时的排序和恢复。
- 更大规模摘要结构。
- Kademlia 或其他无 sponsor 地址发现。
- 多活动空间。
- 是否需要新的传输实现。

这些方向不能反向扩大第一版接口；产品端仍只执行加入和读取状态。

## 18. 完成定义

第一版只有在以下条件全部满足后才算完成：

1. `SpaceMembershipGossip` 独自拥有通讯录传播、确认、重试、恢复和关闭。
2. 第三方转交地址的三节点真实网络验证成立，或已经采用替代发现方式。
3. 核心三设备离线场景通过，收敛时 sponsor 不在线。
4. OpenMLS 独立成员签名和移除反例通过。
5. 新旧敏感关系数据均以密文保存。
6. 至少三台真实设备使用交付构建完成核心场景。
7. 未执行的平台或设备项目明确记为“跳过”，不得记为“通过”。
