## Key Questions

1. 当前加入空间为何只建立一对一关系，信息在哪一层丢失？
2. 谁应负责从“加入完成”推进到“空间成员最终全部互认”？
3. 新设备、在线老设备和离线老设备如何通过通讯录 Gossip 获得彼此信息？
4. 哪些信息可以安全持久化，哪些必须加密？
5. 如何兼容现有设备和旧协议，且不暗中退回 LAN？
6. 怎样证明发起配对的设备离线后，其余设备仍能直接同步？

## Decisions Made

| Decision | Rationale |
|----------|-----------|
| 当前任务只调查并产出文档，不修改生产代码 | 用户要求先探索并给出规格计划 |
| 新建独立规划目录 | 旧的活动计划已完成且属于不同功能 |
| 以 Issue #950-#955 为需求背景，但以当前代码为事实来源 | Issue 可能滞后，计划必须能落到当前仓库 |
| 当前 OpenMLS 成员树是成员资格依据，每台设备用自己的成员签名确认身份 | 当前代码已支持安全移除；长期旧密钥和共享空间秘密都不能证明具体设备仍是成员 |
| sponsor 向 joiner 转交受保护更新，互认前先补齐保护版本 | 满足 sponsor 离线后新老设备仍能收敛，同时不绕过移除保护 |
| pairing wire 使用 v5，候选不直接入正式成员表 | 当前 v4 已存在且不兼容新增字段，第三方信息也不能直接授予信任 |
| 采用 Space Membership Gossip | 设备互相交换空间通讯录，新设备不再只认识 sponsor |
| OpenMLS 是当前成员资格唯一依据 | Gossip 只传播信息，不能决定谁有权限 |
| 设备使用自己的 OpenMLS 成员签名 | 共享空间秘密不能区分具体设备，独立签名可绑定设备编号与 P2P 公钥 |
| 第一版不做通用 CRDT 和复杂分支合并 | 当前目标只需要完成三设备离线后自动互认 |
| 旧关系加密作为并行工作和发布门槛 | 不阻塞网络与协议验证，但正式交付前必须完成 |
| 不新增正式 CLI；自动化测试直接使用 Engine 稳定入口，真机使用验收宿主 | 仓库已有稳定入口和移动验收宿主，测试驱动能力不应进入产品接口 |

| 原子提交回滚测试首次编译失败，缺少统一提交入口 | 1 | 预期红灯；下一步由加密关系存储实现单次提交能力并注入 Gossip 负责人 |
| 聚焦测试首次传入多个 Cargo 过滤参数 | 1 | 改为运行完整宿主边界测试文件并取得有效红灯 |
| 本机编译缓存进程被系统权限拦截 | 2 | 对本轮 Cargo 与架构检查禁用该缓存后全部通过 |
| iOS 模拟器无签名构建无法访问系统安全存储 | 1 | 增加先失败的约束测试，改为本地临时签名后构建、启动和安全存储通过 |
| Android 模拟器构建复用损坏的临时目录 | 1 | 增加先失败的约束测试，默认使用独立干净目录后构建和安装通过 |
