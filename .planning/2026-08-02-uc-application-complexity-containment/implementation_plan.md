# uc-application 复杂度收口实施计划

## 总体原则

- 前置计划 `.planning/2026-08-02-space-setup-deps-design/` 已完成并通过验收；本计划可以从 Phase 1 开始。
- 每个阶段只迁移一个完整功能，独立提交，保持可回退和可比较。
- 先固定稳定 Engine 行为，再替换内部所有权，最后删除旧入口。
- 不以增加包装层或依赖分组作为完成标准。
- 每个阶段结束时必须删除被替代实现，不保留两套流程。

- [x] 完成空间计划的 Phase 0 至 Phase 8。
- [x] 将搜索、接收准备和成员活动纳入空间会话的固定顺序和失败补偿。
- [x] 将成员传播运行期和成员恢复移出引擎层。
- [x] 删除重复的加密生命周期入口和空壳生命周期入口。
- [x] 保持 Engine 公开操作和错误码不变。

### 退出条件

- [x] 当前空间计划全部完成并独立提交。
- [x] 引擎层解锁、恢复和锁定各只调用一次空间动作。

## Phase 1：固定剩余功能的现有行为

### 目标

在移动内部责任前，固定剪贴板接收、移动上传、文件传输和历史维护的现有可观察行为。

### 工作内容

- 通过稳定 Engine 入口覆盖剪贴板入站成功、重复、解码失败、文件失败和关闭。
- 覆盖只保存拉取与普通接收之间的行为差异。
- 覆盖移动上传开始、追加、完成、取消、追加失败、进度失败和关闭清理。
- 覆盖文件传输只有一个终态。
- 覆盖历史维护的执行顺序和现有失败策略。
- 记录当前错误码、宿主事件和状态结果，禁止把内部步骤固化成新测试契约。

### 退出条件

- 每项行为都有通过稳定入口或新负责人最终 Interface 的保护。
- 未新增对旧内部步骤的直接测试依赖。
- 行为保护形成独立 commit。

## Phase 2：收口搜索构造与运行期

**状态：已完成。**

### 目标

消除搜索半装配状态，并完成与空间会话负责人的连接。

### 工作内容

- 将生产搜索改为一次完整构造。
- 引入 `SearchRuntime` 持有后台协调和关闭。
- 删除运行中补装协调者的入口。
- 删除引擎层对搜索会话恢复的直接调用。
- 为只读测试提供明确构造方式，不复用生产半装配状态。

### 退出条件

- [x] 生产搜索构造后立即完整可用。
- [x] 重复安装导致进程终止的路径已删除。
- [x] 解锁、恢复、锁定和关闭测试保持通过。
- [x] 旧搜索安装入口和对应测试已删除。

## Phase 3：建立完整剪贴板入站模式

### 目标

把任意可选能力组合替换为少数明确且完整的入站模式。

### 工作内容

- 定义 `InteractiveReceive` 和 `StoreOnlyPull` 两种完整模式。
- 为每种模式列出必需能力和明确结果。
- 将文件落地、接收记录、搜索、活动剪贴板、重复内容和宿主事件按模式集中构造。
- 删除生产路径上的连续 `with_*` 拼装。
- 保持普通接收与只保存拉取的现有差异。

### 退出条件

- 无法构造缺少必需能力的生产入站对象。
- 同一模式只有一个构造位置。
- 普通接收、拉取、移动导入和测试路径使用明确模式。
- 旧可选拼装入口已删除或缩为仅内部测试可用的真实 Seam。

## Phase 4：收口剪贴板入站运行期

### 目标

让 `ClipboardInboundRuntime` 完整拥有接收、应用、确认、事件和关闭。

### 工作内容

- 将通知订阅、通知转换、应用结果和接收确认移入应用层。
- 将接收后台循环及其退出原因移入 `ClipboardInboundRuntime`。
- 将宿主事件从完整应用结果统一产生。
- 提供一次启动和一次关闭 Interface。
- 删除引擎层入站循环和结果分支。

### 退出条件

- 引擎层只启动和关闭一个入站运行期。
- 单条通知一定被确认成成功、重复或失败。
- 关闭会等待桥接和接收任务退出。
- 原引擎入站循环及其测试已删除。

## Phase 5：建立文件传输会话

### 目标

让每次文件传输从开始到唯一终态由同一个应用对象负责。

### 工作内容

- 引入内部 `FileTransferSession`。
- 创建会话时完成接收方记录和开始状态。
- 集中进度检查、节流和宿主事件。
- 保证完成、失败和取消互斥、幂等。
- 增加运行期关闭时的活动会话终结。
- 先迁移一条真实入站路径，验证形状后再迁移 Blob 和移动上传。

### 退出条件

- 所有传输都有唯一终态。
- 调用方不再直接调用传输开始、失败或完成。
- 原逐步状态入口不再由 `AppFacade` 公开。
- 旧状态推进测试已由会话 Interface 测试替代。

## Phase 6：收口移动文件上传

### 目标

让应用层完整管理上传句柄、临时文件、进度、终态和关闭清理。

### 工作内容

- 引入 `MobileFileUploadCoordinator`。
- 把活动上传表和不透明句柄生成移入应用层。
- 把临时写入范围、字节统计和进度节流移入应用层。
- 每个上传绑定一个 `FileTransferSession`。
- 追加或完成失败时自动取消临时写入并记录终态。
- 关闭时终结所有仍活动的上传。
- Engine operation 保持开始、追加、完成、取消四个稳定动作，只做输入和结果转换。

### 退出条件

- 引擎层没有活动上传表和临时文件句柄。
- 所有失败分支通过同一清理实现。
- 重复、未知和并发操作得到稳定结果。
- 旧上传管理代码和重复清理分支已删除。

## Phase 7：收口历史维护运行期

### 目标

把维护顺序、间隔、失败策略和关闭收回历史功能。

### 工作内容

- 引入 `HistoryMaintenanceRuntime`。
- 合并启动时维护和定时维护的执行路径。
- 保持缺失文件核对失败时跳过本轮其余步骤的现有规则。
- 保持文件清理失败不阻止保留策略的现有规则。
- 将维护结果汇总和脱敏日志放入应用层。
- 删除引擎层维护接口和循环。

### 退出条件

- 引擎层只启动和关闭历史维护运行期。
- 维护策略只有一份实现。
- 关闭可以立即结束等待中的任务。
- 原引擎维护模块已删除。

## Phase 8：收紧 AppFacade

### 目标

在各功能已经拥有完整流程后，删除绕过入口和半就绪构造。

### 工作内容

- 将 `AppFacade` 内部字段改为私有。
- 保留面向用户动作的方法，删除内部对象 getter 和重复直达路径。
- 将两阶段网络装配集中到唯一 assembly 文件。
- 让运行期只接收完整构造的 `AppFacade`。
- 用明确装配配置替代生产对象中的大量缺失能力状态。
- 删除运行中一次性安装多个功能的入口。
- 删除重复安装导致进程终止的路径。

### 退出条件

- `uc-engine` 无法直接访问应用内部对象。
- 每个 Engine operation 只有一条应用调用路径。
- 应用对象交给运行期时已完整可用。
- 没有新增只转发、不隐藏复杂度的 Module。

## Phase 9：删除旧实现并做架构验收

### 目标

确认所有功能只剩一套流程，并防止复杂度重新外溢。

### 工作内容

- 删除通用生命周期空壳、旧运行期、旧可选构造和旧测试。
- 为以下行为增加架构检查：
  - 引擎层不得订阅并编排剪贴板入站通知。
  - 引擎层不得推进文件传输内部状态。
  - 引擎层不得持有活动移动上传表。
  - 引擎层不得直接恢复搜索或成员后台活动。
  - `AppFacade` 不得公开内部对象字段。
- 对每项负责人执行删除检查。
- 检查生产代码中不新增 `unwrap()`、`expect()`、`println!()` 或 `eprintln!()`。
- 检查日志不包含敏感内容。

### 自动化验证

按改动范围依次运行：

```bash
cargo test -p uc-application --locked
cargo test -p uc-engine --locked
cargo metadata --locked --format-version 1
cargo check --workspace --all-targets --locked
cargo fmt --all -- --check
node scripts/architecture/check-engine-repository.mjs
git diff --check
```

涉及真实网络和设备的验收沿用对应功能既有场景。未执行的设备项目记录为“跳过”，不得计为通过。

### 退出条件

- 规格中的整体验收项全部满足。
- 每个阶段有独立、可说明的 commit。
- 工作区只保留有意留下的后续计划文件。

## 推荐提交顺序

1. `test(application): preserve application workflow behavior`
2. `refactor(search): own search runtime lifecycle`
3. `refactor(clipboard): define complete inbound modes`
4. `refactor(clipboard): own inbound runtime`
5. `refactor(transfer): own file transfer sessions`
6. `refactor(mobile): own streaming upload lifecycle`
7. `refactor(history): own maintenance runtime`
8. `refactor(application): close internal facade access`
9. `chore(architecture): enforce application ownership`

提交名称可按实际改动微调，但不得把多个独立功能合成一个大提交。
