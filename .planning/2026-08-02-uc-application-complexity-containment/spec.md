# uc-application 复杂度收口规格

## 1. 目标

在不改变 `uc-engine` 稳定公开行为的前提下，让 `uc-application` 对每项跨层功能负责完整结果，使 `uc-engine` 不再掌握内部步骤、失败补偿、后台重试和关闭顺序。

本规格覆盖以下功能：

- 空间会话相关的搜索恢复和成员恢复。
- 剪贴板入站接收。
- 文件传输状态和移动文件上传。
- 历史维护。
- 成员查询与成员变更职责。
- `AppFacade` 的完整构造和调用入口。
- 无实际恢复能力的通用生命周期入口。

## 2. 完成标准

每项功能必须同时满足：

1. 有且只有一个负责完整结果的 Module。
2. 调用方只执行一个用户动作，或启动、关闭一个运行期。
3. 调用方不决定内部顺序、失败补偿、重试时机和持久化步骤。
4. 构造完成后即可使用，不存在生产环境下“稍后补装能力”的半成品状态。
5. 每次开始的长流程最终都进入成功、失败或取消，不留下永久进行中的记录。
6. 重启恢复和关闭由负责 Module 自己完成并等待结束。
7. 测试从该 Module 的 Interface 验证可观察结果，不再手工拼装内部步骤。
8. 删除旧入口和旧测试，不长期保留新旧两套实现。

## 3. 不变约束

- `uc-engine` 仍是唯一稳定 Rust 入口。
- 现有 Engine operation、结果和错误码保持兼容。
- 不改变移动端、桌面端和绑定层需要调用的公开流程。
- 不改变现有数据库格式、加密格式和网络协议，除非某一实施阶段另有经过批准的规格。
- 所有新持久化业务数据默认加密。
- 日志不得包含剪贴板内容、设备名称、文件名、文件路径、密钥或完整地址。
- P2P 失败不得自动切换到 LAN 兼容线。
- 本规格不以减少文件数或依赖字段数为目标；只减少调用方必须掌握的知识。

## 4. 实施关系

前置计划 `.planning/2026-08-02-space-setup-deps-design/` 已完成 Phase 0 至 Phase 8，并通过稳定契约、应用层、真实 Engine 场景和全仓交付检查。本规格的前置条件已经满足，可以从后续计划的 Phase 1 开始。

它已经完成：

- 空间创建、解锁、恢复、锁定和重置的统一所有权。
- 搜索、接收准备和成员活动随空间会话统一恢复或暂停。
- 成员传播运行期和成员恢复从引擎层移回应用层。
- 删除重复的加密生命周期入口。

本规格不重新设计这些内容。后续阶段只把它们作为已验证基线，并在整体验收时确认没有回退。

## 5. 总体设计

### 5.1 外部 Seam

`uc-engine` 只通过面向用户动作的应用入口调用功能，不直接取得用例、协调者、仓储或后台任务对象。

允许的外部形状只有两类：

- 短动作：一次调用返回明确结果。
- 长流程：一次启动返回不透明句柄，后续操作仍由同一 Module 接管，最后显式关闭并等待完成。

### 5.2 内部 Seam

实现内部可以保留真正会变化的 Adapter，例如生产存储、内存测试存储、网络实现和测试网络。内部 Seam 不得因为测试方便而暴露给 `uc-engine`。

### 5.3 删除检查

每项改造完成时都执行删除检查：

- 删除新 Module 后，如果内部顺序和恢复规则会重新散落到多个调用方，说明它确实隐藏了复杂度。
- 删除新 Module 后，如果调用方几乎不变，说明它只是转发层，必须合并或重新划分。

## 6. 剪贴板入站

### 6.1 当前问题

当前调用方分别订阅入站通知、启动接收循环、应用内容、确认接收结果、发送事件并处理后台退出。

入站应用还可以通过大量可选能力自由组合，导致相同内容在普通接收、按需拉取或测试路径上可能获得不同的落盘、搜索、活动剪贴板、文件清理和重复内容处理行为。

### 6.2 唯一负责人

新增 `ClipboardInboundRuntime`，负责：

- 启动网络接收循环。
- 接收入站通知。
- 解码和应用内容。
- 文件落地和失败清理。
- 接收进度和终态。
- 活动剪贴板推进。
- 搜索更新。
- 重复内容重新激活。
- 接收确认。
- 宿主事件。
- 取消、关闭和等待后台任务结束。

### 6.3 明确运行模式

只允许命名清楚的完整模式，禁止任意组合：

- `InteractiveReceive`：真实设备收到远端内容，负责落盘、系统剪贴板、活动状态、搜索、进度和事件。
- `StoreOnlyPull`：按需拉取后只保存内容，不直接写系统剪贴板；后续收敛流程负责最终激活。

若后续出现第三种真实行为，必须新增完整模式并说明成功条件，不得继续增加独立可选开关。

### 6.4 外部 Interface

`uc-engine` 只负责：

1. 在网络节点可用后启动一次 `ClipboardInboundRuntime`。
2. 在会话关闭时调用一次 `shutdown` 并等待完成。

单条通知的接收确认和失败分类不得暴露给引擎层。

### 6.5 验收

- 引擎层不再出现“订阅通知、应用通知、确认结果”的循环。
- 普通接收和只保存模式无法构造出缺少必要能力的状态。
- 应用失败、文件失败、确认丢失、取消和关闭都有确定终态。
- 重复内容、部分文件和按需拉取保持现有可观察行为。
- 关闭后没有入站桥接或接收任务残留。

## 7. 文件传输状态

### 7.1 当前问题

调用方需要逐步执行开始、进度、完成、失败和取消，还要提前建立接收方记录。任何调用方遗漏终态都可能留下永久进行中的传输。

### 7.2 唯一负责人

引入应用层内部的 `FileTransferSession`：

- 创建时完成接收方记录和开始状态。
- 更新进度时统一执行节流和合法性检查。
- `complete`、`fail`、`cancel` 互斥且幂等。
- 关闭流程负责终结所有仍活动的会话。
- 不依赖对象销毁时执行异步清理。

`FileTransferFacade` 不再作为 `AppFacade` 的公共逐步操作入口。剪贴板文件、Blob 接收和移动上传通过内部 Interface 使用同一终态规则。

### 7.3 验收

- 每次开始的传输最终都有且只有一个终态。
- 进度失败、业务写入失败和进程关闭不会留下活动记录。
- 不同入站来源产生一致的状态和宿主事件。
- 调用方不再直接调用开始、失败或完成状态方法。

## 8. 移动文件上传

### 8.1 当前问题

引擎层当前负责生成上传范围编号、保存临时句柄、统计字节、节流进度，并在每个失败分支中分别清理临时文件和传输状态。

HTTP 流式上传客观上仍需要开始、追加、完成和取消，但这些动作不应要求引擎层理解临时文件和状态推进细节。

### 8.2 唯一负责人

新增 `MobileFileUploadCoordinator`，内部拥有：

- 不透明上传句柄的生成和登记。
- 临时写入范围和临时文件句柄。
- 文件信息、来源设备、传输编号和已接收字节。
- `FileTransferSession`。
- 进度节流。
- 追加失败后的自动取消。
- 完成失败后的终态记录。
- 单个取消和关闭时全部取消。

### 8.3 外部 Interface

为保持稳定 Engine operation，仍提供四个用户动作：

- `begin_upload`
- `append_chunk`
- `finish_upload`
- `abort_upload`

调用方只保存不透明句柄并转发字节，不得看到临时文件句柄、范围编号或传输状态对象。

### 8.4 验收

- 引擎层不再保存活动上传表。
- 引擎层不再生成临时写入范围编号。
- 任一追加或完成失败会自动清理临时文件并写入终态。
- 重复完成、重复取消、未知句柄和并发追加返回稳定错误。
- 关闭后所有未完成上传均进入取消或失败状态。

## 9. 搜索运行期

### 9.1 当前问题

搜索对象可以在没有后台协调能力时创建，之后再补装。空间解锁或恢复成功后，调用方还必须额外通知搜索恢复。重复补装会导致进程终止。

### 9.2 唯一负责人

`SearchFacade` 构造后必须处于明确的完整模式：

- 生产模式包含查询、状态、修复、重建和后台协调者。
- 明确的只读测试模式只支持查询，并通过不同构造入口表达，不使用生产环境可见的可选字段。

搜索后台任务由 `SearchRuntime` 持有并负责关闭。搜索随空间解锁和锁定的变化通过当前空间计划中的私有活动 Interface 接入，`uc-engine` 不再调用搜索恢复方法。

### 9.3 验收

- 删除运行中补装搜索协调者的入口。
- 生产搜索不存在半装配状态。
- 解锁、恢复和锁定只调用空间动作一次，搜索状态自动随之变化。
- 重建、修复和关闭仍保持现有行为。

## 10. 历史维护

### 10.1 当前问题

应用层分别暴露缺失文件核对、过期文件清理和保留策略三个动作；引擎层决定顺序、运行间隔以及某一步失败后是否继续。

### 10.2 唯一负责人

新增 `HistoryMaintenanceRuntime`，负责：

- 启动时执行一次完整维护。
- 按既有间隔运行。
- 固定三个步骤的顺序。
- 保持现有失败策略：缺失文件核对失败时跳过本轮剩余步骤；文件清理失败不阻止保留策略。
- 汇总每轮结果并记录脱敏日志。
- 关闭并等待任务结束。

历史查询、清空和用户主动删除仍保留在历史功能入口；三个内部维护动作不再对 `uc-engine` 公开。

### 10.3 验收

- 引擎层只启动和关闭一个历史维护运行期。
- 维护顺序、间隔和失败策略只存在一份。
- 启动维护与定时维护使用同一实现。
- 关闭时不等待下一次定时器自然结束。

## 11. 成员查询与成员变更

### 11.1 当前问题

当前成员入口的说明是只读查询，实际却同时负责成员移除、旧空间保护、未完成移除恢复和后台重试，并通过多组可选能力形成不同版本。

### 11.2 目标职责

- 成员查询只负责成员列表、在线状态和公开状态视图。
- 成员移除、旧空间保护、连续安全更新投递和恢复属于空间成员功能。
- 后台重试和上线唤醒由空间成员运行期持有。
- 生产构造不得通过可选能力决定成员入口“能不能移除”或“能不能恢复”。

该项并入当前空间重构计划，不新增与 `SpaceFacade` 竞争的公开入口。

### 11.3 验收

- 成员查询测试不再构造移除和恢复依赖。
- 成员移除一次调用完成关系变更、清理、投递安排和恢复记录。
- 引擎启动不再单独调用成员恢复并建立自己的重试循环。
- 旧空间和当前保护空间的现有行为保持不变。

## 12. AppFacade 与应用构造

### 12.1 当前问题

`AppFacade` 同时公开内部对象和对应的转发动作。调用方可以绕过统一动作。部分对象在应用构造后再次安装，导致应用对象存在半就绪状态，并以进程终止处理重复安装。

### 12.2 目标形状

在前述功能完成后：

- `AppFacade` 的内部字段全部私有。
- 对 `uc-engine` 只公开用户动作和少量运行期启动、关闭动作。
- 不提供内部对象 getter。
- 网络注册需要的两阶段装配保留在唯一 assembly 文件内。
- `AppFacade` 只在必需能力完整后返回给运行期。
- 查询型测试或工具使用明确的装配配置，不通过生产对象中的大量 `Option` 表示缺失能力。
- 删除运行中一次性补装多个功能的入口和重复安装导致的进程终止路径。

### 12.3 验收

- `uc-engine` 不能直接访问任何应用内部对象。
- 同一用户动作只有一条应用调用路径。
- 应用对象返回后不存在“功能稍后才可用”的正常状态。
- 删除任一功能负责人后，其复杂度会明显重新出现在调用方，证明负责人不是转发层。

## 13. 通用生命周期入口

当前通用生命周期入口没有执行真实恢复，只修改状态，也没有生产调用者。

处理方式：

- 随当前空间重构删除该入口。
- 不创建新的通用生命周期总管。
- 每个功能由自己的运行期负责启动、恢复和关闭；需要跟随空间会话的活动由空间会话负责人按固定顺序协调。

## 14. 明确保留的现有设计

以下功能暂不重构：

- `ActiveClipboardFacade`：已经拥有后台工作、恢复来源和关闭流程。
- `ConfigMigrationFacade`：已经完成前置检查、完整动作和失败回滚。
- `BlobTransferFacade`：虽然实现较大，但已经隐藏大部分取消和状态顺序；只需改为使用内部 `FileTransferSession`。
- `ClipboardSnapshotDeps`：它集中同一重建能力所需依赖，不要求调用方推进内部步骤。

文件大、依赖多或实现复杂本身不构成本规格的改造理由。

## 15. 兼容与迁移策略

每个功能按以下顺序替换：

1. 先通过稳定 Engine 入口固定现有行为。
2. 新负责人在内部接管完整流程。
3. 调用方切换为新 Interface。
4. 删除旧入口、旧运行期和旧测试。
5. 执行删除检查和架构检查。

禁止长期双写、双运行或用功能开关保留旧流程。若需要短暂过渡，必须在同一阶段结束前删除。

## 16. 整体验收

- 当前空间重构计划完成。
- 剪贴板接收、移动上传、搜索和历史维护各自只有一个运行期负责人。
- 文件传输不会留下无终态记录。
- 成员查询不再承担成员变更和恢复。
- `AppFacade` 不公开内部对象，也不存在运行中补装。
- `uc-engine` 中不再出现应用内部步骤的循环、重试和失败补偿。
- 稳定 Engine 行为和错误码兼容。
- 安全、架构、格式和工作区检查通过。
- 实体设备未执行项目明确记录为“跳过”。
