# Findings

## 2026-08-12

- 正式旧版本来源为 `UniClipboard/UniClipboard` 的 `v0.19.0` 标签，解引用提交为 `01637f7b2c8438aaad2409f0d22a71df803cc1b6`。
- 临时检出目录为 `/tmp/uniclipboard-v019.ps28h7`。
- `cargo build -p uc-daemon -p uc-cli --locked` 已成功完成，真实旧端程序可运行。
- `0.19` 长期存在的内容入口是 `uniclipboard/clipboard/0`；当前实现仅用空连接探测该入口，不监听它，也不向它发送旧格式内容。
- 旧 E2E `TestDaemon::spawn` 每次启动都会清理 profile，不能直接表达原地升级；跨版本宿主必须保留旧端资料，并允许用另一代程序重启同一设备。
- 当前 Engine 测试宿主支持复用同一目录和同一安全存储重启，但现有实现使用内存安全存储；真实升级探针必须接上可跨进程复用的旧端安全存储或等价导入边界。
- 下一道验收门槛是资料接管，不是本地网络：先证明当前 Engine 能读取 `0.19` 创建的单机资料，再投入双机完整混跑。
- 首次真实接管探针结果：`RecoverSession` 成功，旧 `device_id` 仍可从设备列表读取，说明目录和 KEK 接线正确。新的签名成员历史初始为空是预期过渡态，不能用它代替旧关系保留的验收。
- 启动接线曾在解锁前尝试恢复旧空间安全状态并记录失败；这属于启动顺序噪声，不能据此断言迁移缺失。真正验收应观察解锁后两台设备的发现、升级提示、内容暂停和后续恢复。
- `UC_IROH_BIND_PORT` 能让旧版长期后台在重启后保持相同 IPv4 UDP 端口；日志已确认 A、B 分别绑定 `55101`、`55102`。
- 同机运行两个旧后台还必须从初始化开始使用不同 `UC_PROFILE`。profile 同时隔离本地控制端口、资料目录和网络身份；配对后再切 profile 会生成新的网络身份并污染成员视图，因此该组资料不能用于验收，必须从零重建。
- 可用的干净双机资料位于 `/tmp/uc-v019-e2e.RVsKkh`：A 使用 `UC_PROFILE=a`、端口 `55101`、设备 `394fce94-b64d-43d5-b7a0-c67124d6fdda`；B 使用 `UC_PROFILE=b`、端口 `55102`、设备 `f4e5aed0-21bb-4d4d-a4b0-5a3374ad5ad4`；Space 为 `1f024ae5-230a-4119-81ce-5489cabeb623`。
- 旧版双向同步基线已由接收端历史确认：B 读到 A 的 `ADR020-V019-A-TO-B-20260813-0019`，A 读到 B 的 `ADR020-V019-B-TO-A-20260813-0019`，均在第一次轮询即出现。
- 首次单边升级已经恢复 A 的数据库和安全会话，但当前节点没有使用已接管的 `iroh-identity` 目录，而是在主 `keyring` 生成了另一把网络身份。B 能看到新地址和连接，却不会把新身份认作原来的 A，因此无法进入可信关系上的旧版本识别流程。
- 0.19 的网络身份文件名是 `iroh-identity:v1` 的十六进制编码，内容是 32 字节原始密钥；当前配置导入也把 `iroh-identity/` 明确定义为独立文件身份目录。运行节点和配置导入应共用该目录，主安全存储继续负责 KEK 等其他安全资料。
- 新的干净双机资料位于 `/tmp/uc-v019-v11-e2e.B00X7g`：A 使用 `UC_PROFILE=a11`、端口 `55201`、设备 `4744e9f0-cfcc-4e26-adaa-20f165deabac`；B 使用 `UC_PROFILE=b11`、端口 `55202`、设备 `061f9cc2-5662-4263-ba64-0a81e469fd0c`；Space 为 `272295d6-6dff-4ab3-a6a6-90843e855970`。
- 新资料的 0.19 双向基线已由接收端历史确认：B 读到 `ADR020-V019-A-TO-B-20260813-0048`，A 读到 `ADR020-V019-B-TO-A-20260813-0048`。
- 网络身份接管回归测试已经证明当前版本首次启动和重启都复用 0.19 身份，且主安全存储不再生成第二身份；配置迁移库 32 项测试也通过。
- 身份修复后的真实单边升级仍在约 68 秒后失败，唯一未满足条件是 A 的升级提示没有包含 B。`WorkspaceConvergence` 的运行入口只在收到新的 `Online` 事件时核对成员；A 恢复已有 Space 时没有对已保存且已在线的 B 主动执行核对，是真实启动场景尚未被局部测试覆盖的触发缺口。
- 局部回归 `runtime_start_reconciles_an_existing_legacy_member_without_a_new_online_event` 在旧实现上稳定于 1 秒超时，实际执行 1 项；启动时复用已有 `synchronize_chain` 后同一测试在 0.01 秒通过。根因是缺少启动触发，不是旧入口探测或错误分类本身。
- 真实单边升级再次在 68.31 秒失败，但新增启动日志证明核对已经进入：它在会话恢复前因“收敛资料锁定”退出；约 8 秒后会话恢复完成，却没有第二次核对。因此真实缺口是解锁后的生命周期触发，而不是简单的进程启动触发。
- 把核对接到会话恢复后，第三次真实用例仍在 68.24 秒超时；这次没有锁定错误，核对正常返回但未探测 B。正式 0.19 资料没有 1.1 新增的签名成员历史，`synchronize_chain` 只从新历史选择候选，因此得到空集合；旧关系的可联系事实仍保存在配对地址仓库。
- 在成员历史为空时改用旧关系留下的配对地址选择候选后，第四次真实单边升级通过：正式 0.19 B 持续运行，A 原地升级并在 17.47 秒内保存 B 的升级提示；实际执行 1 项、0 项失败。
- 旧空间安全提升实现仍存在，但生产网络入口与后台运行曾被当前改动误删；这会阻断原有 Space 原地建立共同保护状态，必须恢复。旧格式内容入口仍不监听、不发送普通内容。
- 旧成员表缺少当前流程要求的完整签名身份，不能直接转换成成员历史。双方完成升级后，设备标识稳定排序确定唯一发起端；发起端建立唯一历史起点，每台设备提交自己签名的当前身份资料，随后只运行当前成员历史核对。
- 正式双机完整场景通过：A 单独升级后提示跨重启保留，A/B 双向普通内容均未进入接收端历史；停止 B 的正式 0.19 进程并原地升级后，两端收敛到同一份两成员历史，A 清除提示，双向唯一内容均由接收端历史读回。1 项通过、0 项失败，耗时 33.57 秒。
