# Findings

- ADR-020 currently makes OpenRaft 0.9.25, strict majority, joint membership, and a unique committed successor normative across join, removal, recovery, persistence, and tests.
- ADR-015, ADR-016, ADR-017, ADR-019 and specs 015/016/017/019 directly refer to the current quorum design.
- The newly accepted product rule permits a stale but locally authorized member to create a divergent branch, admit another device, and disclose content/keys available on that branch before conflict discovery.
- Conflict can only freeze a device after that device observes incomparable histories; no design may claim instantaneous global read-only behavior during a partition.
- Membership conflict resolution cannot safely select a global winner without reintroducing an authority. The simple recovery is to archive the conflicted lineage and explicitly create a new Space lineage.
- Branch security must rotate forward secrets on membership changes so one branch cannot decrypt future content created exclusively on another branch. Already disclosed historical content is unrecoverable and explicitly accepted.
- Repository rules require an architecture-bible maintenance update for every repository modification.
- Related ADR/spec documents contain extensive unimplemented OpenRaft target text. Their status now explicitly marks those clauses superseded; rewriting the four specifications is a separate implementation-spec task.
- Final product choice: a linear unseen `RemoveDevice` is not auto-applied. Each receiving device records a pending destructive decision and asks its user.
- Accepting the removal applies the existing signed operation locally and may restore consistency on the same history; it does not create a duplicate removal event.
- Rejecting the removal records a signed rejection and marks the peer/history relationship diverged. It does not imply `RemoveDevice(author)`.
- Diverged branches remain usable internally. Ordinary content and membership propagation are blocked only across the diverged peer relationship.
- Full topology execution exposed a shared startup regression rather than 14 protocol failures: every fresh `DeviceHarness` passes a not-yet-created `private` directory, while `adopt_v019_profile_directories` previously required that directory to exist. The correct boundary is to skip v0.19 adoption when the root is absent, but retain failure for real inspection errors and legacy/current directory conflicts.
- The post-fix serial topology matrix proved 9 scenarios and left 5 concrete failures. `concurrent_accept_and_reject...` reached the expected branch states but D-to-B content returned a receiver rejection. `removed_device_rejoins...` rejected a new member instance with conflict. The two sponsor-offline cases left A on the old 2-event history while C/D held 3/4 events. `stale_removed_sponsor...` reached its assertions but D shutdown exceeded 15 seconds amid failed relay address lookup.
- The concurrent accept/reject failure reproduced alone in 58.82s. All four devices reached the expected two branch digests before D-to-B dispatch, so this is not a branch-state wait race. The receiver returned a typed rejection; the next diagnostic run records both rosters and both convergence summaries at that exact boundary.
- Notifying only peers already marked pending is still order-dependent: in the four-device concurrent run, B retained D as pending because D decided before its local relationship map included B. A signed decision must therefore go to every effective device on the sender's applied branch; the bounded workspace size and receiver validation keep this scoped.
- Concurrent accept/reject is now resolved. The notification set is captured from the applied branch before an acceptance removes its target; matching decisions restore same-branch relationships, opposite decisions isolate every cross-branch pair. The full four-engine case passed in 13.18s, including receiver-confirmed A/C and B/D content plus blocked A/D traffic.
- The final shutdown timeout was not an Iroh connection failure. The test abandoned a peer-query future when the stale join completed, but the Engine retained that cancelled future in its in-flight registry until the shutdown deadline. Tying registry cleanup to the future lifetime removes the stale entry without weakening shutdown deadlines.
- The final serial topology matrix ran all 17 declared cases: 15 passed, 0 failed, and 2 official-v0.19 fixture cases were skipped in 431.74 seconds. The skipped cases remain separate from the already recorded real two-device v0.19-to-1.1 acceptance.
