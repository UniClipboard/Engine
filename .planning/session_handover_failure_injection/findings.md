# Findings

## Requirements

- 故意制造会话交接失败。
- 失败后旧 Space 权限不可重新开放。
- 同一身份不能同时出现两个网络入口。
- 故障解除后当前进程自动恢复，不依赖应用重启。
- 保持三秒配对性能方案和现有公开接口。
- 覆盖 Space 切换过程中被取消，以及仍有真实业务请求在途时切换。

## Research Findings

- 规格 043 已把“提交成功后新会话构造失败”和“恢复重试”列为未完成验收。
- 上一提交已经让切换 watcher 在网络存在但会话为空时尝试恢复，但缺少可重复的真实故障证据。
- 现有 `dev-tools` 已提供公开测试入口和网络 endpoint 查询，可用于证明恢复前后没有重绑；没有现成的会话准备失败开关。
- 最小新增面应放在 Engine 内部会话工厂，而不是污染 Infra 协议、Application 业务或公开稳定操作。
- 当前 `QueryNetworkEndpointId` 虽从网络测试门读取数据，但执行前仍要求活动 facade；故障窗口内应通过另一个不依赖会话的测试观测入口检查网络是否仍在。
- Engine 的 dev 操作本身仍受最外层 Engine 生命周期保护，但不经过普通业务会话操作门；适合承载测试开关和匿名网络计数。
- `execute_dev` 目前无条件先取得 facade，导致本来只读网络测试门的操作也无法在会话空窗执行；应让各操作只取得自己实际需要的依赖。
- dev-tools 合同集中在 `crates/uc-engine/src/dev/mod.rs`，新增一次性故障动作不会进入默认构建或平台稳定接口。
- 首次真实运行已观察到注入失败：普通操作返回不可用，切换 watcher 一秒后重新准备会话并完成目标 Space 加入。
- endpoint identity 由设备密钥决定，即使重绑也可能相同；必须用网络构造次数而不是只比较 identity 证明没有第二次构造。
- 规格 043 剩余关键边界包括切换前封口失败、持久提交失败和新会话发布前失败；上轮已经覆盖正式提交后的会话准备失败。
- 后续测试继续通过现有公开 Engine 操作发起完整加入，通过开发测试操作只制造故障和读取匿名计数。
- 新会话准备之后还有一次完整发布边界；在那里制造失败可以验证已经启动的新会话会被清理，固定网络仍可用于下一次恢复。
- 持久切换完成动作在正常切换和启动恢复各有一个调用点。若注入只覆盖一个调用点，恢复路径会绕过故障，因此故障能力必须围绕同一个完整完成动作，而不是散落判断。
- 切换前封口失败会保留旧会话，但操作门已经关闭；是否有稳定的再次唤醒来源需要先确认，不能先假定它会自动恢复。
- 真实完成错误此前统一转换成内部且不可重试；当第一次完成失败后的就地恢复也失败时，watcher 会永久停止，违背当前进程恢复责任。
- 完成错误目前只有业务终止与带来源的状态失败两类，但 Engine 路径没有更细的稳定可用性分类；会话监督器必须把这类运行期完成失败保留为可后台恢复，而不是普通一次性操作错误。
- 发布失败发生在 Application 已启动之后，清理会依次停止 Engine 会话任务、Application 和会话级传输进度；长期网络本身不在该关闭对象内。
- 首次发布失败的关闭流程能够返回，但下一次准备长时间无进展，说明问题更可能是 Application 重启后的共享运行状态，而不是直接关闭了长期网络 owner。
- 正常切换本来就会关闭一个 Application 后再次启动，因此问题不是普通重启本身，而是“新 Application 已启动但网络能力尚未发布”这一特殊失败窗口。
- `ProductionSession::shutdown` 会显式调用 Space `on_shutdown`，随后释放 Application 与会话级进度任务；需要用窄化日志确认第三次启动停在哪个子阶段。
- Space 运行期关闭会消费当前 `SpaceApplication`，但每次会话准备都会构造新的 `SpaceFacade`，因此同一 facade 不可重启并不是本次卡住的直接原因。
- 会话准备结果中的尚未发布 handler 仍持有本次新会话对象；失败清理时它与已启动 Application 的释放顺序可能影响共享资源，需通过一次失败的窄化复现确认。
- 会话准备里唯一明显的长异步资源创建是 Blob 能力安装，之后才组装 Application 并启动其运行期；下一次复现需要区分这三个检查点。
- 单次发布失败的检查点证明：失败会话已完整准备并启动，关闭三段均返回；一秒后新的准备已经开始，但卡在 `prepare_daemon_session` 内，尚未完成网络会话准备。
- 因为准备流程会重新打开同一 Blob 存储，而尚未发布的 handler 只被丢弃，没有显式异步关闭，该资源是当前最可疑的目录锁持有者。
- 已确认 Blob 存储启动了内部长期任务，并依赖协议 handler 的异步 `shutdown` 结束；尚未发布的会话被直接丢弃时不会走代际退休的 handler 关闭流程。
- 这解释了恢复卡住：失败会话遗留的 Blob 存储继续持有同一数据库文件，下一次准备在重新打开该文件时等待。
- 协议注册表的发布失败此前会消费并直接丢弃完整 handler 集合，同样无法异步关闭；因此不能只修测试注入分支，真实发布拒绝也必须完整关闭未发布集合。
- 注册表发布只有“已有活动代际”一个前置失败；最终由注册表自己关闭被拒绝的完整集合，调用方只处理发布结果，避免把失败资源先返还再二次编排。
- 增加未发布会话显式关闭后，单次发布失败可在一秒后重新完成全部准备、启动和发布，确认 Blob 文件占用就是阻塞根因。
- 现有 session generation 模块没有直接覆盖“第二次发布被拒绝后，返还的 handler 必须关闭”；需要补一个纯内存关闭探针，避免未来再次退化成直接 Drop。
- 现有代际测试已有可统计 `shutdown` 的 handler，可直接增加“活动代际存在时拒绝第二次发布，返还集合关闭一次且不影响当前代际”的纯内存场景。
- 新一轮继续沿用已经确认的 Engine 公开操作测试 seam；开发测试入口只允许控制故障时机和读取匿名结果。
- 工作区已有用户新增的架构维护记录和 `skills/` 目录，本轮必须保留且不纳入任务提交；架构圣经若需更新只能在现有记录上追加。
- 规格 043 已明确两个未验收场景：新会话发布后、正式安装前被取消；以及文件发送、Blob 下载或进度回传在途时切换。
- 公开 Engine 生命周期入口可以与真实加入并发触发 suspend/resume；切换 watcher 和 suspend 共用同一把生命周期锁，适合作为第一轮“切换被生命周期取消”的真实测试。
- 现有开发入口的 Blob 发布与拉取会经过当前真实会话能力，但还缺少可控的在途停顿；网络分区只能制造连接失败，不能稳定证明请求已经进入旧会话。
- 第一颗最小测试选择“连续准备失败形成可恢复空窗后 suspend，等待原 watcher 重试期限，再 resume 完成加入”：它能确定 suspend 获胜后旧 watcher 不得重建网络，并且 resume 只能重建一次。
- 生命周期取消场景当前直接满足契约，不需要生产修复；这说明 lifecycle 互斥和“无网络、无会话”状态检查在恢复空窗中有效。
- 普通 Engine 操作持有会话操作凭据，切换会先等待或取消它们；开发 Blob 操作不持有该凭据，但仍经过真实会话网络能力，适合专门验证网络代际是否能取消旧请求。
- 单纯使用网络分区只能让连接失败，不能稳定证明 Blob 请求已经进入并停留在旧代际；在途测试需要一个只在测试构建启用、可确认“已进入”并可控释放的窄停顿。
- 现有网络分区门能追踪和关闭真实连接，但只统计在线检查连接；它无法证明某条 Blob 请求已经取得旧会话权限。
- 最窄的确定性控制点应位于共享会话注册表取得旧会话使用权之后，而不是 Blob 业务内部；这样既能覆盖真实 Blob 协议，又不把停顿逻辑复制进每个业务处理器。
- 共享会话注册表已有真实本机连接测试，能够证明已取得旧会话使用权的挂起请求在封口时连接关闭、使用权释放，新会话随后只处理新请求；重复增加同类假 handler 测试没有价值。
- 因此本轮在途端到端测试应补更上层的真实产品动作：让一个文件发送操作稳定停在宿主文件读取中，再触发 Space 切换，验证操作门在宽限期后取消旧动作且切换继续完成。
- `SendFiles` 在进入发送前会同步读取宿主文件，并在每个分块之间检查取消；如果测试让单次同步读取永久阻塞，会同时阻止 future 响应取消，这测到的是宿主适配器违规而不是会话切换。
- 可控文件源应分块返回并在读取间设置短延迟，让操作持续超过切换宽限期但仍能在下一次取消检查退出；这能稳定测试产品操作取消而不伪造不响应的宿主。
- 会话操作门先等待两秒，随后发出取消并再等两秒；文件导入在每个 64 KiB 分块前检查取消。因此测试文件用多于二十个、每块约 100ms 的读取可稳定进入取消分支，并在下一块安全退出。
- E2E 设备宿主目前固定使用空文件能力，最小测试改动是让现有启动辅助方法接收可选文件能力；不改变生产接口。
- 文件导入只在显式错误返回时删除本次临时目录；若会话取消直接丢弃正在等待的导入 future，成功复制但尚未返回的目录缺少自动清理保护。这是本轮测试应同时验证的资源责任。
- 慢文件设置约三秒总读取时间：超过两秒正常宽限、低于四秒取消后的第二段等待；这样切换会等待操作响应取消，而不是绕过仍运行的旧操作。
- 首次红测中，切换已在两秒后发出取消，但同步文件读取直到约三秒才把控制权交回；此时取消和发送结果同时就绪，现有无优先级选择接受了成功结果。
- 这意味着会话切换已决定终止旧操作后，旧操作仍可能以成功结束；最小修复是在会话取消与业务结果同时就绪时固定让取消优先。
- 加入网络交换和持久提交在会话切换前仍需时间，三秒慢读取不足以保证跨过真正的取消时点；改用七秒窗口，覆盖配对交换以及最多四秒的两段排空等待。
- 七秒场景实际触发了两秒宽限超时和两秒取消等待超时；切换随后继续，文件操作在恢复执行权后因取消优先返回不可用，临时导入目录为空，目标 Space 最终完成。
- 该结果证明不响应式同步宿主调用不会永久阻塞切换，但也说明会话关闭可能先于宿主调用返回；旧操作必须依靠取消优先保证不能在关闭后报告成功。
- 加强后的测试同时证明：旧网络入口未改变、网络只构造一次、临时导入为零，并且目标 Space 能收到新的真实正文。
- “发布成功、写入监督状态前取消”在当前实现中没有可插入的异步等待点：注册表成功发布后在同一次执行中立即写入监督状态。人为加入停顿只会创造生产中不存在的窗口，因此本轮不增加该测试开关。

## Technical Decisions

| Decision | Rationale |
| --- | --- |
| 优先注入会话准备失败 | 它位于持久切换完成和新权限发布之间，是最危险且最能证明恢复责任的边界 |
| 故障开关与网络计数放在 SessionSupervisor 的 dev-only 测试控制器 | 既能覆盖真实工厂路径，也不向 Infra 或稳定接口泄露生命周期步骤 |
| 同时统计注入消费次数和网络构造次数 | 防止故障未触发或身份相同的重绑造成假通过 |
| 下一轮优先覆盖持久切换完成失败与新会话发布失败 | 分别验证提交前恢复和提交后清理，补齐上轮准备失败之外的两个不同边界 |
| 1103 切换完成失败改为可重试的不可用状态 | 监督器承诺当前进程恢复；不可重试会让操作门永久关闭且只能依赖重启 |
| 未发布会话必须拥有显式异步关闭能力 | 仅靠 Drop 无法停止 Blob 内部任务；发布失败必须先关闭全部未发布 handler，再重试 |
| 注册表自行关闭被拒绝的会话能力 | 发布接受与拒绝由同一负责人处理，节点无需理解失败资源的清理步骤 |
