# Issue #951 实施计划：可靠成员撤销与分层密钥

## 目标

把现有“本机隐藏成员”升级为可证明的前向撤销：成员被撤销后仍可读取撤销前已经拿到的内容，但不能加入新的成员状态、不能取得新密钥、不能解密或接收撤销后的内容；整个过程不得重加密历史正文。

## 完成标准

- 撤销会产生新的群组代次和新的内容密钥，旧成员只持旧密钥时无法通过新代次准入。
- 保留成员能继续读取历史；历史密文字节不因撤销发生全量改写。
- 所有新持久化业务负载仍为密文，日志不出现密钥、正文、文件名或路径。
- 崩溃、离线成员、重复请求、消息乱序和并发成员变更都有明确恢复结果。
- 旧格式只读兼容，新写入只有一条新格式路径；不长期维护双写。
- `uc-engine` 是唯一稳定入口，iOS、Android、HarmonyOS 绑定同版本交付。
- P2P 失败不得自动退回 LAN；不支持安全换钥的旧成员会阻止“可靠撤销”启用。
- 本功能测试中的端口替身全部使用 `mockall`，并由 helper 集中配置；真实数据库测试继续使用真实仓储。

## 明确不做

- 不承诺删除被撤销设备已经下载的历史明文或文件。
- 不在本 issue 中实现远程擦除。
- 不自行设计新的群组密码协议；成熟实现不满足跨平台要求时，先停在 ADR 决策，不以临时协议替代。

## 推荐设计

### 1. 一个统一的密钥代次模块

在核心层定义少量稳定概念：

- `GroupEpoch`：成员状态的单调代次。
- `ContentKeyId`：内容密钥的不透明标识。
- `ContentKeyPurpose`：正文、传输、搜索等用途，具体算法不进入核心层。
- `RevocationId` 与 `RevocationStatus`：可恢复撤销流程的身份和状态。

应用层只面对一个小接口：开始撤销、查询状态、恢复未完成流程。群组协议、密钥包装、格式版本、存储、重试和兼容判断都收在实现内部，不散落给每个调用方。

### 2. 群组成员状态使用成熟协议

默认验证并采用 OpenMLS：

- 每个 Space 对应一个群组；每台设备拥有独立的签名凭据和 KeyPackage。
- 加入使用 Welcome；移除使用群组提交；新代次只对保留成员可用。
- 从当前代次导出互相隔离的包装密钥和准入密钥，不再用内容密钥直接做身份自证。
- 离线成员先接收并合并缺失的群组提交，完成前不得收发新代次业务消息。
- 同代次并发提交必须通过实测的分叉恢复路径收敛；无法安全收敛时进入“需要恢复”，不得回退旧密钥继续同步。

OpenMLS 只是推荐实现，不直接暴露到 `uc-core` 或 `uc-engine` 的稳定接口。

### 3. 内容密钥目录

- 把现有 Space `MasterKey` 导入为保留的 `legacy-v1` 内容密钥，旧数据无需改写。
- 新代次生成新的随机内容密钥；正文和传输再按用途派生子密钥，避免跨用途复用。
- 历史内容密钥放入密钥目录，只重包小体积密钥条目，不重加密正文和 blob。
- 密钥目录与群组私有状态必须由本机安全存储保护；数据库中只保存密文或包装后的密钥。
- 当某把历史内容密钥已无任何密文引用时，允许后台安全回收。

### 4. 新密文格式

- JSON 加密负载升级为 V2，增加 `content_key_id`、`group_epoch` 和用途绑定。
- UCBL 文件头升级为 V2，增加同样的密钥标识；V1 仍按 `legacy-v1` 只读。
- 分块传输升级为 V4，在解密前校验 Space、代次和密钥标识。
- AAD 统一绑定格式版本、Space、代次、密钥标识、用途和业务对象身份。
- 搜索索引改为使用密钥目录中的专用搜索密钥，换代时只重包密钥，不重建全部历史索引。

## 分阶段实施

### 阶段 0：安全止血与方案验证

**改动范围**

- 删除 `HmacProofAdapter` 中密钥前缀日志，并加入日志扫描回归测试。
- 新增中文 ADR，固定威胁模型、前向撤销定义、代次提交点、离线成员语义、旧客户端策略和恢复原则。
- 建立独立验证 crate，验证 OpenMLS `0.8.1` 在桌面、iOS、Android、HarmonyOS 目标上的编译、存储、体积和基本三成员流程。
- 验证 `remove -> export secret -> Welcome/commit -> offline catch-up -> fork recovery`，不得只验证能编译。

**通过条件**

- 密钥相关日志扫描无命中。
- 三成员验证证明被移除成员无法导出新代次秘密，保留成员能一致导出。
- 四类目标均能构建；若任一失败，记录 ADR 并暂停后续实现，不手写替代群组协议。

### 阶段 1：建立密钥代次领域模型和持久化真相

**改动范围**

- `uc-core`：增加代次、密钥标识、撤销状态和最小 ports；把“成员活跃”和“撤销记录”分开，保留持久撤销事实。
- `uc-infra`：增加加密的群组状态、密钥目录、撤销日志、提交 outbox 和成员确认记录。
- 数据库迁移只允许代次、随机标识、状态枚举等结构字段明文；成员身份、密钥包、密钥目录和提交内容必须密文保存。
- 提供一个原子提交能力，同时写入撤销状态、下一代群组状态、密钥目录和待发送提交。

**通过条件**

- 重复开始同一撤销返回同一个进行中结果，不创建第二次换代。
- 任意写入点模拟崩溃后，重启能判断是安全回滚还是只能向前恢复。
- 明文探针扫描数据库、缓存、搜索索引和状态文件均无泄漏。

### 阶段 2：把单密钥读写迁入密钥目录

**改动范围**

- 将当前 `InMemorySession` 从单一主密钥容器改为按用途和 `ContentKeyId` 解析的会话密钥目录。
- `BlobCipherAdapter`、加密写入装饰器、`EncryptedBlobStore`、分块传输、搜索密钥派生及所有直接读取 `MasterKey` 的路径统一走密钥目录。
- 写入只产生 V2/V4；读取自动识别 V1/V2/V3/V4，旧格式统一映射到 `legacy-v1`。
- 启动迁移只导入现有主密钥并生成新的当前内容密钥，不扫描或改写历史正文。

**通过条件**

- 迁移前后的 V1 历史、UCBL blob 和搜索结果均可读。
- 新数据只出现 V2/V4 格式，且使用当前密钥标识。
- 迁移前后所有历史密文文件和数据库业务密文字节保持不变；只允许密钥目录和迁移状态变化。
- 缺失密钥、错误代次、损坏包装和错误 AAD 都明确失败，不尝试旧密钥兜底。

### 阶段 3：把配对和准入切换到群组代次

**改动范围**

- 配对请求增加明确的安全能力、群组凭据和 KeyPackage；不再把原始 keyslot 作为长期共享准入根。
- Sponsor 在用户明确邀请后提交成员新增，并通过 Welcome 分发当前群组状态与加密的历史密钥目录。
- 准入证明改用当前群组代次凭据；删除“用 Space 内容主密钥做 HMAC 自证”的稳定路径。
- 为现有 Space 增加 `Legacy -> Migrating -> Ready` 状态。所有保留成员确认升级前，同一个移除操作只能进入明确标记的 `LocalOnly` 结果：停止本机同步并保留加密撤销记录，但绝不宣称已安全撤销。
- 旧客户端可以读取既有内容，但不能参与新代次写入；不做静默降级或 LAN 回退。

**通过条件**

- 新设备只有在收到当前 Welcome 后才能加入并解新内容。
- 持有旧 Space 主密钥但没有当前群组状态的设备无法通过准入。
- 混合版本测试证明系统失败关闭，不会为了兼容继续用旧共享密钥发送新内容。

**实施切片**

1. 目录可移植化：分开本机保护根与 `legacy-v1` 历史内容密钥，加入设备可导入 sponsor 的完整历史目录而不共享本机 keyslot。
2. 准入证明换根：证明只绑定口令派生结果、本次邀请码、会话和挑战，不再读取内容主密钥；旧内容密钥不能生成新证明。
3. MLS 产品接入：基础设施内部生成/持久化凭据、KeyPackage、Welcome 和群组快照；应用层只见不透明字节和代次结果。
4. 配对协议 v4：能力字段、KeyPackage、Welcome 和加密目录进入 wire；缺字段或旧版本明确拒绝。
5. 配对端到端：证明 sponsor/joiner 安装同一目录、重启仍可读、旧协议失败关闭、P2P 不可用不回退 LAN。

### 阶段 4：实现可恢复的可靠撤销

**状态流程**

1. `Prepared`：校验目标不是本机、Space 已 Ready、保留成员能力齐全；持久化目标、旧代次和保留成员快照。
2. `Staged`：生成移除提交、新内容密钥和重包后的历史密钥目录，并与 outbox 原子保存。
3. `Activated`：本机合并新代次并启用新内容密钥；从此绝不回退旧代次。
4. `Distributing`：向保留成员发送提交，记录每台设备确认；离线成员保持 stale，恢复前禁止业务同步。
5. `Complete`：清理目标的活跃成员、地址和信任记录，保留加密撤销记录；回收不再需要的临时状态。
6. `RecoveryRequired`：只有无法自动收敛的分叉或损坏进入此状态；网络保持失败关闭。

**关键规则**

- `Activated` 之前失败可以安全取消；之后只能向前重试。
- 被撤销设备永远不进入新提交或新密钥目录的收件集合。
- 旧代次消息在本机激活新代次后直接拒绝。
- 用户看到“本机已生效”“等待 N 台保留设备”“全部完成”三种真实结果，不把待确认写成成功。

**通过条件**

- A、B、C 三设备中 A 撤销 C 后，A/B 可解新内容，C 不能解、不能重新自证加入；三者仍可读取各自已有的旧内容。
- B 离线时，A 可本机生效并显示等待；B 重连先补换代再同步，C 始终拿不到新密钥。
- 每个状态点强制终止进程后均可恢复，且不会出现成员已删但密钥未换或密钥已换但状态丢失。
- 撤销耗时和写入量与成员数、历史密钥代次数量相关，与历史条目数和 blob 总大小无关。

### 阶段 5：稳定入口、绑定和宿主状态

**改动范围**

- 保持一个 `RemoveMember` 入口：Legacy/Migrating Space 返回明确的 `LocalOnly` 过渡结果，Ready Space 执行可靠撤销；迁移窗口结束后删除过渡分支，不长期保留第二条本地删除路径。
- `uc-engine` 返回结构化撤销状态并发出进度事件；提供查询当前撤销状态的稳定操作。
- UniFFI 与 HarmonyOS NAPI 同步映射同一版本；Android 继续只通过 UniFFI 依赖 `uc-engine`。
- 宿主只展示真实状态，不接触密钥、成员提交或持久化细节。

**通过条件**

- `uc-engine` 公共契约、UniFFI、HarmonyOS NAPI 和三类验收宿主的操作、结果和错误保持一致。
- 未执行的真机矩阵明确记为“跳过”，不得记为通过。

### 阶段 6：端到端验收与发布

**必须覆盖**

- 正常撤销、重复撤销、撤销不存在成员、禁止撤销本机。
- 保留成员在线/离线、撤销成员在线/离线、消息重复/乱序/重放。
- 两台设备并发变更成员导致的分叉与自动恢复。
- V1 历史迁移、重启解锁、密钥目录损坏、磁盘写满、outbox 重发。
- 旧客户端与新客户端共存时失败关闭。
- P2P 不可用时不自动退回 LAN。
- 明文持久化扫描、日志敏感信息扫描、内存密钥清理和错误信息脱敏。

**最终证明**

- 记录三设备端到端证据：撤销前后代次、各设备可解内容范围、重新加入结果和历史密文字节哈希。
- 运行完整工作区测试、全目标检查、格式检查、架构检查和发布包校验。
- 绑定与 `uc-engine` 使用同一版本，只通过带校验信息的 GitHub Release 交付。
