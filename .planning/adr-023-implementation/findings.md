# Findings

## 2026-08-17 new-space admission baseline gap

- The production Engine test reaches the V10 sponsor path immediately after creating a Space, but `verified_admission_base_history()` returns `RecoveryRequired` because A1 persists the owner and marks setup complete before the convergence owner has created the one-device protection group and trustworthy membership starting point.
- Waiting for the automatic legacy-upgrade runtime is not a valid fix: successful A1 must itself guarantee that an immediate first invitation has a durable base history.
- The narrow ownership boundary is one application-internal new-Space membership initializer implemented by `WorkspaceConvergence`. `InitializeSpaceUseCase` invokes it after saving the owner and before setting `SetupStatus.has_completed = true`; callers continue to invoke only A1.
- The initializer reuses the existing `GroupBootstrapPort` and `initialize_upgraded_legacy_space()` behavior. It must be idempotent so A1 can resume after an intermediate failure without exposing the internal sequence.
- After the new-Space baseline was fixed, the production test exposed two later lifecycle gaps. First, the joiner saved Active but did not compact the terminal record before Engine queried the profile projection, so a successful join returned no status. `WorkspaceConvergence::activate_joiner_complete()` now compacts the locally settled result before the channel sends the rebuildable CompleteAck.
- Second, cross-Space admission compared the verified target base history byte-for-byte with the source Space history. The correct rule is lineage-sensitive: an admission to the same lineage must match the current base exactly; a different lineage carries its own independently verified full target history and is staged by the cross-Space transition owner.
- The production Engine test `stable_join_routes_a_fresh_device_then_switches_an_existing_device` now passes end to end using the stable `JoinSpace::Active` result for both the fresh join and the cross-Space switch.

## Stage 6 mDNS ticket boundary

- `swarm-discovery` limits each TXT key/value pair to 254 bytes and exposes all received TXT attributes through `Peer::txt_attributes()`.
- A real `EndpointAddr` encoded as postcard+hex can exceed one TXT attribute; keeping all addresses requires ordered chunks rather than ticket truncation.
- The shared format now uses `tn` for a canonical chunk count and `t0` through `t4` for 240-byte chunks, with a 1,200-byte total ticket bound. Missing, duplicate, out-of-range, non-canonical, oversized, or non-hex ticket fields are rejected before dialing.

## Stage 6 continuation findings

- The stable public status types are present, but the production join path still completes through the V9 `Ready` / `AdmissionSaved` exchange.
- `DurableAdmissionTransaction` already owns Candidate, Prepared, Commit, Applied, Complete, rejection, cancellation, replay, and restart recovery, but no production pairing code calls those transitions.
- The first protocol slice must give the initial authenticated request stable `attempt_id`, `join_id`, and request-message identity, then carry the five durable business messages without interpreting them as old pairing success.
- Pairing V10 must expose its version before decoding the business body so an incompatible peer cannot be mistaken for corrupt admission data.
- `AdmissionSecurityTransitionAdapter::prepare_sponsor` and `stage_joiner` already provide the required no-side-effect security staging: they derive staged private state and the shared public commitment without installing either side as current. The missing behavior is production orchestration, not another security abstraction.
- The legacy production path still calls `DefaultSpaceAccessAdapter::admit_group_member` and `install_group_join`, which persist or install current security before the durable Candidate/Prepared/Commit/Applied boundary. Those calls must leave the V10 path rather than be reused inside the new transaction.
- Production `JoinSpace` still branches before admission ownership: a fresh profile redeems pairing and immediately installs the joined security state, while an existing profile enters the separate legacy switch workflow. The Spec 023 path must acquire one durable profile admission attempt before either dial/send path and must not select two different workflow owners from setup state.
- `DurableAdmissionTransaction::reset_join_projection_if_quiet` and the repository transaction already implement the admission-side ResetSpace rule: busy state returns a version conflict without changing attempts or profile metadata; quiet state advances the public floor and revision while retaining terminal/replay facts.
- Production `ResetSpace` still calls `AppFacade::reset_space` directly under a normal session lease. It does not consult `ProfileWorkspaceConvergence`, so a pending admission can currently have setup state and invitations cleared. The narrow production fix is a profile-level reset preparation method invoked before the existing facade reset.
- The production ResetSpace route is now admission-gated. It intentionally advances the durable projection floor before invoking the legacy setup clear, because doing the legacy clear first would permit a new admission to race into the supposedly quiet boundary and would violate the required zero-side-effect busy result.
- `ProfileFactoryReset` already owns the correct forward-only lifecycle phases but has no production capabilities. The legacy factory reset cannot be used as the new capability because it combines active key deletion with relationship/setup clearing before a restartable `ClearingState` phase is saved.
- Production factory-reset wiring therefore needs two narrow infrastructure capabilities: key-only deletion/verification for active KEK/keyslot, current migration key, profile admission key, and file-backed network identity; then state-only database/filesystem clearing after the lifecycle marker reaches `ClearingState`. The Engine session supervisor is the existing owner that can close operations and stop the active runtime.
- Factory reset must break every runtime reference to the old database before deleting its files. The production solution releases the session rebuild configuration and swaps the retired shared pool to an isolated in-memory connection; otherwise the old SQLite handle survives even after normal shutdown.
- Configuration import staging is profile state, not disposable diagnostics. Leaving `import-staging` or `pending-import.json` behind lets startup recreate the old setup after a successful database/key wipe, so both belong to the state-clearing capability.
- A startup that observes WipingKeys or ClearingState must finish the forward-only reset and refuse to expose the old Engine session. The host then creates a new Engine against the advanced profile generation.
- The production network path is still incomplete: the durable transaction owns all five business messages, but pairing still uses the legacy Ready/AdmissionSaved completion interpretation. No production-complete claim is valid until the initial saved JoinRequest drives Candidate, Prepared, Commit, Applied, and Complete with receiver persistence evidence.
- Persisting only attempt_id/join_id/message_id is insufficient for production J0 recovery. The same encrypted pending member credential, KeyPackage, private join state, member instance, and resume credential must reopen together; otherwise a retry can reuse identifiers while silently presenting a different member identity, making full-history and both-sides-save evidence invalid.
- Pairing V10 now includes a distinct `CompleteAck` frame (wire kind 6). `Complete` proves the joiner saved and activated the result; `CompleteAck` is the sponsor's final receipt that permits both endpoints to retire resumable delivery state without treating a closed connection as proof.
- Current-member credential export must derive the member instance exactly as the existing security group does: device id plus signing public key. Deriving it from a broader credential digest creates a second identity for the same device and makes a real joiner reject its own J0 material.
- A legacy membership history can be promoted to a V2 admission baseline only when it is demonstrably a single-device self-history: one known/applied event, one effective member, no remote member projection, unchanged current member instance, and a current credential that verifies the event. Any multi-member legacy space must enter recovery instead of inventing unverifiable historical credentials.
- `verified_admission_base_history` now enforces the V2 or honest single-device legacy baseline rules but is not yet consumed by production Candidate construction. Its temporary unused status is an integration marker, not a warning to suppress.
- Sponsor security preparation is now one narrow complete capability. It reads the current protected generation, creates the next MLS state, rotates a complete content-key catalog in memory, seals the existing-member update, derives the public commitment from the staged state, and returns an explicit delivery list without saving or installing the target generation.
- Existing-member delivery recipients are explicit credential-bound inputs. The security adapter sorts and rejects duplicate device or credential recipients, so stale member-profile rows cannot silently enter the admission bundle.

## Stage 1 source findings

- `MembershipEvent` stores the author member instance and signature, while `AddDevice` carries `AdmissionChangeFacts` without a durable history-verification credential.
- `MembershipReconciliation::receive_verified` trusts its caller to have verified signatures; the history aggregate does not own end-to-end historical verification.
- Current signature ports resolve and verify against current security membership, which cannot prove a removed author's earlier authority.
- Existing core tests mostly construct unsigned placeholder events and call `receive_verified`, so Stage 1 needs a new verified-history entry without breaking the legacy importer boundary prematurely.
- Stage 1 ownership: `MembershipReconciliation` owns historical authorization and deterministic validation; algorithm-specific signature checking remains behind a core port for Stage 2 infrastructure.

## Stage 1 design direction

- Do not add optional V2 fields to the V1 event. The specification requires explicit `V1Evidence` and `V2` variants so unknown or incomplete layouts cannot masquerade as valid history.
- Add one deep `VersionedMembershipHistory` domain entry that owns V2 event, decision, credential, receipt, checkpoint, and activation validation.
- Keep the existing V1 aggregate unchanged as a temporary read/migration source until the protocol-isolation stage removes its production success path.
- The V2 history entry accepts a pure historical-signature verifier; it chooses the exact credential itself and never asks the verifier to resolve a member.
- The first vertical slice stores credentials permanently by member instance, rebuilds exact-parent membership/activation snapshots, and records one signed activation receipt per AddDevice.

## Stage 3 continuation findings

- The first transaction slice still accepts opaque `prepared_proof`, history-position, candidate-event, and security-commitment bytes. The application owner therefore cannot prove that Candidate -> Prepared performed V2 historical authorization or an independent security-state derivation.
- `VersionedMembershipHistory` already owns exact-parent authorization, historical credential selection, signature verification, AddDevice validation, and permanent activation-receipt validation. Stage 3 must call this deep entry instead of duplicating its checks.
- `AdmissionSecurityTransitionAdapter` already derives the same public result from sponsor Commit state and joiner Welcome state, but it is a concrete infrastructure helper rather than an injected capability. The application transaction needs one narrow core-owned port so it can invoke that capability without depending on `uc-infra`.
- The admission owner must persist typed V2 history/event/commitment values as encrypted attempt payloads. Raw bytes may remain the encrypted repository representation, but they must be produced only after the owner has validated the structured values.
- No durable `VersionedMembershipHistory` repository exists yet. The encrypted admission repository is the narrowest correct owner for the profile's V2 history because S2/J2/S3 must advance attempt state and formal history atomically; a separate store would require a second write-ahead coordinator.
- Prepared stores a verified staged history inside the attempt only. It is not current-member authority. J2 must atomically publish the AddDevice plus receipt on the joiner, S2 must publish the AddDevice on the sponsor, and S3 must add the same receipt to the sponsor's permanent history.

## Stage 4 design findings

- Prepared target-access material contains the existing JSON-compatible `KeySlot` shape. Postcard cannot safely round-trip that nested shape because `EncryptedBlob.aad_fingerprint` is conditionally omitted; its missing positional field is read as the following field's Option discriminant. The opaque material therefore uses JSON inside the admission attempt's existing AEAD envelope. This preserves the established keyslot format without writing any target secret in plaintext.
- Explicit target activation can reuse the existing join-install rollback boundary: snapshot the source keyslot, KEK, and in-memory session; verify the prepared target keyslot unwraps to the exact prepared MasterKey; write target KEK then keyslot; switch the session last. This remains an internal sub-step of the future generation transition and must not be wired directly to a product or application caller.
- The existing `SwitchSpaceUseCase` replaces the active key/session during its handshake, backs up only inline clipboard rows, permits writes after the initial backup, overwrites the active main table row by row, and resumes independently from `try_resume_session` and `unlock_space`. These are exactly the legacy behaviors specification 023 replaces.
- The infrastructure already has encrypted V3 workspace slots, a verified active pointer, and forward-only staging/activation cleanup for workspace convergence state. Stage 4 should reuse that storage mechanism rather than create another current-workspace truth.
- `AdmissionAttemptV1.space_transition` is currently unused encrypted payload capacity. A typed `CrossSpaceTransitionV2` can be encoded there without exposing phases to product or network callers.
- The application transaction must save the received Complete fact before beginning J3, then persist every forward phase. A crash after any external side effect is safe only if the transition capability is idempotent by attempt and returns evidence that is saved before the next step.
- The narrow cross-layer boundary is one `AdmissionSpaceTransitionPort`: prepare only when the verified target differs from the active source, advance exactly one durable phase, and idempotently discard target artifacts only before ActivationStarted when a formal rejection is saved. Two methods were insufficient because pre-activation rejection otherwise leaked a target keyslot/backup and permanently retained the profile slot. `DurableAdmissionTransaction` remains the sole flow owner and loops/restarts internally; callers still perform one admission action.
- Cross-Space Active cannot be saved until target runtime recovery and cleanup finish. The final migrated/preserved counts must survive terminal compaction, so the attempt and terminal replay record need a durable transition result separate from the transient phase record.
- The current durable admission payload stages MLS security state but does not yet stage a target MasterKey/keyslot or a complete business-data generation. The legacy switch handshake overwrites the active key/session, so it cannot implement the new port safely. Production assembly must remain fail-closed until a real generation-based adapter is wired; this is a prerequisite, not a completed Stage 4 path.
- Source inspection confirmed the missing material is structural: `AdmissionSecurityTransitionAdapter` stages only MLS client state, while the legacy `JoinerHandshakeCoordinator::install_group_join` derives and installs the target MasterKey/keyslot directly from the passphrase and encrypted catalog. The durable transaction has neither the passphrase-derived target access material nor an isolated target keyslot reference. Real Cross-Space preparation therefore depends on moving target access staging into the versioned admission channel before activation; reusing `install_group_join` would overwrite the source and violate J1/J3.
- Legacy recovery now enters only through profile-level `WorkspaceConvergence`. The infrastructure privately parses the old JSON layout, validates the old backup and inline primary-record evidence, advances HandshakeDone/Swapped only forward, preserves all artifacts on ambiguity, and deletes the old file only after completion. Public legacy creation and progress types remain because the versioned target-key/data-generation path has not replaced new legacy switches yet.
- The existing Engine session supervisor already drains all ordinary operations and stops every source runtime. Cross-Space activation cannot invoke that drain from inside `joiner_activate`, because the JoinSpace request itself owns an ordinary operation lease. Complete receipt must therefore persist and return transition-required without advancing J3; only the Engine lifecycle owner may exclude that lease, drain the rest, stop the source session, and invoke the profile recovery entry.
- Engine needs only a two-method transition recovery capability from application: inspect the durable transition-required signal and recover after the session is drained. Exposing the concrete `WorkspaceConvergence` type would violate the application facade whitelist and leak unrelated membership behavior, so assembly exports only this narrow capability.
- Event ids, credential ids, member-set digests, and receipt ids use distinct domain-separated canonical encodings.
- Database generation promotion must replace the pool below `DieselSqliteExecutor`, not rebuild repositories or expose a switching protocol to each repository. Config export and SQLite snapshots use the same shared handle so they also follow the active generation.
- The first real generation adapter proves encrypted target artifacts and atomic database/blob/manifest switching, but it still treats target history and security as opaque side files. Stage 4 is not complete until those verified facts replace source-Space relationship, security, and convergence rows and are reopened through the production read path.
- The target transition input carries a single staged security blob but not the target content-key directory. This is insufficient to reconstruct the exact target security state promised by the public commitment; the durable admission payload must carry and validate that directory before promotion.
- Fresh and Same-Space are not separate product workflows. They are two source-generation cases of the same admission result: Fresh creates the first complete generation, Same-Space atomically publishes verified history/security into the existing Space generation, and Cross-Space creates then promotes a replacement generation.
- Target business payload rewrapping must use the target generation's current content key, not merely its MasterKey. Installing the verified content-key catalog only after rewrap creates ciphertext that becomes unreadable as soon as the normal target security state is loaded.
- Activating a prepared target keyslot resets the shared in-memory session to its legacy content key. The transition must immediately reopen the promoted target security record through the production repository and install it before any runtime is exposed.
- Relationship rows copied from a source generation cannot remain after target-key promotion: their lookup keys and ciphertext are source-MasterKey derived. The target generation must clear them, rebuild member/trust/address projections from the verified admission relationship snapshot, and reopen the result with the target session before manifest promotion.
- A Fresh profile cannot be represented by `Option<CrossSpaceTransitionV2>`: `None` currently conflates Fresh and Same-Space and lets both become Active without installing history/security. The durable transition model needs an explicit tagged Fresh state before new-device J3 can be correct.
- Runtime-installed revision triggers must exclude `__diesel_schema_migrations`; the former single-underscore spelling both counted migration bookkeeping as business data and broke migration rollback after the revision table was removed. The revision migration down path must explicitly remove all triggers for tables present at that migration point; later tables disappear with their later down migrations.
- The encrypted active manifest is the sole generation pointer, so syncing only the temporary file is insufficient for the claimed crash boundary. Non-Windows promotion also syncs the parent directory after atomic rename; Windows uses replace-existing with write-through.
