# 设备组恢复结构性修复

## 目标与完成标准

用户要求先写能覆盖既有问题的红测，再修复结构性根因。不提交、不推送，不触碰个人配置 a/b/c/d。
完成必须包括旧分支任务隔离、当前历史派生的资料维护、合法历史核对及可恢复拒绝推进；真实四/五配置 GUI 场景、坏现场恢复与移除安全断言均需验证。

## 当前阶段与下一步

阶段 5：结构性修复及四/五配置故障恢复已通过，正在完成扩大回归与证据整理。

## 已确认的测试边界

- 用户已经确认的 Engine 选择、完整设备组查询、重启和真实文本同步入口。
- Core 已有公开的已签名历史导出/接收能力，用已调查到的真实模式形成快速回归。
- 既有 Infra 完整分支 transition 与 Application 维护能力的契约测试，验证真实存储及外部可读成员结果，不验证私有调用次数。
- Desktop 已建立的隔离四/五配置 GUI 工具，不用个人资料，不降低断言。

## 阶段

- [x] 1. 根因红测：旧分支效果污染新分支；合法旁支/决定导致增量误拒绝；恢复调度不能永久停住。
- [x] 2. 分支切换与资料维护：唯一完整负责人，当前已验证历史为资料维护依据，旧任务不得跨分支执行。
- [x] 3. 历史交换：统一证明范围、校验和恢复结果，删除不兼容的旧路径，保留真实无效资料的安全拒绝。
- [x] 4. Engine 定向/扩大验证、存储与重启回归、已有坏现场恢复；原版本已有的重发错误分类失败单列，不宣称全仓全绿。
- [ ] 5. Desktop 新程序构建、四/五配置 GUI 复验、文档和未执行项说明。

## 删除与替换清单

- 旧分支 ledger 的执行状态直接 clone 到新历史。
- Infra 从历史 Activated 移除效果自行决定清理成员的业务规则。
- 增量重建接收方全部归档后要求与发送方全部归档摘要相同的规则。
- 将可恢复的资料差异一律升级为永久 Invalid 的处理。
- 不保留平行旧实现，不在查询层补造健康状态，不放宽签名、授权和显式用户选择。
