# Issue #1516 网络自动恢复详细执行计划

## 计划状态

- **计划制定：完成**
- **生产实现：进行中，发送终态与跨端通知已补齐，等待完整验证**
- **设备验收：Windows 双机、HarmonyOS 宿主、iPhone 物理机和 Android 真机恢复检查均跳过；iOS/Android 已完成产物生成和接口核对，未作为真机互通通过**

## 目标

在不退出应用的前提下，识别“本机中转连接已经恢复，但到曾经在线设备的实际路径仍然失效”的半恢复状态。先执行一次低成本恢复；仍失败时，由 Engine 自动、安全、单次地重建当前 P2P 运行会话。重建保留设备身份、当前 Space、设置、密钥和加密持久化数据，不自动切换到 LAN 兼容模式。

## 不在本次范围

- 不修复诊断中出现的成员身份分歧；它需要单独 Issue。
- 不增加 P2P 失败后自动切换 LAN 的路径。
- 不迁移持久化数据，不增加兼容层或旧新双实现。
- 不改变现有 `RefreshPeerConnections` 的轻量刷新语义。
- 不自动重放结果未知的前台发送、恢复、导出等用户操作。

## 完成标准

- 自动判断同时使用本机网络变化和设备实际拨号结果，普通对端关机不会触发会话重建。
- 对“本机刚换网且此前在线设备持续不可达”的已确认故障，目标是在系统网络已稳定后 10 秒内重新可用；这是 Windows 双机验收指标，不是对真实断网的承诺。
- 两次仅供严格自动恢复路径使用的快速确认均失败后，才允许升级；同一失败周期最多成功重建一次。
- 自动触发、用户手动恢复和失败后的自动重试全部汇入同一个恢复负责人，同一时刻只有一次执行。
- 重建严格遵守“关门、清场、停旧、建新、安装、开门”顺序；旧 Endpoint、Router 和所有旧引用释放后才创建新会话。
- 新会话继续使用原安全身份；设备身份、当前 Space、设置、数据库和密钥不变。
- 新会话创建失败时不回退到已关闭的旧会话，不留下半运行状态；失败可见、可重试，并按有界退避自动再试。
- 恢复期间新前台操作快速返回可重试的暂时不可用；系统剪贴板观察等待新会话后继续，不拿旧引用运行。
- 活动接收和发送进度都有明确的“连接恢复中断”终态；已持久化的最新离线内容仍由现有补发流程处理。
- 重建后立即刷新所有已知设备；成功表示新会话已经安装，不虚假承诺对端一定在线。
- Engine、UniFFI 和 HarmonyOS 提供同一套手动动作、状态查询和恢复事件；绑定只做转换。
- 聚焦测试、工作区检查和两台 Windows 真机验收全部有证据；未跑的设备项明确记为跳过。
- `docs/architecture/architecture-bible.md` 正文和维护记录随实现同步更新。

## 最终设计

### 唯一负责人

| 负责人 | 所在层 | 只暴露的主要入口 | 完整负责的结果 |
| --- | --- | --- | --- |
| `NetworkRecoveryRuntime` | `uc-application` | 接收脱敏观察、请求一次恢复、查询当前状态 | 触发条件、失败周期、单次执行、自动/手动合并、退避、次数上限、公开状态 |
| `SessionSupervisor` | `uc-engine` 运行期 | `rebuild_session()` | 停止新工作、等待/取消旧工作、结束传输、关闭旧会话、创建并安装新会话、重新开放 |

应用层只向监督者请求“重建当前运行会话”这一个完整动作，不接触 Endpoint、Router、任务关闭顺序或文件传输内部步骤。监督者不判断何时应该自动恢复，也不拥有退避政策。

删除检查：删掉应用层恢复运行期，触发、合并、退避和状态会散回 Presence、Engine 和产品端；删掉会话监督者，关闭顺序和失败清理会散回生命周期、剪贴板、文件传输和每个调用方。因此两个模块都隐藏了真实复杂度，不是转发层。

### 分层落点

- `uc-infra`：执行第三方库允许的低成本动作，识别中转状态变化和完整拨号结果；只产生脱敏技术观察，不决定是否重建。
- `uc-application`：持有恢复状态机和单次执行；只依赖一个“重建运行会话”的窄接口及可替换测试实现。
- `uc-engine`：把基础设施观察映射到应用层，组装会话监督者，并通过稳定 Engine 操作、结果和事件公开少量状态。
- `uc-core`：只新增文件传输的稳定业务终止原因 `ConnectivityRecovery`；不放第三方网络观察或应用流程状态。
- 绑定：逐字段映射 Engine 的动作、查询结果和事件，不复制触发或重试规则。

### 触发流程

```text
已稳定运行的本机会话观察到：中转异常 -> 中转恢复
  -> 打开 60 秒本机网络变化窗口
  -> 某个“此前在线”的设备在 2 秒快速确认窗口内仍失败
  -> 执行一次解析状态刷新 + network_change
  -> 立即再执行一次 2 秒快速确认
  -> 仍失败，且本机中转健康、窗口仍有效
  -> 请求一次完整运行会话重建
```

快速确认仅服务于上述自动恢复路径，不能缩短日常传输和普通设备刷新的现有拨号预算。以下情况不自动重建：从未在线的设备离线、没有本机网络变化窗口、冷启动中转首次连上、任意设备已完成新鲜拨号并成功、同一周期已经成功重建。用户手动恢复不要求上述窗口，但仍使用同一个单次执行和同一套安全关闭路径。

### 状态与重试

- 内部状态：`Idle`、`Recovering`、`RetryScheduled`、`Failed`、`Stopped`。
- 查询只返回产品需要的稳定摘要：当前是否恢复中、是否等待重试、下次重试时间、最近失败是否可重试。
- 事件至少包含：开始、成功、已安排重试、最终失败；不复用 `Suspended` 或生命周期失败事件。
- 新会话构建失败时，初次失败后按 `1s -> 2s -> 5s -> 10s -> 30s` 再试，共最多 6 次构建尝试。
- 6 次均失败后停在可重试失败状态；用户手动动作可立即开始新的有界周期。平台暂停或 Engine 关闭会取消等待和正在执行的后续重试。
- 私有策略值集中定义，并允许测试注入；不增加产品配置项。
- 快速路径的时间预算固定为：两次确认各最多 2 秒、低成本恢复最多 1 秒、旧会话操作宽限最多 2 秒。诊断中，新会话重新连通约需 2.25 秒；因此将系统网络稳定后 10 秒内重新在线设为验收目标。实际关闭与创建耗时必须由测试和 Windows 实测记录，并按 20 轮中至少 19 轮达标验收。

### 重建顺序

1. 会话监督者取得唯一生命周期执行权，重复请求加入当前结果。
2. 关闭会话操作门；新的前台操作立即得到可重试的暂时不可用结果，系统剪贴板观察在门外等待。
3. 暂停文件传输注册表的新会话创建。
4. 给在途会话操作 2 秒宽限；超时后取消，等待其 future 退出并释放旧引用。
5. 停止会话事件转发、历史维护、搜索、剪贴板入站/出站、离线补发、成员和网络后台任务。
6. 给所有活动接收传输写入 `ConnectivityRecovery` 唯一终态；发送侧进度运行期对仍活跃项发出同一原因的终态。
7. 显式丢弃 `AppFacade` 及其他旧代能力引用，再完整关闭旧 Iroh Endpoint 和 Router；沿用 Iroh 自身有界关闭，不在外层强行截断。
8. 旧 `ProductionSession` 完全消费并释放后，使用原依赖、设置、安全身份和路径创建新会话。
9. 新建成功后原子安装新会话，重新开放文件传输和会话操作门。
10. 立即调用现有轻量刷新，探测所有已知设备；设备上线事件继续驱动现有最新离线内容补发。
11. 发布成功状态。若第 8 步失败，保持无活动会话、门继续关闭、传输继续暂停，交由应用层按退避重试。

## 执行阶段

### 阶段 0：锁定行为基线与失败测试

**目标：** 在实现前固定 Issue 的触发边界和不可破坏行为。

- 在 `crates/uc-application` 新增恢复运行期的接口级测试替身：可控时钟、记录型会话重建器、可阻塞重建器。
- 先写失败测试：中转恢复后，曾在线设备在两次各 2 秒的快速确认中持续失败，第一次失败允许轻量恢复，第二次失败才请求重建。
- 先写反例：从未在线、普通离线、冷启动首次连中转、没有本机变化窗口都不重建。
- 先写并发测试：多个设备同时耗尽、自动触发与手动请求并发时只调用一次重建器，所有等待者得到同一结果。
- 先写代次测试：旧会话迟到观察被忽略；任意新鲜拨号成功清除失败周期；同一周期成功重建后不再次升级。
- 先写退避测试：6 次上限、具体间隔、手动提前唤醒、暂停/关闭取消等待。

**退出条件：** 新测试按预期失败，失败原因是能力尚未实现，不是测试装配错误。

### 阶段 1：实现应用层恢复运行期

**目标：** 先建立单一事实来源，不接第三方网络细节。

- 新增 `crates/uc-application/src/facade/network_recovery/`，内部拆分状态、运行期和接口测试；通过 `facade/mod.rs` 只导出完整 facade、观察句柄、稳定状态和重建端口。
- 定义一个方法的 `RebuildNetworkSessionPort`，返回“新会话已安装”或收敛后的可重试失败；生产实现由 Engine 注入，测试使用记录实现。
- `NetworkRecoveryRuntime` 串行消费观察，维护 60 秒窗口、会话代次、已在线事实、是否已升级、当前单次执行和有界重试。
- 手动请求加入正在执行的自动恢复；若正在等待退避，手动请求提前开始下一次，但不并行创建会话。
- 状态先写入运行期，再发布通知；查询直接读取同一状态，不从事件反推。
- 运行期持有并关闭自己的任务；后台任务异常转成可见失败状态，不只写日志。

**退出条件：** 阶段 0 的应用层测试全部通过，调用方只需“观察、请求、查询”三个稳定动作，不知道内部恢复步骤。

### 阶段 2：建立安全的运行会话监督者

**目标：** 跑通最小但完整的手动重建端到端路径。

- 将 `ProductionSession` 的创建、当前槽位和关闭顺序收口到 `crates/uc-engine/src/runtime/session_supervisor.rs`；`ProductionRuntime` 不再自行散落 `take/build/install`。
- 新增 `session_operation_gate.rs`。除恢复请求和状态查询外，所有 `ProductionRuntime::execute` 操作先取得会话租约；恢复关闭门后拒绝新前台操作。
- 用租约取消令牌包住整个操作 future，保证 2 秒宽限后即使具体操作不主动检查取消，也会被丢弃并释放其旧会话引用。
- 系统剪贴板观察使用同一个门，但在门关闭时等待新会话；把任务取消纳入等待，保证失败重试或最终关闭时不会挂死。
- 把现有 `suspend`、`resume`、`shutdown` 改为调用监督者，并用同一生命周期锁与自动重建串行；暂停先停恢复运行期，恢复成功后再重新启用。
- 新会话构建失败时不安装占位对象，不重开门，不继续使用旧会话；下一次重试仍走相同入口。
- 记录代次、阶段、耗时和计数；不记录设备名、文件名、路径、内容、令牌或第三方完整错误。

**退出条件：** Engine 测试证明停旧发生在建新之前、构建失败没有活动会话、操作门能等待/取消、系统剪贴板不会跨代使用旧对象、暂停/关闭不会与恢复重叠。

### 阶段 3：补齐传输终态与会话关闭所有权

**目标：** 所有旧网络引用都能退出，用户能看到准确结果。

- 在 `FileTransferCancellationReason` 增加 `ConnectivityRecovery`，同步加密事件存储映射、投影、host event 标签和测试；不新增持久化明文字段。
- 把 `FileTransferFacade` 的创建门扩展为 `Open / Paused / Closed`；新增原子的“暂停并快照活动会话”和“重新开放”，最终 `close` 仍不可逆。
- 让统一取消入口接收明确原因，删除恢复路径使用 `Unknown` 的做法；用户主动取消的公共输入枚举不开放系统生命周期原因。
- 把发送侧进度翻译任务收口成有关闭结果的运行期，跟踪未终止的发送项；会话恢复关闭时为它们发出 `connectivity_recovery` 终态后再退出。
- `ProductionSession::shutdown` 消费自身并显式按顺序关闭所有运行期、丢弃 facade、关闭节点，方法返回才表示旧代资源不再可达。
- 已持久化的离线投递记录不改写；新会话上线事件继续交给现有 `ClipboardSyncRuntime` 补发最新内容。

**退出条件：** 接收、发送进度、并发开始传输和恢复竞态测试均只有一个终态；恢复后可创建新传输；最终关闭后仍永久拒绝。

### 阶段 4：接入低成本恢复和自动升级观察

**目标：** 将真实 Windows 半恢复故障接到阶段 1 的状态机。

- 在 Iroh 网络目录增加测试可替换的观察接口，由 Engine 中的薄 adapter 转成应用层观察；不把 Iroh 类型或错误带入应用层和公共契约。
- `net_recovery.rs` 只在一个已经稳定运行的会话真实经历“健康 -> 异常 -> 恢复”时报告本机网络恢复；冷启动首次连上不报告。
- Presence 在改变公开在线状态前保存此前状态。对有效本机窗口内的此前在线设备，新增仅供恢复使用的快速确认：复用现有三路尝试，但整体最多等待 2 秒；普通拨号的既有预算不变。
- 第一轮快速确认失败后，只有应用层允许时才执行一次解析器刷新和 `network_change`，随后立即进行第二轮快速确认；并发设备共享一次低成本动作。
- 第二轮成功只报告“新鲜拨号成功”并保持现有 `Online` 语义；第二轮仍失败报告“曾在线设备路径耗尽”，公开结果仍只是 `Offline`。
- 观察携带内部会话代次；旧会话关闭期间的迟到消息被应用层丢弃。
- LAN 兼容线不参与此流程；P2P 失败绝不自动切换 LAN。

**退出条件：** 基础设施测试证明健康中转下也能在两次 2 秒快速确认内执行失败后的低成本恢复，第二次失败才升级；普通拨号预算和应用层反例全部保持不变。

### 阶段 5：稳定 Engine 契约和三端绑定

**目标：** 产品只看到一个动作、一份状态和一类事件。

- 保留 `RefreshPeerConnections` 原行为；新增 `RecoverNetwork` 和 `QueryNetworkRecoveryStatus`，手动动作等待当前单次恢复的最终结果。
- 新增稳定状态摘要和 `NetworkRecoveryChanged` 事件，表达开始、成功、已安排重试、最终失败及是否可重试。
- 恢复失败使用新的稳定错误编号、`Unavailable` 类别和正确的 `retryable`；不暴露内部阶段名或第三方错误文本。
- UniFFI 同步新增方法、结果、事件字段、worker command 和契约测试；iOS/Android 生成绑定通过现有准备/核验流程更新。
- HarmonyOS N-API 同步新增方法、类型声明、事件映射和宿主 smoke/contract 测试。
- 对事件流积压继续使用现有 `RefreshRequired`；产品收到后查询恢复状态，不依赖瞬时成功事件重建真相。

**退出条件：** Rust、UniFFI、HarmonyOS 对同一状态和失败的映射一致，绑定层没有判断触发条件或实现重试。

### 阶段 6：自动化验证与架构检查

**聚焦测试：**

- `cargo test -p uc-application network_recovery --locked`
- `cargo test -p uc-infra net_recovery --locked`
- `cargo test -p uc-infra presence_adapter --locked`
- `cargo test -p uc-engine network_recovery --locked`
- `cargo test -p uc-engine session_supervisor --locked`
- `cargo test -p uc-application --test file_transfer --locked`
- `cargo test -p uc-engine-uniffi --locked`
- `cargo test -p uc-ohos-napi --locked`

**必须新增的集成证明：**

- 同一安全身份连续建立两代节点，Endpoint 身份完全一致。
- 旧节点完成关闭后才开始新节点绑定，任一时刻只有一代可接受连接。
- 构建失败后没有旧会话回流、没有半安装新会话、操作门和传输门保持关闭。
- 手动请求加入自动恢复；多个自动信号只重建一次。
- 正常对端离线不重建；本机恢复窗口过期不重建；旧代迟到观察不重建。
- 活动接收和发送都有唯一终态；新会话安装后文件传输重新可用。
- 重建后设备上线会触发现有最新内容补发，但取消的前台操作不自动重放。
- 平台暂停、恢复、关闭与自动恢复串行，关闭后没有后台任务复活。
- 可控时钟测试证明快速路径在 `2s + 1s + 2s + 2s` 内开始新会话；Windows 实测把系统网络稳定到双方重新在线的时长作为单独指标记录。

### 阶段 7：Windows 双机真机验收

**准备：**

- 两台 Windows 设备安装包含本次 Engine 的同一开发版本，记录提交、构建时间和应用版本。
- 先确认两端使用 P2P 默认模式、同属一个 Space、设备身份稳定、初始在线。
- 验收前先双向发送文字、图片和代表性文件，建立基线；日志使用脱敏编号关联两端时间线。

**场景 A：单端网络变化。**

- 设备 A 断开并重新连接网络，再分别覆盖 Wi-Fi 重连、Wi-Fi 与有线切换。
- 不点击手动恢复、不退出应用，观察 A 的中转恢复、设备路径失败、轻量恢复、会话重建和重新在线。
- 记录从系统网络稳定到双方重新在线的耗时；两个场景各执行 10 轮，共 20 轮，已确认的换网卡死场景至少 19 轮应在 10 秒内完成。
- 恢复后分别从 A 到 B、B 到 A 发送文字、图片和文件，确认结果和进度终态。

**场景 B：双端同时换网。**

- 两台设备同时切换到另一个局域网，保持应用运行。
- 确认双方各自最多一个恢复执行，没有互相触发的重建循环；最终双方持续在线。
- 再次完成文字、图片、文件双向传输。

**稳定性重复：**

- 场景 A 和 B 各连续执行 10 轮，共 20 轮。
- 每轮核对只有一个活动运行会话、旧 UDP 监听已消失、任务和句柄数量没有随轮次单调增长。
- 恢复后持续观察至少 5 分钟，确认没有延迟重建、在线/离线振荡或重复补发。

**留存证据：**

- 两端同一时间线上的本机网络恢复、轻量恢复、重建开始/成功、旧会话关闭、新会话安装、设备重新在线日志。
- 每轮恢复耗时、重建次数、活动传输终态和三类内容双向传输结果。
- 不保留文件名、路径、剪贴板正文、设备备注、密钥、令牌或原始第三方错误。

**退出条件：** 两个场景和重复轮次均无需重启或手动恢复，三类内容双向可用，没有重建循环、重叠会话或可见资源增长；20 轮中至少 19 轮在 10 秒内重新在线。任何未执行项明确标为跳过。

## 已确定的取舍

| 决定 | 原因 |
| --- | --- |
| 重建整个 `ProductionSession`，不只替换 Endpoint | 当前 AppFacade、剪贴板、Blob、Presence 和多个任务都直接持有旧网络能力；局部替换会留下旧引用或引入大面积代理 |
| 不把自动恢复伪装成 suspend/resume | 网络自愈不是平台生命周期，产品不应看到错误的暂停状态 |
| 不在普通离线时自动重建 | 对端关机和休眠是正常状态，不能用本机重建解决 |
| 保留轻量刷新并新增完整恢复动作 | 两者成本和承诺不同，不能让既有名称静默改变含义 |
| 重建失败后保持无活动会话 | 旧会话已关闭，回退会重新引入已知坏资源和双会话风险 |
| 事件之外提供状态查询 | 事件可能积压或丢失，查询才是恢复状态的单一事实来源 |
| 发送和接收都要写终态 | 只处理接收端会让发送端界面永久停在传输中 |
| 策略值不做产品配置 | 当前问题不需要用户调参，增加配置只会扩大接口和测试面 |
| 换网卡死路径采用两次 2 秒快速确认 | 不再为升级连续等待两轮常规拨号；严格限定触发条件，保持普通连接预算不变，并以 10 秒内恢复作为验收目标 |
| 成员身份分歧另开问题 | 它可能影响恢复后的在线稳定性，但不是重启后立即恢复拨号的根因 |
