# Issue #1516 调查结论与决策依据

## 用户要求

- 给出详细、可直接执行的修复计划。
- 自动恢复优先，手动重试只能作为最后的补充。
- Engine 负责完整结果，产品端不编排内部网络步骤。
- 最终必须通过两台 Windows 真机切换网络验证。

## 已确认事实

- Windows 网络变化时，系统通知可能因短时间过多而丢失。
- 当前恢复只刷新网络解析状态并提示现有连接重新检查。
- 该浅层恢复只在拨号前执行，而且本机中转健康时直接跳过；拨号完成后无论成功或失败都不会把结果反馈给恢复模块。
- 当前健康判断只看本机中转连接；它恢复后，自动恢复会停止。
- 设备专属连接仍可能持续失败，因此界面长期离线。
- 完全退出再打开会创建全新的网络资源，三台对端在约两秒内恢复拨号。
- 当前主分支仍保留同一判断和同一浅层恢复方式。
- 现有“刷新设备连接”只在当前网络会话上重新尝试，不能替换卡死的会话。
- 现有 Engine 暂停再恢复可以重建整套运行会话，但同时停止搜索、同步等无关工作并取消活动文件传输，范围过大。
- 最近加入的离线内容补发能在连接恢复后重试内容，但不能修复卡死的网络会话。
- 诊断中存在另一个成员身份分歧；它可能让恢复后的连接再次离线，但不能解释重启后迅速恢复拨号。
- Presence 拨号失败目前被归一为 `Offline` 并发出状态事件，而不是错误；这是正常的产品语义，但恢复模块需要额外接收不含第三方细节的“拨号失败且中转健康”观察。
- 每轮设备拨号已经包含 3 次并发尝试，总时间预算最长约 4.5 秒；继续增加同类重试只会推迟离线结果，不能替代会话重建。
- Presence 当前会消费并归一化拨号结果，公开查询只返回在线或离线；恢复协调器需要旁路接收少量脱敏观察，不能改变现有在线状态语义，也不能把第三方错误直接暴露给产品。

## 恢复触发原则

- 不能因任意离线设备就重建网络：对端关机、休眠或无网都是正常情况。
- 自动深度恢复只针对一个明确失败周期：设备之前在线，随后路径失效；本机中转健康；两次仅供恢复使用的 2 秒快速确认仍失败。
- 第一次快速确认失败先做浅层恢复并重试；第二次快速确认仍失败才向应用层报告可升级观察。普通拨号继续使用原有最长约 4.5 秒的预算。
- 从未在线的设备只保持离线，不触发自动深度恢复；手动重试仍可显式请求同一路径。
- 任一设备成功拨号后清除当前失败周期；一次深度重建后若仍失败，不因同一周期重复重建，直到出现新成功或新的明确网络变化证据。
- 当前网络依赖为 `iroh 1.0.0-rc.1` 和 `netwatch 0.18.0`；本机有对应依赖源码，可直接核对受支持的恢复接口。
- 依赖源码确认 Windows 的地址变化和路由变化回调使用有界通道的非等待发送，通道满时只记录警告并丢弃通知，与诊断日志一致。
- Iroh 内部确实存在连接检查和 relay rebind，但它们是内部方法，不是 Endpoint 对外承诺的恢复接口；计划不能依赖私有实现或复制其内部步骤。
- Endpoint 的公开恢复面只有解析器访问、网络变化提示和完整关闭，没有公开的 relay actor 重启或 socket 原地重绑；受支持的深度恢复方式是关闭旧 Endpoint 后用 Builder 创建新 Endpoint。
- Endpoint 完整关闭会等待连接关闭通知，但底层 UDP 资源只有在所有 Endpoint 副本释放后才彻底释放；重建前必须停止接收新操作并等旧操作释放其网络引用，不能只从会话槽中取走旧对象就立刻绑定新节点。
- `IrohNodeBuilder` 每次从同一个安全身份存储读取既有密钥后创建 Endpoint，因此关闭旧节点再绑定新节点可以保持相同设备网络身份，不需要迁移或复制身份数据。

## 约束

- 不保留旧实现和新实现两套长期路径，不增加兼容层。
- 网络库细节留在基础设施层；恢复流程由应用流程层负责；Engine 只装配和提供稳定入口。
- 基础设施层只能提供可停止、可替换、错误已收敛的网络能力，不能自行拥有跨步骤恢复政策。
- 长时间、事件驱动、带重试和失败状态的恢复过程应由应用层单一协调器负责；状态和转移必须显式。
- Engine 只能通过应用层 `facade/` 入口触发或查询恢复，不能直接持有应用层内部协调器。
- 每个长期网络任务都必须由自然所有者保留句柄并确定性关闭，任务崩溃和关闭失败都必须可见。
- 恢复过程的后台失败必须写回统一应用状态，不能只记日志后继续假装健康。
- 应用层事件必须明确来源、消费者、幂等性和丢失处理，不能用全局事件广播替代恢复状态机。
- 不新增持久化敏感明文字段，不记录设备名称、文件名、文件路径或内容。
- 生产代码禁止使用会直接崩溃或直接打印的写法。
- 每次修改仓库都必须更新 `docs/architecture/architecture-bible.md`。

## 已收口的原待确认项

- 第三方库支持完整关闭后从同一安全身份重新绑定，设备网络身份保持不变；Blob 内容存储等进程依赖由原装配依赖复用，新会话重新创建其网络 adapter。
- 当前没有可复用的稳定网络代理；长期持有旧 adapter 的对象跨越 `SyncEngineAssembly`、`AppFacade`、剪贴板和后台任务，因此选择完整重建 `ProductionSession`。
- 自动升级只使用“已稳定会话的本机中转异常后恢复 + 曾在线设备两轮 2 秒快速确认失败”；连接关闭、普通传输失败和普通离线不单独触发。
- 接收传输复用现有单一终态机制并新增准确原因；发送侧进度运行期需要在关闭时为活跃项补同一终态。
- Engine 事件流和宿主事件总线属于进程级，可以跨运行会话重建继续使用；瞬时事件之外新增状态查询作为事实来源。

## 最终参数

- 本机网络变化窗口：60 秒。
- 换网卡死快速路径：两次确认各最多 2 秒，低成本恢复最多 1 秒；系统网络稳定后以 10 秒内重新在线为目标，Windows 双机验收要求两个场景各 10 轮、共 20 轮中至少 19 轮达成。
- 在途会话操作宽限：2 秒，之后取消并等待引用释放。
- 新会话构建：初次尝试加 `1、2、5、10、30` 秒后的 5 次重试，共 6 次；全部失败后等待手动请求。
- 同一失败周期：最多成功重建一次；任意新鲜设备拨号成功或新本机网络变化会重置周期。

## 当前所有权图

- `SyncEngineAssembly` 不只是一个网络节点：它还持有配对、成员、剪贴板、blob、活动剪贴板、成员更新重试和多项后台运行期；这些对象都直接引用当前网络实现。
- 因此“只换 endpoint/router”并不可行，旧网络对象仍会被多个 facade 和 worker 引用；真正可独立替换的现成边界至少是整个 `SyncEngineAssembly`。
- `ProductionSession` 又在 `SyncEngineAssembly` 外持有 `AppFacade`、剪贴板运行期、搜索、历史维护、事件转发和传输超时清理。
- 当前 `AppFacade` 在创建时直接拿到 `SyncEngineAssembly` 里的多个 facade/port；如果只重建 `SyncEngineAssembly`，旧 `AppFacade` 不会自动指向新一代。
- 当前完整 `ProductionSession` 重建路径已经能重新建立所有这些引用，正确性基础最好，但会短暂停止并重启搜索、历史维护、剪贴板后台任务和会话事件任务。
- 计划需要在两种方案间做明确取舍：先复用完整运行会话重建以快速修复，或先引入稳定代理以把重建缩到 P2P 相关对象。选择标准是是否能在不散布换代知识的情况下显著减少中断，而不是文件数量。
- 宿主事件总线和 Engine 事件发送器属于进程级共享依赖，完整运行会话重建后可以重新订阅并继续向同一宿主事件流发送，不需要宿主重新连接。
- 剪贴板运行期直接持有当前网络接收、presence、发送和 blob 能力，因此它必须与 `SyncEngineAssembly` 同代停止和重建。
- 文件传输注册表属于进程级共享 facade，当前 `cancel_active_sessions()` 会给所有活动会话写入 `Unknown` 取消原因且不永久关闭注册表；适合恢复后继续使用，但原因不够明确。
- 完整 shutdown 才调用 `close()` 永久拒绝新传输；网络重建只能暂时关门、取消当前会话、随后重新开放或确认共享注册表仍可接受新会话。
- Engine 顶层已有完整的“停止接收新操作、等待、超时后取消、再暂停/恢复”机制，但该机制只由宿主调用的生命周期方法拥有；当前运行时内部无法反向调用它。
- 自动恢复若放在 `ProductionRuntime` 内，必须有同等明确的会话级操作门：先拒绝新会话操作，等待或取消仍持有旧网络对象的操作，再销毁旧会话。直接拿走 `session` 并重建会与并发操作竞争。
- 不应把自动恢复伪装成 Engine 的平台暂停/恢复状态；恢复期间 Engine 仍在运行，网络相关操作应短暂返回稳定的可重试不可用结果，恢复结果通过专门状态/事件表达。
- 系统剪贴板观察任务属于进程级任务。它会从当前会话克隆 `facade`、捕获、索引和网络发送引用后释放会话锁，再继续执行；因此它可能在会话被取走后继续持有旧网络引用。恢复操作门必须覆盖这个后台入口，且等待计数必须包含它，不能只等待公开 `Engine::execute` 操作和会话自己的任务表。

## 架构文档给出的直接边界

- `uc-application` 已被定义为恢复、后台任务和完整流程的所有者，宿主不得拼装恢复步骤。
- 生产 `AppFacade` 必须一次完整构造，不能在运行中向同一对象补装或替换一部分能力。
- 因此若只重建 P2P 资源，调用方需要一个在完整构造时就注入、内部可原子换代的稳定能力入口；不能让 Engine 重建后逐个改写 facade 和 worker 的引用。
- 正常暂停会在网络停止后取消活动文件会话；这条已有终止语义可作为网络重建时的候选规则，但必须验证是否会误伤无关工作。
- 用户主动发起且有副作用的操作在暂停后不自动重放；网络重建只能恢复后台连接与已持久化补发，不能偷偷重放未知结果的前台操作。
- 在线状态只是当前可达性观察，不等于成员或信任状态；恢复判断不能改变成员关系。

## 可复用的仓库模式

- 仓库已有“应用层定义一个窄能力接口，Engine 在装配时提供实现”的做法，例如文件接收就绪和诊断能力；不必把第三方网络类型带进应用层。
- 这允许恢复状态机留在 `uc-application/facade` 内，同时只向 Engine 请求一个完整动作，例如“重建当前 P2P 运行会话”，而不是暴露关闭节点、重新绑定、重启 worker 等步骤。
- 该接口应是应用流程的装配依赖，不是宿主公共接口；宿主仍只看到现有 Engine 生命周期和可选的单次重试动作。
- 仓库没有现成的可换代网络代理或通用运行会话替换器，不能假设低成本局部替换已经存在。
- 空间会话已有相似的应用层协调器：它把暂停、恢复、失败补偿和活动顺序收口在一个对象中，底层能力通过窄接口注入；网络恢复可沿用这种结构，不另造通用生命周期框架。
- 文件接收已有“关闭接收入口、取消活动会话、写入唯一终态、启动时清理遗留”的机制；网络重建应复用这些入口，并增加准确的“网络会话重建”终止原因或映射，不能把它伪装成用户取消。
- 当前启动清理使用“应用重启期间中断”的说明；进程内网络重建若会经过同一路径，需要改成不撒谎且稳定的原因。
- 文件传输注册表已有串行创建门和单一终态保证，但只有“永久关闭”与“取消当前传输”两种动作；网络重建需要在同一注册表上增加可恢复的临时暂停/重新开放，不建立第二套注册表。
- `cancel_active_sessions()` 当前统一写入 `Unknown`。应让调用方传入原因，并增加 `NetworkSessionRebuilt`（最终命名以领域语言为准）；公开用户取消枚举不应接受这个内部生命周期原因，避免产品伪造系统原因。
- 现有 `RefreshPeerConnections` 已贯通 Engine、UniFFI 与 HarmonyOS，语义是“在当前会话重新探测全部已知设备”。保留其轻量语义；新增统一手动恢复动作，直接请求同一个恢复协调器。若自动恢复正在执行，手动请求加入并等待同一结果，不启动第二次重建。
- 恢复进度应走进程级 Engine 事件流，至少表达 `Started`、`Succeeded`、`Failed { retryable }`；不复用平台生命周期事件，也不暴露第三方网络错误、设备名称或地址。
